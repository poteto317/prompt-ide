# レビュー指摘から得られた実装パターンと教訓

ソース管理パネル拡張(diffタブ・履歴表示・amend・gitignore追加、および後続の
push/pull/fetch追加・ブランチ切替追加・ブランチ作成/削除追加・ファイル単位の変更の取り消し追加・ブランチのマージ追加・stash 追加・ハンク単位と一括の変更の取り消し追加)の開発中、コードレビューループを指摘が0件になるまで
繰り返す中で見つかった不具合を、個別の修正記録としてではなく「どんな状況で
同じ種類の問題が起こりうるか」という汎用的なパターンとして整理する。次に
似た実装をする際のチェックリストとして使う。

各パターンは次の構成で書く。

- **どういう時に問題が起こるか**: この問題を引き起こす具体的な状況・入力
- **原因**: なぜそれが問題になるのか、メカニズムの詳細
- **このプロジェクトでの実例**: 実際に見つかった箇所と修正内容
- **汎用的な対策**: 次に同種の実装をするときに気をつけること

---

## 1. チェックと使用の間に別プロセスが状態を変えられる(TOCTOU)

### どういう時に問題が起こるか

「対象の状態を確認する(lstat・stat等)」→「その結果を信じて別の非同期処理(read/write)を
行う」という2段階の処理を、両者の間に他プロセスが割り込めない前提で書いてしまったとき。
確認と使用の間に必ず一瞬の時間差(await境界)ができるため、その間に対象ファイルが
シンボリックリンクへ差し替えられる、削除される、別ファイルに置き換わる、といった
外部要因が入り込む余地がある。

### 原因

`isSymbolicLink(path)`(内部で`fs.lstat`を呼ぶ)が`false`を返した「その瞬間」の状態を
保証しているに過ぎず、次の行の`readFileBuffer(path)`や`writeFile(path)`が実行される
時点での状態までは保証しない。JavaScriptのシングルスレッドモデルでは、`await`を挟む
限り、たとえ数ミリ秒でも他のプロセス(別ターミナルからの`ln -sf`等)がファイルシステムを
変更する余地がある。

この種のバグは「起きた時にすぐ気づける」バグとは違い、通常の使い方では絶対に再現しない
(自分自身のアプリの中でこの2行の間にファイルを差し替える手段が無いため)。しかし
シンボリックリンクを含む悪意あるリポジトリを開く、または外部ツールと同時に同じ
ディレクトリを操作する、といったシナリオでは実際に成立しうる。

### このプロジェクトでの実例

- `gitignoreService.ts`: `.gitignore`がシンボリックリンクでないことを`lstat`で確認した後、
  `readFileBuffer`/`writeFileContent`(いずれもシンボリックリンクを辿る)で読み書きしていた。
  確認と書き込みの間にシンボリックリンクへ差し替えられると、サンドボックス外のファイルを
  上書きしうる。
- `gitService.ts`の`getDiff`: 未追跡ファイルの疑似diffを組み立てる際、`isSymbolicLink`で
  判定した直後に`getFileSize`/`readFileBuffer`/`isExecutableFile`を呼んでいた。

いずれも**このプロジェクトでは「見送り」と判断した**。理由は、対象が「単一ユーザーが
自分のマシンでローカルに使うElectronアプリ」であり、この種の競合を成立させるには
攻撃者が既にローカルでファイルシステム操作ができる状態(=既にアプリのサンドボックスを
突破する必要すらない状態)にある必要があるため、追加の防御による実利が薄いと判断した。
**マルチユーザー環境で動くサーバーサイドの処理や、信頼できない入力を扱うCLIツールでは
同じ判断にはならない**点に注意する。

### 汎用的な対策

- 「確認してから使う」の2段階処理を書く前に、まず対象システムの信頼境界を考える。
  同一ユーザー・同一プロセスの範囲内でしか状態変化が起こり得ないなら、TOCTOUは
  理論上のリスクに留まる。外部プロセス・他ユーザー・ネットワーク越しの入力が
  関与するなら、実際に悪用可能なバグとして扱う
- 対策する場合は「確認」と「使用」を1回のシステムコールにまとめる(例:
  `open(O_NOFOLLOW)`でシンボリックリンクなら失敗させてから読み書きする)のが唯一の
  確実な方法。「先にlstat、次にread」という2段階の実装は、間に何を挟んでも
  原理的にレースを完全には防げない
- 見送る場合も「なぜ見送るか」を必ずコードコメントに残す。次にレビューする人(人間でも
  AIでも)が同じ箇所を再度「バグではないか」と指摘してくることを前提に、判断根拠を
  再利用可能な形で残しておく

## 2. ストリームデータのマルチバイト文字がチャンク境界で分割される

### どういう時に問題が起こるか

子プロセスの`stdout`/`stderr`のように、`Buffer`が複数回の`'data'`イベントに分かれて
届くストリームを、イベントごとに独立して`toString()`(UTF-8デコード)してから文字列
連結する実装。日本語などのマルチバイト文字(UTF-8で1文字が2〜4バイト)を含む出力で、
たまたまOSのパイプバッファの都合でその文字の途中でチャンクが分割されると発生する。

### 原因

UTF-8は可変長エンコーディングで、1文字が何バイトになるかは先頭バイトを見ないと
わからない。`Buffer.toString('utf-8')`は「渡されたバイト列だけで完結したテキスト」
として独立にデコードする。もしバイト列の途中で他の文字の一部が途切れていたら、
その不完全なバイト列は不正なUTF-8シーケンスとして扱われ、Node.jsの仕様により
`U+FFFD`(置換文字、いわゆる文字化けの■)に変換される。

具体的に検証した例(日本語の「日」= `E6 97 A5`の3バイト):

```js
const buf = Buffer.from('日本語', 'utf-8') // 9バイト
const chunk1 = buf.subarray(0, 1) // 0xE6 だけ
const chunk2 = buf.subarray(1) // 0x97 0xA5 ... 残り

chunk1.toString('utf-8') // => "�"  (不完全な1バイトが化ける)
chunk2.toString('utf-8') // => "��本語" (先頭2バイトも不完全なので化ける)
```

チャンクごとに独立してデコードしている限り、文字列を連結してもこの文字化けは
元に戻らない。「たまたま同じ日本語がテスト環境で1チャンクにまとまって送られてくる」
ケースではこの不具合は再現しないため、テストでチャンク分割を明示的に再現しない限り
気づけない。

### このプロジェクトでの実例

`gitApply.ts`の`runGitApply`が、`git apply`失敗時のエラーメッセージ(日本語ファイル名を
含みうる)を`stderr`から`chunk.toString()`で蓄積していた。テストで意図的にバイト列の
途中でチャンクを分割して送り、実際に文字化けすることを確認した上で、
`node:string_decoder`の`StringDecoder`に置き換えて修正した。

```ts
// Before: チャンクごとに独立デコード。マルチバイト文字が境界で分割されると化ける
let stderr = ''
proc.stderr.on('data', (chunk: Buffer) => {
  stderr += chunk.toString()
})

// After: StringDecoder が不完全な末尾バイトを次の write まで内部に保持し、
// チャンクをまたいでも正しく結合してくれる
const stderrDecoder = new StringDecoder('utf-8')
proc.stderr.on('data', (chunk: Buffer) => {
  stderr += stderrDecoder.write(chunk)
})
```

### 汎用的な対策

- 子プロセスの標準出力/エラー出力、ソケット通信、ファイルの分割読み込みなど、
  「バイト列を複数回に分けて受け取り、テキストとして結合する」処理を書くときは、
  `chunk.toString()`の単純な連結ではなく`StringDecoder`(Node.js)や`TextDecoder`
  (`{ stream: true }`オプション、ブラウザ/Node両対応)を使う
- ASCII文字だけを前提にしたテストはこの種のバグを検出できない。マルチバイト文字を
  含むデータを、意図的に1バイト単位・不自然な位置で分割して送るテストケースを
  最低1つ用意する

## 3. 文字数(UTF-16コード単位)とバイト数の取り違え

### どういう時に問題が起こるか

「入力サイズが一定の上限を超えたら打ち切る」というガードを、JavaScript文字列の
`.length`で判定してしまったとき。対象がASCII文字だけなら文字数とバイト数は
ほぼ一致するが、マルチバイト文字(日本語・絵文字等)が混ざると成立しなくなる。

### 原因

JavaScriptの文字列は内部的にUTF-16で表現されており、`.length`は「UTF-16コード単位の
個数」を返す。一方、`Buffer`や実際のファイル・通信のサイズは常にバイト数で決まる。
UTF-8で3バイトの日本語1文字は、UTF-16では1コード単位(`.length`は1)にしかカウント
されない。つまり同じ「見た目の上限」を設定しても、日本語主体のテキストは英語主体の
テキストよりも**実際のバイト数ベースでは最大3倍近く**、意図した上限を超えて蓄積されうる。

「メインプロセスのメモリを守るためにNバイトで打ち切る」という意図で書いたコードが、
文字数で判定していたせいで実質的に機能していない、という食い違いが起きる。

### このプロジェクトでの実例

`gitApply.ts`の`stderr`蓄積上限(`MAX_STDERR_BYTES`)を、当初`stderr.length`
(デコード後の文字数)と比較していた。日本語を含む大量のエラー出力を送るテストを
書いて、実際のバイト数が上限の約3倍まで蓄積されてしまうことを確認した上で、
判定を`chunk.length`(Bufferの実バイト数)の累計に変更した。

```ts
// Before: stderr.length は UTF-16 コード単位数。マルチバイト文字は
// 1バイトあたり1文字未満に圧縮されるため、意図した上限を実質的に超過する
if (stderr.length >= MAX_STDERR_BYTES) return
stderr += chunk.toString()

// After: chunk.length(Buffer の実バイト数)の累計で判定する
if (stderrBytes >= MAX_STDERR_BYTES) return
stderrBytes += chunk.length
stderr += stderrDecoder.write(chunk)
```

### 汎用的な対策

- 「バイト数の上限」を実装するときは、必ずデコード前の`Buffer`/バイト列の段階で
  サイズを数える。デコード後の文字列の`.length`を使ってはいけない
- どうしても文字列の`.length`しか手元にない場合は`Buffer.byteLength(str, 'utf-8')`で
  実バイト数に変換してから比較する
- 変数名・定数名に`BYTES`と付けているのに実装が文字数を数えている、という食い違いは
  コードレビューでも見逃されやすい。テストでマルチバイト文字を使った検証を書くことが
  最も確実な検出手段

## 4. 複数の非同期処理が同じ状態を更新するときの「後から解決した方が勝つ」問題

### どういう時に問題が起こるか

同じ状態(Reactの`state`、キャッシュ等)を更新しうる非同期処理が2つ以上存在し
(例: マウント時の初回取得と、ユーザー操作によるリフレッシュ)、それぞれが
「自分より後に同じ処理が始まっていないか」だけをキャンセル条件にしているとき。
片方が別のトリガー(コミット操作等)で追加に発生した場合、「後から始まった処理」と
「先に始まったが解決が遅れた処理」が競合し、**遅い方が先に始まった処理であっても、
後から解決すれば新しい状態を上書きしてしまう**。

### 原因

典型的な「タブ切り替え時に前のリクエストを無視する」ガードは、「フォルダ/タブが
変わったかどうか」という**単一の軸**でしか古さを判定していない。しかし今回の
不具合は、フォルダもタブも変わっていない状態で、**同じ対象に対して2種類の異なる
きっかけ(マウント時のload、ユーザー操作によるrefresh)から非同期処理が二重に
発生する**ケースだった。この場合、「フォルダが変わったか」を見るガードは
無力(フォルダは変わっていないので`false`のまま)であり、単純に「後から`await`が
解決した方」が状態を書き込んで終わる。

つまり、開始した順序と完了する順序が入れ替わりうる非同期処理が2つ以上あるとき、
「新しい要求ほど優先されるべき」という意図を実装するには、**開始した順序を追跡する
仕組みそのもの**が必要で、単なるフラグ(bool)の前後関係チェックでは表現できない。

### このプロジェクトでの実例

`useGitHistory.ts`で、フォルダを開いた直後の初回`load()`が完了する前に、素早く
コミットして`refresh()`が呼ばれると、両方が同じ`gitStatusFiles`相当の状態
(`log`/`branches`/`tags`)を更新しようとする。`refresh()`(新しい・正しい状態)が
先に解決して画面に反映された後、遅れて解決した`load()`(古い・コミット前の状態)が
それを上書きし、コミットした内容が履歴一覧から一瞬消えるように見えてしまっていた。

修正は、呼び出しごとに増分する「世代番号(request generation)」を導入し、
「自分より新しい呼び出しが既に始まっているか」を毎回チェックする方式にした。

```ts
// 呼び出しのたびにインクリメントする世代カウンタ。フォルダ切替判定とは別の軸
const latestRequestIdRef = useRef(0)

useEffect(() => {
  const requestId = ++latestRequestIdRef.current
  void fetchGitHistoryData(
    folderPath,
    setters,
    () => cancelled || latestRequestIdRef.current !== requestId // 世代が古ければ中断
  )
}, [folderPath, setters])

const refresh = useCallback(async () => {
  const requestId = ++latestRequestIdRef.current // refresh の呼び出しも同じ世代を消費する
  await fetchGitHistoryData(folderPath, setters, () => latestRequestIdRef.current !== requestId)
}, [folderPath, setters])
```

これにより、「フォルダ切替」「初回ロード」「リフレッシュ」「追加ロード」など、
発生源が異なっていても、**常に一番最後に開始した呼び出しだけが状態を書き込める**
ようになる。

### 汎用的な対策

- 同じ状態を更新しうる非同期処理の発生源が2つ以上あるかを洗い出す(初回取得・
  ポーリング・ユーザー操作によるリフレッシュ・楽観的更新後の再検証、など)
- 発生源が1つしかない場合は「フォルダ/IDが変わったか」のような単純なガードで足りる。
  2つ以上ある場合は、発生源をまたいで共有する単調増加のカウンタ(またはタイムスタンプ)
  を用意し、「自分が最新の呼び出しか」を解決時に必ずチェックする
- 「開始した順序」と「完了する順序」は無関係であることを常に疑う。ネットワーク越しの
  IPC・fetchは特に、後から始めたリクエストの方が先に返ってくることが普通に起こる

## 5. 複数の主体が同じロックを共有するときの非対称なチェック漏れ

### どういう時に問題が起こるか

同じリソース(このプロジェクトでは`.git/index`)に対して、異なる経路(ファイル全体の
stage/unstageと、ハンク単位のstage/unstage)から書き込みが発生しうる設計で、
共有ロックを導入したものの、**片方の経路だけ**「自分以外の全体がロック中か」まで
チェックし、もう片方は「自分自身に関係する範囲だけ」しかチェックしていなかったとき。

### 原因

排他制御を「後から」複数箇所に継ぎ足していくと、最初に手を入れた箇所は最新の
設計思想(「他の誰かが何かをロックしていたら待つ」)を反映しているが、その後に
同じロック機構を使い始めた別の箇所は、最初に実装したときの狭い要件(「同じパスへの
多重クリック防止」)のままになりがちで、後から追加された「他のパスに対する操作」との
競合まではカバーできていない。

このプロジェクトの例で言えば:

- `useGitOperations`(ファイル全体のstage/unstage)は、後から「無関係な別ファイルへの
  stage中も新規のstageをブロックする」よう修正された(`stagingPathsRef.size > 0`や
  `lock.isAnyLocked()`を見るようになった)
- 一方`useDiffOperations`(ハンク単位のstage/unstage)は、その修正が入る前の設計の
  ままで、`lock.isLocked(自分の対象パス)`しか見ていなかった

その結果、「ファイルBを全体stage中に、無関係なファイルAのハンクをステージする」
操作が、`useDiffOperations`側のガードをすり抜けて実行されてしまい、`git add`と
`git apply --cached`が同時に`.git/index`へ書き込みに行く状態になっていた。
UIのボタンの`disabled`判定も同様の非対称性を持っており、「押せそうに見えるのに
押しても無言で何も起きない」ボタンが残っていた。

### このプロジェクトでの実例

```ts
// Before: 対象パス単独のロックしか見ていない
if (
  activeDiffTab === null ||
  isHunkOperationInProgressRef.current ||
  lock.isLocked(activeDiffTab.path)
) {
  return
}

// After: useGitOperations 側と同じ isAnyLocked() を追加し、対称にする
if (
  activeDiffTab === null ||
  isHunkOperationInProgressRef.current ||
  lock.isLocked(activeDiffTab.path) ||
  lock.isAnyLocked()
) {
  return
}
```

ボタンの`disabled`判定側でも、`ChangesSection`/`StagedSection`に`isAnyLocked`を
渡していなかったため配線を追加し、さらに「stagingPathsに自分のパスが含まれているか
(`stagingPaths.has(f.path)`)」ではなく「stagingPathsが空でないか
(`stagingPaths.size > 0`)」で判定する必要があることも、テストを書いて確認した。

### 汎用的な対策

- 「同じロックを複数の経路が共有している」設計を見つけたら、それぞれの経路が
  ロックの状態を**同じ厳しさで**チェックしているかを横並びで比較する。片方だけが
  「自分自身」の状態しか見ていないなら、それは大抵バグ
  (もしくは意図的な緩和である場合はコメントで明記する)
- 排他制御を後から1箇所に追加したら、同じ排他制御を使っている(または使うべき)
  他の箇所すべてに同じ修正が要るかを機械的にチェックする。`grep`でロックオブジェクトの
  全使用箇所を洗い出し、1つずつ「ここも対称になっているか」を確認する
- 「実行を弾くロジック」と「ボタンのdisabled表示」は別々に実装されがちだが、
  両者がズレると「押せるのに反応しない」「押せなさそうなのに実は関係ない」という
  UXの不整合になる。同じ条件式を両方から参照するか、少なくとも同じテストで
  両方を検証する

## 6. 「1要素だけ変化する」前提のロジックが複数要素の同時変化で壊れる

### どういう時に問題が起こるか

「配列から要素が1つ削除されたら、その位置にあった要素を基準に次の要素を決める」
という設計のヘルパー関数を、実際には**複数の要素が1回の更新で同時に削除される**
呼び出し元(例: ディレクトリを削除すると配下のファイルタブが全部消える)からも
使ってしまったとき。

### 原因

「削除位置の要素(1つ削除後にその位置に来る要素、つまり元の右隣)を返す」という
ヘルパーは、削除前後で配列の**長さがちょうど1つ短くなる**ことを暗黙の前提にしている。
複数要素が同時に削除されると、「削除位置」という単一のインデックスでは元の配列との
対応が取れなくなり、「本来隣接していたはずの要素」を通り越して、さらに先の要素を
指してしまう。

具体例: `[a, b, c(アクティブ), d, e]`から`b`と`c`を含むディレクトリを削除すると
`[a, d, e]`になる。アクティブだった`c`の削除前インデックスは`2`。単純に
`next[2]`を返すヘルパーを使うと`e`が返るが、正しくは`c`の直後に生き残った`d`が
選ばれるべきである。

### このプロジェクトでの実例

`useFileSystem.ts`の`setOpenFilesAndFixActive`が、アクティブなタブが配列から
消えたときの隣接タブ計算に`computeAdjacentItem`(削除位置ベース)を使っていた。
`useFileTreeOperations.deleteEntry`がディレクトリ削除時に配下のファイルを
`isPathAtOrInside`で一括フィルタする(1回の更新で複数要素を除去する)ため、
このケースでタブが1つ飛び越されるバグがあった。

一方で、同じ関数はリネーム(要素数が変わらず、中身の`path`だけが変わる)にも
使われており、その場合は位置ベースの計算が偶然正しく動いていた(リネームされた
要素は元の位置にそのまま残るため)。そのため、修正では「要素数が変わっていないか」
で場合分けし、変わっていない場合は既存の位置ベース計算を、要素数が減っている場合は
「削除された範囲の先頭から、まだ配列に存在する要素を探す」という内容ベースの
探索に切り替えた。

```ts
const fallback = (() => {
  if (prevIndex === -1) return next[0]?.path ?? null
  // 要素数が変わっていない(リネーム等)場合は位置ベースでよい
  if (next.length === prev.length) return computeAdjacentItem(next, prevIndex)?.path ?? null
  // 要素数が減っている(複数タブ同時削除)場合は、削除範囲の先頭から
  // まだ存在する要素を探す
  for (let i = prevIndex; i < prev.length; i++) {
    const candidate = findFile(next, prev[i].path)
    if (candidate !== null) return candidate.path
  }
  for (let i = prevIndex - 1; i >= 0; i--) {
    const candidate = findFile(next, prev[i].path)
    if (candidate !== null) return candidate.path
  }
  return null
})()
```

### 汎用的な対策

- 「配列の要素が1つ変化する」ことを前提にしたヘルパー関数を書いたら、そのヘルパーの
  Docコメントに前提条件(「1要素の削除/置換のみ対応」)を明記する
- そのヘルパーを新しい呼び出し元から使う前に、その呼び出し元が本当に「1要素だけ」を
  変化させるのか、それとも「フィルタ処理で複数要素が同時に消えうる」のかを確認する。
  `filter`を使っている実装は複数要素の同時変化を疑う
- テストは「1要素削除」だけでなく「複数要素が同時に削除され、かつその中にアクティブな
  要素が含まれる」ケースを必ず書く。今回のバグはまさにこのテストケースが
  存在しなかったことで見過ごされていた

## 7. 特殊文字を含む文字列の構文的な意味を無視した単純比較

### どういう時に問題が起こるか

ある文字列が、特定のフォーマット(gitignore、正規表現、シェルのクォート等)の中で
特別な意味を持つ文字(`!`, `#`, `\`, `*`など)を含みうるときに、「同じ意味の行かどうか」
を判定するために、そのフォーマットの構文を考慮せず**生の文字列同士をそのまま比較**
してしまったとき。

### 原因

`.gitignore`の`!pattern`は「patternへの否定(un-ignore)」、`#comment`は「コメント行」
であり、これらは行頭に来た瞬間にまったく別の意味を持つ。ある機能が「このファイルは
既にgitignoreに書かれているか」を重複チェックする際に、ユーザーが選択したファイル名
(例: 実際にファイル名が`!important.txt`であるケース)をそのまま既存の行と文字列比較すると、
既存の`!important.txt`という行(実際には無関係な否定パターン)と偶然一致してしまい、
「既に無視されている」と誤判定して、本来追加すべきエスケープ済みパターン
(`\!important.txt`)を一度も書き込まないまま処理が正常終了してしまう。

このバグの厄介な点は、**失敗が静かであること**。エラーは出ず、UIは成功したように
見えるが、実際にはファイルは無視されないままになる。

### このプロジェクトでの実例

`gitignoreService.ts`の重複判定が、エスケープ後のパターンだけでなく、手書きの
`.gitignore`との互換性のために生の`relativePath`も比較対象に含めていた。しかし
`relativePath`が`!`または`#`で始まる場合、その生の形は構文上「否定」「コメント」を
意味してしまうため、比較対象から除外する必要があった。

```ts
// 生の relativePath の先頭が '#'(コメント)・'!'(否定)の場合、行頭に来ると
// gitignore の構文上まったく別の意味になるため、既存の無関係な行と文字列が
// 一致しても「このファイルは既に無視されている」ことを意味しない
const rawFormChangesGitignoreSemantics = /^[#!]/.test(relativePath)
if (
  existingLines.includes(pattern) ||
  existingLines.includes(escaped) ||
  (!rawFormChangesGitignoreSemantics &&
    (existingLines.includes(relativePath) || existingLines.includes(`/${relativePath}`)))
) {
  return
}
```

### 汎用的な対策

- 何らかのDSL・フォーマット(gitignore、正規表現、URLクエリ、シェル引数など)の
  文字列を「生の値」と「エスケープ済みの値」の両方で比較する実装を書くときは、
  「生の値がそのフォーマットの構文として別の意味に解釈されるケースがあるか」を
  必ず洗い出す。多くの場合、行頭・先頭の特定文字だけが特別な意味を持つので、
  そこだけ`/^[特殊文字]/`のような判定で除外すればよい
- 「エスケープしていない手書きの値との互換性を保つ」ための緩い比較を追加するときは、
  緩さが逆に別の意味の値と衝突しないかを必ず検討する。互換性のための例外処理が、
  新しい誤判定を生むことがある

## 8. 固定長prefixによる文字列解析が、フォーマットの可変性を考慮していない

### どういう時に問題が起こるか

外部コマンド(ここでは`git diff`)の出力を、「先頭何文字かは常にこの固定文字列で、
残りが可変部分」という前提で`slice(固定長)`によって解析していたが、実際にはその
外部コマンドが状況に応じて出力フォーマットを変える場合があり、その分岐を
考慮していなかったとき。

### 原因

`git diff`の`+++ b/<path>`という行は、通常`path`をそのまま出力するが、`path`が
リテラルなダブルクォート(`"`)やバックスラッシュ(`\`)、制御文字を含む場合、gitは
自動的にパス全体をダブルクォートで囲み、内部の特殊文字をCスタイルでエスケープした
`+++ "b/path"`という形式に切り替える(`core.quotePath=false`を設定していても、
これは非ASCII文字のクォート抑止とは別の、常に効くエスケープ規則)。

`"+++ b/".length`ぶんを単純に`slice`する実装は、この「クォートされる場合」を
想定していないため、クォートされた行に対しては全く違う位置で文字列を切ってしまい、
壊れた(クォート記号やエスケープ文字が混入した)パス文字列を組み立ててしまう。

### このプロジェクトでの実例

`diffParser.ts`の`toSelfDiffHeaderLines`(リネームを伴うdiffから1ハンクだけを
取り出す際に、新パスに対する自己diffヘッダーを組み立てる関数)が、`+++ b/`という
固定長prefixで新パスを切り出していた。ファイル名にダブルクォートを含むリネームで
実際に壊れることを、実機の`git`コマンドで再現確認した。

修正は、「パスの中身をデコードして再構築する」のではなく、「`+++`行に現れた`b/`側の
表記(クォート・エスケープの有無を含めて)をまるごと保持し、先頭の`b/`または`"b/`を
`a/`または`"a/`に置き換えるだけ」という、中身を一切解釈しない方式に変更した。
これにより、クォートされているかどうかに関わらず、常に元の`git`が出力した表記を
壊さずに`a/`側を組み立てられるようになった。

```ts
// クォートの中身を解釈せず、"b/" → "a/" の置換だけを行う
function toAPathToken(bPathToken: string): string {
  if (bPathToken.startsWith('"b/')) return `"a/${bPathToken.slice('"b/'.length)}`
  if (bPathToken.startsWith('b/')) return `a/${bPathToken.slice('b/'.length)}`
  return bPathToken
}
```

### 汎用的な対策

- 外部コマンドの出力をパースするときは、そのコマンドの公式ドキュメント・ソースを
  確認し、「同じフィールドが状況によって別の形式で出力されることがあるか」を
  先に調べる(今回のケースは`core.quotePath`とは独立した、gitのC-quoting規則)
- 固定長`slice`による解析は、対象が本当に固定長であることを実機で確認してからでないと
  危険。可能なら「対象を丸ごと保持し、必要な部分だけを置換する」設計の方が、
  中身を解釈する必要がなく壊れにくい
- 特殊文字(ダブルクォート、バックスラッシュ、非ASCII文字、絵文字)を含むファイル名は
  滅多に遭遇しないが、実際に作成できてしまう以上、パーサーは「特殊なフォーマットの
  入力が来たら壊れずにエラーになる」か「正しく解析できる」かのどちらかであるべきで、
  「気づかずに壊れたデータを生成する」のが最も避けるべき挙動

## 9. ロケール引数を省略した日時フォーマットAPI呼び出し

### どういう時に問題が起こるか

`Date.prototype.toLocaleDateString()`のようなロケール依存APIを引数無しで呼び出し、
その結果を他の固定言語の文言(例: 日本語UIの「3分前」)と並べて表示するとき。

### 原因

`toLocaleDateString()`にロケールを指定しないと、実行環境(OS・ブラウザ・Node.jsの
`ICU`設定)のデフォルトロケールに従ってフォーマットされる。開発者の手元(日本語ロケール)
では`2026/9/27`のように表示されて何の問題も無いように見えるが、英語ロケールの
環境では`9/27/2026`のように、アプリの他の部分(日本語固定文字列)と表示形式が
食い違った状態でユーザーの目に触れる。

このバグは**開発者のロケール設定に依存して再現しない**ため、通常の手元確認では
気づけない。テストで明示的に別ロケールとの差分を検証しない限り見過ごされる。

### このプロジェクトでの実例

`dateFormat.ts`の`formatRelativeDate`が、1ヶ月以上前のコミットや未来日時
(クロックスキュー)の場合に`target.toLocaleDateString()`(ロケール省略)へ
フォールバックしていた。`'ja-JP'`を明示するよう修正し、テストでは
`toLocaleDateString('ja-JP')`と`toLocaleDateString('en-US')`の両方を計算して、
実装の結果が`en-US`ではなく`ja-JP`の形式と一致することを確認する形にした。

```ts
// Before
return target.toLocaleDateString()
// After
return target.toLocaleDateString('ja-JP')
```

```ts
// テスト側: 実行環境のロケールに依存せず検証する
expect(formatRelativeDate(date.toISOString(), now)).toBe(date.toLocaleDateString('ja-JP'))
expect(formatRelativeDate(date.toISOString(), now)).not.toBe(date.toLocaleDateString('en-US'))
```

### 汎用的な対策

- アプリの表示言語を固定している(国際化対応をしていない、または特定ロケール向けに
  作っている)場合、日時・数値のロケール依存フォーマットAPI(`toLocaleDateString`,
  `toLocaleString`, `Intl.NumberFormat`等)には**必ず対象ロケールを明示的に渡す**。
  省略した場合の既定値は実行環境まかせであり、開発機と本番機、あるいは異なるユーザーの
  OS設定で結果が変わりうる
- 逆に国際化対応をしている場合は、ロケールをアプリの状態(ユーザー設定言語)から
  明示的に渡す設計にし、「環境まかせ」を避ける。どちらにしても「暗黙のロケールに
  依存する」状態を残さないことが重要
- テストは実行環境のロケール設定に左右されない形で書く。期待値をハードコードした
  文字列(`'2026/9/27'`)ではなく、`toLocaleDateString('固定ロケール')`で動的に
  計算した値と比較すると、CI環境のロケール差異にも強くなる

## 10. 外部プロセスのタイムアウト・強制終了漏れ

### どういう時に問題が起こるか

`child_process.spawn`等で起動した外部プロセスの完了を`Promise`で待つ実装に、
「プロセスがハングして`close`イベントが永久に来なかった場合」の対策(タイムアウト)が
無いとき。さらに、タイムアウト時に`kill()`を呼んでいても、そのプロセスが
`SIGTERM`(既定のシグナル)を無視するケースへのエスカレーション(`SIGKILL`への
切り替え)が無いとき。

### 原因

ファイルシステムのロック競合、ウイルス対策ソフトによる横取り、壊れたリポジトリ状態
など、外部要因で子プロセスが応答しなくなることは(頻度は低くとも)起こりうる。
`close`/`exit`イベントだけを頼りに`resolve`/`reject`する`Promise`は、プロセスが
本当にハングした場合に**永久に解決しない**。呼び出し元がその`Promise`を`await`して
何らかのロック解除処理をfinally節に書いていても、そのfinallyは実行されないまま、
アプリ内の該当機能が(場合によってはアプリを再起動するまで)無期限に使えなくなる。

タイムアウトを設定して`proc.kill()`(既定で`SIGTERM`)を送っても、プロセスが
シグナルハンドラで`SIGTERM`を無視する実装になっていれば、それだけでは終了しない。
一定の猶予時間をおいて`SIGKILL`(無視できない強制終了シグナル)にエスカレーションする
処理が別途必要になる。

### このプロジェクトでの実例

`gitApply.ts`の`runGitApply`(`git apply --cached`を実行する)にタイムアウトが
無かったため追加し、さらに単発の`proc.kill()`だけでは不十分と判断して、
このプロジェクトの別の外部プロセス実行箇所(`cliService.ts`)に既にあった
`SIGTERM`→猶予時間→`SIGKILL`のエスカレーションパターンを踏襲した。

```ts
const timeoutId = setTimeout(() => {
  if (settled) return
  proc.kill() // まず SIGTERM
  const escalationTimer = setTimeout(() => {
    if (!exited) proc.kill('SIGKILL') // 猶予時間内に終了しなければ強制終了
  }, SIGKILL_GRACE_MS)
  escalationTimer.unref() // このタイマーだけでプロセスの生存を延ばさない
  settleReject(new Error(`git apply timed out for ${filePath}`))
}, GIT_APPLY_TIMEOUT_MS)
```

テストは`vi.useFakeTimers()`でタイムアウトを再現し、(1)プロセスが`SIGTERM`を無視して
`close`を発火しない場合に猶予時間後`SIGKILL`が呼ばれること、(2)`SIGTERM`後に
正常終了すれば`SIGKILL`へはエスカレーションしないこと、の両方を検証した。

### 汎用的な対策

- 外部プロセスの完了を待つ`Promise`ラッパーを書くときは、必ずタイムアウトを設定する。
  「まず動くものを作ってから後で足す」のではなく、最初から設計に含める
- タイムアウト時の`kill()`は既定で`SIGTERM`(プロセスが横取りして無視できる)である
  ことを意識し、無視された場合に備えて猶予時間後の`SIGKILL`エスカレーションを
  セットで用意する
- エスカレーション用の`setTimeout`は`unref()`する。`unref()`しないと、正常系で
  プロセスがすぐ終了しても、猶予時間が経過するまでNodeのイベントループがこの
  タイマーのために生き続け、アプリ終了が遅延する
- 同じプロジェクト内に類似の実装(今回で言う`cliService.ts`)が既にある場合は、
  そのパターンを流用する。独自の簡易実装を新設すると、後から見たときに
  「なぜここだけ違う設計なのか」という保守コストが生まれる

## 11. gitのポーセリン出力における特殊な状態(マージコンフリクト等)の見落とし

### どういう時に問題が起こるか

`git status --porcelain`が返す2文字のステータスコード(`index`/`workingDir`)を
解釈するロジックを書くとき、「変更なし(スペース)」「追跡済み変更あり」
「未追跡(`?`)」のような主要なケースだけを想定し、マージコンフリクト由来の
特殊なコード(`U`, および`AA`/`DD`のような両者一致コード)を考慮していなかったとき。

### 原因

未解決のマージコンフリクトは、`git status --porcelain`で`UU`(両者変更)、
`AA`(両者追加)、`DD`(両者削除)、`AU`/`UA`/`DU`/`UD`(追加/削除と未マージの組み合わせ)
という、通常の「ステージ済み/未ステージ」の2値では表現しきれない状態になる。
「indexの文字がスペースでなければステージ済み」のような単純な判定式は、これらの
コードもすべて「ステージ済み」に分類してしまう。

実際には、コンフリクト状態のファイルは`git add`で明示的に解決マーク(実際には
コンフリクトマーカーを取り除いた内容を`git add`することで「解決した」と扱われる)を
付けるまでは、通常の意味でのステージ済みではない。それを「ステージ済み・コミット可能」
として一覧やコミットボタンの有効/無効判定に含めてしまうと、ユーザーに
「解決していないコンフリクトがあたかも準備完了しているかのように」見せてしまう。

### このプロジェクトでの実例

`gitUtils.ts`の`isStagedFile`が、`index !== ' ' && !isUntrackedFile(f)`という
条件だけで判定していたため、`UU`等のコンフリクト状態のファイルも`true`と
判定してしまっていた。実機で`git merge`を発生させたリポジトリを作り、
`simple-git`経由でこのコードが返す実際の`index`/`workingDir`の値
(`'U'`/`'U'`)を確認した上で、コンフリクト検出関数を追加して除外した。

```ts
function isConflictedFile(f: GitFileStatus): boolean {
  if (f.index === 'U' || f.workingDir === 'U') return true
  if (f.index === 'A' && f.workingDir === 'A') return true
  if (f.index === 'D' && f.workingDir === 'D') return true
  return false
}

export function isStagedFile(f: GitFileStatus): boolean {
  return f.index !== ' ' && !isUntrackedFile(f) && !isConflictedFile(f)
}
```

### 汎用的な対策

- 外部ツール(git、パッケージマネージャ等)のステータス表現を独自のbool値に
  変換するロジックを書くときは、「正常系の2〜3パターン」だけでなく、その
  ツールが持つ**すべての特殊状態**(コンフリクト、部分的失敗、進行中操作等)を
  一度公式ドキュメントで洗い出してから実装する
- 実機で該当の特殊状態を意図的に発生させ(今回で言えば実際に`git merge`で
  コンフリクトを起こす)、ライブラリ(`simple-git`)がその状態をどう表現して
  返してくるかを確認してからコードを書く。ドキュメントの記述とライブラリの
  実装が完全に一致するとは限らない

## 12. サブエージェント/自動化への指示のスコープ逸脱

### どういう時に問題が起こるか

AIエージェントに「PRをレビューして」のような広い目的だけを与え、実行してよい
操作の範囲を明示しなかったとき。エージェントがリポジトリ内の文脈情報
(運用手順書、スクリプト)を参照した結果、指示者が意図していない外部通知アクション
(このプロジェクトでは、課金上の理由で使用停止中のCopilotへのレビュー依頼)を
自発的に実行してしまうことがある。

### 原因

エージェントは「タスクを達成するために有用そうな情報を能動的に探して使う」よう
設計されている。リポジトリに「PRレビューの運用手順書」があり、そこに
「Copilotへのレビュー依頼」という手順が明記されていると、エージェントは
「PRをレビューする」という指示を「この手順書に従ってPRレビューを回す」と
解釈し、手順書内の全ステップ(依頼中の停止事情を知らないまま)を実行しうる。

この種の逸脱は、指示文に**明示的な除外事項**が無いことが根本原因であり、
エージェントの能力や注意力の問題というより、指示の設計の問題として扱うべきである。

### このプロジェクトでの実例

「PR#32をレビューし、GitHub上にコメント・Approve判定を投稿する」というタスクを
与えたサブエージェントが、リポジトリ内の`docs/pr-review-loop.md`(Copilotへの
再レビュー依頼手順を含む)を参照し、指示していない`Copilotへのreview_request`
イベントを実行してしまった。実行結果自体は「quota limit reached」で不発に
終わったため実害は無かったが、意図しない外部アクションが発生したことに変わりはない。
2周目以降のタスク依頼では、プロンプトの冒頭に「Copilotへのレビュー依頼は絶対に
実行しないこと。該当のスクリプト・手順書は参照・実行しないこと」という**明示的な
禁止事項**を追加し、再発しないことを確認した。

### 汎用的な対策

- エージェントに外部への書き込み・通知を伴うタスク(PRコメント投稿、レビュー依頼、
  デプロイ、メッセージ送信等)を依頼するときは、目的だけでなく「やってよいこと」
  「絶対にやってはいけないこと」を具体的に列挙する。特に、対象のリポジトリ/
  環境に既存の自動化手順書やスクリプトがある場合、それらへの言及・実行を
  許可するかどうかを明示する
- 課金・外部サービスへの影響がありうる操作(このケースのCI/Actions消費)は特に、
  「現在使用可能かどうか」の前提条件が変わりうることを意識し、エージェントが
  古い手順書を鵜呑みにしないよう、都度最新の制約を明示的に伝える
- エージェントの実行結果は必ず検証する。「意図した通りに完了しました」という
  報告だけでなく、実際に外部システム(GitHubのタイムライン等)に予期しない
  イベントが記録されていないかを確認する習慣を持つ

## 13. 外部ライブラリのタイムアウト機構が、別のオプションとの組み合わせを前提にしている

### どういう時に問題が起こるか

ネットワークI/O等の外部プロセスの完了を待つ処理に対し、「一定時間応答が無ければ
強制終了する」というタイムアウト機構を外部ライブラリ経由で導入したが、そのタイム
アウト機構自体が「何をもって応答ありとするか」の判定を、別の任意オプションの
有無に依存させていた場合。

### 原因

`simple-git`のtimeoutプラグインは、実装上「spawnした子プロセスの`stdout`/`stderr`に
一定時間データが来なければ強制終了する」というロジックになっている(実ソースの
`timeoutPlugin`を確認: `stdout`/`stderr`の`'data'`イベントでタイマーをリセットする
`wait()`関数)。一方、git自体の仕様として、標準出力/標準エラー出力が端末(tty)に
接続されていない場合(パイプ経由で子プロセスとして起動される場合は常にこれに該当)、
既定では進捗表示(`Compressing objects: NN%`等)を一切出力しない。この進捗表示を
強制的に有効にするのが`--progress`フラグであり、`simple-git`は`progress`オプション
(コールバック)を渡した場合にのみ、内部の`progressMonitorPlugin`が有効になり、
`push`/`pull`/`fetch`/`clone`/`checkout`コマンドに自動的にこのフラグを付与する。

つまり「`timeout`オプションだけ設定すれば、応答がない場合に安全に強制終了できる」
と考えるのは誤りで、実際には「`timeout`オプションが監視している`stdout`/`stderr`への
データ到着」自体が、別のオプション(`progress`)を明示的に指定しない限り発生しない。
この2つのオプションは名前・目的が別物に見えるため、ドキュメントを読んでいても
両者の依存関係に気づきにくい。

この問題は特に発見しにくい。タイムアウト機構自体の単体テストは、`simple-git`を
モックして「タイムアウトオプションが渡されているか」だけを確認する形になりがちで、
「実際のgitプロセスの出力ストリームに何が流れるか」までは検証しない。結果、
タイムアウトのテスト自体は通っているのに、実機では「正常に進行中の、多少時間の
かかる転送」まで巻き添えでタイムアウト扱いされてしまう、本番でしか顕在化しない
バグになる。

### このプロジェクトでの実例

`gitService.ts`のpush/pull/fetchRemoteに、認証プロンプト待ちや到達不能ホストでの
ハングを防ぐため、`simple-git`の`timeout: { block: 30000 }`オプションを追加した。
この時点のレビューでは見逃されたが、次のレビュー周回で「timeoutプラグインの実装は
`stdout`/`stderr`へのデータ到着を監視しているが、`progress`オプションを渡していない
ため、実際の転送中(圧縮・送受信)は何もデータが流れず、正常に進行中の操作でも
30秒経過すると強制終了されてしまう」ことが判明した。`simple-git`の実ソース
(`node_modules/simple-git/dist/cjs/index.js`)を直接読み、`progressMonitorPlugin`が
`--progress`をpush/pull/fetch/checkout/cloneにのみ付与すること、それが
`config.progress`の有無で分岐していることを確認した上で、`progress: () => {}`
(中身は使わないno-op)を追加して対処した。

```ts
function simpleGitWithRemoteTimeout(folderPath: string): SimpleGit {
  return simpleGit(folderPath, {
    timeout: { block: GIT_REMOTE_TIMEOUT_MS },
    // progress を渡さないと --progress が付与されず、timeout プラグインが
    // 監視する stdout/stderr に実際の転送中も何も流れないため、正常に
    // 進行中の操作まで誤ってタイムアウトしてしまう
    progress: () => {}
  })
}
```

### 汎用的な対策

- 外部ライブラリのタイムアウト・ヘルスチェック機構を導入するときは、「何を監視して
  生存/応答ありと判定しているか」を必ずソースコードレベルで確認する。ドキュメントの
  記述だけでは、他のオプションとの依存関係(暗黙の前提条件)まで説明されていない
  ことがある
- 監視対象が「外部プロセスの出力ストリーム」である場合、そのストリームが「常に
  何かデータを吐くとは限らない」ことを疑う。多くのCLIツールは進捗表示・詳細ログを
  tty接続時のみ出力し、パイプ経由(非対話的実行)では既定で沈黙する。タイムアウト
  機構と組み合わせるなら、明示的に詳細出力を要求するオプション(`--progress`,
  `--verbose`等)の併用が要らないか確認する
- タイムアウト機構を追加したら、「実際に長時間かかるが正常に完了する操作」で
  テストし、誤発火しないことを確認する。モックだけのテストでは、監視対象の
  ストリームに実際何が流れるかまでは検証できない

## 14. 同一の業務ルールをUI層とロジック層の双方に別々の表現で実装してしまう

### どういう時に問題が起こるか

「ある操作を実行してよい条件」(業務ルール)を、実行を実際に止めるガード条件
(ロジック層)と、ボタンの見た目を無効化する判定(UI層)の両方に、それぞれ独立した
式として書いてしまったとき。両者が同じルールを表現しているつもりでも、実装としては
別のコードなので、どちらか一方だけを変更すると即座に食い違いが生まれる。

### 原因

「実行を止める」処理と「ボタンを押せなくする」処理は、関心事としては同じ(「今
この操作をしてよいか」)だが、コードの置き場所が異なる(前者はカスタムフック内の
実行関数、後者はUIコンポーネントの`disabled`属性)ため、実装時に別々の式として
書いてしまいがちである。最初に機能を作った時点では両者が一致していても、後から
新しい排他条件(例えば「別の操作Xの実行中は待つ」)を追加する際に、片方の式だけを
更新して満足してしまうと、もう片方は古いルールのまま取り残される。

この不整合は、「押せそうに見えるのに実行しても何も起きない」(ロジック層だけ
更新した場合)、あるいは「実際には実行できるはずなのに押せない」(UI層だけ更新
した場合)という、机上のコードレビューでは見つけやすいが、実際に操作しないと
気づきにくいUXバグを生む。

### このプロジェクトでの実例

push/pullの排他制御を実装する際、「pushとpullは同時実行不可」「pullはcommit・
ハンク操作中も不可」という業務ルールを、当初は`useGitRemoteOperations`フックの
実行ガード(`isBusy()`)と`SourceControlToolbar`コンポーネントの`disabled`判定の
両方に、それぞれ`isPulling || isPushing`のような式として個別に書いていた。
レビューで、この2箇所が同じルールを別々に保持していること自体が問題であり、
将来ルールを変更する際(例えばfetchも排他対象に加える等)に両方を同時に直さないと
整合が崩れる、という指摘を受けた。

対応として、業務ルールの判定結果そのもの(`isPushBlocked`、`isPullBlocked`、
`isRemoteOperationDisabled`という「他操作や状態によってブロックされているか」を
表すbool値)をフック側で計算して返すように変更し、UIコンポーネント側は受け取った
値をそのまま`disabled`属性に渡すだけにした。これにより、ルールの中身(何と何が
排他か)を変更する必要が生じても、修正箇所はフック内の1箇所に閉じるようになった。

```ts
// フック側: 業務ルールの判定結果を計算して返す
const isPushBlocked = isPulling || lock.isAnyLocked()
const isPullBlocked = isPushing || lock.isAnyLocked()
return { ..., isPushBlocked, isPullBlocked, isRemoteOperationDisabled }
```

```tsx
// UI側: 判定結果をそのまま使うだけ。業務ルールの中身を知らない
<button disabled={isRemoteOperationDisabled || isPulling || isPullBlocked}>プル</button>
```

### 汎用的な対策

- 「実行を止める条件」と「ボタンを無効化する条件」がコード上に2箇所以上存在するのを
  見つけたら、それらが本当に同じ式を表現しているか突き合わせる。少しでも表現が
  異なる(例えば片方だけ`lock.isAnyLocked()`を含む)なら、どちらかが古いままである
  可能性を疑う
- 業務ルールは「それを実際に評価する場所」を1箇所に決め、そこから計算された結果
  (bool値)を他の場所(UI等)へ受け渡す設計にする。UI側が業務ルールの中身(何と何が
  排他か)を知らなくても正しく動く状態を目指す
- 新しい排他条件・新しい操作を追加するときは、既存の「実行ガード」と「UI表示」の
  対がどこにあるかを`grep`等で洗い出し、両方を同時に更新する

## 15. 新機能を既存の排他制御・ロック機構に追加する際、対象範囲の見落とし

### どういう時に問題が起こるか

既に複数の操作(A, B)が共有ロックによって相互排他されている状態に、新しい操作(C)を
追加するとき。Cが「Aとは同時実行しても安全」という理由だけで排他条件の検討を
済ませてしまい、「Aと同時実行しても安全なCが、実はBとは安全でない」という見落としを
したとき。

### 原因

新しい操作を実装する際、開発者は自然と「その操作自体が何を読み書きするか」を
起点に安全性を検討する。今回のケースで言えば、push操作は「リモートのrefを
更新するだけで、ローカルのworking tree/indexは変更しない」という理由から、
「ローカルの状態を変更する操作(stage/unstage)とは同時実行しても安全」という
結論に至りやすい。

しかし、この検討は「pushが何を書き込むか」にのみ着目しており、「pushが何を
読み込むか」を見落としている。pushは実行時点のHEAD(直近のコミット)をリモートに
送る。もし別の操作(commit/amend)がその瞬間にHEADを書き換えている最中だと、
pushは「書き換え中の、まだ確定していない状態」を読んでしまう可能性がある。
特にamendは既存のコミットを別の内容で置き換える操作であり、「amendの実行中に
pushが古いHEADを読み、pushが完了した直後にamendが新しいHEADで確定する」という
タイミングが発生すると、ローカルのgit logは新しいコミットを指しているのに、
リモートには古いコミットが送られてしまうという状態の食い違いが生まれる。

この種の見落としが起きやすいのは、「同時実行不可にすべき操作の組」を、実装時の
直感(「同じリソースを書き込むかどうか」)だけで判断してしまい、「一方が読み取る
対象を、他方が書き換えている最中でないか」という、読み取り側の一貫性の観点を
検討しないためである。さらにこの種のバグは日常的な単独操作では発生せず、
「ユーザーがコミットした直後、間を置かずにプッシュする」という、複数の操作を
連続して素早く行う一般的な操作パターンでのみ顕在化する。

### このプロジェクトでの実例

`useGitRemoteOperations`のpush実装で、当初の`isBusy()`条件は「push自身の多重発火」
「pull実行中」のみを排他対象とし、`lock.isAnyLocked()`(commit/amend実行中、
およびハンク単位のstage/unstage実行中を示す共有ロック)を含んでいなかった。
レビューで「コミットしてすぐプッシュ、という一般的な操作パターンで、amendが
HEADを書き換えている最中にpushが古いHEADを読んでしまうレースが起こりうる」という
指摘を受け、push側の`isBusy()`にも`lock.isAnyLocked()`を追加した。

```ts
// Before: pull実行中と自分自身の多重発火しか見ていない
const push = (): Promise<void> =>
  runRemoteOperation({
    isBusy: () => isPushingRef.current || isPullingRef.current || isRemoteOperationDisabled,
    ...
  })

// After: commit/amend・ハンク操作中(lock.isAnyLocked())も待つ
const push = (): Promise<void> =>
  runRemoteOperation({
    isBusy: () =>
      isPushingRef.current ||
      isPullingRef.current ||
      lock.isAnyLocked() ||
      isRemoteOperationDisabled,
    ...
  })
```

なお、この修正はハンク単位のstage/unstage操作(`git apply --cached`)中もpushを
待たせるという副次的な制約を伴う。ハンク操作自体はpushの安全性に直接関係しないが、
共有ロックがcommit実行中とハンク操作実行中を区別なく同じ`isAnyLocked()`という
シグナルで表現しているため、両者を分離できない。この副次的な制約はコード
コメントで明示し、意図した設計であることを残した。

### 汎用的な対策

- 新しい操作を既存の排他制御に追加するとき、「この操作が何を書き込むか」だけで
  なく「この操作が何を読み込むか、そしてその読み込み対象を書き換えている最中の
  操作は無いか」を必ず検討する。読み取り専用に見える操作でも、他の操作が
  書き換え中の対象を読むこと自体がレースになりうる
- 「一般的な操作の組み合わせパターン」(今回で言えば「コミットしてすぐプッシュ」)を
  具体的に洗い出し、それぞれの組み合わせが安全かを個別に検討する。抽象的に
  「読み書きが衝突するか」だけを考えるのではなく、実際のユーザー操作の連続を
  想像する
- 共有ロックの粒度が粗く、複数の異なる操作を区別なく1つのシグナル(`isAnyLocked()`
  等)で表現している場合、新しい排他条件を追加すると意図しない副作用(今回で言えば
  ハンク操作中もpushが待たされる)が発生しうる。この副作用が許容範囲かどうかを
  判断し、許容する場合はコメントに理由を残す

---

## 16. テストが検証対象と無関係な副作用によってたまたま成功する(テストの偽陽性)

### どういう時に問題が起こるか

「あるガード条件Xが正しく機能しているか」を検証するテストを書いたが、テスト対象の
コードが複数のガード条件(X, Y)を`||`で組み合わせており、テスト実行時にXを無効化
しても、別のガード条件Yが偶然同じタイミングで真になっているため、テストの結果
(最終的な振る舞い)自体は変わらず、テストがパスし続けてしまうとき。

### 原因

このプロジェクトのpull操作は、`isPullingRef.current`(自分自身の多重発火防止)
`|| isPushingRef.current || lock.isAnyLocked() || isRemoteOperationDisabled`という
複数条件のORで実行可否を判定している。「自分自身の多重発火防止
(`isPullingRef.current`)」を単体で検証するテストを書く際、他の条件をすべて
デフォルト(false)にしたつもりでも、pull操作自体が実行開始時に
`onStart: lock.lockGlobal`という副作用を持っていた場合、1回目の呼び出しでこの
副作用が発火し、`lock.isAnyLocked()`が(意図せず)trueに変化してしまう。

その結果、2回目の呼び出し時に`isBusy()`を評価すると、たとえ`isPullingRef.current`の
チェック自体を削除しても、`lock.isAnyLocked()`がtrueになっているため、依然として
`isBusy()`全体はtrueとなり、2回目の呼び出しはブロックされる。つまり、テストが
検証したかった「`isPullingRef.current`自体の効果」とは全く別の経路
(`lock.isAnyLocked()`)によって、たまたま同じ観測結果(2回目は実行されない)が
得られてしまう。

この種のテストの偽陽性は非常に発見しにくい。テストは実際にgreenで、しかもテストが
意図した通りの振る舞い(多重呼び出しを防ぐ)を実際に確認できているように見える
ためである。しかし、このテストが本当に検証しているのは「push/pull全体としての
多重発火防止」であり、「`isPullingRef.current`という特定の実装の正しさ」ではない。
もし将来`isPullingRef.current`のチェック自体にバグが入っても(例えば削除されても)、
このテストは検知できず、赤信号を出さないままリファクタや変更が積み重なっていく。

この問題が実際に発覚したのは、レビューでミューテーションテスト(意図的に実装の
一部を壊して、対応するテストが本当に落ちるかを確認する手法)を行った際だった。
`isPullingRef.current`のチェックを削除しても対応するテストが落ちないことが判明し、
原因を追跡した結果、`lock.lockGlobal()`という副作用が意図せず保護膜になっていた
ことが分かった。

### このプロジェクトでの実例

`useGitRemoteOperations.test.ts`のpullの「実行中の多重呼び出しは`gitApi.pull`を
1回しか呼ばない」というテストが、`lock`引数を渡さずに(デフォルトの実際の
`useFileOperationLock()`を使って)実行されていた。デフォルトのロックは
`lockGlobal()`を呼ぶと本当に`globallyLockedRef.current`を`true`にする実装で
あるため、1回目のpull呼び出しでこのロックが実際に立ってしまい、
`isPullingRef.current`自体のチェックが機能しなくても、2回目の呼び出しは
`lock.isAnyLocked()`経由でブロックされていた。

修正は、`isAnyLocked`が常にfalseを返す固定のモックロック(`makeFileLock()`)を
明示的にテストへ渡すことで、他のガード条件をすべて無効化し、
`isPullingRef.current`単体の効果だけを検証できるようにした。

```ts
// Before: 実際のロックを使っていたため、lockGlobal() の副作用で
// isPullingRef.current 自体のチェックが機能していなくても検知できない
const { result } = renderHook(() => useGitRemoteOperations(repoStatus, refreshGitStatus))

// After: isAnyLocked が常に false を返す固定モックを明示的に渡し、
// 他の経路からの保護を排除して対象のロジックだけを検証する
const lock = makeFileLock()
const { result } = renderHook(() => useGitRemoteOperations(repoStatus, refreshGitStatus, lock))
```

修正後、`isPullingRef.current`チェックを削除するミューテーションを当てると、
実際にテストがタイムアウトで失敗する(2回目の呼び出しがブロックされず、対応する
Promiseが永久に未解決のまま残る)ことを確認した。

### 汎用的な対策

- 複数のガード条件を`||`で組み合わせている実装のうち、特定の1条件だけを検証したい
  テストを書くときは、他の条件がテスト中に意図せず真にならないことを保証する。
  副作用(このケースでは`lockGlobal()`)を持つ実行パスをテストする場合は特に注意する
- テストを書いたら、それが本当に「対象のロジック」を検証しているかを、意図的に
  対象のロジックを壊す(コメントアウトする、条件を反転する等)ミューテーションに
  よって確認する習慣を持つ。「テストがgreenである」ことと「テストが対象のバグを
  検知できる」ことは別の話であり、後者を確認しない限りテストの存在価値は
  保証されない
- 依存を注入できる設計(このケースでは`fileLock`を引数として渡せる設計)になって
  いる場合、単体テストでは実際の依存ではなく、テストが検証したい条件以外を
  すべて固定した最小限のモックを明示的に使う。デフォルト値(暗黙的に生成される
  実際の依存)に頼ると、その依存が持つ副作用がテストの独立性を壊すことがある

## 17. UIの動的な視覚状態とアクセシビリティ属性(aria-\*)の不同期

### どういう時に問題が起こるか

ボタン等のUI要素が、状態(実行中かどうか等)に応じて表示テキストを動的に切り替える
(例:「フェッチ」→「フェッチ中...」)実装をしたときに、`aria-label`のような
アクセシビリティ用の属性を固定値のまま残してしまい、視覚的には状態変化が見えるのに、
スクリーンリーダー等の支援技術には状態変化が伝わらなくなるとき。

### 原因

`aria-label`は、そのDOM要素の「アクセシブルネーム」(支援技術が読み上げる名前)を
明示的に上書きする属性である。ボタンにテキストコンテンツ(子要素の文字列)がある
場合、通常はそのテキストがアクセシブルネームとして扱われるため、`aria-label`を
付けなくても、テキストの変化がそのまま読み上げに反映される。しかし、いったん
`aria-label`を明示的に指定すると、それが子要素のテキストよりも優先されるため、
ボタンの表示テキストだけを動的に変更しても、支援技術から見た「名前」は
`aria-label`に指定した固定値のまま変わらなくなる。

この不整合は、開発者が画面を目で見て確認する通常のQAでは気づかれない(見た目には
「フェッチ中...」と正しく表示されているため)。スクリーンリーダーを使う、あるいは
テストで`getByRole('button', { name: ... })`のようにアクセシブルネームを明示的に
検証しない限り、発見されない種類のバグである。

### このプロジェクトでの実例

`SourceControlToolbar`のフェッチ/プル/プッシュボタンが、表示テキストは
`{isFetching ? 'フェッチ中...' : 'フェッチ'}`のように動的に切り替えていたが、
`aria-label="フェッチ"`のように固定値を指定していた。レビューで、既存の
コンポーネント(`CommitSection.tsx`のコミットボタン)が、動的に変化するボタンには
`aria-label`を一切付けず、テキストコンテンツにアクセシブルネームを語らせる
慣習になっていることが指摘され、この慣習からの逸脱として扱われた。

対応として、`aria-label`を表示テキストと同期させる
(`isFetching ? 'フェッチ中' : 'フェッチ'`)よう修正した。

```tsx
// Before: aria-label が固定のまま、表示テキストだけが動的に変わる
<button aria-label="フェッチ" disabled={isRemoteOperationDisabled || isFetching}>
  {isFetching ? 'フェッチ中...' : 'フェッチ'}
</button>

// After: aria-label を表示テキストと同期させる
<button
  aria-label={isFetching ? 'フェッチ中' : 'フェッチ'}
  disabled={isRemoteOperationDisabled || isFetching}
>
  {isFetching ? 'フェッチ中...' : 'フェッチ'}
</button>
```

テストは`getByRole('button', { name: 'フェッチ中' })`のようにアクセシブルネームを
直接検証する形にし、実行中は`getByRole('button', { name: 'フェッチ' })`(旧名)では
ヒットしないこと(`queryByRole(...).not.toBeInTheDocument()`)まで確認した。

### 汎用的な対策

- ボタン等の要素の表示テキストを状態に応じて動的に切り替える実装を書くときは、
  `aria-label`を付けるかどうかをまず検討する。テキストコンテンツだけで意味が
  伝わるなら`aria-label`自体を付けない方が、この種の不同期を構造的に防げる
- 何らかの理由で`aria-label`を付ける必要がある場合(アイコンのみのボタン等)、
  状態が変化するたびに`aria-label`の値も必ず同時に更新する。表示テキストと
  `aria-label`が別々の場所にハードコードされている限り、片方だけの更新漏れは
  起こりうる
- テストで`getByText(...)`だけでなく`getByRole('button', { name: ... })`も使い、
  アクセシブルネームの変化まで検証する。前者は視覚的なテキストの存在だけを
  確認し、後者はアクセシビリティツリー上の名前を確認するため、両者を使い分ける
  ことで今回のような不整合を検出できる

## 18. 外部ライブラリの内部エラーメッセージがそのままUIに露出する

### どういう時に問題が起こるか

外部ライブラリ(`simple-git`等)が投げる例外を、アプリ側で変換せずそのまま
呼び出し元まで伝播させ、最終的にUIのエラー表示にその例外の`message`をそのまま
表示している場合、ライブラリの内部実装の言語(通常英語)で書かれた技術的な
文字列が、他がすべて日本語のUIに混在して表示されてしまうとき。

### 原因

多くのエラーハンドリング実装は、「エラーを握りつぶさず、原因をユーザーに
伝える」という良い意図のもとで、`catch`した例外オブジェクトの`message`
プロパティをそのまま画面に出す設計になりがちである。これは大半のケース
(例えばgitコマンド自体が返すエラーメッセージ)では有用だが、ライブラリが
独自に生成する内部的なエラー(今回で言えば`simple-git`のタイムアウトプラグインが
投げる`GitPluginError`の`"block timeout reached"`という固定文字列)は、ユーザー
向けの説明として設計されたものではなく、開発者がライブラリの内部動作を
デバッグするための文字列に過ぎない。

このような文字列をそのままエンドユーザーに見せると、(1)アプリの他の文言が
日本語なのに、この部分だけ英語になり体裁が崩れる、(2)「タイムアウトした」
という事実は伝わっても、ユーザーが次に何をすべきか(認証情報を確認する、
ネットワークを確認する等)が全く伝わらない、という2つの問題が生じる。

この種の問題は、エラーハンドリングの実装時点では見過ごされやすい。開発者
自身がテストする際には、そのエラーメッセージの意味を理解しているため、
「英語で分かりにくい」という感覚が湧きにくいためである。

### このプロジェクトでの実例

`gitService.ts`のpush/pull/fetchRemoteに追加したタイムアウト機構が発火すると、
`simple-git`の`GitPluginError`(`plugin: 'timeout'`、`message: 'block timeout
reached'`)がそのまま呼び出し元(`useGitRemoteOperations`)まで伝播し、
`remoteOperationError.message`としてUIにそのまま表示されていた。レビューで
「アプリの他のUI文言はすべて日本語であり、このメッセージだけ英語の内部文字列の
ままで、原因の推測にもつながらない」という指摘を受けた。

対応として、`GitPluginError`のうち`plugin === 'timeout'`であるものだけを判定し、
原因の推測(認証情報未設定、ネットワーク問題)を含んだ日本語メッセージに差し替えて
から再送出するようにした。`GitPluginError`は`GitError`を継承した型で、`plugin`
プロパティによって「どのプラグインが投げたエラーか」を判別できることを、
`simple-git`の型定義から確認した上で実装した。

```ts
function toRemoteOperationError(err: unknown): unknown {
  if (err instanceof GitPluginError && err.plugin === 'timeout') {
    return new Error(
      '操作がタイムアウトしました。認証情報が未設定か、ネットワークに問題がある可能性があります'
    )
  }
  return err // timeout 以外の GitPluginError や通常の GitError は素通しする
}
```

`plugin`の種類で判定を絞り込み、timeout以外の`GitPluginError`(またはコマンド
自体の失敗による通常の`GitError`)は変換せずに素通しした。変換対象を広げすぎると、
本来ユーザーに伝えるべき具体的なgitのエラーメッセージ(例えば認証失敗の詳細)まで
一律に潰してしまうリスクがあるためである。

### 汎用的な対策

- 外部ライブラリの例外をそのままUIに表示する設計を採用する場合、そのライブラリが
  「ユーザー向けに設計されたメッセージ」と「開発者向けの内部的なメッセージ
  (ライブラリ自身のプラグイン・内部処理が生成するもの)」の両方を投げうるかを
  確認する。後者に該当する例外は個別に判定し、アプリの言語・文脈に合わせた
  メッセージへ変換する
- 変換の判定は、可能な限りエラーオブジェクトの型・専用プロパティ(今回で言えば
  `GitPluginError`の`plugin`)で行い、`message`文字列の内容(例えば`"timeout"`という
  単語を含むか)でパターンマッチしない。文字列マッチは、ライブラリのバージョン
  アップでメッセージの言い回しが変わった際に静かに機能しなくなる
- 変換は対象を狭く限定する。「何でもかんでも日本語に変換する」よう広く網をかけると、
  本来ユーザーに伝えるべき具体的な情報(認証失敗の詳細など)まで一律の文言に
  潰してしまう。「このエラー種別だけは内部的な文字列で、ユーザーに見せる価値が
  ない」というものだけを個別に変換する

## 19. 外部操作でディスクが書き換わったあと、メモリ上のコピーが古いまま残る

### どういう時に問題が起こるか

アプリが「ディスク上のファイルの内容」をメモリ(エディタのバッファ、キャッシュ、
一覧の表示状態など)に保持している状態で、アプリ自身の別機能や外部コマンドが、
そのファイルをディスク上で直接書き換えたとき。このプロジェクトでは`git checkout`
によるブランチ切り替えがこれに当たる。checkoutはworking treeのファイルを切り替え先
ブランチの内容へ一括で置き換えるが、エディタのタブに読み込み済みの文字列は
一切連動して更新されない。

### 原因

問題は2段階に分かれており、それぞれ別の事故を起こす。

1. **未保存の編集がある場合**: エディタ上に「切り替え前のブランチのファイルを編集
   した内容」が残ったまま、ディスクだけが切り替え後のブランチの内容になる。その
   状態でユーザーが保存すると、**切り替え前の内容が切り替え後のブランチのファイルを
   丸ごと上書き**する。差分として見えるのは「切り替え後のブランチには存在しなかった
   はずの変更」であり、ユーザーには何が起きたのか分かりにくい。エラーは一切出ない
2. **未保存の編集が無い(dirtyでない)場合も**: エディタは古いブランチの内容を
   表示し続ける。「dirtyでないなら何もしなくてよい」と考えがちだが、ディスクと
   表示が食い違っているという意味では、dirtyかどうかに関係なく同じ問題を抱えている。
   ユーザーは「切り替えたのに古いコードが見えている」と混乱し、それを元に新たな
   編集を始めれば1と同じ事故につながる

原因の根本は、「ディスクの内容が外部要因で変わりうる」ことを、状態を持つ側が知る手段
(ファイル監視など)を持たず、変更を起こす操作の前後に明示的に同期する処理も入れて
いなかった点にある。ファイル監視(file watcher)が無いアプリでは、ディスクを書き
換える操作を実装した側が、その操作の前後で同期する責任を負う。

### このプロジェクトでの実例

`useAppState.ts`のブランチ切り替えラッパーで、次の順序を強制するようにした。

```ts
const checkoutBranch = async (branchName: string): Promise<void> => {
  // (1) 切り替え前: 未保存の編集を捨ててよいか確認する。拒否されたら何もしない
  if (!fileSystem.confirmDiscardAnyDirty()) return
  const succeeded = await gitBranchOperations.checkoutBranch(branchName)
  // (2) 切り替え後: dirtyかどうかに関係なく、開いている全タブをディスクの最新内容へ
  //     再読込する。ただし成功したときだけ(パターン20)
  if (succeeded) await fileSystem.reloadOpenFiles()
}
```

- `confirmDiscardAnyDirty`は「どれか1つでもdirtyなタブがあれば確認ダイアログを出す」
  関数として`useFileSystem`に追加した。単一ファイルの切り替えではなく、全タブが
  対象になる操作だから
- `reloadOpenFiles`は、開いている全タブをディスクから読み直し、読み込みに失敗した
  タブ(切り替え先に存在しないファイル等)の扱いも含めて`useFileSystem`側にまとめた

### 汎用的な対策

- 「ディスク上のファイルを一括で書き換える操作」(checkout、pull、merge、
  stash pop、外部ツールによる整形など)を追加するときは、それが**メモリ上のコピー
  にどう影響するか**を必ず設計に含める。チェックリスト: (1)操作前に未保存編集を
  どうするか、(2)操作後に開いているコピーをどう同期するか
- 同期の対象は「dirtyなもの」だけでは足りない。ディスクと食い違うのは、dirtyかどうか
  に関係なく全てのコピー
- 「ディスクの変更を検知する仕組み」(file watcher)が無い間は、ディスクを書き換える
  操作の**呼び出し側**が同期を担当するしかない。仕組みが入るまで、この責務を各操作の
  実装者が意識しなければならないことをコメントに残す
- テストは「未保存編集がある状態で操作を実行する」「dirtyなタブが無い状態で操作を
  実行する」の両方を書き、後者でも再読込が呼ばれることを検証する

## 20. 「失敗しても例外を投げない」処理の後続処理が、失敗時にも実行される

### どういう時に問題が起こるか

ある操作が失敗しても`Promise`をrejectせず(エラーは別のstateに反映して正常終了する)、
呼び出し元はその関数を`await`して**成功した前提の後続処理**を続けて書いてしまうとき。
さらに、その後続処理が「何かを上書きする・捨てる」性質のもの(再読込、キャッシュ
クリア等)だと、失敗したのに副作用だけが実行される。

### 原因

UIから呼ばれる非同期操作は、エラーを`try/catch`で受け止めて画面に表示するため、
呼び出し元へは例外を投げず`void`で正常終了する設計になりやすい。この設計自体は
UIの都合として妥当だが、呼び出し元から見ると次の3つが区別できなくなる。

- 実際に実行されて成功した
- 実行されて失敗した(エラーはstateにだけ反映された)
- 実行されなかった(別の操作が実行中で開始条件を満たさず、何もせず戻った = no-op)

3つとも`await`が戻ってくるだけで、見た目上は同じ。そのため`await checkout(); reload()`
のように書くと、checkoutが**切り替え先ブランチと衝突する未コミット変更がある**
などの理由で失敗しても、`reload()`は無条件で実行される。

この`reload()`は「ディスクの内容でエディタのバッファを上書きする」処理なので、
失敗した結果(=ディスクは切り替え前のまま)を読み込み直すことになり、ユーザーが
編集していた**未保存の内容がサイレントに失われる**。ブランチが切り替わっていない
ので、ユーザーは失われたことにすら気づきにくい。

### このプロジェクトでの実例

共通の排他実行ヘルパー`useRunExclusiveGitOperation`の戻り値を`Promise<void>`から
`Promise<boolean>`(実際にexecuteが実行され、成功したか)に変更した。

```ts
return async ({ isBusy, setBusy, onStart, onEnd, execute }) => {
  if (isBusy()) return false // no-op
  ...
  let succeeded = false
  try {
    await execute()
    setError(null)
    succeeded = true
  } catch (err) {
    setError(toError(err)) // 失敗: 例外は投げず、succeededはfalseのまま
  } finally { ... }
  return succeeded
}
```

呼び出し元のラッパーは`if (succeeded) await reloadOpenFiles()`と分岐する。
push/pull/fetchは戻り値を使わないため、公開する型は従来どおり`Promise<void>`のまま
にして、外部への挙動変化が出ないようにした(内部の型と公開する型を分ける)。

### 汎用的な対策

- 「エラーを例外にしない」関数を作るときは、**成否を戻り値でも伝える**。少なくとも、
  後続処理が失敗時に困る呼び出し元が1つでも存在する場合は必須
- 「no-op(実行されなかった)」と「失敗」を区別する必要があるかを検討する。区別
  不要なら`boolean`、区別が要るなら`'skipped' | 'failed' | 'succeeded'`のような
  列挙にする
- 後続処理が**破壊的(上書き・破棄)**な場合ほど、成功時のみ実行するガードを
  最優先で入れる。破壊的でない後続処理(再取得など)なら、失敗時に実行しても
  無害なことが多い
- テストは「操作が失敗した場合に後続処理が呼ばれない」「no-opの場合も呼ばれない」
  の両方を書く。成功パスだけのテストは、この種のバグを検出できない

---

## 21. 外部入力がコマンドライン引数の位置に渡り、オプションとして解釈される(引数インジェクション)

### どういう時に問題が起こるか

IPC・HTTP・ユーザー入力などの信頼境界を越えて届いた文字列を、CLIコマンド
(`git checkout <name>`等)の**位置引数**にそのまま渡すとき。文字列が`-`や`--`で
始まっていると、コマンド側はそれを位置引数ではなくオプションとして解釈する。

### 原因

`simple-git`のようなライブラリは、シェルを経由せず`spawn`で直接プロセスを起動する
ため、`;`や`&&`、`$(...)`によるシェルインジェクションは成立しない。しかし
「シェルインジェクションが無い」ことと「コマンドの引数として安全」は別の話である。
`git checkout --orphan`のように、`-`始まりの文字列はgit自身の引数パーサーがオプション
として読む。UIからは実在のブランチ名の一覧から選ばせているので通常は発生しないが、
IPCハンドラーは任意の文字列を受け付ける口であり、レンダラープロセスが(バグや
XSS等で)想定外の値を送る可能性を排除できない。

「UIが安全な値しか送らないから大丈夫」という判断は、**UIとIPC境界の間に信頼の
境界がある**ことを見落としている。検証は、値を受け取った最後の砦(メインプロセスの
ハンドラー/サービス)で行う必要がある。

### このプロジェクトでの実例

`gitService.ts`の`checkoutBranch`で、渡された`branchName`が**実在するローカルブランチ名
の集合に含まれるか**を検証してから`git.checkout`を呼ぶようにした(許可リスト方式)。

```ts
export async function checkoutBranch(folderPath: string, branchName: string): Promise<void> {
  const git = simpleGit(folderPath)
  const summary = await git.branchLocal()
  if (!summary.all.includes(branchName)) {
    throw new Error(`存在しないブランチです: ${branchName}`)
  }
  await git.checkout(branchName)
}
```

`-`始まりの文字列を拒否する(拒否リスト方式)ではなく許可リストを選んだのは、
拒否リストは「他にも危険な形式がないか」を網羅し続けなければならないが、許可リスト
は「有効な値の集合」だけを定義すればよく、想定外の形式が自動的に弾かれるため。

### 汎用的な対策

- 信頼境界(IPC、HTTP、ファイルからの読み込み)を越えた値をCLIの引数に渡すときは、
  「シェルを使っているか」ではなく**「値がオプションとして解釈されうるか」**を
  確認する。ライブラリがシェルを使わないと分かっても、検証を省略してよい理由には
  ならない
- 検証は可能なら**許可リスト**(実在する値の集合に含まれるか)で行う。ブランチ名、
  タグ名、ファイル名などは、実在する一覧を取得できることが多い
- 許可リストが作れない場合は、`--`(オプション終端)をコマンドの位置引数の前に入れる
  ことでオプション解釈を止める。ただしライブラリが`--`を自動で挿入するかどうかは
  ライブラリの実装に依存するため、ソースを確認する
- 「UIは安全な値しか送らない」ことはコードコメントに書いておき、それでも境界で
  検証している理由を明示する。後から読む人が「UIが制限しているから不要」と
  判断して検証を消すのを防ぐ

## 22. ボタン起点のポップオーバー/メニューでフォーカスの出入りを管理していない

### どういう時に問題が起こるか

キーボード(Enter/Space)で開けるボタンから、ポップオーバー、ドロップダウン、
メニューを表示するとき。特に、メニュー内に矢印キー操作などのキーボードナビゲーション
を実装しているのに、開いた直後のフォーカス位置と、閉じたあとのフォーカス位置を
指定していない場合。

### 原因

DOMのフォーカスは、明示的に`.focus()`を呼ばない限り、それまで持っていた要素に
残り続ける。ポップオーバーを開く操作は「トリガーボタンにフォーカスがある状態で
Enterを押す」ことなので、開いた直後もフォーカスはトリガーボタンにある。

- **開いたとき**: メニュー内の`onKeyDown`(矢印キーのハンドラー)は、メニュー内の
  要素にフォーカスがあるときにしか呼ばれない。フォーカスがトリガーに残ったまま
  矢印キーを押しても、イベントはトリガー側に届くだけでメニューには届かない。
  実装済みの矢印キー操作は、もう一段`Tab`を押さないと辿り着けず、キーボードのみの
  ユーザーにとって実質使えない
- **閉じたとき**: メニューが閉じるとフォーカスを持っていた要素がDOMから消える。
  ブラウザはフォーカスを`<body>`に落とすため、キーボードユーザーは「今どこに
  いるのか」を見失い、ページの先頭から`Tab`でやり直すことになる

既存の`ExplorerContextMenu`(右クリックで開くメニュー)を手本にして実装すると、
この問題を見落としやすい。右クリックは開く操作自体がマウスであり、キーボードの
フォーカスという概念がそもそも必要ない。**参考にした実装が、自分の使い方と入力
手段の前提が違う**ことに気づけなかった。

### このプロジェクトでの実例

- `BranchSwitcherMenu`: マウント時に、先頭の選択可能なブランチへ`.focus()`する。
  ただし依存配列を空にしてマウント時の1回に限定した(選択状態が変わるたびに再
  フォーカスすると、矢印キー操作中のフォーカスを奪ってしまうため)
- `onClose`に`restoreFocus: boolean`を追加し、閉じ方で挙動を分けた

  | 閉じ方                                           | `restoreFocus`                       | 理由                                                 |
  | ------------------------------------------------ | ------------------------------------ | ---------------------------------------------------- |
  | Escape                                           | `true`                               | キーボード操作の一環。トリガーへ戻すのが自然         |
  | ブランチ選択                                     | (`handleSelect`が直接トリガーへ戻す) | 操作完了後、元の位置へ戻す                           |
  | 外側クリック                                     | `false`                              | ユーザーがクリックした別の要素へフォーカスを移そうと |
  | している。トリガーへ戻すとその意図を奪ってしまう |

- `BranchSwitcher`はトリガーボタンの`ref`を保持し、閉じるときに`.focus()`する

### 汎用的な対策

- キーボードで開けるトリガーから出るUI(ポップオーバー、メニュー、ダイアログ)では、
  次の2点を必ず実装する: (1)開いたら、メニュー内の最初の操作対象へフォーカスを移す、
  (2)閉じたら、トリガーへフォーカスを戻す
- 「閉じる」理由によってフォーカスの戻し先が違う場合は、閉じるコールバックに理由
  (または`restoreFocus`のような真偽値)を渡して区別する。**外側クリックでフォーカスを
  トリガーに戻してはいけない**。ユーザーの意図を奪う
- 参考にする既存実装を選ぶときは、コードの見た目が似ているかではなく、
  **入力手段(マウス/キーボード/タッチ)と開閉のきっかけが同じか**を確認する
- テストでは、`userEvent`などで実際にフォーカスを移動し、`document.activeElement`
  が期待する要素になっているかを検証する。開閉の表示/非表示だけを検証するテスト
  では、フォーカス管理の欠落は検出できない

## 23. 排他制御の「方向」を分析せず、実装の簡単さだけで範囲を決める / 既知の競合を記録しない

### どういう時に問題が起こるか

新しい操作(ブランチ切り替え)を、既存の複数の操作(push/pull/commit/ハンク操作)
が共有している排他制御に追加するとき。「どの操作とどの操作を同時に実行させない
か」を、操作の組み合わせごとに向きを含めて整理せず、とりあえず全てを止める、または
逆に一部を見落とす。また、スコープ外と判断した競合を記録せず、後から発見した人が
同じ調査をやり直す。

### 原因

排他制御は「AとBを同時に実行しない」という対称的な表現で語られがちだが、実際の
安全性は**操作ごとの読み書きの対象**で決まる。パターン15で述べたとおり、ある操作が
何を書き込むかだけでなく何を読むかも検討する必要がある。今回は次の非対称性があった。

- **checkout実行中にpush**: checkoutはworking tree・index・HEADを書き換える。pushは
  HEADが指すコミットを読んでリモートへ送るため、checkoutが書き換え中のHEADを読む
  可能性がある。**止める必要がある**
- **push実行中にcheckout**: pushはリモートのrefを更新するだけで、working tree・
  index・HEADは書き換えない。checkoutが自由に書き換えても、pushの読み取りに影響
  しない。**止める必要がない**

方向によって結論が異なるため、片方向だけロックを取れば足りる。ここで「念のため
両方向で止める」とすると、pushの実行中(ネットワークの都合で数十秒かかりうる)に
ブランチ切り替えが無効化され、ユーザーには理由の分からない操作不能として見える。

一方、既存の共有ロックがこの構造を実現していたため、**push側のコードを変更せず**、
checkoutが`lockGlobal()`を取るだけで成立した。pushの実行条件が既に
`lock.isAnyLocked()`を見ていたためである。

さらに、この設計でも解決しきれない競合がある。checkoutの実行中に、開いたままの
ファイルへの`saveFile`が割り込むと、その保存内容が新ブランチのファイルに混ざり、
直後の`reloadOpenFiles`がそれを「ディスクの最新内容」として受け入れてしまう。
`saveFile`は`lock.isAnyLocked()`を見ていない。ただしpull(working treeを書き換える
点はcheckoutと同じ)にも既に同種の競合があり、対処にはsaveFile側へのロック待ちの
組み込みという、ブランチ切り替え機能のスコープを超える設計変更が要る。

### このプロジェクトでの実例

- `useGitBranchOperations`は`onStart: lock.lockGlobal`でロックを取り、push/pull側は
  無変更のまま「checkout中は待つ」が成立している(統合テストで検証)
- 「逆方向(push中のcheckout)は対象外」の理由をコミットメッセージとコードコメントに
  残した
- saveFileとの競合は、`useAppState.ts`のコメントに「既知の制約」として、発生条件・
  影響・pullにも同じ問題がある事実・対応しない理由・対応する場合に必要な変更を書いた
- トリガーボタンは、実行中(`isCheckingOut`)だけでなく、他操作中(`isBlocked`)も
  `disabled`にした。排他制御で実行が弾かれるのに、ボタンは押せる見た目のままだと、
  「押しても何も起きない」ように見える(パターン5、14と同じ問題)

### 汎用的な対策

- 排他が必要な操作の組は、「AとB」ではなく「**Aの実行中にBを開始する**」と
  「**Bの実行中にAを開始する**」を別々に検討する。それぞれで、後から始まる方が読む
  対象を、先に始まっている方が書き換え中でないかを確認する
- 一方向で足りる場合は、その理由(何を読み書きするか)をコメントに書く。理由を残さ
  ないと、後の人が「対称でないのはバグ」と誤って両方向に広げる
- 既存のロックの構造で新しい操作の排他が実現できるなら、既存の呼び出し側を変えずに
  済む形を優先する。変更箇所が少ないほど、他の操作への回帰リスクが小さい
- スコープ外にした競合は、**発生条件・影響・なぜ今回対応しないか・対応に必要な変更**
  をコメントに書く(パターン1と同じ方針)。「既知だが放置」と「未発見」は、次にレビュー
  する人にとって全く別の情報になる

## 24. 検証ツールが「正しい」と判定した値が、実際に使うコマンドでは別の意味に解釈される

### どういう時に問題が起こるか

入力値の妥当性を、外部ツールの検証コマンドに任せたとき。検証コマンドが「受理」した値を
そのまま別のコマンドに渡すと、そのコマンドが値を特別な記号・別名として解釈し、ユーザーの
意図と違う動作をすることがある。このプロジェクトではブランチ名 `@` がこれに当たった。

### 原因

git には、名前の形式が正しいかを確かめる `git check-ref-format --branch <name>` がある。
このコマンドは `@` を「ブランチ名として有効」と判定し、`git checkout -b @` でも実際に
`@` という名前のブランチを作成できる。

ところが、作成したブランチへ切り替えるときに実行する `git checkout @` では、git は `@` を
ブランチ名ではなく **`HEAD` の別名**(git の revision 記法で `@` 単独は HEAD を指す)として
解釈する。その結果、次のことが起こる。

- `git checkout @` は「今の HEAD をチェックアウトする」= 何もしない操作として扱われる
- 終了コードは 0(成功)で、エラーメッセージも出ない
- アプリ側は「切り替えに成功した」と判断して後続処理(エディタの再読込等)を進める
- 画面上のブランチは元のままで、ユーザーには何が起きたのか分からない

根本には、**「検証」と「使用」が別のコマンド・別の文法で行われている**ことがある。
`check-ref-format` が見ているのは「refs/heads/ 配下に置けるファイル名として正しいか」で、
`checkout` の引数の解釈規則(revision 記法・パス指定・別名の解決)は見ていない。
検証が通ったことは「その値をどのコマンドに渡しても意図どおりに解釈される」ことを
保証しない。

この種のバグは、正常系のテスト(普通のブランチ名で作成 → 切り替え)では絶対に
再現しない。検証を通過する「境界の値」を、作成した後に**実際に使うところまで**
試さないと発見できない。

### このプロジェクトでの実例

ブランチ作成機能の最終レビューで、実機の git 2.50.1 を使った再現により発覚した。
`@` のみの名前を、main 側(git に渡す前)と renderer 側(入力ダイアログ)の両方で
拒否するようにした。判定は両者で食い違わないよう `@shared/branchName` に置いて共有した。

```ts
// src/shared/branchName.ts
export function getBranchNameRuleViolation(name: string): BranchNameRuleViolation | null {
  if (name.length === 0) return 'empty'
  if (name.startsWith('-')) return 'leading-dash'
  // check-ref-format --branch は '@' を通すが、`git checkout @` は HEAD の別名として
  // 解釈されるため、作成できても切り替えられないブランチになる
  if (name === '@') return 'head-alias'
  return null
}
```

レビューでは、他の紛らわしい名前(`ORIG_HEAD`、`FETCH_HEAD`、`refs/heads/x`)も同様に
作成 → 切り替えまで実機で試し、こちらは曖昧さの警告は出るものの正しいブランチへ
切り替わる(`@` と同じ問題は起きない)ことを確認したうえで、`@` のみを拒否対象にした。

### 汎用的な対策

- 外部ツールの検証コマンドに頼るときは、「そのツールが何を検証しているか」と
  「値を最終的に渡すコマンドがどう解釈するか」を分けて考える。両者の文法が違うなら、
  検証を通った値でも使用側で別の意味になりうる
- 検証を通過する境界の値(記号 1 文字、予約語、別名、特殊な接頭辞)を洗い出し、
  **作成して終わりではなく、その値を使う後続の操作(切り替え・参照・削除)まで**
  実機で試す
- 「成功したのに何も起きない」系の失敗は、終了コードでは検出できない。後続の操作が
  値を特別扱いしうるなら、入口で拒否するのが最も確実

## 25. 検証コマンドが入力を展開・正規化してから成功を返し、入力と違う値を検証している

### どういう時に問題が起こるか

外部コマンドの「検証が成功したか(終了コード)」だけを見て、検証結果として出力された
値を確認していないとき。検証コマンドが入力を展開・正規化する仕様だと、**入力とは別の
値を検証して成功**していることがある。

### 原因

`git check-ref-format --branch <name>` は、単なる形式チェックではなく「ブランチ名として
解決した結果」を出力する。このとき次の記法を**実在のブランチ名へ展開**してから検証する。

- `@{-1}`: 直前にチェックアウトしていたブランチ(例: `topic`)
- `@{-1}x` のような連結: 展開後の `topicx`
- `@{u}`: 現在のブランチの upstream 名

例えば入力が `@{-1}` のとき、git は `topic` を検証して成功し、`topic` を出力する。
終了コードは 0 なので、終了コードだけを見ると「`@{-1}` は正しいブランチ名」と誤判定する。
その後 `git checkout -b @{-1}` に進むと、git は別の規則で解釈するため、意図と違う名前の
ブランチを作るか、分かりにくいエラーになる。

これは「検証コマンドの戻り値は真偽値」という思い込みから起こる。多くの検証 API は
真偽値だけを返すが、正規化を伴う検証 API は「正規化後の値」も返す。その値が入力と
一致しない場合は、**入力そのものは検証されていない**と考える必要がある。

### このプロジェクトでの実例

`assertCreatableBranchName`(gitService.ts)で、`check-ref-format --branch` の出力
(前後の空白を除去したもの)が入力と一致しない場合も拒否するようにした。

```ts
let normalized: string
try {
  normalized = (await git.raw(['check-ref-format', '--branch', branchName])).trim()
} catch {
  throw invalidBranchNameError(branchName)
}
// --branch は '@{-1}' 等を実在のブランチ名へ展開して成功扱いにするため、
// 正規化後の名前が入力と一致することも確認する
if (normalized !== branchName) throw invalidBranchNameError(branchName)
```

テストでは、モックの `check-ref-format` が `@{-1}` に対して `topic\n` を返すケースを書き、
実機で `@{-1}` → `topic` と展開されることを確認してからモックの戻り値に落とし込んだ。

### 汎用的な対策

- 検証コマンド・正規化関数の仕様を確認し、「入力をそのまま検証する」のか「展開・正規化
  してから検証する」のかを区別する(`realpath`、URL の正規化、Unicode 正規化、
  パスの `..` 解決なども同じ種類)
- 正規化を伴う検証では、**成功したことに加えて、正規化後の値が入力と一致すること**を
  確認する。一致しない入力は、意図しない解釈がされる余地があるものとして拒否するか、
  正規化後の値を以降の処理で一貫して使う
- テストでは「検証は成功するが出力が入力と異なる」ケースを明示的に作る。終了コードだけ
  を見る実装は、このケースで必ず失敗する

## 26. 名前の重複を完全一致だけで判定し、階層構造による衝突を見落とす

### どういう時に問題が起こるか

新しく作る名前が既存の名前と「重複していないか」を、文字列の完全一致だけで判定した
とき。保存先が**階層構造(ディレクトリ・パス・ネームスペース)**になっていると、
完全一致しなくても親子関係にある名前は共存できない。

### 原因

git のブランチは `.git/refs/heads/` 配下のファイルとして保存され、名前の `/` は
ディレクトリの区切りになる。例えば `main` と `main/sub` を同時に作ろうとすると次のように
なる。

- `main` は `refs/heads/main` という**ファイル**
- `main/sub` を作るには `refs/heads/main/` という**ディレクトリ**が必要
- 同じパスにファイルとディレクトリは共存できない

そのため git は次のようなエラーで失敗する。

```
fatal: cannot lock ref 'refs/heads/main/sub': 'refs/heads/main' exists; cannot create 'refs/heads/main/sub'
```

逆向き(`feature/x` がある状態で `feature` を作る)も同じ理由で失敗する。packed-refs に
まとめられている場合も、git は同じ規則で拒否する。

重複チェックを `existingNames.includes(name)` のような完全一致だけで書くと、この衝突は
チェックをすり抜けて git の実行時まで進み、**英語の生のエラーメッセージ**がそのまま
ユーザーに表示される(パターン18と同じ問題)。`feature` と `feature/login` のような
命名はよく使われるため、実際に起こりやすい。

一方で、単純な前方一致(`name.startsWith(existing)`)で判定すると、今度は `feature-x` と
`feature` のような**共存できる名前まで誤って拒否**してしまう。衝突するのは階層の区切り
(`/`)で親子になる場合だけである。

### このプロジェクトでの実例

コードレビューの1巡目で、実機の git で再現したうえで指摘された。衝突する既存ブランチ名を
返す関数を共有モジュールに置き、main 側の事前検証と renderer 側の入力ダイアログの両方で
使うようにした。

```ts
// src/shared/branchName.ts
export function findConflictingBranchName(
  name: string,
  existingNames: readonly string[]
): string | null {
  return (
    existingNames.find(
      (existing) => name.startsWith(`${existing}/`) || existing.startsWith(`${name}/`)
    ) ?? null
  )
}
```

テストでは、両方向の衝突、深い階層(`a/b/c/d` と `a/b`)に加えて、**衝突しない前方一致**
(`feature-x` と `feature`、`feat` と `feature/x`、`feature/xy` と `feature/x`)を
並べ、区切り文字を境界として判定していることを固定した。

### 汎用的な対策

- 名前の重複チェックを書く前に、その名前が**どこにどういう形で保存されるか**を確認する。
  ファイルパス、URL パス、キー階層、ネームスペースなど、区切り文字で階層になる保存先では、
  完全一致の重複に加えて**親子関係の衝突**も検査する
- 親子関係の判定は「区切り文字付きの前方一致」で行う(`a/` で始まるか)。区切り文字なしの
  前方一致は、衝突しない名前を誤って拒否する
- テストは「衝突する例」だけでなく「前方一致するが衝突しない例」も必ず書く。後者が無いと、
  区切り文字を忘れた実装を検出できない

## 27. 外部コマンドの出力を改行で分割し、行末の `\r` が残ったまま比較する

### どういう時に問題が起こるか

外部コマンドの出力を `split('\n')` で行に分け、各行を文字列比較や前方一致で解析する
とき。Windows 上の git など、**CRLF(`\r\n`)で出力する**ツールがあると、各行の末尾に
`\r` が残る。

### 原因

`'a\r\nb\r\n'.split('\n')` の結果は `['a\r', 'b\r', '']` になる。各行の末尾に見えない
`\r` が残るため、次のような処理が静かに失敗する。

- 行から切り出した値(ブランチ名など)の末尾に `\r` が付き、`'main\r' !== 'main'` となる
- 集合(`Set`)に `'feature/x\r'` が入り、`has('feature/x')` が false になる
- 完全一致の比較が常に外れるが、例外は出ない

このプロジェクトでは、worktree 一覧の出力から「どこかでチェックアウト中のブランチ」を
集める処理で、この見落としがあった。見落とすと次の流れで**誤った確認が出る**。

1. 他の worktree で使用中のブランチを、使用中と判定できない
2. 事前チェックを通過し、マージ済み判定へ進む
3. 未マージと判定され、「強制削除しますか？」と確認を出す
4. ユーザーが承諾しても、git 自身が使用中を理由に削除を拒否する

開発者の手元(macOS / Linux)では LF で出力されるため、テストでも実機でも再現しない。
Windows 環境でのみ起こる種類のバグである。

### このプロジェクトでの実例

単一責任のリファクタリングで、worktree 一覧の解析を git 呼び出しから切り離して
純粋関数にした際に見つかった。解析を独立させたことで、CRLF の入力を直接与える単体テストが
書けるようになった。

```ts
// src/main/gitWorktreeParser.ts
export function parseWorktreeBranches(output: string): Set<string> {
  return new Set(
    output
      .split('\n')
      .map((line) => line.trimEnd()) // Windows の CRLF 出力で残る \r を取り除く
      .filter((line) => line.startsWith(BRANCH_LINE_PREFIX))
      .map((line) => line.slice(BRANCH_LINE_PREFIX.length))
  )
}
```

### 汎用的な対策

- 外部コマンドの出力を行単位で解析するときは、`split('\n')` の後に各行の末尾の空白を
  取り除く(`trimEnd()`)か、`/\r?\n/` で分割する。値として末尾の空白が意味を持つ
  フォーマットでは、`\r` だけを取り除く
- 出力の解析は、コマンドの実行から切り離した純粋関数にする。そうすると、実行環境に
  依存する入力(CRLF、ロケール、空出力)をテストで直接与えられる
- テストデータには CRLF のケースを 1 つ含める。開発環境が LF だけなら、このケースを
  明示しない限り検出できない

## 28. 失敗時のエラーから原因を判定しようとして、ロケールや別の原因と区別できない

### どういう時に問題が起こるか

「まず実行してみて、失敗したらエラーの内容で原因を判断する」という設計で、原因ごとに
異なる対応(確認ダイアログを出す、別の手段を提案する等)をしたいとき。エラーの内容が
**ロケールで変わる**、または**別の原因でも同じ形式になる**と、判定を誤る。

### 原因

ブランチの安全削除(`git branch -d`)は、未マージのブランチに対して失敗する。当初は
「失敗したら未マージとみなし、強制削除を提案する」設計を考えたが、次の 2 つの理由で
成り立たなかった。

1. **ロケール依存**: simple-git は削除の失敗を解析し、git の出力が `error: ... '<name>'`
   という**英語の形式**のときだけ、構造化されたエラー(`GitResponseError`)に変換する。
   日本語化された git では `エラー: ...` と出力されるため変換されず、未マージかどうかを
   構造的に判定できない。ロケールを英語に固定するには環境変数を渡す必要があるが、
   simple-git の `env()` はこのプロジェクトでは別の制約(`getLog` 参照)で使えない
2. **別の原因と同じ形式**: 他の worktree でチェックアウト中のブランチを削除しようとした
   ときも、git は `error: cannot delete branch '<name>' used by worktree at ...` という
   **未マージと同じ `error: ... '<name>'` 形式**で失敗する。simple-git はこれも同じ
   構造化エラーに変換するため、未マージと区別できない

2 つ目を見落とすと、使用中のブランチに対して「マージされていないコミットが失われます。
強制削除しますか？」と**誤った理由で**強制削除を促してしまう。しかも承諾しても強制削除
(`-D`)も同じ理由で失敗する。

根本には、**「失敗の結果」から「失敗の理由」を逆算しようとした**ことがある。エラーは
表示用に作られた出力であり、原因を区別するための API ではない。

### このプロジェクトでの実例

削除の前に、構造化された問い合わせ(出力の有無だけで判定でき、ロケールに依存しない
コマンド)で原因ごとの条件を**先に**確かめる設計にした。

- 他の worktree で使用中か: `git worktree list --porcelain` の `branch refs/heads/<name>` 行
- マージ済みか: git 本体の `branch -d` と同じ基準(upstream が実在すれば upstream、
  なければ HEAD)で、`git for-each-ref --merged=<基準> refs/heads/<name>` の出力の有無

```ts
export async function deleteBranch(folderPath, branchName, force) {
  const git = simpleGit(folderPath)
  await assertDeletableBranch(git, branchName) // 存在・現在ブランチ・他 worktree で使用中
  if (!force && !(await isBranchMerged(git, branchName))) {
    return { deleted: false, reason: 'not-fully-merged' } // 例外ではなく戻り値で返す
  }
  await git.deleteLocalBranch(branchName, force)
  return { deleted: true }
}
```

事前チェックと削除の間に状態が変わる競合(別プロセスが同時にマージする等)は残るが、
その場合も git 自身が削除を拒否するだけでコミットは失われない。この判断はコメントに
残した(パターン1と同じ方針)。

### 汎用的な対策

- 原因ごとに異なる対応が必要なら、「実行して失敗の内容を見る」のではなく、「実行前に
  原因ごとの条件を問い合わせる」設計を優先する。問い合わせには、機械が読む前提の出力
  (porcelain 形式、JSON、終了コード、出力の有無)を使う
- 失敗の内容で判定するしかない場合は、そのエラー形式が**ロケールで変わらないか**、
  **別の原因でも同じ形式にならないか**を実機で確認する。ライブラリの構造化エラーも、
  変換条件(どの出力形式のときに変換されるか)をソースで確認する(パターン13と同じ)
- 事前チェックの判定基準は、実行するツール自身の基準に合わせる(ここでは git の
  `branch_merged`)。独自の基準にすると、事前チェックと実際の実行結果が食い違う

## 29. 内容に合わせて幅が決まるポップオーバーで、日本語の文言が折り返される

### どういう時に問題が起こるか

`position: absolute` で配置し、幅を明示しない(内容に合わせて縮む = shrink-to-fit)
ポップオーバーやメニューに、日本語のボタン文言を置いたとき。他の項目が短いと、
メニューが最小幅まで縮み、日本語の文言が 2 行に折り返される。

### 原因

幅を指定しない絶対配置要素の幅は、おおまかに次のように決まる(shrink-to-fit)。

- 内容を折り返さずに並べたときの幅(max-content)を上限とする
- 包含ブロック(最も近い `position: relative` の祖先)から使える幅を目安にする
- 内容を最大限折り返したときの幅(min-content)を下限とする

このプロジェクトのブランチメニューでは、包含ブロックがトリガーボタン(`main` のような
短い文字列)だけを包む小さな要素だったため、使える幅がかなり狭かった。そのため
メニューは `min-width: 160px` まで縮んだ。

ここで日本語の特性が効く。英語は単語の間(空白)でしか改行できないが、日本語は
**ほぼすべての文字の間で改行できる**。そのため「＋ 新しいブランチを作成…」の
min-content はほぼ 1 文字分しかなく、幅の下限として働かない。結果として
「＋ 新しいブランチを作 / 成…」と 2 行に折り返された(実測でボタンの高さは 49px)。

このバグは、ブランチ名が長いリポジトリ(メニューの他の項目が広い)では起こらない。
開発者が普段使うリポジトリの状態によって再現したりしなかったりするうえ、jsdom は
レイアウトを計算しないため単体テストでも検出できない。

### このプロジェクトでの実例

PR レビューで、実際の `base.css` と `main.css` を headless Chrome で描画して実測した
うえで指摘された。作成ボタンに `white-space: nowrap` を指定し、文言の幅そのものが
メニュー幅の下限になるようにした。

```css
.source-control-panel__branch-menu-create {
  border-bottom: 1px solid #454545;
  white-space: nowrap;
}
```

修正後はボタンの高さが 31px(1 行)、メニュー幅は 181px になった。副作用として、
メニューがサイドバー(幅 240px、`overflow: hidden`)からはみ出さないことも確認した
(右端は 193px)。

レイアウトそのものは jsdom で計算できないが、実際の `main.css` を jsdom に読み込めば、
カスケード後の宣言値は `getComputedStyle` で取得できる。これを使い、「必要な宣言が
その要素に当たっていること」をテストで固定した。

```ts
beforeAll(() => {
  styleElement = document.createElement('style')
  styleElement.textContent = readFileSync(resolve(__dirname, '../../../assets/main.css'), 'utf-8')
  document.head.appendChild(styleElement)
})

it('作成ボタンの文言は折り返さない(white-space: nowrap)', () => {
  renderMenu()
  expect(getComputedStyle(getCreateButton()).whiteSpace).toBe('nowrap')
})
```

### 汎用的な対策

- 幅を指定しないポップオーバー・メニュー・ツールチップに、1 行で見せたいラベル
  (特に日本語)を置くときは、`white-space: nowrap` を指定するか、十分な `min-width` を
  与える。日本語は min-content が小さく、幅の下限として働かないことを前提にする
- 見た目の確認は「内容が短いとき」「内容が長いとき」の両方で行う。普段の開発環境の
  データでは、片方の状態しか目にしないことが多い
- `nowrap` を足すときは、はみ出しの副作用(親の `overflow: hidden` でのクリップ、
  画面端からのはみ出し)を実際の寸法で確認する
- CSS の宣言は、実際のスタイルシートを jsdom に読み込めば `getComputedStyle` で
  検証できる。レイアウト(折り返し・幅)は検証できないので、実機での確認項目として別に残す

## 30. 同じ見た目を保つために CSS の宣言を丸ごと複製する

### どういう時に問題が起こるか

既存の要素と「同じ見た目」の新しい要素を追加するときに、既存のクラスの宣言をコピーして
新しいクラスに貼り付け、差分だけを書き足したとき。

### 原因

ブランチメニューに作成ボタンを追加した際、メニュー項目(`.source-control-panel__branch-menu-item`)
と同じ見た目にするため、padding・色・フォントサイズ・ホバー時の背景色など 9 個の宣言と
`:hover` 規則を新しいクラスにコピーした。違いは区切り線(`border-bottom`)だけだった。

コメントにも「メニュー項目と同じ見た目」と書かれていたが、これは**「2 つの宣言が
同じであり続けること」を人の注意力に頼っている**ことを意味する。メニュー項目の余白や
ホバー色を変えたとき、作成ボタン側も同じように直さなければ見た目がずれる。テーマ対応で
色を変数化するときも、2 か所を直す必要がある。どちらも忘れやすく、ずれてもテストでは
検出されない。

### このプロジェクトでの実例

単一責任の観点でのレビューで指摘された。作成ボタンにはメニュー項目のクラスを**併用**し、
作成ボタン固有のクラスには差分(区切り線)だけを書くようにした。

```tsx
<button className="source-control-panel__branch-menu-item source-control-panel__branch-menu-create">
```

```css
/* .source-control-panel__branch-menu-item を併用して見た目を揃え、区切り線だけを足す。
   .branch-menu-item の border: none より後に置くことで border-bottom が優先される */
.source-control-panel__branch-menu-create {
  border-bottom: 1px solid #454545;
}
```

2 つのクラスは詳細度が同じなので、後に書いた方が優先される。この**宣言順への依存**は
コメントに明記し、パターン29のテスト(`getComputedStyle` で `padding` と
`border-bottom` を検証)で、併用が外れたり順序が逆転したりすると失敗するようにした。

### 汎用的な対策

- 「同じ見た目にしたい」ときは宣言をコピーせず、既存のクラスを併用して差分だけを
  新しいクラスに書く。共通部分が 1 か所にあれば、変更も 1 か所で済む
- 併用する場合は、詳細度と宣言順のどちらで上書きが成立しているかを把握し、宣言順に
  依存するならコメントに残す
- コメントに「〜と同じ」と書きたくなったら、それは重複の兆候と考える

## 31. 責務を切り出した後、元の場所のテストに同じ検証が残る

### どういう時に問題が起こるか

大きなコンポーネントや関数から一部の責務を別の単位(子コンポーネント、純粋関数)に
切り出し、切り出した単位に新しいテストを書いたが、**元の単位のテストに残っていた同じ
検証を削除しなかった**とき。

### 原因

リファクタリングでは、新しい単位のテストを書くことに意識が向き、元のテストの整理が
後回しになりやすい。元のテストは切り出し後も(子コンポーネントを経由して)通り続ける
ため、削除しなくても何も壊れず、重複に気づくきっかけがない。

このプロジェクトでは、ブランチ一覧の 1 行(radio・削除ボタン・`Delete` キー)を
`BranchMenuItem` に切り出した後も、メニュー側のテストに次の 5 件が残っていた。

- 現在ブランチ以外にだけ削除ボタンがある
- 削除ボタンのクリックで onDelete だけが呼ばれる
- 削除ボタンが `tabIndex=-1`
- `Delete` キーで onDelete が呼ばれる
- `aria-keyshortcuts` が付く

同様に、worktree 一覧の CRLF の扱いが、解析関数のテストとサービスのテストの両方にあった。

重複したテストには次の保守コストがある。

- 1 行の見た目や操作を変えると、無関係なはずのファイルのテストも直す必要がある
- テストが落ちたとき、どの単位が壊れたのか分かりにくい(2 ファイルが同時に落ちる)

同じ種類の問題として、**テストのたびに全 Props を手書きする**書き方もあった。
`BranchSwitcherMenu` のテストでは、全 Props を並べた描画が 22 回書かれていた。
Props を 2 つ追加しただけで 22 か所の書き換えが必要になり、実際にこの機能の差分の
大半はその機械的な修正だった。各テストが「検証したい振る舞い」と「コンポーネントの
配線一式」の両方を抱えている状態である。

### このプロジェクトでの実例

単一責任の観点でのレビューループ(5 巡)で順に指摘され、次のように整理した。

- 1 行分の検証は `BranchMenuItem.test.tsx` に一本化し、メニュー側には「各行へ onDelete を
  配線していること」を確かめるテストを 1 件だけ残した
- CRLF の扱いは解析関数のテストに一本化し、サービス側は「使用中なら拒否する」だけにした
- 作成ダイアログのテストは、ブランチ名の検証文言を規則ごとに再検証していたため、
  文言の検証は検証関数のテストに任せ、ダイアログ固有の配線(既存名の一覧が渡ること、
  `/` を含む名前を受け付けること)だけを残した
- 全 Props の手書きは、既定値を持つ `renderMenu(overrides)` ヘルパーにまとめ、各テストは
  検証に関わる Props だけを渡すようにした

テストを削除するときは、削除した検証が別のテストで担保されていることをレビューで確認し、
実装を壊すと残したテストが落ちること(ミューテーション)を確かめた。

### 汎用的な対策

- 責務を切り出したら、新しい単位のテストを書くのと同時に、元の単位のテストのうち
  「切り出した責務そのもの」を検証しているものを洗い出して移す。元の単位には
  「新しい単位を正しく使っている(配線している)こと」の確認を最小限だけ残す
- テストファイルごとに「この単位の責務は何か」を意識し、下位の単位が保証している
  振る舞いを上位で再検証しない(上位では配線だけを見る)
- 描画ヘルパーには Props の既定値を持たせ、各テストは検証に関わる Props だけを
  上書きする。Props の追加がテストの一括書き換えにつながる構造を避ける
- テストを削除・統合したら件数が減る。減った分の検証が別の場所で担保されていることを
  確認し、その根拠を残す

## 32. 実装やレビュー対応の変更に、コメント・設計書の記述が追従していない

### どういう時に問題が起こるか

責務の切り出しや、レビュー指摘への対応で実装を変えたときに、その周辺のコメントや
設計書の記述を更新し忘れたとき。コメントや設計書が、実装と違う内容を説明している状態になる。

### 原因

コード中のコメントや設計書は、テストでも型チェックでも検査されない。実装が変わっても
何も壊れないため、更新漏れに気づく仕組みがない。特に次の場面で起きやすい。

- **関数を切り出した後**: 元の関数に書かれていた説明が、切り出した先の実装と合わなくなる。
  このプロジェクトでは、不正なブランチ名のエラーについて「形式違反はどれも同じ文言にする」と
  書いたコメントが残っていたが、実装は `-` 始まりにだけ専用の文言を返していた。コメントを
  信じた人が文言を統一すると、`-` 始まりの専用文言を検証するテストが意図せず壊れる
- **対象範囲を広げた後**: 「push/pull/fetch とブランチ切替で disabled 判定が食い違う」という
  コメントが、判定を作成・削除にも広げた後も「ブランチ切替」のままだった
- **機能を追加した後、設計書の一部だけ更新**: 階層衝突のチェックを追加した際、設計書の
  「仕様」と「エラーハンドリング」の節は更新したが、「アーキテクチャ」節の処理手順、
  「テスト方針」、リファクタリングの対応表の 3 か所が古いままだった。設計書を手順書として
  読んだ人が、チェックを不要なものと判断して外すおそれがある
- **参照先を書かずに移したコメント**: 実装計画書にあった「Task 2 冒頭の『前提』を参照」という
  コメントが、どの計画書かを書かないままテストに残っていた。リポジトリには「Task 2」を含む
  計画書が複数あり、辿れない

### このプロジェクトでの実例

いずれもレビューで指摘され、次のように直した。

- コメントは実装どおりの記述に直した(「原則同じ文言にする。例外は `-` 始まりで、直し方が
  明確なため専用の文言を返す」)
- 設計書は、変更した仕様に言及している節をすべて検索して更新した
- 辿れない参照は、ドキュメントの構成に左右されない参照先(同じ前提を説明している本番
  コードのコメント)に書き換えた

### 汎用的な対策

- 関数の切り出しや対象範囲の変更をしたら、変更したシンボル名・機能名でコメントと
  ドキュメントを検索し、説明が実装と合っているか確認する(CLAUDE.md の
  「ドキュメントの同期管理」)
- 設計書に機能を追加したら、「仕様」の節だけでなく「アーキテクチャ(処理手順)」
  「エラーハンドリング」「テスト方針」など、同じ機能に触れているすべての節を更新する
- コメントで別の文書を参照するときは、ファイルパスまで書く。可能なら、文書の構成に
  左右されない参照先(同じ前提を説明しているコード)を選ぶ

## 33. サブエージェントに委譲した作業で、エージェント自身の属性がプロジェクトの規約を上書きする

### どういう時に問題が起こるか

コミットの作成など、プロジェクト固有の規約(署名・書式・命名)がある作業をサブエージェントに
委譲したとき。サブエージェントが、指示された規約ではなく**自分自身の既定の振る舞い**で
作業してしまう。

### 原因

このプロジェクトでは、コミットメッセージの末尾に決められた `Co-Authored-By` 行を付ける
規約がある。実装タスクごとに別のサブエージェントへ委譲した際、指示には正しい行を書いて
いたが、軽量モデルで動かしたサブエージェントの 1 つが、**自分のモデル名**を署名した
コミットを作った。

サブエージェントは、自分が作るコミットには自分の名前を署名する、という既定の振る舞いを
持ちうる。指示の中で規約を明示していても、それが「一般的な注意事項」として埋もれると、
既定の振る舞いが優先されることがある。この逸脱はコードの差分には現れないため、
差分だけを見るレビューでは検出されない(実際、タスクのレビュー担当は「差分からは確認
できない」と報告していた)。

これはパターン12(サブエージェントが指示の範囲を逸脱する)と同じ系統の問題で、
**「指示したこと」と「実際に行われたこと」を、成果物のメタデータまで含めて検証しないと
気づけない**。

### このプロジェクトでの実例

タスクごとにコミットのトレーラーを `git log --format='%(trailers:key=Co-Authored-By,valueonly)'`
で確認していたため発見できた。該当のコミットはまだ push していなかったため、同じ
サブエージェントに差し戻し、トレーラー行だけを修正させた(コードの差分が変わらないことを
`git diff <修正前> HEAD` が空であることで確認)。以降のタスクの指示では、署名の行を
「自分のモデル名ではなく、必ずこの文字列」と明示するようにした。

### 汎用的な対策

- サブエージェントに規約のある作業を委譲するときは、規約を「一般的な注意」ではなく、
  具体的な値(そのまま使う文字列)として、**自分の既定値ではなくこれを使う**と明示する
- 委譲した作業の検証は、コードの差分だけでなく、コミットメッセージ・トレーラー・
  ブランチ名などのメタデータまで行う。差分だけを見るレビューでは、これらの逸脱は見えない
- メタデータの逸脱は、push する前なら安全に直せる。委譲した作業のたびに、その場で
  確認する習慣を持つ

## 34. 同じガード条件を別の操作に適用したが、その条件のテストを追加していない

### どういう時に問題が起こるか

既存の操作 A にある開始条件(ガード)を、新しく追加した操作 B にも同じ形で適用したが、
操作 A にあったガードのテストを、操作 B には書かなかったとき。

### 原因

ブランチ操作のフックでは、checkout・作成・削除のいずれも「他の Git 操作がロックを持って
いる間(`lock.isAnyLocked()`)は開始しない」という条件を持つ。作成には「他操作中は API を
呼ばない」テストがあったが、削除には同じテストが無かった。

実装はコピーで正しく移植されていたため、テストが無くても動作は正しい。しかし、削除の
開始条件から `lock.isAnyLocked()` を消しても**既存のテストはどれも落ちない**状態だった。
将来、削除だけ条件を緩める変更(意図的なものも、誤りも)が入っても検出できない。

削除は全体ロックを取らない(パターン23)という点で checkout・作成と扱いが違うため、
「削除はロックに関係しない」と誤解して条件ごと外される危険が特に高かった。
「ロックを取らない」ことと「他操作中は開始しない」ことは別の性質で、前者だけが
テストされていた。

### このプロジェクトでの実例

ブランチ全体の最終レビューで、ミューテーション(条件を消してテストが落ちるか)により
指摘された。他操作がロックを持つ状態を固定したモックで、削除 API が呼ばれないことを
検証するテストを追加した。あわせて、単一責任のリファクタリングで開始条件を
`isBranchOperationBusy` に共通化した後、「リポジトリが無いときはどの操作も API を
呼ばない」「作成の実行中は 3 操作とも API を呼ばない」を `it.each` で操作ごとに検証する
テストを加え、共通化した条件がすべての操作に効いていることを固定した。

### 汎用的な対策

- ガード条件を別の操作に適用したら、そのガードのテストも操作ごとに書く。条件を共通化
  した場合は、共通化した条件がすべての利用箇所に効いていることを `it.each` 等で操作ごとに
  検証する
- 「似ているが扱いが違う」操作(ロックを取る/取らない等)は、違う部分だけでなく、
  **同じであるべき部分**もテストで固定する。違いに注目したテストだけだと、同じであるべき
  条件が外されても気づけない
- テストの検知力は、条件を 1 つずつ消してテストが落ちるか(ミューテーション)で確かめる
  (パターン16)

## 35. パターン照合の問い合わせを「出力があるか」で判定し、前方一致で別のエントリを拾う

### どういう時に問題が起こるか

「このパスは X の状態か」を外部コマンドへの問い合わせ(`git ls-files -- <path>` 等)で
調べ、**出力が空かどうか**だけで判定したとき。問い合わせに渡したパターンが、対象そのもの
だけでなく、対象を接頭辞に持つ別のエントリにも一致する場合に誤判定する。

### 原因

git の pathspec は、`:(literal)` でグロブを無効にしても**ディレクトリの前方一致**として
働く。`git ls-files -- ':(literal)foo'` は、`foo` という追跡済みファイルが無くても、
`foo/a.ts` が追跡されていればそれを出力する。

変更の取り消しでは、「`ls-files` に出力があれば追跡済み(restore で戻す)、無ければ未追跡
(ゴミ箱へ移す)」と判定していた。追跡済みの `foo/a.ts` を削除し、同じ名前の**ファイル**
`foo` を新しく作ると、status は ` D foo/a.ts` と `?? foo` になる。この `?? foo` の
取り消しで `ls-files -- foo` を問い合わせると `foo/a.ts` が出力されるため、未追跡の `foo` を
追跡済みと誤判定する。その結果、`git restore -- foo` が実行され、git は `foo/a.ts` を復元する
ために `foo` をディレクトリへ置き換える。履歴に無い `foo` の内容は、ゴミ箱も経由せずに
消える。

「出力があるか」という判定は、問い合わせのパターンが対象だけに一致するという暗黙の前提に
立っている。パターンの一致規則(前方一致・グロブ・大文字小文字の扱い)を確かめないまま
その前提を置くと、関係の無いエントリの存在が判定を左右する。パターン26 の「階層構造に
よる衝突」と同じ構造が、問い合わせの側で起きている。

### このプロジェクトでの実例

ローカルのレビューループで Critical として指摘された(git 2.50.1 の実機で再現)。
問い合わせに `-z`(NUL 区切り)を付け、出力をエントリごとに分けて、**対象のパスと完全に
一致するエントリがあるか**で判定するように改めた(`classifyDiscardTarget`)。コンフリクトの
判定(`ls-files -u`、行は「mode sha stage<TAB>path」)と intent-to-add の判定
(`diff --diff-filter=A`)も同じく完全一致にし、「配下のファイルだけがコンフリクト中なら、
このパスはコンフリクト扱いしない」等のテストで固定した。

### 汎用的な対策

- 外部コマンドへの問い合わせ結果は「出力があるか」ではなく「対象と一致するエントリが
  あるか」で判定する。一致の比較は、区切りを誤らない形式(`-z` 等)で出力を分割してから行う
- 問い合わせに渡すパターンの一致規則(前方一致・グロブ・大文字小文字)を、ドキュメントと
  実機で確かめる。「リテラル指定なら完全一致」と思い込まない
- テストには、対象を接頭辞に持つ別のエントリだけが出力されるケースを必ず入れる

## 36. 破壊的な操作が、対象と階層で重なる別のエントリまで置き換える

### どういう時に問題が起こるか

「対象 1 つを元に戻す」つもりの操作(`git restore`、`git checkout -- <path>` 等)を、
対象のパスの**配下や親**に別の(バージョン管理外の)エントリがある状態で実行したとき。

### 原因

ファイルシステム上で、同じパスはファイルとディレクトリを同時に持てない。restore は対象を
index の内容で書き戻すために、その位置や途中の階層にある邪魔なものを確認なしで取り除く。

- **配下**: 追跡済みのファイル `foo` を削除し、同じ名前のディレクトリ `foo/` を作って中に
  未追跡の `foo/x` を置くと、status は ` D foo` と `?? foo/x` になる。` D foo` を restore
  すると、`foo` をファイルとして書き戻すために `foo/x` がディレクトリごと消える
- **親**: 追跡済みの `foo/a.ts` を削除し、同じ名前のファイル `foo` を作ると、
  ` D foo/a.ts` と `?? foo` になる。`foo/a.ts` を restore すると、親の `foo` をディレクトリに
  するためにファイル `foo` が消える。親が外部を指すシンボリックリンクの場合もリンク自体が
  消える
- どちらも、`.gitignore` で無視されているファイル(ignored)も同じく消える

git から見ると「index の状態へ戻す」という正しい動作だが、ユーザーが確認したのは「`foo` の
変更を取り消す」ことであり、別のパスにある未追跡ファイルの削除は確認していない。
未追跡のファイルは履歴に内容が無いため、消えると復元できない。

対策を「配下」だけで実装すると、「親」の配置が漏れる。最初の修正では配下の重なりだけを
検出しており、次のレビューで親の配置を指摘された。配置の種類は、対象の位置・配下・すべての
祖先の 3 方向がある。

### このプロジェクトでの実例

ローカルのレビューループで、配下(Important)と親(Critical)が別々の周回で指摘された
(いずれも実機で再現)。`overlapsUntracked` を追加し、restore の前に
`git ls-files -z --others -- <対象> <親1> <親2> ...` を 1 回問い合わせるようにした。出力が
「親そのもの」「対象自身」「対象の配下」のいずれかと一致すれば「未追跡のファイルと重なる
ため取り消せません」で拒否する。親の pathspec は、親が通常のディレクトリなら配下の無関係な
未追跡ファイル(兄弟)にも一致するため、それだけでは拒否しない。ignored も消えるため
`--exclude-standard` は付けない。配下・親・2 階層上の親・兄弟だけのケースと、
`--exclude-standard` を付けないことをテストで固定した。

### 汎用的な対策

- 破壊的なコマンドを使う前に、そのコマンドが**対象以外に**何を消しうるかを実機で確かめる。
  特にファイルとディレクトリの入れ替わり(同名のファイル⇔ディレクトリ)を試す
- 階層で重なる配置は、対象の位置・配下・すべての祖先の 3 方向を洗い出す。1 方向を直したら、
  残りの方向も同じ周回で確認する
- 重なりの検出で祖先を問い合わせるときは、祖先の配下にある無関係なエントリで誤って拒否
  しないよう、一致の条件を「祖先そのもの」に限定する

## 37. 大文字小文字を区別しないファイルシステムで、区別する前提の照合をする

### どういう時に問題が起こるか

パスの一致を大文字小文字を区別して判定する処理を、macOS(APFS)・Windows(NTFS)の既定の
ような、大文字小文字を区別しないファイルシステムで動かしたとき。

### 原因

大文字小文字を区別しないファイルシステムでは、`Foo` と `foo` は同じエントリを指す。git は
これを `core.ignorecase=true` で扱い、restore は大文字小文字だけ違う既存のエントリも
「同じ位置のもの」として置き換える。

パターン36 の重なりの検出は、`:(literal)` の pathspec と、`===`・`startsWith` による
大文字小文字を区別した比較で実装していた。追跡済みの `Foo/a.ts` を削除して、ファイル
`foo` を作ると、status は ` D Foo/a.ts` と `?? foo` になる。このとき
`ls-files --others -- ':(literal)Foo/a.ts' ':(literal)Foo'` は `foo` を返さないため、
重なりを検出できない。一方で restore は `Foo` ディレクトリを作るために `foo` を消す。
検出側は「別のパス」、実行側は「同じパス」と見ており、両者の見方が食い違っている。

開発者が大文字小文字を区別する環境(Linux)でテストしていると再現しない。また、
simple-git をモックした単体テストは git の一致規則を再現しないため、この種の漏れを
検出できない(パターン41)。

### このプロジェクトでの実例

ローカルのレビューループで Critical として指摘された(macOS APFS、`core.ignorecase=true`
で再現)。問い合わせを常に `:(literal,icase)` で行い、出力も小文字にそろえて比較するように
した。`core.ignorecase` は読まない。大文字小文字を区別するファイルシステムでは拒否が
増えるだけで、データを失う側には倒れないためである。親・配下・対象自身・出力側が大文字の
ケースを単体テストに、実際に消えないことを実 git の統合テストに加えた。比較の小文字化を
1 か所ずつ外すミューテーションで、すべてテストが落ちることを確認した。

### 汎用的な対策

- パスの一致判定は、実際に操作を行う側(git・OS)と同じ規則で比べる。規則が環境で変わる
  場合は、破壊的な操作を**止める側**の規則(区別しない方)に寄せる
- 大文字小文字だけ違うケースは、入力側・出力側の両方が大文字のパターンをテストに入れる
  (片方だけだと、片側の正規化を外しても通ってしまう)
- 開発環境と利用者の環境でファイルシステムの性質が違うことを前提にする

## 38. 状態の問い合わせが、破壊的な操作の影響範囲にあるエントリをすべては報告しない

### どういう時に問題が起こるか

「破壊的な操作の前に、消えてしまうものが無いか問い合わせる」という安全確認を実装したが、
問い合わせに使ったコマンドが報告する範囲と、操作が実際に消す範囲が一致していないとき。

### 原因

パターン36 の検出には `git ls-files --others`(未追跡のファイルの一覧)を使っていた。
しかし、ネストした git リポジトリ(ディレクトリの中に `.git` があるもの)は、git からは
「別のリポジトリ」として扱われ、`--others` にも `--others --directory` にも出力されない。
追跡済みのファイル `bar` を削除して、同じ位置で `git init` したディレクトリ `bar/` を作ると、
status は ` T bar`(または ` D bar`)だけになり、未追跡のエントリは現れない。

ところが `git restore -- bar` は、`bar` をファイルとして書き戻すために、ディレクトリ `bar/` を
`.git`(そのリポジトリのコミット履歴)ごと消す。安全確認は「未追跡のファイルが無い」と答え、
操作はそれ以上のものを消している。

問い合わせのコマンドを選ぶときに「未追跡のもの = 消えうるもの」と同一視したことが原因で
ある。`--others` は「index に無いファイル」を列挙するコマンドであり、「restore が消すもの」を
列挙するコマンドではない。

### このプロジェクトでの実例

ローカルのレビューループで Critical として指摘された(実機で再現)。git には
「checkout のために消す必要があるファイル」を列挙する `ls-files -k` があり、ネストした
リポジトリを `bar/` として報告する。問い合わせを `ls-files -z --others -k` にして、既存の
検出と 1 回にまとめた。親がネストしたリポジトリの場合は、git が通常のディレクトリとして
扱い、restore は中にファイルを書くだけで何も消さないことも実機で確認し、対策の範囲を
決めた。ネストしたリポジトリ(コミットあり・なし)で拒否し `.git` が残ることを統合テストで
固定し、`-k` を外すとテストが落ちることを確認した。

### 汎用的な対策

- 破壊的な操作の安全確認は、「その操作が消すもの」を直接列挙する手段があればそれを使う
  (git なら `ls-files -k`)。無ければ、確認の範囲と操作の影響範囲の差を明示的に洗い出す
- 確認に使うコマンドが**報告しない**種類のエントリ(ネストしたリポジトリ、シンボリック
  リンク、ignored 等)を、コマンドの仕様から列挙して 1 つずつ実機で試す
- 対策の範囲を決めた根拠(親がネストしたリポジトリなら何も消えない、等)は実機で確かめ、
  コメント・設計書に残す

## 39. 「一覧に無い」ことを別の状態の根拠にして、破壊的な操作を選ぶ

### どういう時に問題が起こるか

状態が A・B の 2 種類しか無いという前提で、「A の一覧に無いから B」と**否定から**分類し、
B に対して A とは別の破壊的な操作を行うとき。入力の表記が一覧の表記とずれていると、A の
対象が B として扱われる。

### 原因

変更の取り消しでは、「`ls-files`(追跡済みの一覧)に完全一致するエントリが無ければ未追跡」
と判定し、未追跡はゴミ箱へ移していた。追跡済みと未追跡の 2 種類しか無いなら正しいが、
実際には「一覧に無い」理由がもう 1 つある。**渡されたパスの表記が、一覧の表記と違う**場合で
ある(パターン40)。

- macOS で日本語のディレクトリ名がディスク上 NFD(濁点が別の文字として分解された形)の
  とき、git の一覧は NFC(合成済みの形)で返る
- 大文字小文字を区別しないファイルシステムで、ディレクトリ名を `Src` から `src` に
  変えたとき、git の index は `Src/a.ts` のまま

どちらも、表記のずれたパスを渡すと、追跡済みで変更のあるファイルが「一覧に無い = 未追跡」
と判定され、ゴミ箱へ移る。確認ダイアログは追跡済みとして「変更を取り消しますか？」と
出しているため、ユーザーは index の内容へ戻すつもりで承諾する。実際にはファイルが
ゴミ箱へ移り、status は ` D` になる。

否定による分類は、「分類できない」という第 3 の結果を持てない。判定が外れたときに、
2 つの破壊的な操作のどちらかへ必ず進んでしまう。

さらに、肯定の根拠を取る問い合わせにも落とし穴があった。`ls-files --others -- ':(literal)src/a.ts'`
は、大文字小文字を区別しないファイルシステムで index に `Src/a.ts` があっても `src/a.ts` を
「未追跡」として返す。`:(literal,icase)` を付けて初めて index のエントリと突き合わされ、
出力されなくなる(パターン37)。

### このプロジェクトでの実例

PR のレビューで Important として指摘された(git 2.50.1 / macOS APFS で再現)。別の
サブエージェントで前提を検証したうえで、次のように直した。

- 追跡済みに一致しないときは `ls-files -z --others --directory -- ':(literal,icase)<path>'` に
  `<path>` か `<path>/` が**完全一致**したときだけ未追跡とする(`isUntracked`)
- どちらにも一致しなければ、新しい分類 `unknown` として「状態を判定できないため
  取り消せません」で拒否し、ゴミ箱へも restore へも進まない
- レビュアーの案(肯定判定)は icase なしでは大文字小文字のケースを防げないことを実機で
  確かめ、icase を付けた

一致なし・大文字小文字だけ違うエントリ・配下のエントリだけの各ケースで拒否すること、
問い合わせの引数(icase・`--directory`・`-k` なし)を単体テストで固定した。実装を
`git stash` で戻すと落ちることも確認した。

### 汎用的な対策

- 破壊的な操作を選ぶ分類は、各分類を**肯定の根拠**で決める。どの根拠にも当てはまらない
  ときは「判定不能」として操作を止める
- 「一覧に無い」理由を列挙する(本当に別の状態、表記のずれ、競合で消えた等)。2 種類しか
  無いと思える分類ほど、第 3 の理由を疑う
- 肯定の根拠を取る問い合わせ自体も、表記のずれで誤って肯定しないかを確かめる

## 40. 境界でパスを正規化し直し、別のシステムが持つ識別子と表記がずれる

### どういう時に問題が起こるか

別のシステム(git の index 等)が持つ識別子としてのパスを受け取り、境界(IPC ハンドラ等)で
realpath などによって正規化し直してから、そのシステムへ問い合わせるとき。

### 原因

取り消しの IPC(`git:discardChanges`)は、stage 等と共通の `resolveAndAssertRelativePath`
を使っていた。これは親ディレクトリを realpath し、ディスク上の表記で相対パスを作り直す。
`.gitignore` への追記ではディスク上の表記にそろえる必要があったため、この処理が共通化されて
いた。

しかし、renderer から渡るのは git status のパス、つまり **index の表記**である。realpath は
ファイルシステムが保持している表記を返すため、次のように化ける。

- macOS: NFD で保存された日本語のディレクトリ名は NFD で返る。git は argv を NFC に
  そろえて(precompose)一覧を返すため、比較が一致しない
- 大文字小文字を区別しないファイルシステム: ディスクが `src/` なら `src/a.ts` になり、
  index の `Src/a.ts` と一致しない

stage 等では、表記がずれても git が何もしないかエラーで止まるだけで、データは失われない。
取り消しだけが「一致しない」ことから破壊的な操作を選んでいた(パターン39)。同じ変換処理が
操作によって無害にも有害にもなるため、共通化の時点では問題が見えなかった。

### このプロジェクトでの実例

パターン39 と同じ PR レビューの指摘で、ハンドラ側も直した。`git:discardChanges` 専用の
`resolveAndAssertStatusRelativePath` を追加し、境界チェック(許可フォルダ内か)はこれまで
どおり行うが、相対パスは realpath で作り直さず、renderer が渡した status の表記のまま返す。
相対パスが `..` または `../` で始まる、空、または絶対パスなら、git へ渡さずに拒否する
(fail-safe)。

この fail-safe は最初 `startsWith('..')` で書き、`..env` のような正当なファイル名まで
拒否してしまうことにテストで気づいて、`=== '..'` と `startsWith('../')` に改めた。
realpath が大文字小文字違い・NFD を返しても status の表記のまま渡すこと、フォルダ外の
拒否、`..env` を通すことをハンドラのテストで固定した。

シンボリックリンクの祖先を経由したパス(`linkd/t.txt`)は、以前は realpath で実体の
`d/t.txt` へ作り直すことで「未追跡と誤判定して実体をゴミ箱へ移す」ことを防いでいた。
現在は判定不能として拒否されることを、実 git の統合テストで固定した。

### 汎用的な対策

- パスが「ディスク上の場所」なのか「別のシステムの識別子」なのかを区別する。識別子として
  使うパスは、そのシステムの表記のまま扱い、境界で作り直さない
- 境界での正規化は、検証(許可範囲内か)のためだけに使い、下流へ渡す値には使わない。
  使う場合は、下流のシステムが同じ表記で比較することを確かめる
- 共通化した変換処理を新しい操作に使うときは、表記のずれがその操作で無害か(何もしない・
  エラー)、有害か(別の操作を選ぶ)を確認する
- `..` の判定は文字列の接頭辞ではなく、パスの要素(`..` そのもの、`../` で始まる)で行う

## 41. 外部コマンドをモックしたテストだけで、外部コマンドの挙動に依存する判定を固定する

### どういう時に問題が起こるか

判定の正しさが外部コマンド(git 等)の出力規則に依存しているのに、テストがそのコマンドを
モックし、「こういう出力が来たらこう判定する」ことしか検証していないとき。

### 原因

`discardFileChanges` の単体テストは simple-git をモックし、`ls-files` 等の出力を手で
与えていた。このテストで確かめられるのは「与えた出力に対する分岐」だけで、「実際の git が
この pathspec に対して何を出力するか」は確かめられない。

パターン37(大文字小文字)とパターン38(ネストしたリポジトリ)は、どちらも「git がこの
配置で何を出力しないか」という問題だった。モックには、テストを書いた人が想定した出力しか
入らない。想定していない配置は、テストにも実装にも現れない。レビュアーはこれを「実装を
壊したら落ちるかという点では十分だが、git の実際の出力は検証されていない」と指摘した。

また、実 git を使うテストを追加すると、今度は開発者の環境に依存する。グローバルの git
設定で `commit.gpgsign=true` があると、テスト内の `git commit` が署名に失敗して全件落ちる。
グローバルの `core.hooksPath` のフックもテスト内で動いてしまう。

### このプロジェクトでの実例

ローカルのレビューループの指摘を受けて、実 git を使う統合テスト
`gitService.discard.integration.test.ts` を新設した。一時ディレクトリに実際のリポジトリを
作り、重なる未追跡ファイル・ignored・大文字小文字違い・ネストしたリポジトリが restore で
消えないこと、NFD・シンボリックリンクのパスを拒否することを、ファイルの中身で確かめる。

環境依存は次のように切り離した。

- テスト側の `git` 実行と、`discardFileChanges`(simple-git が起動する git)の両方に、
  `GIT_CONFIG_GLOBAL=os.devNull` と `GIT_CONFIG_NOSYSTEM=1` を与える(後者は `vi.stubEnv`)
- ユーザー名・メールは `-c` で渡す
- NFD のケースは期待値を `git ls-files` の出力(その環境での index の表記)から組み立て、
  macOS と Linux のどちらでも成り立つようにする
- 大文字小文字のケースはファイルシステムの性質を実測して `skipIf`、シンボリックリンクは
  Windows で `skipIf` する

壊れた署名設定を `GIT_CONFIG_GLOBAL` に指定しても全件通ることを確認した。

### 汎用的な対策

- 判定の正しさが外部コマンドの出力規則に依存するなら、モックの単体テストに加えて、実物を
  使う統合テストを少数でも用意する。特に「データを失わない」ことはファイルの中身で確かめる
- 実物を使うテストは、開発者の設定(グローバル設定・フック・署名)から切り離す。子プロセス
  経由で起動される分(ライブラリが起動するコマンド)にも環境変数が届くようにする
- OS・ファイルシステムで挙動が変わるケースは、期待値を環境から組み立てるか、前提が
  成り立たない環境では skip する。前提は OS 名ではなく実測で判定する

## 42. 判定に使わない出力まで外部コマンドに全件列挙させる

### どういう時に問題が起こるか

外部コマンドに広い範囲を問い合わせ、その出力の一部だけを判定に使うとき。問い合わせの
範囲に大きなディレクトリが含まれると、使わない出力のために時間とメモリを消費する。

### 原因

パターン36 の重なりの検出では、対象の**親**も pathspec に渡している。親が通常の
ディレクトリなら、その配下の未追跡ファイルすべてに一致する。`--exclude-standard` を
付けていない(ignored も検出するため)ので、親の配下にある `node_modules` のような巨大な
ignored ディレクトリも、1 ファイルずつすべて出力される。

判定に使うのは「親そのもの」「対象自身」「対象の配下」と一致するエントリだけで、
兄弟の大量のファイルは読み込んだ後に捨てていた。レビューでの計測では、2 万 5 千
ファイルの `node_modules` で出力は約 1.7MB、取り消し 1 回ごとにファイル数に比例して
増える。monorepo では数 MB になる。

### このプロジェクトでの実例

ローカルのレビューループで Minor として指摘された。`--directory` を付け、未追跡の
ディレクトリを `<dir>/` の 1 行にまとめるようにした(計測では 1 行・約 10 分の 1 の時間)。
まとめた `<dir>/` も「対象の配下」と同じ前方一致で判定できる。対象と親をすべて pathspec に
渡しているため、git は深い pathspec を含むディレクトリをまとめない。そのため、対象の
位置の検出が失われないことをレビュアーが実機で確認した。問い合わせに `--directory` が付く
ことを単体テストで、親の配下の ignored の `node_modules` を残して restore することを
統合テストで固定した。

### 汎用的な対策

- 外部コマンドへの問い合わせは、判定に必要な粒度で出力させる(ディレクトリ単位で足りるなら
  まとめるオプションを使う)
- 検証用の小さなリポジトリでは性能の問題が見えないため、`node_modules` のような大きな
  ディレクトリがある配置を想定して、出力量が何に比例するかを考える
- 出力をまとめるオプションを足したら、まとめられた形でも判定が変わらないことを、
  各配置で確かめる

## 43. 名前の解決が曖昧なとき、外部コマンドは黙って別の対象を選び、検証も同じ解決経路を通って素通りする

### どういう時に問題が起こるか

ユーザーが選んだ名前(ブランチ名)を外部コマンド(`git merge <name>`)へそのまま渡すとき、その名前が
複数の参照(タグ・別のブランチ・別のファイル)に解決されうる状態だったとき。さらに、それを防ぐための
検証を「同じ名前を同じ方法で解決して比べる」形で書いたとき。

### 原因

git は、名前が曖昧なとき、決まった優先順位で 1 つを選ぶ。`git merge feat` は `$GIT_DIR/feat` →
`refs/feat` → `refs/tags/feat` → `refs/heads/feat` → `refs/remotes/feat` の順で探し、最初に見つかった
ものを使う。したがってブランチ `feat` と同名のタグ `feat` が別のコミットを指していると、`git merge feat` は
**タグのコミットをマージ**する。git は `warning: refname 'feat' is ambiguous` を stderr に出すだけで、
終了コードは 0 のままである。simple-git は終了コードが 0 なので reject せず、アプリは「選んだブランチを
マージできた」と信じたまま、ユーザーが選んでいないコミットを現在のブランチへ取り込む。

この問題に対して、最初の対策は「名前の解決先(`rev-parse <name>^{commit}`)と、ブランチの先端
(`rev-parse refs/heads/<name>^{commit}`)を比べ、食い違えば拒否する」という検証だった。ところが、
大文字小文字を区別しないファイルシステム(macOS・Windows の既定)では、この検証が**同じ誤りを繰り返して
素通りする**ことが、次の周のレビューで分かった。

- ブランチ `feat` が `packed-refs` にあり、別のブランチ `Feat` が loose ref(`.git/refs/heads/Feat` という
  ファイル)として存在するとする。`Feat` は `feat` とは別のブランチだが、ファイルシステム上では
  `.git/refs/heads/feat` と `.git/refs/heads/Feat` が同じ名前として扱われる
- `rev-parse feat^{commit}` も `rev-parse refs/heads/feat^{commit}` も、どちらも loose ref のファイル
  `Feat` を読みに行き、**同じ SHA を返す**。2 つの結果が一致するので検証は通る
- その後の `git merge feat` も同じ解決をするため、`Feat` のコミットが警告なしでマージされる

つまり、検証に使った 2 つの問い合わせが、検証対象の処理(`git merge`)と**同じ名前解決の経路**(ref を
ファイルとして読む処理)を通っていた。検証と実行が同じ経路を共有していると、経路そのものの誤りは
検証でも再現されて打ち消し合い、検出できない。パターン24(検証を通った値が、実際に使うコマンドでは
別の意味に解釈される)の一種だが、こちらは「検証の手段を実行と独立させていなかった」ことが原因である。

### このプロジェクトでの実例

ブランチのマージのタスクレビューで、同名タグの件が Important として指摘された(実機で再現)。名前の
解決先とブランチの先端を比べる検証を追加した。続くローカルのレビューループの 1 周目で、大文字小文字を
区別しない FS では素通りすることを Important として指摘された(macOS APFS、`core.ignorecase=true` で
再現)。ブランチの先端の取得を、ファイルを読む `rev-parse` から、ref を名前で列挙する
`git for-each-ref --format='%(refname) %(objectname)' refs/heads/<name>` に変えた。`for-each-ref` は
`packed-refs` と loose ref を ref 名で突き合わせるため、`feat`(packed)の SHA を正しく返す。出力は
refname が `refs/heads/<name>` と**完全一致する行**を選ぶ(パターンは配下の `refs/heads/<name>/x` にも
一致しうるため)。この先端と、名前の解決先(`rev-parse <name>^{commit}`)を比べ、空・食い違い・一致する行が
無いときは拒否する。同じコミットを指すタグは拒否しない(内容は同じで無害。ただし git はタグの方を
マージするため、マージコミットの件名が `Merge tag '<name>'` になることを既知の制約に記載した)。

単体テストは `for-each-ref` の出力(完全一致の行・配下の行だけ・複数行・空)ごとに固定した。統合テストは
`feat`(packed)と `Feat`(loose)を実際に作り、`Feat` のファイルが working tree に入らず拒否されることを
確認する。大文字小文字を区別する FS では 2 つを共存できないため、FS の性質を実測して skipIf する。

### 汎用的な対策

- ユーザーが選んだ名前を外部コマンドへ渡すときは、名前が複数の参照に解決されうることを疑う。渡す名前を
  `refs/heads/<name>` のような完全な形にできればそれが最も確実だが、コマンドの出力(マージコミットの件名等)が
  変わる副作用がないかを実機で確かめる。副作用が大きいときは、検証で曖昧さを拒否する
- **検証は、実行と別の手段・別の経路で行う**。同じ問い合わせを 2 回して比べる検証は、その問い合わせ自体の
  誤りを検出できない。一次情報(ref の一覧など、名前を構造的に扱うコマンド)から取った値と、実行と同じ
  解決で得た値を比べる
- 環境(ファイルシステムの大文字小文字の扱い、ref の保存形式)で名前解決の結果が変わる場合は、その環境を
  実際に作って試す。開発環境が区別する側(Linux)だと再現しない

## 44. ライブラリの解析結果のフラグが、特殊な状態を認識しない

### どういう時に問題が起こるか

外部コマンドの出力を解析するライブラリが返す真偽値(`detached: true` など)を、そのまま状態の判定に使ったとき。
ライブラリがその値を立てる条件が、実際に起こりうる状態の一部しか覆っていないとき。

### 原因

simple-git の `branchLocal()` は、`git branch -v` の先頭行が `(HEAD detached at X)` または
`(HEAD detached from X)` の形のときだけ `detached: true` を返す。しかし git は、HEAD がブランチを指していない
状態を、状況ごとに違う表記で出力する。

- 対話的 rebase を `edit` で止めた間: `* (no branch, rebasing main) …`
- bisect の途中: `* (no branch, bisect started on main) …`

これらの行はライブラリの 2 つ目の正規表現(`^([*+]\s)?(\S+)\s+([a-z0-9]+)\s?(.*)$`)に当たり、ブランチ名が
`(no` として解析される。結果は `current: "(no"`、`detached: false`(`all` にも `"(no"` が混ざる)である。
アプリの「detached HEAD ならマージを拒否する」という検証は素通りし、rebase が `edit` で止まっている間
(作業ツリーはきれいで `MERGE_HEAD` も無い)に `git merge` が実行された。実機で `interactive rebase in progress`
のまま、rebase の途中の履歴にマージコミットが入った。

単体テストはこの穴を踏まなかった。`branchLocal()` をモックし、`detached: true` を**直接与えて**いたため、
ライブラリがどの出力でその値を立てるか(立てないか)は検証されていなかった。統合テストも
`git checkout --detach`(ライブラリが認識する唯一の形)しか扱っていなかった。これはパターン41(モックの
テストだけでは、外部コマンドの実際の出力を検証できない)の具体例でもある。

### このプロジェクトでの実例

ローカルのレビューループの 3 周目で Important として指摘された(実機で再現)。判定を `git symbolic-ref -q HEAD`
に置き換えた(`isOnBranch`)。`symbolic-ref` は HEAD が指す ref を直接返す一次情報で、ブランチ上なら
`refs/heads/main`、そうでなければ何も出力せず終了コード 1 で終わる。`-q` を付けると stderr が空なので
simple-git は reject せず空文字で resolve し、「空ならブランチ上にいない」と判定できる。
`branchLocal().current` は、ブランチ上にいることが確定した後の「自分自身」の判定にだけ使う。

統合テストに、rebase を `edit` で止めた状態と bisect の途中を追加した(Windows では skipIf)。修正前は
どちらもマージが実行されてしまうことを確認した。判定を元の `summary.detached` に戻すと統合テストと単体テストが
落ちる。

4 周目のレビューで、同じ「ブランチ上にいるが途中状態にある」の仲間として `git am` の途中が見つかった。
HEAD はブランチを指したままなので `symbolic-ref` では検出できず、作業ツリーもきれいなため、am セッションの
途中でマージが実行される(git 本体の `merge` もこの状態を拒否しない)。データは失われず、検出には
`git rev-parse --git-path rebase-apply` の存在をファイルシステムで調べる必要があるため、既知の制約として
設計書と ROADMAP に記載した。一方、cherry-pick と revert の途中は git 自身が拒否する。

### 汎用的な対策

- ライブラリが返す真偽値・列挙値を安全性の判定に使う前に、ライブラリが**どの出力形式で**その値を立てるかを
  ソースで確かめる。特殊な状態(rebase・bisect・merge・cherry-pick・am・shallow・空のリポジトリ・worktree)を
  実機で作り、ライブラリの戻り値を印字して確かめる
- 状態の判定は、ライブラリの解析結果ではなく、git の一次情報(`symbolic-ref`、`rev-parse`、`MERGE_HEAD` などの
  ファイルの有無)から直接取る
- 「進行中の操作」を仕様として列挙する。ブランチ上にいない状態は 1 種類ではない。列挙から漏れた状態は、
  拒否する・既知の制約として記載する、のどちらかを意識的に選ぶ
- モックのテストでライブラリの戻り値を直接与えるだけでなく、その値を返す実際の出力をライブラリに通して
  確かめるテストを 1 つは用意する

## 45. ユーザーの設定が外部コマンドの既定の動作を変え、成否判定の前提が崩れる

### どういう時に問題が起こるか

外部コマンドを既定の引数で呼び、その終了コード・出力・副作用(状態ファイルが残るか)から成否を判定して
いるとき。ユーザーの git 設定(`git config`)が、そのコマンドの動作を黙って変えてしまう場合。

### 原因

git は多くのコマンドの動作を設定で変えられる。マージでは `branch.<ブランチ>.mergeoptions` に書いた
オプションが、コマンドラインの引数より**先に**適用され、コマンドラインの指定が優先される。ユーザーが
`git config branch.main.mergeoptions --squash` と設定している(定番の設定例)と、`git merge --no-edit <name>` は次の
ように振る舞う。

- `--squash` では、コンフリクトしても git は `MERGE_HEAD` を作らない。終了コード 1・stderr 空で終わるので
  simple-git は reject せず、`mergeBranch` は正常終了する。アプリの「`MERGE_HEAD` が残っていれば中止する」
  という判定をすり抜け、`UU` とコンフリクトマーカー入りのファイルが残る。`git merge --abort` は
  `There is no merge to abort` で戻せない。renderer は成功とみなしてマーカー入りのファイルを再読込する。
  コンフリクトしない場合も、変更がステージされるだけで HEAD は動かないのに成功扱いになる
- `--no-commit` では、分岐したマージが `MERGE_HEAD` を残して止まる。アプリはこれを「途中で止まった」と判断して
  毎回中止し、「マージを完了できなかったため中止しました」(detail は空)を出す

アプリの成否判定は「コミットまで完了する」「コンフリクトなら `MERGE_HEAD` が残る」という、既定の動作を
前提にしていた。設定がその前提を崩すと、判定は正しく動かない。

### このプロジェクトでの実例

PR レビューの 1 周目で Minor として指摘された(実機で再現)。別のサブエージェントが、`--squash`・
`--no-commit`・`--ff-only`・`--no-ff`・`-s ours`・`-X theirs` など複数の設定で、現状の引数と修正案の引数を
実機で比較した。引数を `git merge --no-edit --commit --no-squash <name>` にして、**アプリの成否判定が
前提としている 2 点(コミットまで行う、squash しない)だけを固定**した。

一方で、次は固定しなかった。

- `--ff`: 付けると `merge.ff=only` などのユーザーの早送りの方針まで上書きしてしまう。ユーザーの方針は
  尊重する。どの ff 設定でも結果は「コミットされる」「何も変えずに reject」「`MERGE_HEAD` を残して止まる」の
  いずれかで、現行の判定で安全に扱える
- `-s ours` / `-X theirs`: コマンドラインから打ち消せない(`-s` は追加されるだけで、消すには
  `-c branch.<name>.mergeoptions=` が必要)。ユーザーが意図して設定するもので、コミットは正しく作られ
  戻せるため、既知の制約として記載するにとどめた

統合テストに、`--squash` 設定 × コンフリクト(中止して元に戻る)、`--squash` × 分岐(親が 2 つのマージコミット)、
`--squash` × 早送り、`--no-commit` × 分岐、`merge.ff=only` × 分岐(拒否は変わらない)を追加した。引数を
元に戻すと統合 4 件と単体 1 件が落ちる。2 周目のレビューでは、`merge.conflictStyle`、署名、フック、
`GIT_MERGE_AUTOEDIT`、`--quiet`、`core.autocrlf` など、他の設定でも判定が壊れないことを実機で確かめた。

### 汎用的な対策

- 外部コマンドの成否を、終了コード・出力・状態ファイルの有無から判定するなら、**その判定が前提としている
  動作をコマンドラインの引数で固定する**。設定より引数が優先される仕組みかを実機で確かめる
- 固定する範囲は「アプリの判定が依存する性質」だけに絞る。ユーザーの方針(早送りの扱い、マージ戦略)まで
  上書きすると、ユーザーの意図を無視する。方針が変わっても判定が壊れない設計かを、複数の設定の組み合わせで
  実機で比較する
- 固定できない設定は、影響を確かめたうえで既知の制約として記録する
- 「引数を固定する」修正には、固定を外すと落ちる統合テスト(設定を実際に書いて実行する)を必ず付ける

## 46. テストの前提が、環境の既定値(ロケール・ref の保存形式・ファイルシステム)に依存する

### どういう時に問題が起こるか

実際の git を使う統合テストが、開発者・CI の環境の既定値(ロケール、git の ref の保存形式、ファイルシステムの
大文字小文字の扱い、グローバル設定)に依存しているとき。自分の環境では通るが、別の環境で落ちる、または
検証したいことを検証できなくなる。

### 原因

統合テストは実際の git を動かすため、環境の影響を直接受ける。今回見つかったのは次の 3 つである。

- **ロケール**: bisect のテストが、前提の確認に `git branch -v` の出力が英語の
  `(no branch, bisect started on main)` を含むことを使っていた。`LANG`/`LC_ALL` は子プロセスへ引き継がれるため、
  翻訳を持つ git(Homebrew の git など)を翻訳のあるロケール(`de_DE.UTF-8`)で使うと、出力が
  `(kein Branch, binäre Suche begonnen…` となって落ちる(実機で再現)。日本語の翻訳は git に無いので、手元の
  環境では再現しない
- **ref の保存形式**: 大文字小文字だけ違うブランチのテスト(パターン43)は、loose ref が**ファイルとして**
  保存される files backend を前提にしていた。`GIT_DEFAULT_REF_FORMAT=reftable`(または将来 reftable が既定に
  なる git)では、`feat` と `Feat` が別の ref として共存し、`rev-parse` も正しく解決するため、マージが
  正しく通って「拒否される」という期待が外れる
- **ファイルシステム**: 大文字小文字を区別する FS(Linux)では `Feat` と `feat` の共存自体を作れず、
  テストが成立しない

### このプロジェクトでの実例

ローカルのレビューループの 2〜4 周目で Minor として指摘された(いずれも実機で再現)。

- 統合テストの共通ヘルパー(`realGitRepo.ts`)の `isolatedGitEnv` に、`GIT_CONFIG_GLOBAL=/dev/null`、
  `GIT_CONFIG_NOSYSTEM=1` に加えて `GIT_DEFAULT_REF_FORMAT: 'files'` と `LC_ALL: 'C'` を追加した。この環境は
  テストが実行する git と、テスト対象の関数(simple-git が起動する git)の両方に同じものが渡る
- bisect の前提確認を、出力の文言ではなく状態で確認する形にした。`.git/BISECT_LOG` が存在すること、
  `symbolic-ref -q HEAD` が失敗すること(HEAD がブランチを指していない)である。こちらが本質的な修正で、
  `LC_ALL=C` は防御として残した(外側から `de_DE` を指定して、`LC_ALL` を消しても落ちないことを確認した)
- ファイルシステムの性質は、OS 名ではなく**実際にファイルを作って実測**して skipIf する
  (`isCaseInsensitiveFs()` を共通ヘルパーに置いた)。Windows で動かないシェルスクリプトやシンボリックリンクは
  `process.platform === 'win32'` で skipIf する
- 外側から `GIT_DEFAULT_REF_FORMAT=reftable` や `LANG=de_DE.UTF-8 LC_ALL=de_DE.UTF-8` を指定して統合テストが
  通ることを、修正の検証手順に含めた

### 汎用的な対策

- 統合テストの実行環境は、グローバル設定・システム設定・ロケール・ref の保存形式などを**テスト側で明示的に
  固定**し、開発者の環境を引き継がない
- テストの前提確認は、外部コマンドの**出力文言**ではなく、**状態**(ファイルの有無、コマンドの成否)で行う。
  文言はロケール・バージョンで変わる
- ファイルシステムや OS に依存するテストは、条件を実測して skipIf する。skip する理由をコメントに書く
- 修正を検証するときに、環境を変えて(別のロケール、別の ref 形式)再実行する。今回のレビュアーが
  そうして問題を見つけた

## 47. 同じ検証が操作ごとにコピーされ、境界を変えるときに揃え忘れる

### どういう時に問題が起こるか

新しい操作を足すたびに、既存の操作の入力検証(許可リストの確認など)をコピーして貼り付けたとき。
また、共通化した後で、共通化前の重複(薄い別名、同じ内容のテスト)が残ったとき。

### 原因

セキュリティ上の境界(パターン21: IPC から届く任意の文字列を、`git` にオプションとして解釈させないため、
実在するローカルブランチ名だけを許可する検証)は、`checkout`・`削除`・`マージ`の 3 か所に、同じ形
(`branchLocal()` の結果に `summary.all.includes(name)` があるか、無ければ `存在しないブランチです: <name>` を
投げる)でコピーされていた。マージの追加で 3 つ目になった。検証の判定や文言を変えるときに、3 か所を揃えて
直す必要があり、1 か所を直し忘れると、操作ごとに境界の強さが食い違う。パターン14(同じ業務ルールを別々に
実装する)の、セキュリティの境界版である。

テストにも同じ構造の重複があった。

- 共通化した後も、`mergeBranch` のテストに許可リスト拒否の検証が 3 か所に残った(共通の `it.each`、マージ単体の
  拒否テスト、検証順序のテスト)。境界を変えると 3 か所を直す必要がある
- 切り出した純粋関数のテストと、切り出し元のテストに同じ境界値(5 件まで/ほか N 件)が残った
- 共通ヘルパーを導入した結果、別のファイルに同じ処理の薄い別名(`git`、`gitOutput`、`runGit`)が 3 つ、
  コミッター情報を設定する方法が 2 通り残った
- 実装をまとめたのに、テストの `setup()` は 27 行が完全に同じまま 2 つの `describe` に残った

### このプロジェクトでの実例

単一責任のレビューの周回(2〜4 周目)で指摘された。

- 許可リストの検証を `assertLocalBranchExists(summary, branchName)` に切り出し、3 か所から呼ぶだけにした。
  `branchLocal()` の呼び出しは、`current` の判定にも同じ結果を使うため各呼び出し元に残す。「3 操作すべてが
  同じ文言で拒否し、git の操作を呼ばない」ことを、`it.each` で操作ごとに 1 つのテストにまとめた。同じ検証を
  していた重複テスト 2 件を削除した
- 削除するテストは、**残るテストが同じ内容をもれなく覆っていること**を先に確認した。共通 `it.each` が
  `mockRaw` の未呼び出しまで検証しているので、`merge`・`abort`・`rev-parse`・`status` のいずれも
  呼ばれないことを覆っている
- 文言の境界値は `gitMergeMessages.test.ts` に一本化し、`gitService.test.ts` には「`buildMergeAbortMessage` の
  結果を投げる」配線の確認だけを残した
- 共通ヘルパーへの統一で残った薄い別名を廃止した(ネストしたリポジトリの中でコミットするケースだけは、
  リポジトリ内の設定が効かないため従来の方式を残し、理由をコメントに書いた)
- `setup()` の重複は、1 つの共通ヘルパー(`setupEditorSyncedGitOperation`)にまとめた

### 汎用的な対策

- 同じ判定・同じ文言が 3 か所目に出てきたら、共通の関数にする。特に入力検証などセキュリティの境界は、
  1 か所で管理する
- 共通化した関数のテストは、**すべての利用箇所に効いていること**を `it.each` で操作ごとに検証する
  (パターン34)。それぞれの利用箇所のテストには、配線の確認だけを残す
- 共通化・切り出しの後は、重複を残さない: 同じ内容のテスト、薄い別名、重複したセットアップ。重複を消す
  ときは、消すテストが検証している内容が残るテストでもれなく覆われているかを先に確認し、足りなければ
  残す側を強化してから消す(パターン31)
- 共通化の後は、その周辺のコメントと設計書の記述も更新する(パターン32)。今回は「checkout/作成/削除」と
  列挙したコメントが、マージの追加後も別のファイルに残っていた

## 48. 網羅しきれない例外的な状態は、根拠つきで「見送る」判断を記録する

### どういう時に問題が起こるか

安全確認を実装するとき、ユーザーの特殊な設定・特殊な git の状態は無数にある。すべてを検出しようとすると、
コードが複雑になり、コストが効果と釣り合わなくなる。一方、黙って見送ると、後から「知らなかった」制約に
なる。

### 原因

今回のレビューでは、実機で再現できるが、対策のコストが効果に釣り合わないものが複数見つかった。

- `git update-index --assume-unchanged` を付けたファイルの未コミットの変更は、`git status` に出ないので
  「未コミットの変更がある間は開始しない」の検証をすり抜ける。分岐していて相手が同じファイルを変更していると、
  git が `Your local changes … would be overwritten` で失敗し、そのファイルが HEAD の内容に戻って変更が
  失われる(git CLI でも同じ)。検出には `ls-files -v` で全追跡ファイルを列挙する必要がある
- `.gitignore` 対象のファイルは、相手のブランチで追跡されていると git が黙って上書きし、コンフリクトで
  自動中止しても復元されない(git の既定。checkout も同じ)
- `rerere.enabled` と `rerere.autoupdate` が両方有効だと、コンフリクトが自動ステージされて未解決ファイルが
  空になり、「コンフリクトしたため中止しました」ではなく git の別の文言が出る(中止とデータの復元は正しい)
- `git am` の途中でマージが実行される(パターン44)
- 同名タグが同じコミットを指すとき、マージコミットの件名が `Merge tag '<name>'` になる
- `mergeoptions` の `-s ours` / `-X` が打ち消せない(パターン45)
- `merge.ff=only` の拒否メッセージが英語のまま出る
- Electron は IPC のエラーメッセージに `Error invoking remote method '<チャンネル>': Error: ` を前置する。これは
  checkout・作成・削除など IPC を通る**全ての操作に共通**する既存の挙動で、今回の機能で新しく生じた問題では
  ないため、この PR では直さない

### このプロジェクトでの実例

これらは「直す」「見送る」のいずれかを、レビューの周ごとに次の基準で判定した。

- 修正が小さく、副作用がない(引数を 2 つ足す、コメントを直す): 直す
- データ損失の可能性があるが、条件が特殊(ユーザー自身が特殊なフラグを付けた)で、検出コストが高い:
  見送り、設計書の「既知の制約」と ROADMAP に**再現手順・影響・見送りの理由・検出方法の案**を記載する
- 既存の全操作に共通する問題: 今回の PR の範囲を超えるため、別の項目として ROADMAP に記載する
- データは失われず、文言だけの問題: 見送り、記載する

見送った項目は、設計書の「既知の制約」と ROADMAP の見送り項目に書き、次のレビュアーに「既知で受容済み」と
伝えて再指摘を避けた。その一方で、レビュアーには「前提が崩れる新事実があれば指摘してよい」と伝え、
見送った判断が誤りだった場合に見つけられるようにした。

### 汎用的な対策

- 安全確認は、ユーザーの意図しない特殊な状態(設定・途中状態・環境)を**実機で洗い出し**、それぞれ
  「検出して拒否する」「見送る」「範囲外」のどれかを意識的に判定する。判定できないまま放置しない
- 見送るときは、**再現手順・影響(データ損失の有無)・見送りの理由・将来検出する場合の方法の案**をセットで
  設計書と ROADMAP に残す。「なぜ直さないか」を書かないと、次に同じ指摘が出たときに議論を繰り返す
- 既存の全操作に共通する問題は、新しい機能の PR で直さない。別の項目として記録する
- 見送り項目をレビュアーに伝えるときは、「前提が崩れる新事実があれば指摘してよい」と併記する。
  それによって、見送りの判断自体の誤りも見つけられる
- 「対応不要」の判定もレビューの成果である。過剰な抽象化や、1 箇所でしか使わない層を増やす指摘は、理由を
  書いて見送る

## 49. ライブラリの安全装置が、ユーザーの入力値を「オプション」と誤検知する

### どういう時に問題が起こるか

ユーザーが自由に入力できる文字列(コミットや退避のメッセージ、名前)を、外部コマンドのラッパー
ライブラリ経由で渡すとき。ライブラリが「危険なオプションの注入」を防ぐために引数列を走査する
仕組みを持っていて、**値の側がたまたま危険なオプションと同じ見た目**だった場合に起こる。

### 原因

simple-git の `blockUnsafeOperationsPlugin` は、git に渡す引数の配列の**各要素**を調べ、
`--upload-pack=...`・`--receive-pack=...`・`--template=...`・`-c ...` のような、コマンド実行や任意
ファイルの読み書きに悪用されうる形を見つけると例外で拒否する。この検査は「その要素がオプションの
位置にあるか、オプションの値の位置にあるか」を区別しない。

`git stash push -m <message>` のように、フラグと値を**別々の要素**として渡すと、値の要素
(`--upload-pack=x` というメッセージ)も単独で検査され、危険なオプションとして拒否される。ユーザー
から見ると、ただのメッセージなのに英語の例外で操作が失敗する。

逆に、`--message=<message>` のように**フラグと値を 1 つの要素にまとめる**と、要素の先頭は常に
`--message=` になるため、値が何であっても検査に引っかからない。git 側でも `=` 以降は値として扱われ、
`-` で始まるメッセージもそのまま件名になる(実機で確認)。

この問題は、通常のメッセージ(日本語や英単語)では**絶対に再現しない**。実装者もテストも普通の文字列
しか使わないので、レビューで「危険なオプションと同じ形のメッセージ」を意図的に入れて初めて見つかる。

### このプロジェクトでの実例

退避(`git stash push`)にメッセージを渡す実装で、最初は `['stash', 'push', '-u', '-m', message]` と
していた。レビューで、メッセージが `--upload-pack=x` のとき simple-git が拒否することが見つかった。
`['stash', 'push', '-u', `--message=${message}`]` の 1 要素形式に変えた。退避を一覧に戻す
`stash store` も同じく `--message=<msg>` にした。統合テストで `--upload-pack=x`、`-c x=y` のような
メッセージでも退避でき、件名がそのまま残ることを固定した。

### 汎用的な対策

- ユーザー入力を外部コマンドの引数へ渡すときは、**フラグと値を 1 要素にまとめられるなら
  `--flag=value` の形にする**。ライブラリの引数検査と、コマンド自身の引数解釈の両方に対して安全になる
- ライブラリに安全装置がある場合、その検査は「値」にも及ぶと考え、**危険なオプションの文字列そのものを
  値として渡すテスト**を実物(統合テスト)で書く。モックでは検査プラグインが働かないので見つからない
- 入力の許可リスト(パターン21)と併用する。引数の形で防げるのは「注入されること」であり、「その値が
  許される入力か」の検証は別に必要

## 50. 事前チェックの「変更あり」と、実行するコマンドの「変更あり」の定義がずれる

### どういう時に問題が起こるか

「実行してよい状態か」を `git status` などで先に確認してから、別のコマンド(`git stash push`)を
実行するとき。**確認に使うコマンドと実行するコマンドが、同じ対象を同じ範囲で数えていない**場合に、
確認は通るのに実行が何もしない、あるいは確認で弾いたのに実行できたはずの状態になる。

### 原因

サブモジュールの中だけを変更した状態では、`git status --porcelain` は ` M <sub>` と「変更あり」を
報告する。しかし `git stash push` はサブモジュールの中身を退避しないため、終了コード 0 で
`No local changes to save` と言って**何もせず成功する**(実機で確認)。

事前チェックが「status が空でなければ退避できる」としていると、サブモジュールだけの変更では次のように
なる。

- 退避: チェックは通る → git は何も退避せず成功 → アプリは「退避した」と扱う。一覧は増えず、ユーザーは
  変更が退避されたと思い込む
- 復元: 逆に、復元側のチェックが「status が空でなければ作業中の変更あり」としていると、サブモジュールの
  変更だけで「戻せません」と言われる。退避は「変更が無い」、復元は「変更がある」と、**両方が行き止まり**に
  なる

また、事前チェックを 2 か所(退避と復元)で別々に書くと、片方だけ引数を直し忘れて、この定義のずれが
再発する。

関連: コミットが無いリポジトリでの退避は終了コード 1 の英語エラー、変更が無いときの退避は終了コード 0 の
`No local changes to save` で、**エラーかどうかでも出力の文言でも判定できない**(パターン28)。

### このプロジェクトでの実例

退避の事前チェックを `status --porcelain -z --untracked-files=all --ignore-submodules=all` にし、
stash が数えない範囲(サブモジュールの中身)を status からも除いた。この status の引数列は退避側
(`assertStashable`)と復元側(`assertRestorable`)で同じでなければならないため、後の単一責任の
リファクタリングで、非公開の `readStashRelevantStatus` に集約した。引数の重複そのものが「定義のずれ」を
生む構造だったため、重複の解消がバグの再発防止になった。

### 汎用的な対策

- 事前チェックと実行は、**同じ対象を同じ範囲で数える**。実行するコマンドが無視するもの(サブモジュール、
  ignored、空ディレクトリ)は、チェックの側でも除外する。差が出そうなコマンドの組は、実機で境界の状態を
  作って「チェックは通るが何も起きない」「チェックで弾くが実行できる」を両方向で試す
- 判定の定義は 1 か所に関数として置き、複数の操作から同じ関数を呼ぶ。引数列をコピーしない
- 「成功した(終了コード 0)」と「期待した変更が起きた」は別。副作用が起きたかは、実行の前後の状態
  (一覧の件数、status)で確かめる(パターン28)

## 51. 「作業ツリーがきれい」の判定に映らない状態を、破壊的な操作が失う

### どういう時に問題が起こるか

破壊的な後始末(`git reset --hard`、`git clean`、`git stash`)を、「作業ツリーが完全にきれいだから失う
ものは無い」という前提で実行するとき。**`git status` が空でも、実際には失われる状態が存在する**場合に、
黙ってデータや作業の途中状態が消える。

### 原因

`git status` が見せるのは「追跡されたファイルの内容が HEAD と index と作業ツリーでどう違うか」であり、
次の状態は status に出ないのに、`reset --hard` や `stash` が影響する。

1. **assume-unchanged が付いたファイルの変更**: `git update-index --assume-unchanged <file>` を付けると、
   git はそのファイルを変更検出の対象から外す。編集しても status は空のままだが、`reset --hard` は
   そのファイルを HEAD の内容へ戻す。事前に「status が空だからきれい」と判断していると、**ユーザーの編集が
   復元失敗時の巻き戻しで消える**。`ls-files -v -z` はタグが小文字(`h` など)のファイルで見分けられる。
   一方 skip-worktree(タグ `S`)は `reset --hard` で消えないため、拒否する必要は無い(実機で確認)
2. **マージ・cherry-pick・revert の途中状態**: コンフリクトを `git checkout --ours f && git add f` の
   ように自分側で解決してステージすると、`ls-files -u`(未解決の一覧)も status も空になるが、
   `MERGE_HEAD` などの ref が残り、「マージの途中」である。この状態で `git stash push` を実行すると
   **成功して `MERGE_HEAD` が消える**。`reset --hard` も `MERGE_HEAD` を消す。結果、解決途中のマージが
   黙って失われ、次のコミットは親が 1 つの普通のコミットになる。巻き戻しが走らなくても、`apply` が成功すると
   途中のマージに退避の変更が混ざる
3. **ユーザー設定が破壊的コマンドの範囲を広げる**: `submodule.recurse=true` だと `git reset --hard` が
   サブモジュールの中まで再帰し、そこにあるローカル変更を消す。status の確認は
   `--ignore-submodules=all` でサブモジュールの中を見ていないため、確認では検出できない(パターン45)

さらに、**対称であるべき 2 つの操作の検証が片方だけ抜ける**問題もあった。退避側の事前検証は
途中の操作(MERGE_HEAD 等)を拒否していたが、復元側は拒否していなかった。復元は失敗時に `reset --hard`
を走らせるので、むしろ復元側のほうが危険だった。

### このプロジェクトでの実例

- 復元前に `ls-files -v -z` で小文字タグ(assume-unchanged)を調べ、見つかれば
  「assume-unchanged を付けたファイルがあるため戻せません」で拒否する(skip-worktree は拒否しない)
- `reset --hard` の引数を `--no-recurse-submodules` で固定した
- 退避の事前検証に `hasInProgressOperation`(`rev-parse --verify -q` で MERGE_HEAD / CHERRY_PICK_HEAD /
  REVERT_HEAD を調べる)を追加し、さらに最終レビューの 1 周目で復元の事前検証にも同じ検査を追加した。実 git の
  統合テストに、ours で解決したマージの途中(status が空・`MERGE_HEAD` あり)は復元を拒否し、
  `MERGE_HEAD` と退避が残る、というケースを追加した

### 汎用的な対策

- 破壊的な操作の前提を「status が空」だけで確認しない。**そのコマンドが何を変更・削除しうるか**を一覧にし、
  各項目を事前チェックが検出できているか突き合わせる(パターン38)。見えない状態(assume-unchanged、途中状態の
  ref)は、専用のコマンドで調べる
- ユーザー設定で範囲が広がるコマンドは、引数で固定する(パターン45)
- 検証は「危険な操作ごと」ではなく「**状態を失いうるコマンドごと**」に揃える。退避と復元のように一対の操作は、
  片方に足した検証をもう片方にも足したかを、テストの対応表で確認する(パターン34, 47)
- 事前に弾けない状態は、最後の手段として「失敗時に状態を壊さない」設計(パターン54)で受ける

## 52. 多段階の操作が「途中まで成功」したとき、例外にすると呼び出し側が作業ツリーの変化を見落とす

### どういう時に問題が起こるか

1 つの操作が複数のステップから成り(適用 → 一覧から削除)、**後ろのステップだけが失敗する**とき。
その失敗を例外(エラー)として投げると、呼び出し側は「操作全体が失敗した、何も変わっていない」と扱う。
実際には前半のステップで作業ツリーが変わっている。

### 原因

復元(pop)は「`stash apply` で作業ツリーに戻す」→「`stash drop` で一覧から消す」の 2 段階である。
apply が成功した後に drop が失敗する(別プロセスが先に消した、SHA の照合で不一致、git の失敗)と、
作業ツリーは復元済みなのに、関数は例外を投げる。呼び出し側(renderer)は例外を「失敗」と
解釈し、成功時にだけ行う「開いているタブの再読込・ファイルツリーの再読込」を行わない。結果:

1. タブには退避前の古い内容が表示されたままになる
2. ユーザーが、そのタブで編集して保存すると、復元された変更を**そのファイルだけ上書きして失う**

巻き戻し自体の失敗(`reset` や `clean` が失敗して途中の変更が残る)でも、同じ構造である。

ここで**二次災害**も起きた。最初の修正は「復元は失敗しても必ず再読込する」(`reloadOnFailure`)
だった。しかし、失敗には 3 種類ある。

| 種類                                                          | 作業ツリーは   | 再読込         |
| ------------------------------------------------------------- | -------------- | -------------- |
| 効果なしの失敗(事前検証の失敗、巻き戻しに成功した apply 失敗) | 変わっていない | してはいけない |
| 効果ありの失敗(巻き戻しの失敗)                                | 変わった       | 必要           |
| 部分成功(apply 成功後の drop 失敗)                            | 変わった       | 必要           |

「失敗なら再読込」にすると、**事前検証で弾かれた**だけの操作でも再読込が走り、ユーザーが破棄に同意して
いない未保存の編集を、ディスクの内容で黙って上書きして消す。たとえば、ディスクに未コミットの変更が
あり、別のタブに未保存の編集がある状態で「戻す」を押すと、確認に OK した直後に main が
「作業中の変更があるため戻せません」と返し、ディスクは何も変わっていないのに、未保存の編集が
消えた。作業ツリーに変更がある状態は普通なので、よく通る経路だった。

### このプロジェクトでの実例

- 復元の戻り値を `StashPopResult`(`{ status: 'restored' }` /
  `{ status: 'dropFailed' | 'rollbackFailed', message }`)にした。「作業ツリーが変わったが警告が要る」
  ケースを例外ではなく**結果**で返す。事前検証の失敗と、巻き戻しに成功した apply 失敗は従来どおり例外
- renderer の `popStash` は、`dropFailed` / `rollbackFailed` では警告をエラー表示にセットしたうえで
  `true`(作業ツリーが変わった)を返し、再読込と一覧の再取得を行わせる。例外のときは `false` で再読込しない
- `reloadOnFailure` は撤去し、共通ユーティリティ `runEditorSyncedOperation` は元の「成功時だけ再読込」に
  戻した。IPC を渡ると `Error` の独自プロパティは失われるため、種別の判別は文言ではなく結果型で行う

### 汎用的な対策

- 多段階の操作は、**どのステップまで進んだか**を呼び出し側が区別できる戻り値にする。「完全に成功 /
  何も変えずに失敗 / 変えたうえで失敗(または警告つき成功)」の 3 種類を、例外の有無と結果型で分ける
- 副作用の後始末(再読込、キャッシュの無効化)は、「成功したか」ではなく「**状態が変わったか**」で
  決める。失敗時にまとめて後始末すると、効果が無かった失敗で無関係な状態(未保存の編集)を壊す
- 例外の文言で分岐しない。IPC・シリアライズを越えるとプロパティが落ちるので、種別は戻り値の型で運ぶ
  (パターン28)
- 検証として、「事前検証で失敗した操作は再読込を呼ばない」「後半が失敗した操作は再読込を呼ぶ」の
  両方を、それぞれテストで固定する

## 53. 位置ベースの識別子は、操作の間にずれて別のものを指す

### どういう時に問題が起こるか

対象を番号や位置(`stash@{0}`、配列の添字、行番号)で指定して、一覧を表示してから操作するまでに時間が
空くとき。その間に、別の操作(アプリ内の別の退避、外部ターミナルでの `git stash`)で一覧が増減する。

### 原因

`stash@{n}` の `n` は「現在の一覧の先頭からの位置」にすぎない。新しい退避が積まれると、既存の退避の番号は
1 つずつ後ろにずれる。画面に「`stash@{1}` を捨てる」の状態を表示してから実際に `drop stash@{1}` を
実行するまでに別の退避が積まれると、**ユーザーが選んだものとは別の退避を消す**。退避の中身は
`git reflog` を知らない限り取り戻せないので、影響が大きい。

また、`git stash apply <sha>` は、すでに `drop` した退避でも、ぶら下がったコミットがまだ残っている間は
成功して**復活させてしまう**。画面に古い一覧が残っていて、捨てたはずの退避を「戻す」と、その後の
`drop` が見つけられなくなる(一覧に無い)。

### このプロジェクトでの実例

- 退避は番号ではなく**コミットの SHA** で識別する。型は `{ sha, message, branch, createdAt }`
- 操作の直前に `stash list` を取り直し、SHA から現在の位置を引き直す(`findStashIndex`)。SHA の形式
  (40 桁の 16 進数)の確認と、**現在の一覧にあること**の確認の両方を行い(許可リスト、パターン21)、
  どちらかが満たされなければ「退避が見つかりません(すでに削除された可能性があります)」で拒否する。
  この検証は pop と drop で共通の `findExistingStash` にまとめた
- 引き直した位置と実際の削除の間にも隙間があるため、`drop` の出力 `Dropped stash@{n} (<sha>)` の SHA を
  要求した SHA と照合し、一致しなければ消した退避を `stash store --message=<msg> <sha>` で戻して
  「もう一度操作してください」と伝える(補償処理)

### 汎用的な対策

- 一覧から選ぶ操作の識別子は、**不変の ID**(コミットの SHA、UUID)にする。位置ベースの識別子は表示専用に
  限る
- 実行の直前に、識別子が**今も有効か**(一覧にあるか)を、信頼できない入力として検証する
- 検証と実行の間の隙間は無くせないので、**実行結果の中に対象の ID を含む出力**があれば照合し、
  食い違えば元に戻す(補償)
- 対策ごとに、一覧が変化した状態(退避を積む・外部で消す)を作って試すテストを書く

## 54. 失敗時の「巻き戻し」は、前提・全ステップの試行・残留物の把握をセットで設計する

### どういう時に問題が起こるか

失敗したときに、作業ツリーを元に戻す後始末(`reset --hard` + `clean -fd`)を用意するとき。

### 原因

巻き戻しは、それ自体が破壊的な操作である。次の 3 つを同時に満たさないと、巻き戻しが新しい損失の原因になる。

1. **前提を満たすときだけ実行する**: 巻き戻しは「実行前の作業ツリーが完全にきれい」を前提に、
   「今あるものは全部復元由来」と見なして消す。実行前に、未コミットの変更・未追跡ファイル・assume-unchanged・
   途中状態が無いことを確認していないと、ユーザーの作業を消す(パターン51)
2. **途中で止めない**: `reset` が失敗しても `clean` は試みる。どちらか一方でも作業ツリーを戻せるからである。
   ただし、片方でも失敗したら、英語の git のエラーではなく「作業ツリーに途中の変更が残っている可能性が
   あります。退避は残っています」と日本語で伝える。原因は `cause` に残す。実装上は、すべてのステップを
   試行して**最初のエラーを保持**する
3. **戻せないものを把握する**: `clean -fd` は ignored のファイルを消さない。復元の途中で作られたファイルが
   その後 ignored になっていると、巻き戻し後も残る。残ったファイルは次の復元で
   `already exists, no checkout` の原因になり、原因を取り除いても復元が失敗し続ける(データは失われず、
   新しい退避にも影響しない)

付随して、診断用の情報の取得(未解決ファイルの一覧)は、**巻き戻しより前に**行う。巻き戻すと、取得できなく
なるためである。取得に失敗しても、巻き戻しは必ず試みる(表示用の補足にすぎない)。

### このプロジェクトでの実例

- `applyOrRollback` を `readConflictedPaths`(失敗時は空配列)・`rollbackToCleanTree`(全ステップを試行し
  最初のエラーを返す)・エラーの選択、に分けた。巻き戻しに失敗したときは `RollbackFailedError` を内部で投げ、
  `stashPop` が結果型 `rollbackFailed` に変換する
- ignored のパスの残留は、実 git で再現し、データ損失が無く、新しい退避にも影響しないことを確認したうえで、
  既知の制約として設計書と ROADMAP に記録した(対応案: 退避由来のパスだけを `clean -fdx -- <paths>` で
  消す)。パターン48 の基準に従い、再現手順・影響・見送りの理由を書いた

### 汎用的な対策

- 破壊的な後始末は、**実行する前提(クリーンな状態)を先に検証する**ステップとセットでしか実装しない
- 複数ステップの後始末は、1 つが失敗しても残りを試し、**最初のエラーを保持**して、ユーザーに「状態が
  中途半端かもしれない」ことを伝える
- 後始末のコマンドの**限界**(`clean` が ignored を消さない、`reset` が untracked に触れない)を一覧にし、
  限界が引き起こす残留を実機で再現して、直すか記録する
- 診断情報は、後始末の前に取る

## 55. 責務を分割したあとに、重複したロジック・テスト・文書が残る

### どういう時に問題が起こるか

大きなファイルから機能を切り出す、または 1 つの関数を小さな関数に分けた直後。分割そのものは正しくても、
**切り出す前に別々の場所へコピーされていたもの**が残り、後の変更で片方だけが更新される。

### 原因

切り出しの作業は「関数を別のファイルに移す」ことに集中するので、移した関数の周囲にある重複に気づきにくい。
今回見つかった重複は次の 4 種類である。

1. **ロジックの重複**: SHA の検証(形式 → 一覧の取得 → 位置の検索 → 見つからなければエラー)が、
   pop 用の関数と drop 用の関数に別々に書かれていた。drop 側は一覧そのものを再利用したいという事情で
   別実装になっていた。結果、片方の検証を変えても他方が変わらない構造だった(パターン47)
2. **定義の重複**: status を調べる引数列が退避と復元で複製されていた(パターン50)
3. **テストの重複**: 検証の順序と拒否の文言を、検証の関数(`gitStashGuards`)のテストと、それを呼ぶ
   上位の関数(`gitStashService`)のテストの両方で網羅的に確認していた。仕様を変えると 2 つのテスト
   ファイルを直す必要があり、直し忘れると片方が古い仕様のまま通り続ける。上位のテストは「検証が拒否したら
   後続のコマンドを呼ばない」の代表 1 ケースと順序に絞り、詳細は検証の関数のテストに一本化した
4. **文書の重複・ずれ**: 設計書が、分割前のファイル名・関数名(`gitService.ts` の `findExistingStashIndex`)
   や、古い挙動(「復元は失敗時も再読込」)を書いたまま残る。同じ内容を設計書の 2 つの節に書くと、
   片方だけが更新される

また、**ファイル名と中身がずれる**問題も起きた。確認ダイアログの文言を作るファイル(`stashConfirmMessage.ts`)
に、一覧の行の表示名を作る関数(`getStashDisplayName`)が同居していた。2 つは呼び合わず、変わる理由も違う
(確認文言の変更、表示名の変更)。ファイル名は「確認文言」なのに、UI がそこから表示名を import しており、
誤読を招く。

### このプロジェクトでの実例

- SHA の検証を `findExistingStash`(一覧と位置を返す)に一本化し、pop の事前確認と `dropStashBySha` の
  両方から呼ぶようにした。形式不正と一覧にない SHA で、pop と drop が同じ文言で拒否し、形式不正のときは
  git を呼ばないことをテストで固定した
- 検証の詳細は `gitStashGuards.test.ts` に、上位は代表ケースと順序だけに整理した
- `getStashDisplayName` を `lib/stashDisplayName.ts` に分離し、テストも分けた
- 統合テスト `gitService.stash.integration.test.ts` を、対象に合わせて `gitStashService.integration.test.ts`
  に改名した。設計書とプランのファイル名・関数名・テスト配置を、実装に合わせて更新した
- プランは実行の記録として本文を書き換えず、冒頭に「実装後に分割した。現在の構成は設計書を参照」と注記した

### 汎用的な対策

- 分割した直後に、**分割前から複製されていたもの**を探す。同じ引数列・同じ検証手順・同じエラー文言を
  `grep` で検索し、2 か所以上に出ていれば共通化する(パターン47)
- テストは、**検証の詳細を持つ層**と**それを使う層**で責務を分ける。上位の層では「検証の結果に応じて
  後続を呼ぶ/呼ばない」の配線だけを確認し、同じ仕様を二重に固定しない
- ファイル名・関数名が責務と合っているかを確認する。1 ファイルに「別々の理由で変わる関数」が同居して
  いたら分ける。ただし、既存の他機能が同じパターンに従っているだけの場合は、過剰に分割しない
- 分割や改名のあとは、旧名で文書を検索し、設計書・プラン・ROADMAP・コメントを更新する(パターン32)。
  実行の記録(プラン)は書き換えず、注記で現在の構成を指す

---

### 追加の実例(2 回目: 取り消しの分類と実行の分離)

「変更の取り消しの拡張」でも同じ型の取り残しが出た。1 周目の分割(分類 `gitDiscardClassifier.ts` と実行
`gitDiscardService.ts`)の後に、次が残っていた。

- **移した後の古いコメント**: 手段を決めているのは `applyDiscard`、拒否を実装しているのは `assertDiscardable`
  なのに、コメントは「`discardFileChanges` が状態ごとの手段を決める」のままで、参照先もずれていた
- **冗長な引数**: `classifyDiscardTarget(git, filePath, pathspec)` の `pathspec` は、呼び出し元 3 か所がどれも
  `toLiteralPathspec(filePath)` を渡していた。「一致しなければならない引数が 2 つある API」になっていたため、
  引数から外して内部で組み立てた
- **拒否文言のコピー**: `discardFileChanges` と `discardHunk` の switch が同じ 3 文言をコピーしていた
  (`assertDiscardable` に一本化)
- **テストの二重**: 分類の問い合わせを振り分けるスタブ(`mockRaw`)が describe ごとに 3 回コピーされ、統合テスト
  の `write`/`read`/setup も 3 回コピーされていた
- **判定のコピー**: `canDiscardHunk` の「未追跡でも intent-to-add でもない」が、別ファイルの
  `movesToTrashOnDiscard` と同じ判定のコピーだった(`canDiscardHunkFor` に集約)

分割のレビューでは、**「引数のすべての呼び出し元が同じ式を渡していないか」「コメントの参照先が移動後の名前か」**を
チェックに加える。

## 56. 流用した汎用部品の固定文字列や配置の記述が、新しい用途と合わなくなる

### どういう時に問題が起こるか

既存の汎用コンポーネント(入力ダイアログ)を新しい用途(退避メッセージの入力)へ流用するとき。部品の中に
**用途に固有の文字列が固定されていて**、流用先でも同じ文字列が出てしまう。また、設計書の
UI の説明が、実装時に変えた配置と食い違う。

### 原因

1. **固定されたアクセシブルネーム**: `NameInputDialog` の入力欄は `aria-label="名前"` が固定だった。
   退避メッセージのダイアログがこれを流用すると、スクリーンリーダーは入力欄を「名前」と読み上げる。
   画面上の見出しは「退避のメッセージ」なのに、支援技術には別の名前が伝わる。視覚的には問題が無く、
   自動テストも通るので気づきにくい。CLAUDE.md の「`aria-label` を適切に設定」に反する
2. **設計書と実装の配置のずれ**: 設計書は「エラーは既存のブランチ操作と同じ、パネル上部のバナーに表示する」
   と書いたが、実装は退避セクション内の `<p role="alert">` に表示した。実装時の判断(退避に関係する
   エラーは退避セクションの近くに出す)を設計書へ反映しなかった

### このプロジェクトでの実例

- `NameInputDialog` に任意の `inputLabel`(既定値は従来どおり「名前」)を追加し、退避の側は
  「退避のメッセージ」を渡した。既存の利用者(作成ダイアログなど)は何も渡さないので挙動が変わらない。
  `getByRole('textbox', { name: '退避のメッセージ' })` で取得できることをテストで固定した
- 設計書のエラー表示の記述を、実装(退避セクション内の `role="alert"`)に合わせた

### 汎用的な対策

- 汎用部品を新しい用途へ流用するときは、部品の中にある**固定の文字列(ラベル、プレースホルダー、
  aria-label、メッセージ)**を洗い出し、用途ごとに指定できる props にする。既定値は従来の値にして、
  既存の利用者を壊さない
- a11y のテストは、画面の見た目ではなく、`getByRole(..., { name })` で**支援技術に伝わる名前**を検証する
- 実装時に配置や挙動の判断を変えたら、同じコミットで設計書の該当節を更新する(パターン32)

## 57. テストが「実装を固定したつもり」になっている(警告だけで通る、片側しか検証していない)

### どういう時に問題が起こるか

実装を意図的に壊しても(ミューテーション)、テストが落ちないとき。または、成功経路しか検証しておらず、
失敗経路・後始末・境界が検証されていないとき。

### 原因

1. **警告だけで通る**: React の `key` に表示文言(メッセージ)を使うと、同じメッセージの項目が 2 つ
   あるときに `console.error`(重複キーの警告)が出るだけで、テストは落ちない。`key` を `entry.sha` から
   `entry.message` に変えるミューテーションが、既存のテストをすり抜けた。重複キーのテストを追加し、
   `console.error` が呼ばれないことを assert して固定した
2. **後始末が検証されていない**: ロックを取る操作のテストが、実行中のロックの取得だけを見て、
   「成功時にも失敗時にもロックを解除する」(`unlockGlobal`)を見ていなかった。解除を忘れると、以後の
   すべての操作が待たされ続ける。さらに、操作が reject したときの戻り値(`false`)とエラー表示の
   セットも未検証だった
3. **失敗経路のテストが欠けている**: 復元の成功・衝突のテストはあるが、後半(drop)の失敗、巻き戻しの
   失敗、その結果を受けた renderer の再読込の有無は、レビューで指摘されるまで検証されていなかった
4. **モックが実物の仕様と食い違う**: 実際のライブラリが備える検査(パターン49)は、モックでは働かない。
   モックの戻り値が常に成功だと、失敗の分岐を通る経路が検証されない
5. **ミューテーションの実施自体の事故**: 変異を入れる作業でバックアップの退避先を取り違えると、変異が
   累積して元に戻せなくなる。退避先に既存のディレクトリがあると、復元の `cp` が意図と違う場所へ入る

### このプロジェクトでの実例

実装者とレビュアーが、主要な分岐ごとにミューテーション(該当の行を外す・反転する)を行い、該当するテストが
落ちることを確認した。落ちなかったものは、テストを追加して落ちるようにした。変異は `cp` でバックアップ
(`mktemp -d` で新規に作ったディレクトリ)に退避してから入れ、テスト後に `cp` で戻して `cmp` で一致を
確認する手順に統一した。

### 汎用的な対策

- 追加したテストは、**実装を意図的に壊して落ちること**を確認する(リポジトリの作業ツリーで
  `git stash` や `git checkout` を使わず、コピー → 変異 → テスト → 復元 → `cmp`)
- 警告で済む不具合(重複キー、act 警告、未処理の Promise)は、`console.error` のスパイで失敗にする
- ロック・タイマー・購読のような「取得と解放」が対になる処理は、**解放が成功時と失敗時の両方で行われること**
  を検証する
- 失敗経路(拒否・途中失敗・巻き戻し失敗)と、その結果を受けた側の動作(再読込の有無、エラー表示)を、
  成功経路と同じ深さで書く
- モックでは働かない外部の検査・環境依存は、実物を使う統合テストで補う(パターン41, 46, 49)
- ミューテーションのバックアップは毎回新しいディレクトリに作り、復元後に必ず `cmp` で確認する

## 58. サブエージェントに委譲する作業で起きた、運用上の事故

### どういう時に問題が起こるか

実装・レビュー・リファクタリングをサブエージェントに委譲するとき。コードの内容以外の、**作業の進め方**に
起因する事故が起こる。パターン12・33 の続き。

### 原因と対策

1. **フォーマッタをディレクトリ単位で実行する**: `npx prettier --write src/renderer/src/components` の
   ように範囲を広く指定すると、その機能と無関係な既存ファイルまで再整形され、差分に紛れ込む(過去に
   無関係な 16 ファイルが再整形された)。依頼文に「prettier は変更・新規ファイルにだけ実行する。
   ディレクトリ全体に実行しない」と明記し、最後に `git status` で無関係なファイルが無いことを確認させる
2. **ミューテーションの退避先の取り違え**: パターン57 のとおり。退避先は `mktemp -d` で毎回新規に
   作らせる。事故が起きたときは、手で戻した後に、テスト全件と個別の再実施で確認させる
3. **リポジトリの状態を変える git 操作**: コミット前の作業ツリーで `git stash` / `git checkout` /
   `git add` を実行すると、未コミットの作業が消えたり混ざる。依頼文で禁止し、検証は `cp` ベースの手順に
   する。なお、一時リポジトリの中で `git stash` を試すテストは問題ない
4. **成果物の所在**: サブエージェントが「ファイルを用意した」と報告しても、実際には存在しない場合がある
   (レビューの本文 JSON が scratchpad に無かった)。受け取った側は、報告のパスを実際に読み込めるか
   確認し、無ければ報告の内容から作り直す
5. **作成者と同じアカウントによる承認**: 自分の PR に対する `APPROVE` は、GitHub 側の制約と、権限の
   分類器による制約の両方で拒否されうる。拒否されたら、別の手段(同じ結果を得る `COMMENT`)で回避せず、
   ユーザーに選択肢を示して明示的な許可を得る。許可を得たうえで、「Approve 相当」と本文に明記した
   `COMMENT` として投稿する
6. **同時に動かす実装者の担当範囲**: ファイルが重ならない 2 人(main 側と renderer 側)を並行で動かす
   場合は、依頼文で担当範囲を限定し、全体のテスト(`npm test`)は自分の担当分だけを実行させて、全体の検証は
   統括側が最後に 1 回行う。途中の状態で全体を実行すると、相手の作業中の状態でテストが落ちる
7. **作業ログの置き場所**: 報告書や中間ファイルをリポジトリ内に作らせると、未追跡ファイルとして残る。
   scratchpad など、リポジトリ外に置かせる。作業用のワークスペースは、最終レビューが済んだら消す

### 汎用的な対策

- 依頼文に、**やってよいこと・いけないこと**(コミットしない、対象外のファイルを触らない、フォーマッタの範囲、
  git 操作の禁止、報告先の場所)を明記する
- サブエージェントの報告は、**事実確認**(実際のファイルの有無、テストの再実行、`git status`)を挟んで
  から信用する
- 権限や承認が必要な操作は、分類器や環境に拒否されたら、回避せずにユーザーへ戻す

## 59. 入力の検証に使う「解釈」と、実行に使う「解釈」が別々で、食い違う

### どういう時に問題が起こるか

信頼できない入力(IPC で届く任意のパッチ、ユーザー入力のパス)を、ある手段(正規表現、`--numstat` などの
別コマンド)で検証してから、別の手段(`git apply` 本体)で実行するとき。**検証側と実行側が同じ入力を同じように
読むとは限らない**ため、検証を通った入力が、検証が見ていない場所に作用する。

### 原因

今回見つかった抜け穴は 2 つとも、この構造だった。

1. **検証が知らない書式**: `git apply` は `rename from <p>` / `rename to <p>` だけでなく、古い形式の
   `rename old <p>` / `rename new <p>` も受け付ける。検証は前者の正規表現しか見ていなかったので、後者で
   `diff --git a/evil.sh b/f.txt` + `rename old evil.sh` + `rename new f.txt` のパッチを作ると、検証は
   「対象は f.txt だけ」と判断し、実行は `f.txt` を消して `evil.sh` を新しく作った(リポジトリ内の存在しない
   任意のパスにファイルを作れる)。
2. **同じコマンドでも方向で結果が変わる**: 検証に使った `git apply --numstat` は、パッチを**順方向**に適用した
   ときの対象(new 側の名前)を返す。しかし実行は `--reverse` で、old と new が入れ替わる。
   rename 行が無くても `diff --git a/other.txt b/f.txt` + `--- a/other.txt` + `+++ b/f.txt` のパッチなら、
   numstat は `f.txt` だけを返して検証を通るのに、`--reverse` で適用すると `f.txt` が消えて既存の
   `other.txt` が上書きされた。**検証コマンドの方向・オプションが、実行と同じでなければ意味が無い。**

加えて、ブラックリスト(危険な行を拒否する)方式は、書式のバリエーションが無数にあるため、必ず穴が残る。

### このプロジェクトでの実例

- パッチの構造を**許可リスト**で検証する関数(`assertHunkPatchTargets`)にした。許可するのは、
  `diff --git a/<p> b/<p>`(a と b が同じで対象と一致)を 1 つ、`index`、`--- a/<p>` / `+++ b/<p>`(削除は
  `/dev/null`)、`@@` の見出しと行数が一致するハンクだけ。それ以外(`rename`、`copy`、`similarity`、
  `Binary files`、`@@` より前の未知の行など)は**すべて拒否**する
- `git apply --numstat -z` を**順方向と逆方向の両方**で実行し、どちらの対象も対象ファイル 1 つだけであることを
  求める(多層防御)
- 日本語のパスは `core.quotepath` の既定で引用符つき(8 進エスケープ)になるため、デコードして比較する
- 悪意あるパッチ(rename の 2 形式、a/b 不一致、複数ファイル、ヘッダーの紛れ込み、行数のごまかし)を一時
  リポジトリで実際に作り、**どのファイルも変化しない**ことを統合テストで固定した

### 汎用的な対策

- 検証と実行を別の手段で行うときは、**検証が見ている対象と、実行が書き換える対象が同じか**を、実際に攻撃する
  入力を作って確かめる。コマンドの方向(`--reverse`)やオプションが検証と実行で揃っているかを必ず見る
- 信頼できない構造化入力は、**許可リスト**で形そのものを限定する。「危険な書式を探して拒否する」方式にしない
- 可能なら、検証に使ったものと同じ値(正規化・加工後のパッチ)を実行にも渡し、検証と実行で別の入力を
  読まないようにする
- 外部コマンドの「古い形式・別名の書式」をドキュメントや実機で洗い出す(パターン7, 8)

## 60. 入力が同じ事実を複数の場所に書いているとき、片方だけ検証すると他方で抜ける

### どういう時に問題が起こるか

構造化された入力の中で、**同じ情報が 2 か所以上に書かれている**とき。片方だけを検証・制限して満足し、
実行側が**もう片方**を採用すると、制限が無効になる。

### 原因

削除されたファイルのハンクを復元するパッチは、ファイルの種類(モード)を 2 か所に持つ。

```
deleted file mode 100644
index 1234567..0000000 120000
```

検証は `deleted file mode` を `100644` / `100755` に限った(`120000` のシンボリックリンクや `160000` の
サブモジュールを拒否するため)。しかし `git apply` は **`index` 行のモードを old_mode として採用する**。
そのため `deleted file mode 100644` を満たしたまま `index` 行に `120000` を書くと、制限をすり抜けて、通常の
ファイルが任意の参照先(`../../../../../../Users`)のシンボリックリンクとして復元された(実機で再現)。

モード変更のパッチ(`old mode` / `new mode`)も同じ型だった。許可リストが `old mode` / `new mode` を
拒否していると、`chmod +x` した実在のファイルの diff が、原因と無関係な文言(「パッチの対象がファイルと
一致しません」)で必ず失敗する(パターン61)。

### このプロジェクトでの実例

- 削除パッチの `index` 行にモードが付く場合は、`deleted file mode` と**一致**することを要求し、不一致
  (`120000` / `160000` / `100755` との食い違い / 形式不正)を拒否した。モードが付かない `index abc..0000000`
  は許可する(実際の git の削除 diff はこの形)
- 変更ファイルの `old mode` / `new mode` は、`old` → `new` の 1 組だけを許可して、検証後に**取り除いて**から
  適用する(内容だけが戻り、モードは残る)。正規化して 1 つの形にしてから使うと、片方を見落とす余地が減る

### 汎用的な対策

- 入力の仕様を読むとき、「**同じ事実が何か所に書かれているか**」を数える。複数あれば、すべてを検証するか、
  1 つの正規形に直して他を捨ててから実行する
- 実行側(`git apply` など)が、複数の候補のうちどれを採用するかを実機で確かめる(行の順序、後勝ち・先勝ち)
- 拒否のテストは、**片方を満たしたまま、もう片方だけを不正にした**入力で書く

## 61. 許可リストが、実在する正常な入力を拒否し、原因と無関係な文言で失敗する

### どういう時に問題が起こるか

信頼できない入力を許可リストで絞ったとき、リストが**現実に存在する正常な入力の書式**を網羅していないと、
正しい操作が必ず失敗する。しかも、失敗の文言が「別の検査の文言」を流用していると、原因が分からない。

### 原因

許可リストはセキュリティ上は安全側に倒れるが、**ユーザーから見ると故障**になる。今回は、

- `chmod +x` したファイルの diff には `old mode 100644` / `new mode 100755` が入る。許可リストにこの
  書式が無く、ボタンは表示されるのに、押すと必ず「パッチの対象がファイルと一致しません」で失敗した。
  ファイル名は正しいので、利用者にもテスト担当者にも原因が分からない
- 追跡中のシンボリックリンクを作業ツリーで削除すると、git 自身の diff は `deleted file mode 120000` になる。
  パターン60 の修正で削除モードを `100644` / `100755` に限ったため、このハンクの取り消しも同じ文言で失敗する

どちらも、レビューで「ボタンが出るのに必ず失敗する」状態として見つかった。**ボタンの表示条件**(何を
許可するか)と**サーバー側の許可リスト**(何を拒否するか)が、別々に決められていたことが根にある。

### このプロジェクトでの実例

- モード変更行は取り除いて適用するようにして、正常系にした(パターン60)
- シンボリックリンクの削除のハンクは、**既知の制約**として設計書に記録した(ファイル単位の取り消しなら
  戻せる)。拒否の理由が見える文言への分離は今後の課題
- 許可リストのテストに、**実際の git の出力から作った正常なパッチ**(複数ハンクの 1 つ、削除、日本語パス、
  CRLF、末尾改行なし、モード変更)を必ず入れた

### 汎用的な対策

- 許可リストを作ったら、**実際のツールが出力する正常な入力**(実機で `git diff` を取って得た実物)を
  すべて通すテストを書く。拒否のテストだけでは「正しい操作が壊れる」ことに気づけない
- UI のボタンの表示条件と、サーバー側の拒否条件は同じ判定を共有する(パターン47)。共有できないなら、
  差が出る範囲を既知の制約に書く
- 拒否の文言は**拒否した理由ごと**に分ける。複数の検査で 1 つの文言を使い回さない

## 62. 確認した対象と、実行する対象が同じかを、件数だけで照合する

### どういう時に問題が起こるか

破壊的な操作の前に確認ダイアログで「N 件を取り消しますか？」と見せ、承諾後に実行するとき。
確認した時点の状態と実行する時点の状態の間に時間差があり、その間に状態が変わりうる。**件数だけを
照合していると、件数が同じまま中身が入れ替わった場合に、確認していないものが処理される。**

### 原因

一括取り消しは、確認時の件数 `expectedCount` と、実行時に `git status` から作り直した対象の件数だけを
比べていた(パターン53 の対策のうち、「状態が変わったら中止する」を件数で代用した)。次のように、件数が
同じまま対象が変わる:

1. 確認時: 未追跡の `scratch.txt` が 1 件(確認ダイアログは「1 件」)
2. ダイアログが開いている間に、外部ターミナルで `git add scratch.txt && echo work >> a.txt`
3. 実行時: `scratch.txt` はステージ済みになり「変更」から消え、代わりに編集された `a.txt` が 1 件
4. 件数は 1 件のままなので照合を通り、`a.txt` の編集が `restore --worktree` で**復元できない形で消えた**

アプリ内の操作は同期の `confirm()` で止まるため割り込まないが、外部ターミナル、並行して動く AI
エージェント、renderer が持つ古い `gitStatus` などから、現実に起きる。さらに、**パスの集合だけで
照合しても足りない**。同じパスで状態だけが変わる(`?? x.txt` → `AM x.txt`)と、集合は同じなのに
ゴミ箱へ移すはずのものが、編集を含むものに変わる。

### このプロジェクトでの実例

- 引数を `expectedCount` から、確認時に見せた対象の一覧 `{ path, status }[]`(`status` は index と
  workingDir の 2 文字)に変えた。main は実行時の `git status` から同じ形の一覧を作り、**パスでソート
  した配列として完全一致**で照合する。不一致なら、分類より前に、何も変えずに中止する
- 検討して採らなかった案: パスの `Set`(重複件数が落ちる)、ハッシュ(ローカルの IPC では利点が無い)、
  「ゴミ箱へ移すか」の有無をキーにする(` R` があるだけで常に中止になる)
- 実 git の統合テストに、「同じ件数で中身が入れ替わる」「同じパスで状態が変わる」を拒否するケースを追加し、
  照合を件数だけに戻すと 4 件が落ちることを確認した

### 汎用的な対策

- 「確認した対象」と「実行する対象」の同一性は、**件数ではなく、対象そのものの識別子の集合と、その状態**で
  照合する。状態が処理の分岐(ゴミ箱 / 復元)を決めるなら、状態もキーに含める
- 照合に使う一覧は、**確認ダイアログを作った元データそのもの**(同じ関数・同じ定義)から作る(パターン50, 63)
- 照合の失敗は安全側(何も変えずに中止)に倒し、利用者には「もう一度操作してください」と伝える

## 63. 同じ集合を 2 つの実装が数えるとき、正規化のずれで「常に中止」または「一致してはいけないものが一致」になる

### どういう時に問題が起こるか

照合のために、**独立した 2 つの実装**(renderer が simple-git の解析結果から作る一覧と、main が自前で
`git status --porcelain -z` を解析して作る一覧)が、同じ集合を作らなければならないとき。1 つでも表記の
ずれがあると、その入力で**毎回「状態が変わった」と中止される**(正しい操作が永久にできない)。

### 原因

今回見つかったずれは、「自前の解析の不具合」と「ライブラリ(simple-git)が入力を加工する範囲との差」の
2 種類だった。

1. **リネーム(` R`)の旧パス(自前の解析の不具合)**: `git add -N` した後にリネームすると、`git status -z` は
   ` R new-name.txt\0old-name.txt\0` を出す(index が空白で、**workingDir 側**が `R`)。自前の解析は
   index が `R`/`C` のときだけ旧パスの要素を読み飛ばしていたため、旧パスを別のエントリとして読み
   (先頭 3 文字を落として `-name.txt`)、main は 2 件、renderer は 1 件と数えた
2. **末尾のスラッシュ**: ネストした git リポジトリは `sub/` と出る。simple-git は `sub/` のまま返すが、
   初版の照合キーは自前の解析が末尾の `/` を削った値(`sub`)を使っていたため、キーが `sub/` と `sub`
   に分かれていた。修正は「照合キーでは `/` を残す」ことだった(実行に使うパスだけ `/` を削る)
3. **空白の削り方**: 初版は両端を `trim()` した。しかし simple-git が削るのは**末尾の空白だけ**で、
   先頭の空白は残す。そのため先頭が空白のパス(未追跡の ` lead`、全角空白で始まる `　zen`、`AM` の
   先頭空白パス)で毎回不一致になった。これは、最初の修正(件数 → 一覧)で入った**退行**で、
   2 周目のレビューで見つかった
4. **ライブラリ自体の解析の制約**: 名前が空白だけのファイル(simple-git が行ごと読み捨てる)、
   `status.renames=copies` でコピー元のパスの 2〜3 文字目に空白がある場合(コピー元を別の行と誤って読む)。
   また、index が空白でパスの先頭も空白の ` M  lead` は、simple-git が行頭を `trim()` してステータスが
   ずれ、renderer の一覧に出ない

### このプロジェクトでの実例

- `parseUnstagedStatusEntries` が、index または workingDir のどちらかが `R`/`C` のときに旧パスを読み飛ばす
  ようにした(原因の 1.)
- 照合キーは「**末尾の `/` は残し**(simple-git の `sub/` に合わせる)、**末尾の空白だけ**を削った生パス」と
  2 文字のステータスの組にした。実行に使うパスは、末尾の `/` を削った解析の値(`path`)で、照合キーとは別
- 統合テストで、**renderer と同じ作りの一覧**(simple-git の `status().files` に `isUnstagedFile` を
  当てたもの)を期待値として組み立て、`sub/`、末尾空白、先頭空白(半角・全角)、` R`、`RM`、`AM`、
  `status.renames=false`、日本語・空白を含むパスで、main の一覧と一致することを確認した。タブ・引用符・
  改行を含むパスは、解析の単体テスト(改行のみ)で見ているだけで、simple-git との突き合わせは
  テストで固定していない
- 原因の 4. のうち、安全側(常に中止される)で実運用に出にくいもの(空白だけの名前、`renames=copies`、
  ` M  lead`)は、設計書の「既知の制約」に記録した(パターン48)。原因の 1. は自前の解析の不具合で、
  修正済みのため既知の制約には入っていない

### 汎用的な対策

- 2 つの実装が同じ集合を作る設計にしたら、**実環境で 2 つを並べて比較するテスト**を書く。期待値を手で
  書かず、片方の実装(今回は renderer が使う simple-git)の出力から作る
- 正規化は**最小限**にする。「念のため `trim()`」は、ライブラリが削らない側の空白を削って不一致を生む。
  ライブラリが何を削るかを、実際の出力で確かめる
- 表記の特殊ケースの一覧を作る: 末尾 `/`、先頭・末尾の空白、全角空白、タブ・改行・引用符、リネーム・
  コピー(両方の列)、`core.quotepath` / `status.renames` などの設定違い、macOS の NFC/NFD
- 照合の失敗が「常に中止」になる方向の不具合は安全だが、**正しい操作が永久にできなくなる**ので、
  既知の制約として記録するか、直す

## 64. 確認文言が、実際の副作用の差を伝えていない

### どういう時に問題が起こるか

確認ダイアログの文言を、操作の「種類」ごとに共通の言い回しにまとめたとき。**同じ種類として数えたものの
中に、副作用の大きさが違うものが混ざっている**と、利用者は実際より小さな操作だと誤解して承諾する。

### 原因

一括取り消しの確認文言は「うち N 件の未追跡ファイルはゴミ箱へ移動します。」だった。しかし未追跡の
ネストした git リポジトリ(`?? sub/`)は、`.git` を含む**フォルダ全体**がゴミ箱へ移る(未 push の
コミットも一緒に)。ファイル単位の取り消しの確認文言には「フォルダとその中身がすべて移動します。」が
あったのに、一括の文言にはその区別が無く、2 つの確認文言が揃っていなかった。

### このプロジェクトでの実例

- ゴミ箱へ移す対象のうち、パスが `/` で終わるもの(フォルダ)を `folderCount` として数え、1 件以上なら
  「うち K 件はフォルダ（git リポジトリ）で、フォルダとその中身がすべて移動します。」を足した
- 文言は完全一致のテストで固定した(`folderCount` が 0 のとき・1 以上のとき、フックで `?? sub/` を含む
  とき)
- ` R`(intent-to-add のリネーム)が main ではゴミ箱へ移す扱いなのに、確認文言の件数には数えられない
  ずれも見つかり、既知の制約に記録した

### 汎用的な対策

- 確認文言は、**実際に起きる副作用を分類ごとに列挙**して書く(件数だけでなく、「フォルダごと」「履歴の
  あるものを失う」などの大きさの差)
- 単位の違う操作(ファイル単位 / 一括)の確認文言は、同じ副作用に対して同じ表現を使う。片方を直したら
  もう片方も見る(パターン34, 47)
- 確認文言に使う「分類」の判定(`movesToTrashOnDiscard` など)は、実行側の分類と同じ定義を共有し、
  ずれる範囲を既知の制約に残す

## 65. 手動テスト仕様書(生成物を含む)は、実コードと突き合わせて検証し、検査テストを付ける

### どういう時に問題が起こるか

実機確認の手順を、実コードを読んだサブエージェントが書いたとき。**実際に動かさずに書かれた期待結果は、
実在しない UI や、実際と違う挙動を前提にしやすい。** 仕様書が間違っていると、確認する人が「アプリの
不具合」と「仕様書の誤り」を区別できず、時間を失う。

### 原因

712 項目の仕様書を、領域ごとに別の担当が書いた。検証の結果、約 40 件が実際と食い違っていた。主な型:

1. **存在しない操作を前提にする**: アプリは暗色固定でテーマ切替が無いのに、「テーマを切り替える」手順の
   項目が 8 件あった
2. **あるはずの挙動を仮定する**: 「ブランチ切替・マージ後にファイルツリーが更新される」「プル後にエディタ
   タブが再読込される」と書かれていたが、実際は更新されない(ROADMAP にも未対応と書いてある)。
   「プッシュ中にフェッチが止まる」など、排他の範囲も実際と違った
3. **自動で起きる後処理を見落とす**: 最後のハンクを取り消すと、diff タブは「差分はありません」を
   表示するのではなく、**自動で閉じる**(状態が変わると未ステージの diff タブを閉じる処理がある)
4. **別の層の文言を書く**: コンフリクト中の一括取り消しの期待結果が、ファイル単位の文言
   (「コンフリクト中のファイルは取り消せません」)になっていた。一括では「取り消せないファイルがあるため、
   何も取り消しませんでした（…）」が出る
5. **画面に出ない文言を操作対象に書く**: `aria-label` だけで画面に出ないボタンを「表示名」として書いた
6. **生成物の安全性**: 仕様書から HTML を生成するスクリプトは、項目の文字列を HTML に埋め込む。
   `escapeHtml` を通らない経路があると、仕様書に書いた文字列で壊れる

### このプロジェクトでの実例

- 書いた担当とは**別のレビュアー**が、全項目を実コード(`grep` で表示文言・`aria-label` を機械的に照合)
  と突き合わせ、食い違いと「確認不能」(OS ダイアログの見た目、Monaco の操作など)を分けて報告した。
  食い違いは実際の挙動に直し(ID は不変)、アプリ側の未対応は「現状の挙動」を期待結果にした。直した項目を
  さらに別のレビュアーが再検証した
- 生成スクリプトには、解析(`parseSpec`)・HTML 生成・ブラウザ側のチェック動作のテストと、**実物の仕様書
  を検査するテスト**(ID の一意性、接頭辞ごとの昇順、1 つの接頭辞は 1 つの領域だけ、手順と期待結果の
  存在)を付けた。書式を間違えて追記すると、テストが落ちる
- 運用は CLAUDE.md に書いた(機能を開発するたびに追記する、ID は不変、削除は欠番を許容する)

### 汎用的な対策

- 実機の手順書は、書いた人とは**別の人(別のエージェント)が、実コードと照合**してから公開する。
  「確認不能」の項目は、確認不能と明記して実機に回す
- 「実機でこう動くはず」という期待は、**コードで根拠(file:line)を引ける**ものだけを書く
- アプリに無い機能(テーマ切替など)を書かない。自動で起きる後処理(タブが閉じる、再読込される)を
  期待結果に含める
- 手順書の書式は**機械的に検査**する(ID の一意性・連番・区切りの有無)。生成物(HTML)は、入力を必ず
  エスケープし、保存先(`localStorage`)が使えない場合のフォールバックを持たせる
- 画面に出る文言と `aria-label` を区別して書く

## 66. 破壊的な一括操作を設計するときのチェックリスト

### どういう時に問題が起こるか

「N 個のものをまとめて取り消す・削除する・移す」操作を新しく作るとき。1 件ごとの操作を単純に繰り返す
だけでは、一括に固有の失敗(一部だけ成功、対象のずれ、確認と実行の乖離)を防げない。この機能の
レビューで見つかった問題は、ほとんどが一括の設計の見落としだった。

### 原因と対策(チェックリスト)

| 観点               | 失敗の例(このプロジェクト)                                          | 対策                                                                                     | 関連   |
| ------------------ | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------ |
| 対象の決定         | renderer の古い一覧を信用して、見せていないものを処理する           | 実行時に main が状態から対象を作り直す                                                   | 53     |
| 確認と実行の同一性 | 件数だけの照合で、中身が入れ替わる                                  | 識別子 + 状態の一覧をソートして完全一致で照合し、不一致は何も変えずに中止                | 62     |
| 2 つの実装の一致   | リネーム・末尾 `/`・空白の扱いが、renderer と main でずれて常に中止 | 実環境で並べて比較するテスト。正規化は最小限                                             | 63     |
| 全か無か           | 1 件が取り消せないのに、他の件を先に実行する                        | 実行の前に全件を分類し、1 件でも不可なら何もしない                                       | 38, 51 |
| 途中失敗           | 済んだものの分だけ作業ツリーが変わり、タブとツリーが古い            | 済み 1 件以上の失敗は例外でなく結果型で返し、再読込する。0 件は throw                    | 52     |
| 確認文言           | ネストしたリポジトリがフォルダごと移ることが分からない              | 副作用の差を分類ごとに列挙する                                                           | 64     |
| 排他               | 実行中に push/ステージ/ブランチ操作と重なる                         | 全体ロックを、確認・破棄の確認の**後**、実行の直前に取る。確認の拒否ではロックを取らない | 23     |
| 未保存編集         | 一括で全タブが再読込され、編集が消える                              | 破棄の確認を挟み、成功時だけ再読込する                                                   | 19, 20 |
| 戻せなさ           | ゴミ箱は戻せるが、restore は戻せない                                | 毎回確認し、戻せない範囲を文言に明記                                                     | 54     |

### 汎用的な対策

- 一括操作は、「対象の決定 → 確認 → 照合 → 全件の事前検証 → 実行 → 部分成功の扱い → 再読込」を
  1 つの流れとして設計し、各段階の失敗を表にして、段階ごとにテストを書く
- 同じ流れを持つ既存の機能(退避の復元、ブランチのマージ)の結果型・ロック・再読込の作りを、先に
  読んで揃える

## まとめ: レビューでこれらを見つけるための着眼点

上記のパターンに共通する見つけ方のコツを最後に整理する。

- **「確認してから使う」の間に`await`があれば、その間に何が起こりうるかを疑う**
  (パターン1)
- **ストリーム・チャンク分割・エンコーディングが絡む処理は、境界条件(ちょうど
  分割される場合)を明示的にテストする**(パターン2, 3)
- **同じ状態を複数の経路から更新できる設計は、「後から始めた処理が必ず勝つ」ことを
  保証する仕組みがあるかを確認する**(パターン4, 5)
- **「1つだけ変化する」ことを前提にしたコードは、複数同時に変化するケース
  (一括削除・一括更新)を必ず疑う**(パターン6)
- **外部フォーマット(gitの出力、DSLの構文)を扱うコードは、そのフォーマットの
  「特殊なケース」を一度は公式ドキュメント・実機で洗い出してから実装する**
  (パターン7, 8, 11)
- **環境依存(ロケール、タイムゾーン)の挙動に依存するAPIは、明示的に固定するか、
  依存を意図的に許容するかをコードで判断できる形にする**(パターン9)
- **外部プロセス・外部サービスとのやり取りには、必ず失敗・無応答時の
  タイムアウトと後始末を設計に含める**(パターン10)
- **AIエージェントへの指示は、目的だけでなく実行してよい範囲の境界を明示する**
  (パターン12)
- **外部ライブラリの安全機構(タイムアウト等)は、ドキュメントだけでなくソース
  コードで「何を監視し、何に依存しているか」を確認する**(パターン13)
- **同じ業務ルールをUI層とロジック層に別々に書かない。判定結果を1箇所で計算し、
  他はそれを使うだけにする**(パターン14)
- **既存の排他制御に新しい操作を加えるときは、「何を書くか」だけでなく「何を
  読むか、それを他の操作が書き換え中でないか」を検討する**(パターン15)
- **テストがgreenであることと、対象のロジックを検証できていることは別。
  ミューテーションでテストの検知力そのものを確認する**(パターン16)
- **動的に変化するUIの表示とアクセシビリティ属性(aria-\*)は同期させる。可能なら
  aria-label自体を付けずテキストコンテンツに語らせる**(パターン17)
- **外部ライブラリの内部エラーメッセージは、型やプロパティで判別してから、
  狭い範囲だけユーザー向けの文言に変換する**(パターン18)
- **ディスクを一括で書き換える操作(checkout、pull等)は、メモリ上のコピー(エディタの
  バッファ等)への影響を、操作の前(未保存編集の扱い)と後(dirtyかどうかを問わない
  再同期)の両方で設計する**(パターン19)
- **エラーを例外にしない関数は、成否を戻り値でも伝える。特に破壊的な後続処理は、
  成功時のみ実行する**(パターン20)
- **信頼境界を越えた値をCLI引数へ渡すときは、シェルの有無に関わらずオプションとして
  解釈されうるかを疑い、許可リストで検証する**(パターン21)
- **キーボードで開けるポップオーバーは、開いたら中へ、閉じたらトリガーへフォーカスを
  移す。ただし外側クリックでは戻さない。参考にする実装は入力手段が同じものを選ぶ**
  (パターン22)
- **排他制御は「Aの実行中にB」「Bの実行中にA」を別々に分析し、方向ごとの結論と
  スコープ外の競合の根拠をコメントに残す**(パターン23)
- **外部ツールの検証を通った値でも、実際に使うコマンドでは別名・特殊記号として解釈され
  うる。境界の値は作成して終わりではなく、後続の操作(切り替え等)まで実機で試す**
  (パターン24)
- **正規化を伴う検証は、成功したことに加えて、正規化後の値が入力と一致することを
  確認する**(パターン25)
- **階層構造で保存される名前は、完全一致の重複に加えて、区切り文字で親子になる衝突も
  検査する。衝突しない前方一致の例もテストに入れる**(パターン26)
- **外部コマンドの出力を行で分割したら、行末の `\r` を取り除く。解析は純粋関数に
  切り出して CRLF の入力をテストする**(パターン27)
- **原因ごとに対応が違うなら、失敗のエラーから原因を逆算せず、実行前に構造化された
  問い合わせで条件を確かめる**(パターン28)
- **幅が内容で決まるポップオーバーに日本語のラベルを置くときは、折り返しを前提に
  nowrap や min-width を検討し、内容が短い状態でも見た目を確認する**(パターン29)
- **「同じ見た目」は CSS の宣言のコピーではなく、クラスの併用で実現する**(パターン30)
- **責務を切り出したら、元の単位のテストに残った同じ検証を移し、元の単位には配線の
  確認だけを残す。描画ヘルパーには Props の既定値を持たせる**(パターン31)
- **実装を変えたら、変更したシンボル名・機能名でコメントと設計書を検索し、関係する
  すべての節を更新する**(パターン32)
- **サブエージェントに委譲した作業は、コードの差分だけでなく、コミットのトレーラー等の
  メタデータまで検証する**(パターン33)
- **ガード条件を別の操作に適用したら、そのテストも操作ごとに書き、同じであるべき部分を
  固定する**(パターン34)
- **外部コマンドへの問い合わせは「出力があるか」ではなく「対象と一致するエントリがあるか」
  で判定する。パターンが前方一致として働かないかを確かめる**(パターン35)
- **破壊的なコマンドが対象以外に何を消しうるかを、配下・親・対象の位置の 3 方向で実機で
  確かめる**(パターン36)
- **パスの一致判定は、実際に操作する側と同じ大文字小文字の規則で行い、規則が環境で変わる
  なら止める側に寄せる**(パターン37)
- **安全確認の問い合わせが報告する範囲と、破壊的な操作が消す範囲の差を洗い出す**
  (パターン38)
- **破壊的な操作を選ぶ分類は肯定の根拠で決め、どれにも当てはまらなければ止める**
  (パターン39)
- **別のシステムの識別子としてのパスは、境界で正規化し直さずにそのまま渡す**(パターン40)
- **外部コマンドの挙動に依存する判定は、実物を使う統合テストでも固定し、そのテストを
  開発者の設定から切り離す**(パターン41)
- **外部コマンドには判定に必要な粒度で出力させる**(パターン42)
- **ユーザーが選んだ名前を外部コマンドへ渡すときは、名前が複数の参照に解決されうることを疑い、検証は実行と別の
  手段・別の経路で行う**(パターン43)
- **ライブラリの解析結果の真偽値を安全性の判定に使う前に、その値を立てる条件を確かめる。特殊な状態(rebase・
  bisect・am 等)を実機で作り、状態の判定は一次情報から取る**(パターン44)
- **外部コマンドの成否判定が前提とする動作(コミットまで行う、squash しない)は、引数で固定する。ユーザーの方針は
  上書きしない**(パターン45)
- **統合テストの環境(ロケール・ref の保存形式・グローバル設定)を明示的に固定し、前提の確認は出力の文言ではなく
  状態で行う。環境を変えて再実行する**(パターン46)
- **同じ検証が 3 か所目に出たら共通化し、共通化の後は重複した別名・テスト・コメントを残さない**(パターン47)
- **網羅しきれない例外的な状態は、再現手順・影響・見送りの理由をセットで「既知の制約」に記録する**(パターン48)
- **ユーザー入力をコマンドの引数へ渡すときは、フラグと値を 1 要素にまとめ、危険なオプションと同じ形の値を実物の統合テストで試す**
  (パターン49)
- **事前チェックと実行するコマンドは、同じ対象を同じ範囲で数える。判定の定義は 1 か所に置く**(パターン50)
- **破壊的な操作の前提を `status` が空であることだけで確かめない。コマンドが失いうる状態を一覧にし、一対の操作の検証を揃える**
  (パターン51)
- **多段階の操作は、「何も変えずに失敗」と「変えたうえで失敗・警告つき成功」を結果型で区別し、後始末は成否でなく状態の変化で決める**
  (パターン52)
- **一覧から選ぶ操作の識別子は不変の ID にし、実行直前に引き直し、結果の ID を照合して食い違えば元に戻す**(パターン53)
- **失敗時の巻き戻しは、前提の検証・全ステップの試行・残留物の把握をセットにし、戻せないものは記録する**(パターン54)
- **分割したあとに、複製されていたロジック・定義・テスト・文書を探して一本化する**(パターン55)
- **流用した汎用部品の固定文字列(aria-label 等)を洗い、用途ごとに指定できるようにする**(パターン56)
- **追加したテストは実装を壊して落ちることを確認し、警告だけで通るもの・後始末・失敗経路を固定する**(パターン57)
- **サブエージェントへの依頼文に禁止事項と範囲を明記し、報告は事実確認を挟んでから信用する。拒否された承認は回避せずユーザーへ戻す**
  (パターン58)
- **信頼できない入力は、検証と実行で同じ解釈・同じ方向・同じ加工後の値を使い、許可リストで形を限定する。実際に攻撃する入力で確かめる**(パターン59)
- **同じ事実が複数の場所に書かれた入力は、すべてを検証するか 1 つの正規形に直す。片方だけ制限しない**(パターン60)
- **許可リストは、実在する正常な入力(実機の出力)をすべて通すテストを付ける。拒否の文言は理由ごとに分ける**(パターン61)
- **確認した対象と実行する対象の同一性は、件数ではなく、識別子 + 状態の一覧の完全一致で照合する**(パターン62)
- **同じ集合を 2 つの実装が数えるなら、実環境で並べて比較するテストを書き、正規化は最小限にする**(パターン63)
- **確認文言は、分類ごとの実際の副作用の差を列挙する。単位の違う操作の文言を揃える**(パターン64)
- **手動テスト仕様書は、書いた人とは別に実コードと照合してから公開し、書式を機械的に検査する**(パターン65)
- **破壊的な一括操作は、対象の決定から再読込までを 1 つの流れとして設計し、段階ごとの失敗を表にして確認する**(パターン66)
