# エージェントが変更したファイルの確認導線 設計書

作成日: 2026-10-06 / 対象: ROADMAP の「エージェント実行の支援（MVP の次）」の「エージェントが変更したファイルの確認導線（ソース管理の変更一覧・diff へすぐ移る。変更を戻す）」

## 目的

MVP（`docs/superpowers/specs/2026-10-04-agent-terminal-mvp-design.md`）で、プロンプトの `実行` から `claude` がアプリ内のターミナルで作業を始め、ファイルを
書き換えるところまでが成立した。しかし、書き換えの後に「エージェントが何を変えたか」を確かめる手段は、ソース管理パネルの変更一覧（Git の差分すべて）しか無い。
この一覧には、実行の前から作業ツリーにあった利用者自身の未コミットの変更も混ざり、既存の取り消し（ファイル単位・ハンク単位・すべて）は作業ツリーを
**index の内容**へ戻すため、エージェントの変更だけを戻すつもりで利用者の編集まで消してしまう（確認の結果 9）。また、ソース管理パネルは外部の変更で
自動では更新されない（MVP の既知の制約）。

この機能では、エージェントの実行を始めた時点の作業ツリーを、利用者の index・stash・HEAD を変えずに記録し、その時点との差分を「エージェントの変更」として
一覧・diff に出し、実行前の内容へ戻せるようにする。コンセプトの「ファイル編集 → プロンプト実行 → Git 操作」の流れのうち、プロンプト実行と Git 操作の
間の「結果の確認」を埋める。

## 範囲

### 含める

- 記録の開始: プロンプトの `実行`（エージェント CLI 方式）で送る直前に、作業ツリーの状態を記録する（記録が無いときだけ。後述「複数回の実行」）。ターミナルに
  直接打ち込んで使う人のために、ソース管理パネルの `いまから記録する` でも始められる
- 一覧: ソース管理パネルの新しいセクション「エージェントの変更」に、記録の時点から変わったファイル（追加・変更・削除）を出す。押すと diff タブを開く
- diff: 記録の時点の内容 → いまの作業ツリーの内容の差分を、新しい種類の diff タブ（`<path> (エージェントの変更)`）で表示する
- 戻す: ファイル単位（変更・削除は記録の時点の内容へ、追加はゴミ箱へ）・ハンク単位（記録の時点の内容へ逆適用）・すべて。確認のダイアログを出し、
  成功したときだけ開いているタブとツリーを読み直す
- 記録の終了: `確認を終える` で記録を捨てる。フォルダの切り替え・リロード・ウィンドウの破棄・アプリの終了でも捨てる
- 導線: ターミナルパネルの見出しの帯に `変更を確認` を置き、押すとサイドバーのソース管理パネルを開いて一覧を取り直し、セクションへフォーカスを移す
- 実行中にアプリで保存したファイルの印（`あなたの保存を含む`）と、戻すときの確認文言への反映

### 含めない（ROADMAP に見送り項目として残す）

- エージェントの実行の完了・許可待ちの検知と、それを契機にした自動の表示・通知（ROADMAP の「セッションの状態表示」「完了・許可待ちの通知」。後述「いつ完了とするか」）
- 変更のリアルタイムの表示（実行中の逐次の更新）、ファイルの監視による一覧の自動更新
- 戻した操作の取り消し（undo。ゴミ箱へ移したファイルは OS のゴミ箱から戻せる）
- Git 管理外のフォルダ・リポジトリのサブフォルダを開いた場合の記録（理由を表示して使えなくする）

> 2026-10-15 に変更: Git 管理外のフォルダは、2026-10-15-agent-changes-non-git-folder-design.md で、アプリの一時領域の隠れた git に記録して使えるようにした。リポジトリのサブフォルダは今も対象外。この行は当時の判断。

- 実行ごとの記録の分割（実行 1・実行 2 を選んで比べる）、ステージ（index）・コミット・ブランチの巻き戻し
- ステータスバーへの表示（ステータスバーは固定の表示のままで、動的化は ROADMAP の別項目）、OS の通知
- 既存の「変更」セクションへの「エージェントの変更」フィルタ（後述「導線の UI」で比べて採らなかった）

## 設計の前提（利用者の決定）

- ROADMAP の項目の文言どおり「ソース管理の変更一覧・diff へすぐ移る。変更を戻す」を満たす
- MVP の安全策（起動の内容・作業ディレクトリは main が決める、IPC の入力の検証と送信元のフレームの確認、所有者〈webContents〉の分離）を踏襲する
- 以下の判断は設計書の推奨で、「決定した点」のとおり利用者の承認を得て確定した（2026-10-07）

## 完了条件（観察できる形）

Electron の実機（macOS）で、次がすべて観察できたら完了とする。手順は手動テスト仕様の新しい接頭辞 `AGC` の項目にする（後述の案）。

1. Git リポジトリを開き、未コミットの変更（ファイル X の 1 行）を作ってからプロンプトの `実行` を押す。エージェントが X の別の行とファイル Y を変え、
   ファイル Z を新しく作った後、ターミナルの帯の `変更を確認` を押すと、ソース管理パネルの「エージェントの変更」に X・Y・Z の 3 件が出る。X の diff には
   エージェントが変えた行だけが出て、実行の前からあった 1 行は出ない
2. X のハンクを戻すと、エージェントの行だけが消え、実行の前からあった 1 行は残る。開いている X のタブ（未編集）はディスクの内容に読み直される
3. Z を戻すと、Z が OS のゴミ箱へ移り、一覧から消える。`すべて戻す` で残りが記録の時点の内容に戻り、一覧が空になる
4. 戻す操作の前後で、利用者の index（ステージ済みの内容）・stash の一覧・HEAD・ブランチが変わらない（ソース管理パネルの「ステージ済み」「退避」「履歴」で確かめる）
5. `確認を終える` を押すと記録が消え、次の `実行` で新しい記録が始まる
6. Git 管理外のフォルダでは、セクションに使えない理由が出て、`実行` は従来どおり送れる

> 2026-10-15 に変更: Git 管理外のフォルダでも記録が始まり、リポジトリと同じ一覧・戻すが使える（2026-10-15-agent-changes-non-git-folder-design.md）。ファイルが多すぎるフォルダ・`.git` の中・bare リポジトリでは理由が出る。

7. 未保存の編集があるタブのファイルを戻そうとすると、確認の文言に未保存の編集の破棄が含まれ、キャンセルすると何も変わらない

## 確認の結果（設計時に実測。2026-10-06〜07）

macOS 26.6（arm64）・git 2.50.1（Apple Git-155）・simple-git 3.36.0・node v24.14.1・Claude Code 2.1.288 で、scratchpad の一時ディレクトリに作ったリポジトリと、
このリポジトリを `git clone --no-hardlinks` した写しで確かめた（このリポジトリの作業ツリー・`.git`・`node_modules` は変えていない）。git は
`GIT_CONFIG_GLOBAL=/dev/null`・`GIT_CONFIG_NOSYSTEM=1`・`LC_ALL=C` で、既存の Git の統合テスト（`realGitRepo.ts` の `isolatedGitEnv`）と同じく利用者の設定から
切り離した。`claude` は `--version`・`--help` だけを、隔離した設定ディレクトリ・ダミーの API キー・閉じたポート（`ANTHROPIC_BASE_URL=http://127.0.0.1:9`）で
実行し、API には接続していない（確認画面も出していない）。起動したプロセスはすべて終わり、`pgrep -fl` で残っていないことを確かめた（既存の
`claude --chrome-native-host` は実験の前からあったもので、触っていない）。

課題の指示にある SDD の `snap.sh` は、このマシンのリポジトリ・`~/.claude` の配下に見つからなかった。同じ手法（一時のインデックスで `git add -A` →
`git write-tree`）を自前のスクリプトで確かめた。

1. **`git stash create` は利用者の index を書き直す**: `stash create` の後、`.git/index` の更新時刻（ナノ秒）が毎回変わった（内容のハッシュは同じ。stat の
   情報を書き直している）。書き直しは `.git/index.lock` を取るので、同じ時刻にエージェントが `git add` すると、エージェント側が `index.lock` で失敗しうる。
   また `git stash create -u` は `-u` をメッセージとして扱い（件名 `On main: -u`、親 2 つ）、**未追跡のファイルを含めない**。記録の手段には使えない
2. **一時のインデックスで記録すると、利用者の状態を変えない**: `.git/index` を一時ファイルへ写し、`GIT_INDEX_FILE=<一時> git add -A` → `git write-tree` で、
   追跡済み・未追跡（ignore されていないもの）の作業ツリーの内容が 1 つの tree になった。前後で `.git/index` の更新時刻（ナノ秒）・内容のハッシュ・
   `git stash list`・`git for-each-ref`・HEAD・`git status` はどれも変わらなかった。ignore されたファイル（`ignored/x`）は入らなかった
3. **記録の時点との差分で、エージェントの変更だけを出せる**: 利用者が実行の前に未ステージの変更（`a.txt` に `unstaged`）・ステージ済みの変更（`b.txt`）・
   未追跡のファイル（`user-untracked.txt`）を持つ状態で記録し、その後に「エージェント」として `a.txt` に 1 行を足し、`d.txt` の 1 行を変え、`c.txt` を消し、
   `user-untracked.txt` を `moved.txt` へ移し、`new.txt`・`bin.dat`（バイナリ）・`ignored/gen` を作った。記録の tree といまの tree の差分は
   `M a.txt`・`A bin.dat`・`D c.txt`・`M d.txt`・`R100 user-untracked.txt moved.txt`・`A new.txt` で、`a.txt` の diff は `+agent` の 1 行だけだった
   （実行の前の `unstaged` は文脈の行）。`b.txt` は出ず、`ignored/gen` も出なかった。同じ時点の `git status` は ` M a.txt`・`M  b.txt`・` D c.txt`・
   ` M d.txt`・`?? bin.dat`・`?? moved.txt`・`?? new.txt` で、利用者の変更（`a.txt` の `unstaged`・`b.txt`）とエージェントの変更が区別できない
4. **実行中の利用者の編集は混ざる**: 記録の後に利用者が `b.txt` に足した行は、エージェントの変更と同じく差分に出た（Git の内容だけでは誰が書いたかは
   区別できない）
5. **記録のインデックスを残しておけば、いまの状態は書き込みなしで一覧できる**: 記録に使ったインデックス（以下「記録のインデックス」）を消さずに残し、
   `GIT_INDEX_FILE=<記録のインデックス> git diff --name-status --no-renames`（記録の時点 → いまの作業ツリーの、追跡済みの変更・削除）と
   `GIT_INDEX_FILE=<記録のインデックス> git ls-files -z --others --exclude-standard`（記録の後に現れたファイル）で、3 と同じ集合が出た（リネームは削除 + 追加に
   なる）。この方法は blob を書かない（未追跡のファイル 20,000 件を作った後に一覧しても、loose object の数は 20,214 のまま）。利用者の `.git/index` は
   変わらなかった
6. **速さ**（いずれも 2 回目以降の値。1 回目はキャッシュで多少遅い）:
   - 追跡済み 10,000 ファイルのリポジトリ: 記録（写し + `add -A`）0.038 秒、一覧（5 の 2 つのコマンド）約 0.07 秒。記録の後に未追跡の 20,000 ファイル
     （ignore されていない `node_modules/` を模したもの）と 50 ファイルの変更を作っても、一覧は `diff` 0.031 秒・`ls-files --others` 0.044 秒。
     `--directory` を付けると 20,000 件は `node_modules/` の 1 行になった（0.028 秒）
   - このリポジトリの写し（追跡済み 852 ファイル）: 記録 0.029 秒、一覧 0.035 秒、記録の写しからの `write-tree` 0.039 秒
   - **記録の時点で ignore されていない未追跡のファイルが多い・大きいと、記録は重い**: 中身の違う未追跡の 20,000 ファイルがある状態の `add -A` は
     1 回目 7.6 秒（blob を 20,000 個書き、`.git` が約 79MB 増えた）・2 回目 1.2 秒。200MB のランダムなファイルが 1 つある状態は 3.2 秒で、`.git` が
     約 195MB 増えた。`add -A -- . ':(exclude,literal)<path>'` で特定のファイルを除けた（除いたファイルは 5 の `ls-files --others` に「新しいファイル」として出る）
7. **記録のインデックスからの復元は作業ツリーだけを変える**: `GIT_INDEX_FILE=<記録のインデックス> git restore --worktree -- ':(literal)<path>'` で、
   `a.txt` は記録の時点の内容（実行の前の `unstaged` を含み、エージェントの行を含まない）に、消された `c.txt` と、エージェントが移した
   `user-untracked.txt`（実 index では未追跡）は記録の時点の内容で作り直された。利用者の `.git/index` は変わらなかった。記録の tree を `--source=<tree>` に
   渡す形でも同じ結果になったが、記録の時点に無いパス（エージェントが作った `new.txt`）は `error: pathspec 'new.txt' did not match any file(s) known to git`
   （終了コード 1）で、ファイルは残った（追加されたファイルは restore では戻せない）
8. **ハンクの逆適用**: 記録のインデックスでの `git diff --no-ext-diff --no-textconv --no-color --src-prefix=a/ --dst-prefix=b/ -U3 -- d.txt`（既存の
   `getDiff` と同じ形式の引数）の出力を、`git apply --reverse`（`--index`・`--cached` なし）で作業ツリーへ当てると、`d.txt` が記録の時点の内容に戻り、
   `.git/index` は変わらなかった。作った後に同じファイルへ 1 行足してから当てると `error: patch failed: a.txt:2`（終了コード 1）で何も変わらなかった。
   **新規ファイルのパッチ（`new file mode`）を `--reverse` で当てると、ファイルが削除された**（ゴミ箱を経由しない。終了コード 0）
9. **既存の取り消しは、エージェントの変更だけを戻せない**: 実行の前に `unstaged` の行があった `a.txt` に、エージェントが行を足した状態で、既存の
   ファイル単位の取り消しと同じ `git restore --worktree -- a.txt`（実 index から）を行うと、`a1 a2 a3` になり、**利用者の `unstaged` の行も消えた**。
   記録のインデックスから行うと `a1 a2 a3 unstaged` になった。既存のハンクの取り消し（`discardHunk`）は分類（`classifyDiscardTarget`）で未追跡のファイルを
   拒否し、一括の取り消し（`discardAllChanges`）は実 index の `git status` の全件との照合を必須にしているため、エージェントの変更の範囲に絞って呼べない
10. **既存の分類と重なりの検査は、記録のインデックスでそのまま使える**: `classifyDiscardTarget`・`overlapsUntracked` は `ls-files`・`ls-files --others -k --directory`・
    `diff --diff-filter=A` で index に問い合わせる作りで、`GIT_INDEX_FILE` を記録のインデックスにすると「記録の時点で追跡していたか」で判定する
    （`ls-files --others` は記録の後に現れた `moved.txt`・`new.txt` を返し、記録の時点からある `user-untracked.txt` は返さなかった）
11. **`restore` は、同じ名前のディレクトリに置き換わったファイルを、中身ごと消す**: 記録の時点にファイルだった `c.txt` を消して、同じ名前のディレクトリ
    `c.txt/x`（内容 `keep`）を作った状態で、記録の tree から `c.txt` を restore すると、終了コード 0 で `c.txt/` と `x` が消えてファイルに戻った（ゴミ箱を経由
    しない）。既存の取り消しの「未追跡と重なる」拒否（パターン 36）と同じ検査が要る
12. **`git gc --prune=now` の後は戻せず、ファイルが消える**: 記録のインデックスだけが参照する blob は、どの ref からもたどれない。記録の後に
    `git gc --prune=now` を実行すると、`restore` は `error: unable to read sha1 file of a.txt (…)`（終了コード 255）で失敗し、**作業ツリーの `a.txt` が消えた**
    （復元できずに削除だけが起きた）。既定の `git gc`（`gc.pruneExpire` は 2 週間）の後は戻せた。戻す前に `git cat-file -e <blob>` で blob の存在を確かめる
    必要がある（2026-10-13 の設計書 `2026-10-13-agent-changes-revert-undo-and-gc-protection-design.md` で、記録中は専用の ref から記録の tree をたどれるようにしたため、記録中の gc ではこの状態は起きなくなった。守りが効かない場合のために、戻す前の検査は残した）
13. **`git diff <tree>`（tree と作業ツリーの比較）は、利用者の index を書き直す**: `git diff --name-status <記録の tree>` の後、`.git/index` の更新時刻と内容の
    ハッシュが変わった（`git status` と同じ index の更新。実験の最初の `git status` の直後にも内容のハッシュが変わった）。また、この形は記録の tree にあって実 index に無いパス
    （`user-untracked.txt`）を削除として出し、記録の後に現れた未追跡のファイルを出さない。tree と tree の比較（`git diff <tree> <tree>`）・
    記録のインデックスでの `git diff`・`restore --worktree`・`apply`（`--index` なし）・`hash-object`・記録は、利用者の `.git/index` を変えなかった
14. **simple-git の `env()` は、利用者の環境変数で例外になる**: `simpleGit(repo).env({ ...process.env, GIT_INDEX_FILE })` は、この環境に `GIT_ASKPASS`
    （VS Code から引き継いだもの）があるため `GitPluginError: Use of "GIT_ASKPASS" is not permitted without enabling allowUnsafeAskPass` で失敗した
    （`gitService.ts` の `getLog` のコメントと同じ現象）。simple-git 3.36.0（`@simple-git/argv-parser`）が拒否する変数（`EDITOR`・`PAGER`・`GIT_ASKPASS`・
    `SSH_ASKPASS`・`GIT_SSH_COMMAND`・`GIT_CONFIG_*` など 18 個）を除いた環境に `GIT_INDEX_FILE` を足すと、例外にならず、記録のインデックスで問い合わせられた。
    `GIT_INDEX_FILE` 自体は拒否の対象ではない
15. **記録のインデックスは、コミットの無いリポジトリ・入れ子のリポジトリでも作れる**: コミットが 1 つも無いリポジトリ（`.git/index` もまだ無い）では、空の一時
    ファイルから `add -A` で記録できた。入れ子の git リポジトリ（`sub/`）は `warning: adding embedded git repository: sub` を出して gitlink（mode 160000）として
    入り、入れ子の側でコミットすると `M sub` として出た（中身の変更は出ない）
16. **gc の自動実行**: 記録・一覧（`add`・`write-tree`・`diff`・`ls-files`）では自動の gc は起きなかった（記録の後も loose object が 20,212 個のまま）。
    loose object が多い状態でのコミットの後には、自動の gc でパックされた（`commit` が `gc --auto` を起動する git の既定の動作。2 週間より新しい
    到達できない object は消さない）
17. **再帰の `fs.watch`（macOS・node v24）**: `{ recursive: true }` で、サブディレクトリの奥のファイルの書き込み・削除も届いた。5,000 ファイルを作ると
    5,003 件の通知になった。通知は「パスが変わった」だけで、変える前の内容は分からない
18. **`claude` の自前の手段**: `claude --help`（2.1.288）には `--continue`・`--resume`・`--settings`・`--bare`（hooks を読まない）などがあり、ファイルの変更の
    記録・巻き戻しの引数は無い。セッションの中のコマンド（巻き戻しの機能があるか）は、API に接続しないと確かめられないため**未確認**

以下の 19〜23 は、実装のプランの作成時（2026-10-07。同じ環境）に実測した結果である（プラン `docs/superpowers/plans/2026-10-06-agent-changes-review.md` の
「設計書との差異」の 1・5〜7）。

19. **simple-git が `env()` で拒否する変数に `GIT_CONFIG_GLOBAL` が含まれていた**: `@simple-git/argv-parser` の表の 18 個の変数に、`GIT_CONFIG_GLOBAL`・
    `GIT_CONFIG_SYSTEM`・`GIT_CONFIG` が含まれていた（他に `EDITOR`・`GIT_ASKPASS`・`GIT_EDITOR`・`GIT_EXEC_PATH`・`GIT_EXTERNAL_DIFF`・`GIT_PAGER`・
    `GIT_PROXY_COMMAND`・`GIT_SEQUENCE_EDITOR`・`GIT_SSH`・`GIT_SSH_COMMAND`・`GIT_TEMPLATE_DIR`・`GIT_CONFIG_COUNT`・`PAGER`・`PREFIX`・`SSH_ASKPASS`）。
    確認の結果 14 のとおりこれらを除くと、記録のインデックスの git は `GIT_CONFIG_GLOBAL` を受け取れず、既定の場所（`~/.gitconfig`・
    `$XDG_CONFIG_HOME/git/config`）の設定を読んだ。そのため、実 git の結合テストは `HOME`・`XDG_CONFIG_HOME` も一時ディレクトリへ向けて隔離した
20. **記録の時点のファイルが同じ名前のフォルダに置き換わると、`ls-files --others` にフォルダの中身が出なかった**: `c.txt` を消して `c.txt/x` を作ると、
    一覧は `D c.txt` だけだった。`c.txt` を戻す操作は、既存の重なりの検査で拒否された（確認の結果 11。フォルダの中身は消えなかった）
21. **`git cat-file -e <sha>` は、blob が無いときに simple-git で resolve した**: 無いときは stderr が空・終了コード 1 で終わり、simple-git の `raw` は
    reject せずに空文字で resolve した（`rev-parse -q --verify` と同じ）。`cat-file -e` では存在の検査がすり抜けた（変異で確かめた）。`git cat-file -t <sha>`
    は、無いときに `fatal` で reject し、あるときは `blob` を出した
22. **blob が消えた後は、変更の一覧の取得が失敗した**: 記録の後に作業ツリーで変わったファイルの blob が消えていると、`git diff --name-status` 自体が
    `fatal: unable to read <sha>` で失敗した。そのため、この失敗を `実行前の内容が見つかりません（git gc などで消えた可能性があります）` に置き換えて出す。
    確認の結果 21 の `cat-file -t` の検査が効くのは、一覧が取れる削除（`D`）・種類の変更のときである
23. **`--pathspec-from-file` で除外を渡せた**: `git add -A --pathspec-from-file=<ファイル> --pathspec-file-nul` で、除外の pathspec（`:(exclude,literal)<path>`）
    が効いた（git 2.50.1）。除外が多くても引数の長さの上限に触れないため、`add -A -- . <除外>` の代わりにこの形で渡す（ファイルは一時ディレクトリに `wx`
    で作る）

## 何を「エージェントが変更したファイル」とみなすか

### 選択肢の比較

| 案                                                         | 内容                                                                                                                           | 良い点                                                                                                                                                                                                                | 問題                                                                                                                                                                                                                                              |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| (a) 実行の開始の時点の記録と、いまとの差分（推奨。改良版） | 実行の直前に、作業ツリーの内容を記録のインデックスへ入れて残す。一覧・diff・戻すは、記録のインデックスと作業ツリーの比較で行う | 実行の前からあった利用者の未コミットの変更が差分から外れる（確認の結果 3）。戻す先が「実行の前の内容」になり、利用者の編集を消さない（確認の結果 9）。利用者の index・stash・HEAD を変えない（確認の結果 2・5・7・8） | 実行中の利用者の編集は区別できない（確認の結果 4）。記録の時点に ignore されていない未追跡のファイルが多い・大きいと重い（確認の結果 6）。記録の blob は gc で消えうる（確認の結果 12）。Git のリポジトリが要る                                   |
| (b) ソース管理の変更一覧（Git の差分すべて）               | 既存の「変更」「ステージ済み」をそのまま見せる                                                                                 | 新しい仕組みが要らない。既存の diff タブ・取り消しがそのまま使える                                                                                                                                                    | 利用者の未コミットの変更とエージェントの変更が混ざる（確認の結果 3）。既存の取り消しは index の内容へ戻すので、エージェントの変更だけを戻すつもりで利用者の編集まで消す（確認の結果 9）。「エージェントの変更」と呼べない                         |
| (c) 実行中に検知した外部変更（`fs.watch`）の集合           | 再帰の監視で、実行中に変わったパスを集める                                                                                     | Git 管理外のフォルダでも使える。リアルタイムに出せる                                                                                                                                                                  | 変える前の内容が無く、diff も戻すこともできない（確認の結果 17）。通知が多い（5,000 ファイルで 5,003 件）。誰が書いたかは区別できない。ignore の判定を自前で持つことになる。アプリの終了・監視の取りこぼしで集合が欠ける                          |
| (d) 組み合わせ                                             | (a) を主に、(c) を「変わったかもしれない」の合図に使う、または (b) の一覧に (a) の印を付ける                                   | (c) の合図で、見るべき時を知らせられる                                                                                                                                                                                | 合図だけのために再帰の監視を持つ費用（通知の量・ignore の判定）に見合わない。(b) に印を付ける形は、行の中身（diff）が (b) のまま利用者の変更を含み、戻す操作の意味が行ごとに違って分かりにくい                                                    |
| (e) `claude` の hooks で、編集したファイルを記録する       | `--settings` で PostToolUse などの hooks を足し、エージェントが書いたパスを受け取る                                            | 「エージェントが書いた」パスだけが分かる（利用者の編集と区別できる）                                                                                                                                                  | MVP の「引数は空で固定」（セキュリティ）を変える。Bash ツール経由の書き込み（`npm install` など）は拾えない。変える前の内容は別に要る。`claude` 以外の CLI には使えない。hooks の挙動は API に接続しないと確かめられない（確認の結果 18。未確認） |

**推奨は (a)**。ただし、記録の tree を毎回作る形（`git stash create`・`write-tree` を一覧のたびに）ではなく、**記録のインデックス（一時のインデックスファイル）を
残し、`GIT_INDEX_FILE` で比べる形**にする。理由:

- ROADMAP の項目の狙い（エージェントの変更を確かめて、要らない変更を戻す）は、「実行の前の内容」という戻す先が無いと満たせない。(b)・(c) には戻す先が無い
- 記録のインデックスは、既存の Git 層の作り（index に問い合わせる分類〈`classifyDiscardTarget`〉・重なりの検査・`getDiff` の引数・ハンクの逆適用）を、
  `GIT_INDEX_FILE` を差し替えるだけで流用できる（確認の結果 5・7・8・10）。tree と tree の比較にすると、一覧のたびに作業ツリーの全ファイルの blob を
  書くことになり（確認の結果 6 の 7.6 秒・79MB）、既存の分類も使えない
- `git stash create` は利用者の index を書き直し、未追跡を含めない（確認の結果 1）
- (e) は将来の候補（「この機能の後の候補」）。(a) の「実行中の利用者の編集が混ざる」を補えるが、MVP の安全策を変えるため別に判断する

> 2026-10-15 に変更: 2026-10-13-agent-changes-user-edit-distinction-design.md で、アプリが起動する claude に --settings で http の hooks を渡し、エージェントのツールが動いていない間に変わったファイルを「利用者の変更」として区別するようにした（(e) の「エージェントが書いたパスを受け取る」形ではなく、ツールの区間と作業ツリーの区切りの差分で区別する）。累積の一覧の印と、すべて戻すの対象から外すことを足した。この表と行は当時の判断。

| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 実行の前からある利用者の未コミットの変更 | 記録に含まれるので、エージェントの変更に出ない。戻しても残る（確認の結果 3・7）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

| 複数回の実行                             | 記録が無いときだけ新しく取る。記録がある間の `実行` は記録を取り直さず、変更は累積する（「最初の実行から、確認を終えるまで」の変更）。区切りたいときは `確認を終える` を押してから `実行` する                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| コミット（利用者・エージェント）         | 記録のインデックスは HEAD に依らないので、コミットしてもファイルの内容が記録の時点と違えば一覧に残る（確認したらコミットして `確認を終える`、という流れ）。HEAD が記録の時点と違えば、セクションに `記録を始めた後に HEAD が変わりました（コミット・ブランチの切り替えなど）。戻すのはファイルの内容だけです` を出す                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

| ステージ（index）の変化                  | 扱わない。エージェントが `git add` した内容は「ステージ済み」に残る。戻すのは作業ツリーだけで、確認の文言に `ステージ（index）・コミット・ブランチは戻しません` を入れる                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 巨大な変更（記録の後に作られた）         | 一覧は blob を書かない（確認の結果 5・6）。`ls-files --others --directory` で、新しいディレクトリは 1 行（`node_modules/`）にまとめる。ただし、記録の前からあったと分かる中身（ignore されたファイル・記録から除外したファイル・記録から外した入れ子のリポジトリ）を含むフォルダは、まとめずに中のファイルを 1 行ずつ出す（フォルダごとゴミ箱へ移すと、それらも移るため）。一覧の行数は 500 行で打ち切り、`ほか N 件` を出す（DiffView の `MAX_RENDERED_DIFF_LINES` と同じく、DOM の量を抑える）。打ち切ったときは `すべて戻す` を押せなくし、理由 `変更が多すぎるため、すべて戻すは使えません。ファイルごとに戻すか、ターミナルで操作してください` を出す（確認のときに見せた一覧と実行時の一覧を完全一致で照合する作り〈パターン 62〉は、見せていない行を含められないため） |
| 巨大な変更（記録の時点にあった未追跡）   | 記録の前に `ls-files -z --others --exclude-standard` で数と大きさを調べる。5MB を超えるファイルは除外して「記録しなかったファイル」にする（既存の `MAX_UNTRACKED_DIFF_FILE_SIZE_BYTES` と同じ値）。未追跡が 5,000 件を超える、または除外の後の合計が 100MB を超えるときは記録しない（`未追跡のファイルが多すぎるため、記録できません。.gitignore を確かめてください`）。確認の結果 6 の 7.6 秒・3.2 秒を避けるため                                                                                                                                                                                                                                                                                                                                                            |

| リネーム                                 | 削除 + 追加の 2 行で出す（記録のインデックスと作業ツリーの比較はリネームを検出しない。確認の結果 5）。戻すときは 2 行を別々に戻す                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| マージ中（コンフリクト中）               | 記録は取れる（`add -A` はマーカー入りの内容を記録する）。実 index で未解決のパスを戻す操作は拒否する（`コンフリクト中のファイルは戻せません`。既存の取り消しと同じ）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

## 導線の UI

### 配置の案

既存のレイアウトは「アクティビティバー → サイドバー（エクスプローラー・ソース管理・プロンプトなど）→ エディタの領域（タブ・本文・下部のターミナルパネル）」。

| 案                                                                                            | 内容                                                                                                                                                                                                               | 良い点                                                                                                                                                                                                                                           | 問題                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. ソース管理パネルに「エージェントの変更」セクション + ターミナルの帯に `変更を確認`（推奨） | ソース管理パネルのバナーの直後（コミットの欄の上）に新しいセクションを置く。ターミナルの見出しの帯の `変更を確認` で、サイドバーをソース管理に切り替えて開き、一覧を取り直してセクションの見出しへフォーカスを移す | 確認（エージェントの変更）→ ステージ → コミットが 1 つのパネルの上から下に並び、「プロンプト実行 → Git 操作」の流れに沿う。diff タブはエディタの領域に開き、既存の diff タブと同じ操作になる。ターミナルとファイルを同時に見ている状態を崩さない | ソース管理パネルが縦に長くなる（記録が無い間は案内の 1 行と `いまから記録する` だけにする。折りたためる）。サイドバーを閉じている人は、帯のボタンを押すまで気づかない                                                                    |
| B. アクティビティバーに新しいパネル「エージェント」                                           | 一覧・diff・戻すを独立したパネルにする                                                                                                                                                                             | 目立つ。ソース管理パネルを変えない                                                                                                                                                                                                               | 確認の後にコミットするとき、パネルを行き来する。変更の一覧がソース管理と二重になり、どちらで戻すかが分かりにくい。アクティビティバーの項目が増える                                                                                       |
| C. ターミナルパネルの中に一覧（帯の下の引き出し）                                             | 見出しの帯の下に、変わったファイルの一覧を開閉で出す                                                                                                                                                               | エージェントの画面のすぐ近くで見られる                                                                                                                                                                                                           | ターミナルパネルは縦の幅が小さく（エディタの領域の 45%・最小 160px）、一覧とターミナルを同時に出すと、どちらも狭い。最大化の間はエディタが隠れ、diff を開くと戻す操作が要る。狭い幅・タッチの縦持ちで窮屈（MVP の配置の案 C と同じ問題） |

既存の「変更」セクションに「エージェントの変更」のフィルタを付ける案は採らない: 行の中身（diff）が index → 作業ツリーのままで、実行の前からの利用者の変更を
含み、行の取り消しは index の内容へ戻す（確認の結果 9）。同じ行の見た目で意味の違う 2 つの戻し方があると、誤って利用者の編集を消す。

**推奨は A**。

### A の詳細

**ターミナルの見出しの帯**

- 記録があるとき（main の状態が `recording`）だけ、`最大化` の前に `変更を確認` のボタンを出す（`aria-label="エージェントの変更を確認（ソース管理を開く）"`）。
  押すと: サイドバーをソース管理パネルにして開く（`usePanelState` に「切り替えて開く」〈閉じない〉操作を足す。今の `handlePanelChange` は同じパネルで
  押すと閉じるため使わない）→ git status とエージェントの変更を取り直す → セクションの見出しへフォーカスを移す（パターン 86。要素がマウントされた後の
  effect で移す）。最大化の間に押したら、最大化を元に戻してから移る
- 件数は帯に出さない（帯は 32px で、`F6 でターミナルから抜けます` の案内と状態の文言が既に並ぶ。件数は押すまで計算しない〈後述「いつ完了とするか」〉）
- パターン 124・154: ボタンは `flex: none; white-space: nowrap`。案内（`F6 で…`）は既に省略の対象。500・640・1280px の幅で、帯が 1 行（32px）のままであることを
  手動テストで確かめる。記録が無いときはボタンを出さず、帯の高さは変わらない（ボタンの出し入れで高さが変わらないことを確かめる）

**ソース管理パネルのセクション「エージェントの変更」**

- 記録の状態ごとの表示:

| 状態                              | 見出し                                 | 本文                                                                                   | ボタン                                      |
| --------------------------------- | -------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------- |
| 記録なし（エージェント CLI 方式） | `エージェントの変更`                   | `プロンプトの「実行」で、実行の前の状態の記録を始めます`                               | `いまから記録する`                          |
| 記録できない                      | `エージェントの変更`                   | 理由（Git 管理外・サブフォルダ・未追跡が多すぎる・git が見つからない・記録の失敗）     | なし（記録の失敗のときだけ `もう一度試す`） |
| 記録中・取得中                    | `エージェントの変更（10:42 から）`     | 前回の一覧を残したまま、見出しに `更新中…`（パターン 112: 取得中は戻す操作を押せない） | `更新`・`すべて戻す`・`確認を終える`        |
| 記録中・変更なし                  | `エージェントの変更（10:42 から）`     | `記録を始めてから、変わったファイルはありません`                                       | `更新`・`確認を終える`                      |
| 記録中・変更あり                  | `エージェントの変更 (N)（10:42 から）` | 一覧（下）。HEAD が変わっていれば帯。打ち切ったら `ほか N 件`                          | `更新`・`すべて戻す`・`確認を終える`        |

> 2026-10-15 に変更: 記録できない理由に、Git 管理外のフォルダでファイルが多すぎる（`too-many-files`）・`.git` の中・bare リポジトリ（`inside-git-dir`）を足し、Git 管理外は理由から外した（区切りの途中で Git 管理外になったときだけ `not-repository`。2026-10-15-agent-changes-non-git-folder-design.md）。

- 従来の方式（API・非対話 CLI）のときは、記録があればセクションを出し（従来の方式でも戻す操作は使える）、記録が無ければ出さない。`確認を終える` で
  セクションが消えたときは、フォーカスをソース管理パネルのツールバーの `更新` へ移す
- 一覧の 1 行: 状態の文字（`A` 追加・`M` 変更・`D` 削除・`T` 種類の変更〈ファイル ↔ リンク〉）・パス（押すと diff タブ。`aria-label="<path> のエージェントの変更を表示"`）・
  `あなたの保存を含む` の印（該当するとき）・`↶`（`aria-label="<path> を実行前の状態に戻す"`。追加のときは `<path> をゴミ箱へ移動`）。記録していない行（`notRecorded`）は `↶` の代わりに
  `記録していないため戻せません` の印を出す。ボタンは常に表示し、タップ領域 32px 以上（コンセプトのタッチ操作。既存の取り消しのボタンは 18px で hover の
  ときだけ出るため、それには揃えなかった）
- 戻すボタンは、他の Git 操作（ステージ・取り消し・pull・ブランチの操作など）の実行中・一覧の取得中は押せない。理由はセクションの上に 1 か所で出し、
  `aria-describedby` で参照する（パターン 126）。既存の `isAnyLocked()` と同じ合成（パターン 111）
- `すべて戻す` は、一覧を打ち切ったとき（後述「巨大な変更」）と、記録していない行が 1 件でもあるときも押せない（理由
  `記録していないファイルがあるため、すべて戻すは使えません。ファイルごとに戻すか、ターミナルで操作してください`。main は全件を先に調べ、戻せない行が
  あれば必ず全体を中止するため、renderer で先に止める）
- 結果の通知（`2 件を実行前の状態に戻しました`・取得の結果 `エージェントの変更: 3 件`）は、セクションの直前に常設した `aria-live="polite"` の要素に入れる
  （パターン 87・151。セクションを出さない間も同じ要素を残し、表示の切り替えで作り直さない〈文言ごと挿入し直した要素は読み上げられないため。従来の方式で
  `確認を終える` を押してセクションが消えるときも `記録を終えました…` を読み上げる〉。折りたたみの `hidden` の外にある。サイドバーは閉じると隠れるが、ここに入れるのはセクションを操作した結果（ファイル・すべてを戻す、取得）だけなので、セクションが見えている間にしか出ない。diff タブでハンクを戻した結果は、ここではなく diff タブ側の要素に入れる（下の「diff タブ」。PR #47 のレビュー B-2 で分けた））。
  既存の `role="status"` とは衝突させない
- セクションは `<section aria-labelledby>`。見出しのボタンで折りたためる（`aria-expanded`）。初期は開いている。折りたたみの状態は保存しない

**diff タブ**

- 新しい種類の diff タブ（ラベル `<path> (エージェントの変更)`）。内容は「記録の時点 → いまの作業ツリー」。DiffView を流用し、ハンクのボタンは
  `このハンクを実行前に戻す` だけを出す（ステージ・アンステージは出さない。エージェントの変更の diff は index の diff ではないため、パッチを
  `git apply --cached` へ渡すと意味が違う）
- 追加されたファイルは既存の未追跡の疑似 diff（`buildUntrackedDiff`）で全行の追加として出し、ハンクのボタンは出さない（ファイル単位でゴミ箱へ移す。
  確認の結果 8 の「新規ファイルのパッチの逆適用は削除になる」を避ける）。削除されたファイルも、ハンクのボタンは出さない（ファイル単位で作り直す）。追加されたフォルダは `フォルダが追加されました（N 件のファイル）` の 1 行にする
- 一覧から消えたパス（戻した・エージェントが元に戻した・`確認を終える`）の diff タブは閉じる（既存の「gitStatus.files から消えた diff タブを閉じる」と同じ作り）
- ハンクを戻した結果（成功 `ハンクを実行前の状態に戻しました`・失敗の文言）は、EditorPanel のタブと本文の外に常設した `aria-live="polite"` の要素に入れる
  （diff が作り直されて押したボタンが消えても、最後のハンクでタブが閉じても、ソース管理パネルが見えていなくても届く。`role="status"` は付けない〈出力パネルの
  常設の status と重ねない〉。PR #47 のレビュー B-2 で追加）
- diff タブの上部には、そのタブのパスについての直前の戻す操作の失敗だけを見た目で出す（`b.txt` の失敗を `a.txt` のタブに出さない。`すべて戻す` の失敗は
  セクションだけ。読み上げは上の要素とセクションの alert が担うため、ここは `role="alert"` にしない。PR #47 のレビュー B-1 で追加）
- ハンクを戻した後のフォーカスは、押したボタンが実行中に押せなくなる・diff の作り直しで消える・最後のハンクでタブが閉じる、のどれでも body に落とさず、
  アクティブなタブ（タブが閉じた後は次にアクティブになったタブ）へ戻す。戻す予約は利用者の次の操作（pointerdown・keydown）まで保ち、利用者がエディタの外へ
  移したフォーカスは奪わない（パターン 86・152。PR #47 のレビュー B-2 で追加、2 回目のレビューで予約の寿命を修正）

## いつ「完了」とするか

### 今ある手段

- セッションの状態は `none`・`starting`・`running`・`exited` だけで、`running` の間に「作業中」「入力待ち」「許可待ち」を区別できない（MVP の
  確認の結果 5: タイトル・bracketed paste の切り替えは作業中の判定に使えない。MVP の既知の制約「エージェントの状態はアプリから分からない」）
- 画面の読み取り（`readViewport`）で入力欄を探す手段はあるが、MVP は「送ってよいか」の判定だけに使い、作業の完了の判定には使っていない
- hooks（Stop など）で完了を受け取る案は、MVP の「引数は空で固定」を変える（確認の結果 18。未確認）

### 実行中の変更をリアルタイムに出すか、押したときに取るか

| 案                       | 内容                                                                                  | 良い点                                                                       | 問題                                                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| リアルタイム             | 再帰の監視（確認の結果 17）または一定の間隔で一覧を取り直し、セクションを更新し続ける | 作業の進み具合が見える                                                       | 作業中のファイルは書きかけで、一覧と diff が揺れる。タッチで押そうとした行が動く。監視の通知が多い（node_modules）。サイドバーを閉じていても計算し続ける |
| 押したときに取る（推奨） | `変更を確認`・セクションの `更新`・既存の契機で取り直す                               | 費用は押したときだけ（一覧は約 0.03〜0.07 秒。確認の結果 6）。表示が揺れない | 自動では最新にならない（いつ取ったかは見出しの `更新中…` と、取得の後の読み上げで分かる）                                                                |

**推奨は「押したときに取る」**。完了の検知が無い以上、「エージェントが終わったと利用者が判断したとき」に取るのが、手段として正確で費用も小さい。
取り直す契機は次の 4 つに限る:

1. ターミナルの帯の `変更を確認`
2. セクションの `更新`（git status とエージェントの変更の一覧の両方を取り直す）、ソース管理パネルの既存の更新のボタン（`refreshGitStatus` の後に続けて取る）
3. 既存の Git の操作・保存の後の `refreshGitStatus`（作業ツリーが変わりうる操作。renderer で `gitStatus` が新しくなったら、記録がある間だけ取り直す）
4. セッションの終了（`agentTerminal:exit`。エージェントの終了は「完了」の確かな合図の 1 つ）

このほか、記録を始めた直後に一覧を 1 回取る（実装で足した。記録の直後は一覧が無く、セクションに何も出ないため。送信の前の準備は一覧を待たない）。

ウィンドウのフォーカスの復帰では取り直さない（既存のソース管理も取り直さない。変えると既存の手動テストの前提が変わる〈パターン 160〉。この機能の後の候補）。

> その後の変更（2026-10-12）: `2026-10-12-agent-changes-runs-and-auto-refresh-design.md` で、上の 4 つに「活動の出来事（完了・許可待ち・確認待ち）」と「ウィンドウのフォーカスの復帰」の 2 つを足して 6 つにした（記録がある間だけ、エージェントの変更の一覧を待ち 300ms・上限 1,000ms で合流して取り直す。ソース管理の git status は今も取り直さない）。上の「4 つに限る」と「フォーカスの復帰では取り直さない」は、この設計書の時点の決定として残す。

## 変更を戻す

### 既存の破棄の再利用の範囲

| 既存の部品                                                                             | 再利用                                                                                                                                                                                                                                      |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `classifyDiscardTarget`・`overlapsUntracked`                                           | 使う。記録のインデックスで問い合わせる git を渡す（確認の結果 10）。`untracked` は「記録の後に現れた」、`tracked` は「記録の時点にあった」になる。`intent-to-add` は記録のインデックスに現れない（`add -A` が実体を入れる）                 |
| `applyDiscard`（restore・ゴミ箱）                                                      | 使う。`tracked` の `git restore --worktree` は記録のインデックスから戻す（確認の結果 7）。`untracked` はゴミ箱へ移す（既存の `moveToTrash`）                                                                                                |
| `isUnmergedPath`                                                                       | 実 index で問い合わせる（コンフリクトは実 index の状態。記録のインデックスには未解決のエントリが無い）                                                                                                                                      |
| `assertHunkPatchTargets`・`stripModeChangeLines`・`listPatchPaths`・`discardHunkPatch` | 使う。`git apply --reverse` は index を使わない（確認の結果 8）。パッチの対象が 1 件で、指定のパスと一致することを順・逆の両方で確かめる既存の手順をそのまま通す                                                                            |
| `discardAllChanges`                                                                    | 使わない。照合の対象が実 index の `git status` で、エージェントの変更の集合と違う。同じ流れ（実行時に main が対象を作り直す → 確認時の一覧と完全一致で照合 → 全件を先に分類 → 途中失敗は `partial`）で、新しい関数を作る（パターン 62・66） |
| `getDiff` の引数（パッチの形式を固定する引数）                                         | 同じ引数を使う。`patchFormatArgs` を `gitService.ts` から切り出して共有する（同じ規則の写しを作らない。パターン 88）                                                                                                                        |
| renderer の `useDiscardFileChanges`・`useDiscardHunk`・`runEditorSyncedOperation`      | 形を揃える（確認 → 実行 → 成功したときだけタブとツリーを同期）。既存の hook は `gitApi` を直接呼ぶため、エージェントの変更用の hook を別に作り、`buildDiscardConfirmMessage` に相当する文言は新しい関数にする                               |

既存の部品は、git の実行（`SimpleGit`）を引数で受け取る形のものが多い（`classifyDiscardTarget(git, path)`・`applyDiscard(git, …)`）。記録のインデックスで
問い合わせる `SimpleGit` を作る部品（確認の結果 14 の環境変数の除外を含む）を 1 つ足せば、既存の関数の中身は変えずに使える。`discardHunk`・
`discardFileChanges` のように内部で `simpleGit(folderPath)` を作る関数は、中身を「git を受け取る関数」と「作って呼ぶ関数」に分ける（挙動は変えない）。

### 実行前の状態へ戻す（記録からの復元）は必要か

必要。既存の破棄は「index の内容へ戻す」ので、実行の前からの未ステージの変更を消す（確認の結果 9）。戻す先を記録の時点にすることが、この機能の中心で、
記録のインデックスはそのために残す。

### 戻す手順（main。ファイル単位）

1. 入力の検証・所有者の確認・記録の世代を控える（後述「セキュリティ」「世代」）
2. 対象のパスが、いまの一覧（記録のインデックス → 作業ツリー）に含まれることを確かめる（一覧に無いパスは拒否。`変更の状態が変わりました。一覧を更新してください`）
3. 実 index で未解決なら拒否。gitlink（mode 160000）なら拒否
4. 記録のインデックスで分類する。`tracked` なら、記録のインデックスの blob が object の DB にあることを `git cat-file -t` で確かめる（無ければ拒否:
   `実行前の内容が見つかりません（git gc などで消えた可能性があります）`。確認の結果 12 の「復元できずに削除だけが起きる」を防ぐ）。設計時に書いた
   `-e`（終了コードだけで答える形）は、blob が無くても simple-git で resolve し、検査がすり抜けるため使わない（確認の結果 21）
5. 拒否する状態（`overlaps-untracked`・`unknown`）は既存の `assertDiscardable` で拒否する（確認の結果 11）
6. 記録しなかったファイル（5MB を超えて除外したもの・記録の時点に ignore されていたもの。一覧で `notRecorded` の行）は拒否する（`実行前の内容を記録していないため戻せません`）
7. `applyDiscard`（記録のインデックス）で戻す

ハンク単位は、手順 1〜6 の後、既存の `discardHunk` と同じパッチの検査を通し、作業ツリーへ逆適用する。追加されたファイル（`untracked`）と、削除されたファイル・種類が変わったファイル（`T`。renderer もボタンを出さないが、main でも拒否する）のハンクは拒否する（ファイル単位で戻す）
（確認の結果 8）。逆適用の前の内容の照合は `git apply` の文脈の照合に任せ、合わなければ `ハンクを戻せませんでした。ファイルが変更された可能性があります。
diff を開き直してください`（既存の文言に揃える）。

`すべて戻す` は、確認のときに見せた一覧（パスと状態の文字）を main へ渡し、main は実行時の一覧と完全一致で照合し、違えば何も変えずに中止する。全件を先に
分類し、1 件でも戻せなければ何もしない（戻せないファイルを文言に最大 5 件）。実行の途中で失敗したら、1 件以上済んでいれば `partial`、0 件なら例外
（既存の `DiscardAllResult` と同じ型を使う）。

### 利用者自身の編集を誤って破棄しない確認

- 実行の前からの編集: 記録に含まれるので消えない（構造で守る）
- 実行中のアプリでの保存: renderer は、記録の開始の後に `saveFile` が成功したパスを覚える（記録の世代ごと。`確認を終える` で捨てる）。一覧に印を出し、
  戻す確認の文言に 1 文を足す
- 実行中のアプリの外での編集: 分からない。確認の文言に常に `記録を始めた後にあなたが編集した内容も戻ります` を入れる
- 未保存の編集: 既存と同じく、対象（フォルダなら配下）のタブに未保存の編集があれば文言に足し、1 回の確認で承諾させる。`すべて戻す` は
  `confirmDiscardAnyDirty` を挟む（既存の `useDiscardAllChanges` と同じ）
- エージェントがまだ動いているかもしれない: セッションが `running` なら、文言に `エージェントが動いている間は、戻した後に同じファイルが書き換えられることがあります` を足す
  （止めることはしない。作業中かどうかは分からないため）

> 2026-10-15 に変更: 区別している記録では、すべて戻すの確認の文言が区別の状態で変わる（`記録を始めた後にあなたが編集した内容も戻ります。` の代わりに、ツールの実行中などの編集がエージェントの変更として戻る旨と、戻さない利用者の変更の件数を出す）。区別していない記録と、行の ↶ の確認の今の文言は変えず、行の ↶ では利用者の変更の行にその旨の 1 文を足す。`あなたの保存を含む` の印と追記は残す（2026-10-13-agent-changes-user-edit-distinction-design.md の「確認の文言」）。

### undo の可否

戻した操作の取り消し（undo）は入れない。理由: 既存の取り消しも「元に戻せません」で統一していて、戻した直前の状態を記録する仕組み（もう 1 つの記録の
インデックス）と、その寿命・UI が要る。ゴミ箱へ移したファイルは OS のゴミ箱から戻せる。直前の状態を記録して「戻した操作を取り消す」は、この機能の後の候補にする。（2026-10-13 の設計書で、直前の 1 回の戻す操作を取り消せるようにした。控えは記録のインデックスではなく、アプリの一時ディレクトリに戻す前のバイト列として持つ。この節の判断は当時のもの）

### 開いているタブ・未保存の編集との整合

- 戻す操作の成功の後に、既存と同じく renderer が明示的に読み直す（ファイル単位・ハンク: `reloadOpenFile`。ゴミ箱へ移したもの: `closeTabsAtOrInside`。
  すべて: `reloadOpenFiles`。いずれも成功したときだけ。`partial` も読み直す。パターン 20・52）。その後に `refreshTree`・`refreshGitStatus`（→ エージェントの変更の取り直し）
- main の書き込みは外部変更の監視（`openFileWatcher`）にも届く。未編集のタブは監視の側でも読み直されるが、明示的な読み直しと重なっても、
  `replaceCleanTabWithDisk` が「控えと一致・未編集・保存の実行中でない」を同期で確かめるので、二重に置き換えても内容は同じ（パターン 150）
- 編集中のタブで、確認で未保存の破棄を承諾した場合は、明示的な読み直しで置き換える（既存の取り消しと同じ）。監視の通知の帯は、読み直しで
  `savedContent` が変わるので消える

## 全体構成

### 責務とファイル構成

新しいファイルは `agentChanges` の語で揃える（MVP の `agent*` と並べ、Git の既存の `git*` と区別する）。

**shared**

- `types/agentChanges.ts`: IPC の型（`AgentChangesState`〈`none`・`unavailable`〈理由の種類〉・`recording`〉、`AgentChangeEntry`〈`path`・`status`〈`A`・`M`・`D`・`T`〉・
  `isDirectory`・`notRecorded`〉、`AgentChangesListResult`〈entries・全件数・打ち切り・HEAD が変わったか・開始の時刻〉、`AgentRevertAllEntry`、
  `AgentChangesUnavailableReason`）と、一覧の打ち切りの上限（500 行）。記録の上限（未追跡 5,000 件・合計 100MB・除外の閾値 5MB・git の打ち切り 10 秒）は main だけが使うので、`agentBaselineGit.ts`・`agentBaselineSnapshot.ts` に置く

**main**

- `agentBaselineGit.ts`: 記録のインデックスで問い合わせる `SimpleGit` の生成（`process.env` から simple-git が拒否する変数と、別の場所を指しうる
  `GIT_DIR`・`GIT_WORK_TREE`・`GIT_INDEX_FILE`・`GIT_OBJECT_DIRECTORY`・`GIT_ALTERNATE_OBJECT_DIRECTORIES`・`GIT_COMMON_DIR`・`GIT_NAMESPACE` を除き、
  `GIT_INDEX_FILE` を記録のインデックスにする。確認の結果 14）。常に `-c core.splitIndex=false` を付ける（記録・一覧・diff・戻す操作のどれでも、
  利用者の `.git` に `sharedindex.*` を書かない）。除く変数の一覧は `@simple-git/argv-parser` の版に依るため、
  テストで「EDITOR・GIT_ASKPASS がある環境で例外にならない」を固定する
- `agentBaselineSnapshot.ts`: 記録を取る（最上位のフォルダの確認 → 未追跡の数と大きさの事前検査 → `.git/index` の写し〈無ければ空〉→ `add -A -- . <除外>` →
  記録の時点の ignore 済みの一覧〈`--directory`〉→ HEAD を控える）。各段に打ち切り（10 秒。パターン 84・138）。記録の前からあった、コミットの無い（HEAD の無い）入れ子のリポジトリは記録から外して控える。
  `add -A` は `-c core.splitIndex=false`（`agentBaselineGit.ts` が付ける）で実行し、利用者の `.git` に `sharedindex.*` を書かない
- `agentChangesQuery.ts`: 一覧（`diff --name-status --no-renames -z` と `ls-files -z --others --exclude-standard --directory --no-empty-directory` を合わせ、
  除外したファイルを `notRecorded` に、打ち切り）と、1 ファイルの diff。記録しなかったファイルは大きさと更新時刻で変わったかを見る。記録の前からあったと
  分かる中身（ignore されたファイル・除外したファイル・記録から外した入れ子のリポジトリ・記録の時点に ignore されていたもの）を含む新しいフォルダは、1 行にまとめずにファイルごとの行に展開する。
  記録の時点に ignore されていたファイル・フォルダ（とその中）、除外したファイルの inode を持つ追加のファイル（リネームの先）は `notRecorded` にする。
  1 ファイルの diff は `getDiff` と同じ引数・同じ上限（追加は `buildUntrackedDiff`）
- `agentChangesRevert.ts`: 戻す（ファイル・ハンク・すべて）。既存の分類・`applyDiscard`・パッチの検査を、記録のインデックスの git で呼ぶ
- `agentBaselineRegistry.ts`: 所有者（webContents の id）→ 記録。世代・所有者ごとの直列化（記録のインデックスへの操作を 1 本の列に並べる。
  `index.lock` の衝突を避ける）・一時ディレクトリの削除・`close()`（アプリの終了）。列の中では記録のフォルダを照合するだけで、違っても記録を捨てない
  （依頼のフォルダは入り口で取ったもので、列で待つ間に切り替わった後の新しい記録がありうる。PR #47 のレビュー A-2 で修正）
- `agentBaselineLifecycle.ts`: `ownerContextLifecycle.ts` の 4 つの契機（破棄・renderer の終了・リロード・フォルダの切り替え）で記録を捨てる。
  `before-quit` で一時ディレクトリを同期で消す
- `handlers/agentChangesHandlers.ts`・`handlers/agentChangesPayloadParser.ts`: IPC の受け口と入力の検証
- 変更（挙動は変えない切り出し）: `gitService.ts`（`patchFormatArgs` を `gitDiffArgs.ts` へ）、`gitDiscardService.ts`（`discardHunk` の検査の部分を
  git を受け取る関数に分ける）、`ipcHandlers.ts`（組み立て）

**preload**

- `api.ts`・`index.d.ts`: 後述の IPC を足す

**renderer**

- `lib/agentChangesApi.ts`: `window.api` の窓口
- `lib/agentChangesMessages.ts`: 文言・押せる条件・確認の文言の組み立て（純粋関数）
- `hooks/useAgentChanges.ts`: 記録の状態・一覧・取得（要求の番号で古い結果を捨てる）・`begin`・`clear`・取り直しの契機、実行中に保存したパスの集合
- `hooks/useAgentChangesRevert.ts`: 戻す（ファイル・ハンク・すべて）の「確認 → ロック → 実行 → 成功したときだけ同期」
- `components/source-control/AgentChangesSection.tsx`・`AgentChangesFileItem.tsx`: セクションと 1 行
- 変更: `useDiffTabs.ts`・`diffTabPath.ts`・`useCombinedEditorTabs.ts`（diff タブの種類に `agent` を足す。後述）、`useDiffOperations.ts`（`agent` のタブは
  `agentChangesApi.getDiff` で取り、ステージの操作を出さない）、`DiffView.tsx`（ボタンの種類を props で切り替える）、`useAgentPromptSender.ts`
  （送信の前に `begin` を待つ。失敗しても送る）、`AgentTerminalPanel.tsx`（`変更を確認`）、`usePanelState.ts`（切り替えて開く）、`useAppState.ts`・
  `SourceControlPanel.tsx`・`GitRepoView.tsx`・`NotRepositoryView.tsx`（配線）

**diff タブの種類**: `DiffTabKey` を `{ path, staged }` から `{ path, kind: 'unstaged' | 'staged' | 'agent' }` に変える案と、`{ path, staged, agent?: true }` の
案がある。後者は `staged` と `agent` の組み合わせに意味の無いもの（`staged: true, agent: true`）を作れる。**前者を推奨**（`staged` を参照する 15 か所を
置き換える。`encodeDiffTabPath` の印は既存の `staged`・`unstaged` を保ち、`agent` を足す）。置き換えは機械的なので、最初のタスクで挙動を変えずに行い、
既存のテストが通ることを確かめてから `agent` を足す。

**依存の向き**: `shared` ← `main`・`preload`・`renderer`。main は `agentChangesHandlers` → `agentBaselineRegistry` → (`agentBaselineSnapshot`・
`agentChangesQuery`・`agentChangesRevert`) → (`agentBaselineGit`・既存の `gitDiscardClassifier`・`gitDiscardService`・`gitApply`・`gitHunkPatch`・
`gitDiffFormatter`)。既存の Git 層は新しいファイルを知らない。`agentBaselineLifecycle` → `agentBaselineRegistry`・`ownerContextLifecycle`。
エージェントのセッション（`agentSession*`）とは依存しない（記録はセッションが無くても使える。セッションの終了は renderer の契機としてだけ使う）。
renderer は コンポーネント → hooks → `lib/*` → `lib/agentChangesApi.ts`。

### IPC（preload の API と許可）

すべて `window.api` に列挙する。チャンネル名は `agentChanges:*`。すべて invoke。

| API                                  | チャンネル                | 引数・戻り値                                                                                                     |
| ------------------------------------ | ------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `beginAgentChanges()`                | `agentChanges:begin`      | なし → `AgentChangesState`。記録があれば何もせずにその状態を返す（累積）。対象のフォルダは main の許可のフォルダ |
| `getAgentChangesState()`             | `agentChanges:getState`   | なし → `AgentChangesState`（一覧を作らない。帯のボタンの表示に使う）                                             |
| `listAgentChanges()`                 | `agentChanges:list`       | なし → `AgentChangesListResult`。記録が無ければ `none`                                                           |
| `getAgentChangeDiff(path)`           | `agentChanges:getDiff`    | リポジトリ相対のパス → diff の文字列                                                                             |
| `revertAgentChange(path)`            | `agentChanges:revertFile` | パス → なし（失敗は日本語の例外）                                                                                |
| `revertAgentChangeHunk(path, patch)` | `agentChanges:revertHunk` | パス・パッチ → なし                                                                                              |
| `revertAllAgentChanges(expected)`    | `agentChanges:revertAll`  | 確認のときの一覧（`{ path, status }[]`）→ `DiscardAllResult`                                                     |

確かめていない）。

### セキュリティ（MVP の安全策の踏襲）

- **renderer から受け取るのはパス・パッチ・確認の一覧だけ**。記録のインデックスの場所・フォルダ・git のコマンドは main が決める。記録のインデックスの
  パスを renderer に返さない（パターン 144）
- **入力の検証**（`agentChangesPayloadParser.ts`。既存の `payloadValidators.ts` を使う）: 送信元は `event.senderFrame` がその webContents のメインフレーム。
  パスは文字列で、既存の `resolveAndAssertStatusRelativePath` と同じ規則（許可のフォルダの中・`..` 始まりでない・絶対パスでない）。パッチは文字列で
  10,000,000 文字以下（既存の `assertPatchArg` は上限を持たないため、粗い上限を足した。差異 2）。確認の一覧は既存の `assertDiscardEntriesArg` と同じ検証
- **所有者の分離**: 記録は送信元の webContents の id で引く。別のウィンドウの記録には触れない。記録のフォルダと、いまの許可のフォルダが違えば
  （フォルダの切り替えの通知より先に要求が来た場合）、`none` として扱い、記録を捨てる。ただし記録を捨てるのは、いまの許可のフォルダと同期で比べる `begin`・状態の取得だけで、
  列で順番を待つ操作（一覧・diff・戻す）はフォルダが違えば記録なしとして失敗するだけにする（列で待っていた古いフォルダの依頼が、切り替えの後の新しい記録を
  捨てていた。PR #47 のレビュー A-2 で修正）
- **記録のインデックスの置き場所**: アプリの一時ディレクトリ（0700）。利用者のリポジトリの `.git` に書くのは、記録の blob（`add -A` が書く loose object）だけ。
  利用者が `core.splitIndex` を有効にしていても、記録の git（記録・一覧・diff・戻す操作）は `core.splitIndex=false` で実行し、`.git` に `sharedindex.*` を書かない
- **git の実行**: 引数は固定。利用者の設定（`diff.external`・`textconv`・`color`）を打ち消す引数は `getDiff` と同じものを使う。`git add` は clean filter
  （LFS など）を実行しうる（既存のステージと同じ。既知の制約）

## データフロー

### 記録の開始（プロンプトの `実行`）

1. renderer（`useAgentPromptSender.send`）: 送信の手順（入力欄を空にする → 貼り付け → Enter）の**前**に `beginAgentChanges()` を待つ。待つ上限は
   10 秒（main の git のコマンドごとの打ち切りと同じ値。記録の全体には上限が無い）。失敗・`unavailable`・待ちの打ち切りでも送信は続ける（記録はおまけで、
   送ることが主）。エージェントが書き始めるのは Enter の後なので、記録が 10 秒以内に終われば、記録は Enter より前に終わっている。10 秒を超えたときは、
   記録の完了を待たずに送り、記録は送信の後に終わる（その後に記録として扱い、一覧を取る。その間にエージェントが書いた変更は記録の時点に含まれる。既知の制約）
2. main（registry）: 入口で所有者の世代を控える。記録があれば返す。同じ世代の記録の途中の依頼があれば、それにまとめる（二重の `実行`・`いまから記録する`）
3. main（snapshot）: 最上位のフォルダの確認 → 未追跡の事前検査 → 写し → `add -A`。`await` のたびに世代を比べ、変わっていれば一時ファイルを消して
   `none` を返す（パターン 141）
4. renderer: 状態を `recording` にし、帯に `変更を確認` を出す。実行中に保存したパスの集合を空にする

### 一覧と diff

1. 契機（「いつ完了とするか」の 4 つ）で `listAgentChanges()`。renderer は要求の番号を進め、古い番号の結果を捨てる（`useGitStatus` と同じ作り）
2. main: 所有者の列に並べ、記録のインデックスで 2 つのコマンドを実行し、合わせて返す。HEAD を比べる
3. renderer: 一覧を表示し、一覧から消えたパスの `agent` の diff タブを閉じる。diff タブがアクティブなら `getAgentChangeDiff(path)` で取り直す

### 状態の持ち主（真実の源）

- 記録（あるか・どのフォルダか・いつからか・記録のインデックス）の真実の源は **main の registry**。renderer は写しを持ち、表示と押せる条件に使う。
  renderer の写しが古くても、main が実行時に照合する（戻す対象が一覧に含まれるか・確認の一覧と一致するか）
- 一覧は保存しない（毎回作業ツリーから作る）
- 「実行中にアプリで保存したパス」の真実の源は **renderer**（保存は renderer の操作で、main は自分の保存と外部の保存を区別しない）。記録の世代と一緒に
  持ち、世代が変われば捨てる。表示と確認の文言にだけ使い、戻す操作の可否には使わない

### 世代

- main: 所有者ごとの世代（記録の開始・`clear`・所有者の文脈の終わりで進める）。`begin` は入口で控えて待つたびに比べる。`list`・`revert*` は列の中で
  実行する（実行中に `clear` が来たら、列の後ろで記録を消す。実行中の `revert` は最後まで行う〈途中で止めると `partial` の扱いが要る〉）
- renderer: 世代（`useAgentChanges` の `generationRef`。フォルダの切り替えと `確認を終える` で進める）と、一覧の取得の要求の番号。`begin` の結果・
  マウント時の `getAgentChangesState` の結果は、送った時点の世代と今の世代が違えば捨てる（フォルダの文字列ではなく世代で照合するため、/a → /b → /a と
  戻った後に届いた古い結果も区別して捨てる）。世代を進める処理（フォルダの切り替え）はマウント時の状態の取得より前に宣言し、切り替えた後の世代で照合する

## 既知の制約（設計時点の項目に、実装で分かったものを追記した）

- 実行中の利用者の編集は、エージェントの変更と区別できない。アプリで保存したパスだけは印を付けるが、アプリの外での編集は分からない
- 記録は最初の `実行`（または `いまから記録する`）から `確認を終える` までの累積で、実行ごとには分けない。`実行` を押さずにターミナルへ直接打ち込んだ
  指示は、`いまから記録する` を押さないと記録されない
- エージェントの実行の完了は検知しない。一覧は `変更を確認`・`更新`・Git の操作・セッションの終了で取り直し、自動では最新にならない
- Git 管理外のフォルダ・リポジトリのサブフォルダでは使えない

> 2026-10-15 に変更: Git 管理外のフォルダは使えるようになった（2026-10-15-agent-changes-non-git-folder-design.md。既知の制約はその設計書を参照）。リポジトリのサブフォルダは今も使えない。

> 2026-10-19 に追記: 記録の時点に読めないファイル・フォルダ（パーミッション）があると記録しない（git を実行できない、と出る）。読めないフォルダは以前は黙って記録から外れ、後で読めるようになると「追加」として一覧に出て、戻すとゴミ箱へ移っていた（ローカルレビュー第 33 周の指摘 1 で修正。2026-10-15-agent-changes-non-git-folder-design.md の「既知の制約」）。読めるが実行できないフォルダ（`chmod 600` など）の中の追跡済みのファイルは、以前は古い内容のまま記録され、権限を戻すと記録の前からの変更がエージェントの変更として出ていた（ローカルレビュー第 35 周の指摘 1 で修正）。フォルダの外の大域の除外・属性のファイル（`~/.config/git/ignore` など）が読めないだけでは記録は止まらない（第 35 周の修正の後は、この警告でどのフォルダでも記録が失敗していた。ローカルレビュー第 36 周の指摘 1 で修正）。

- 記録の時点に ignore されていない未追跡のファイルが 5,000 件を超える・合計が 100MB を超えると記録しない。5MB を超える未追跡のファイルは記録せず、
  エージェントが変えても戻せない
- ignore されたファイルの変更は一覧に出ない。リネームは削除 + 追加の 2 行になる
- 入れ子のリポジトリ・サブモジュールの変更は戻せない（ターミナルで操作する）
- 入れ子のリポジトリ・サブモジュールの中の未コミットの変更は一覧に出ない（HEAD が動いたときだけ `M` で出る。2026-10-18 から。2026-10-15 の設計書の「既知の制約」を参照）
- 戻すのは作業ツリーだけで、ステージ（index）・コミット・ブランチは戻さない。戻した操作は取り消せなかった（ゴミ箱へ移したものは OS のゴミ箱から戻せる）（2026-10-13 から、直前の 1 回の戻す操作はセクションの帯の「戻した操作を取り消す」で取り消せる。2026-10-13 の設計書の「既知の制約」を参照）
- 記録の blob はどの ref からもたどれなかったため、`git gc --prune=now` などの後は戻せなかった（戻す前に拒否していた）。既定の gc（2 週間）では消えない（2026-10-13 から、記録中は専用の ref から記録の tree をたどれるため、記録中の `git gc --prune=now` では消えない。守りが効かない場合は今も戻す前に拒否する。2026-10-13 の設計書の「既知の制約」を参照）
- 記録のために、記録の時点の未追跡・変更済みのファイルの blob を利用者のリポジトリの object の DB に書く（`git add` と同じ。到達できない object として、
  既定の gc で 2 週間の後に消える）。LFS などの clean filter・fsmonitor の設定は、記録の `git add` でも働く（`filter=` が記録の `git add` でもかかり、戻しで記録の時点の内容が失われるため拒否することは、統合テストで確認済み。fsmonitor は未確認）
- リロード・フォルダの切り替え・ウィンドウの破棄・アプリの終了で記録は消える。異常終了で残った一時ファイルは OS の掃除に任せる

> 2026-10-15 に変更: 記録の一時ディレクトリ（名前に pid と起動ごとの ID を含む新しい形）は、次の起動で消す（2026-10-15-agent-changes-non-git-folder-design.md「記録の一時ディレクトリの名前と起動時の掃除」）。取り消しの控えと古い形の名前のものは今も OS の掃除に任せる。この行は当時の判断。

- 一覧は 500 行で打ち切り、打ち切ったときは `すべて戻す` を使えない（新しいフォルダは 1 行にまとめるので、通常は届かない。ただし ignore されたファイルを
  含む新しいフォルダは、ファイルごとの行になる）
- 戻す操作は、エージェントの動作中でも実行できる（止めない）。戻した後にエージェントが同じファイルを書き換えることがある
- ウィンドウのフォーカスの復帰では一覧を取り直さなかった（2026-10-12 の実行ごとの記録と一覧の自動の取り直しから、記録がある間はエージェントの変更の一覧を取り直す。git status は今も取り直さない）
- 記録・一覧・戻すの git は、`GIT_CONFIG_GLOBAL`・`GIT_CONFIG_SYSTEM` などの環境変数で変えた設定の場所を使わず、既定の場所の設定を読む（simple-git の制限）
- 記録の時点のファイルを、エージェントが同じ名前のフォルダに置き換えると、一覧にはファイルの削除だけが出て、フォルダの中身は出ない（戻すと「未追跡のファイルと
  重なる」で拒否される。ターミナルで操作する）
- 記録の時点に大きすぎて記録しなかったファイルは、大きさと更新時刻が変わったときだけ一覧に出る（内容だけが同じ大きさ・時刻で変わったものは出ない）
- 記録の時点からあった、コミットの無い入れ子のリポジトリは記録せず、一覧では「記録していない」行になる。記録していない行が 1 件でもあると `すべて戻す` は
  使えない（ファイルごとに戻すか、ターミナルで操作する）
- 記録の時点に ignore されていたファイル・フォルダは、記録の後に ignore の規則（`.gitignore`・`.git/info/exclude`・`core.excludesFile`）から外れると、
  一覧に「記録していない」行として出て、戻せない（フォルダごと ignore されていたフォルダは 1 行で、記録の後にエージェントがその中へ足したファイルも戻せない）。
  記録しなかったファイル（ignore されていたもの・大きすぎて記録しなかったもの）をエージェントが移動・コピーすると、移した先は新しいファイルとして扱い、戻すと
  ゴミ箱へ移る（OS のゴミ箱から戻せる）。ただし、大きすぎて記録しなかったファイルを同じファイルシステムの中で別の名前へ移した場合は、移した先も
  「記録していない」行にして戻せない（新しいフォルダの中へ移した場合は、そのフォルダの 1 行になり拾えない）
- 送信の前に記録の開始を待つのは 10 秒まで（main の打ち切りは git のコマンドごとで、記録の全体には上限が無い）。記録に時間がかかる大きいリポジトリで
  10 秒を超えると、記録の完了を待たずに送り、記録は送信の後に終わる。その間にエージェントが書いた変更は記録の時点に含まれ、一覧に出ず、`すべて戻す` でも戻らない
- `.gitattributes` で `filter=` が付いたファイル（LFS・nbstripout など）は戻せない（記録は clean filter を通した後の内容で、記録の時点の作業ツリーの内容が
  失われうるため。ファイル・ハンク・`すべて戻す` のいずれも拒否する。ファイルごとにターミナルで操作する。判定は、記録の時点の `.gitattributes`（記録のインデックス）と作業ツリーの
  `.gitattributes` の両方を調べ、どちらかに filter があれば拒否する。記録の後にエージェントが filter の行を消しても拒否する）
- `.gitattributes` の `text=auto`・`eol` や `core.autocrlf` で改行コードを変換するリポジトリでは、戻した後の改行コードが記録の時点の作業ツリーと
  変わることがある（記録は変換した後の内容で、戻すときに設定どおりに書き戻すため）。`ident`・`working-tree-encoding` も同じで、戻した後の内容が記録の時点とバイト単位で違いうる

> 2026-10-15 に追記: Git 管理外のフォルダの記録（隠れた git）では、隠れた git の設定に `core.autocrlf=false`・`core.safecrlf=false` を書くため、利用者の大域・システムの `core.autocrlf`・`core.safecrlf` では改行コードを変換しない（記録と戻すはバイトのまま。`core.safecrlf=true` でも記録できる。ハンクで戻す `git apply` も隠れた git の設定で動かす〈ローカルレビュー第 6 周で追加〉）。フォルダの `.gitattributes` の `text`・`eol`（と大域の `core.attributesFile`）による変換・`ident`・`working-tree-encoding` は今も効く（2026-10-15-agent-changes-non-git-folder-design.md の「既知の制約」）。この行はリポジトリの方式では今も当てはまる。

## 実装の分割案

タスクごとにレビューを挟む（サブエージェント駆動）。main → renderer の順で、各タスクの終わりで既存のテストがすべて通る状態を保つ。

1. **実測の再確認と共通部品の切り出し（挙動を変えない）**: 未確認事項 1・2 を Electron の main で確かめて記録する。`patchFormatArgs` の切り出し、
   `discardHunk`・`discardFileChanges` の「git を受け取る関数」への分割
2. **`agentBaselineGit` と記録**（`agentBaselineSnapshot`）: 環境変数の除外、最上位の確認、未追跡の事前検査、除外、打ち切り。実 git の結合テスト
   （確認の結果 1・2・6・14・15 の回帰）
3. **一覧と diff**（`agentChangesQuery`）: 実 git の結合テスト（確認の結果 3〜5・13 の回帰、打ち切り・`--directory`・`notRecorded`）
4. **戻す**（`agentChangesRevert`）: ファイル・ハンク・すべて。実 git の結合テスト（確認の結果 7〜12 の回帰）と変異
5. **registry・lifecycle・IPC・preload・shared の型**: 世代・直列化・所有者の分離・一時ディレクトリの後始末・入力の検証
6. **diff タブの種類の置き換え（挙動を変えない）**: `staged` → `kind`。既存のテストがすべて通ることを確かめる
7. **renderer の hook と記録の開始**: `useAgentChanges`・送信の前の `begin`・実行中に保存したパス・取り直しの契機
8. **セクションと戻す操作の UI**: `AgentChangesSection`・`useAgentChangesRevert`・確認の文言・タブの同期・`agent` の diff タブ（DiffView のボタンの切り替え）
9. **ターミナルの帯の `変更を確認` とパネルの切り替え**: フォーカス・最大化の解除・狭い幅の CSS（パターン 124・154 を最初から）

## 決定した点

利用者の決定（2026-10-07。いずれも設計書の推奨のとおり）:

1. **記録の区切り**: 最初の `実行`（または `いまから記録する`）から `確認を終える` までの変更を累積して見せる。`実行` のたびに記録を取り直さない
2. **導線の配置**: 案 A（ソース管理パネルのセクション「エージェントの変更」+ ターミナルの帯の `変更を確認`）
3. **戻す操作の範囲**: ファイル単位・ハンク単位・すべての 3 つを入れ、undo は入れない
4. **記録の寿命**: リロード・フォルダの切り替え・ウィンドウの破棄・アプリの終了で記録を捨てる（MVP のセッションと揃える）
5. **Git 管理外のフォルダ・リポジトリのサブフォルダ**: 対象外とし、理由を表示する

> 2026-10-15 に変更: Git 管理外のフォルダは 2026-10-15-agent-changes-non-git-folder-design.md で対象にした。リポジトリのサブフォルダは今も対象外。この決定は当時の判断。
