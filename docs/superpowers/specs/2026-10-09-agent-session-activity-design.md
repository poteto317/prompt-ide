# エージェントのセッションの状態表示 設計書

- 日付: 2026-10-09
- ROADMAP の項目: 「エージェント実行の支援（MVP の次）」→「セッションの状態表示（実行中 / 入力待ち / 許可待ち / 終了）と、ステータスバー・タブへの反映」
- 前提の設計書: `2026-10-04-agent-terminal-mvp-design.md`（「作業中を画面から確実に判定できない」既知の制約、今後の課題の「状態の表示」「ステータスバー」）、`2026-10-09-agent-multi-session-tabs-design.md`（タブ・`useAgentSessions`）

## 目的

動いている `claude` が、いま何をしているか（作業中か、入力を待っているか、ツールの許可を待っているか、ほかの確認を待っているか）を、
タブ・パネルの帯・ステータスバーで分かるようにする。複数のタブで並行して動かしているときに、利用者の操作が必要なタブに気づけるようにする。

## 決めたこと（利用者の確認済み）

| 項目 | 決定 |
| --- | --- |
| 判定の方式 | 画面の読み取り。出力が落ち着いたら xterm の画面を読み、記録済みの画面の特徴で判定する。`claude` の起動の引数は空のまま（hooks は使わない） |
| 表示先 | タブ（印と読み上げの名前）・パネルの帯の状態の文言・ステータスバー（全タブのまとめ。押すとパネルを開き、利用者を待っているタブを選ぶ） |
| 状態の分け方 | ツールの許可の確認（`Do you want to …?`）を「許可待ち」、それ以外の入力欄の無い選択の画面（フォルダの信頼の確認・`/model`・新しい表示の案内など）を「確認待ち」とする |

## 範囲

含めるもの:

- 画面から活動の状態を判定する純粋な関数と、記録済みの画面（`agentScreens.json`）での固定
- タブごとに、出力のたびに（落ち着いてから）判定し直す仕組み
- タブの印・読み上げの名前・帯の文言の状態の細分化
- ステータスバーのまとめと、押したときの移動

含めないもの（ROADMAP の別項目）:

- 通知（ウィンドウが背面でも気づける。次の項目「完了・許可待ちの通知」）
- 状態の変化をきっかけにしたエージェントの変更の一覧の自動の取り直し
- `claude` の hooks による正確な検知
- 状態の変化の読み上げ（`aria-live`）。通知の項目で扱う

## 状態

既存のセッションの状態（`AgentSessionStatus`: `none`・`starting`・`running`・`exited`）はそのまま残し、`running` の間だけ、
画面から判定した**活動**（`AgentActivity`）を重ねる。

| 活動 | 意味 | 判定（上から順に、最初に当てはまったもの） |
| --- | --- | --- |
| `permission`（許可待ち） | ツールの実行の許可を待っている | 入力欄が無く、字下げのある番号付きの選択肢の行（` ❯ 1.` など。カーソルの `❯` の付いた行）から上へ、空行・ほかの番号付きの選択肢の行（`   1. Yes`。番号の桁がカーソルの行と同じ行に限る。折り返した問いの `2.md?` を飛ばさないため。ローカルレビュー第 14 周で変更）・その折り返しの行（番号の桁より深く字下げされた行）を飛ばした先の段落が問い。段落は、最初に当たった空でない行から上へ、番号の桁と同じかそれより浅い字下げの空でない行が続く間（空行・罫線の行 `────`・`╌╌╌╌` と、番号の桁より深く字下げされた行で区切る）で、その先頭の行が行頭の空白の後に `Do you want to ` で始まり、最後の行（選択肢の直上）が `?` で終わる（問いが画面の幅を超えると claude は 1 行目と同じ字下げで折り返すため。ローカルレビュー第 12 周で変更。問いと選択肢を画面全体から別々に探すと、履歴の `❯ 1. …` のプロンプトや応答の継続行の `  Do you want to …` で誤るため。ローカルレビュー第 11 周で変更） |
| `confirm`（確認待ち） | ほかの選択の画面で操作を待っている | 入力欄が無く、選択肢の行（1 文字以上の字下げの後が `❯ ` で、その後に文字がある。1 桁目から始まる `❯ hello` は会話の履歴に残る利用者のプロンプトなので選択肢とみなさない）か、`Enter to confirm` を含む行がある |
| `working`（作業中） | 応答・ツールの実行の途中 | スピナーの行（1 桁目がスピナーの文字〈`·✢✳✶✻✽*`〉で、空白の後に文字が続く行。作業の後の要約の行〈`✻ Worked for 1m 3s` のような、1 語 + ` for ` + 経過時間で終わる行〉と、`/compact` の後の圧縮の行〈スピナーの文字 + 空白 + `Conversation compacted` で始まる行〉を除く）があるか、`esc to interrupt` がある。入力欄のある画面では、スピナーの行は入力欄の上の罫線から上へ空行と字下げのある行（1 桁目が空白の行）を飛ばした最初の行だけ、`esc to interrupt` は入力欄の下の罫線より下の案内の行だけで見る（入力欄の無い画面は画面全体を見る） |
| `idle`（入力待ち） | 入力欄で次の指示を待っている | 入力欄がある（`locateInputBox` が見つける）。ただし入力欄が画面の高さを超えて上の罫線が見えない画面、および入力欄の上が画面の上端まで字下げの行で、上の罫線の上（空行を除いて最も近い）の字下げの行から上へ折り返しの継続行（字下げが todo の項目の記号の桁〈5 桁〉以上で、todo の項目の行でない行）を飛ばした最初の行（項目の先頭の行）が todo の項目の行（`☐☒◻◼` の記号の行。1 行目の `  ⎿  ☐ …` も 2 行目以降の `     ☐ …` も）か tip の行（`  ⎿  Tip: …`）でスピナーの行が見えない画面は除く（下の案内に `esc to interrupt` が無ければ `unknown`。最後の項目・tip が画面の幅で折り返された場合も同じ）。その項目の先頭の行が todo の項目の行・tip の行でない画面（画面より長い応答の継続行・箇条書き・ツールの結果・`!` のシェルのモードやスラッシュコマンドの出力〈テストランナーの `✔ …` の行を含む〉が上端まで続く画面）は `idle` |
| `unknown`（不明） | 上のどれにも当たらない（起動の直後の描画の途中・`claude` の版の違い・入力欄が画面の高さを超えて上の罫線が見えない、または入力欄の上が画面の上端まで字下げの行だけで、上の罫線の上の最も近い項目の先頭の行が todo の項目の行・tip の行でスピナーの行が見えず、作業中か入力待ちかの根拠が画面に無い場合など） | それ以外 |

- 書きかけがあると `esc to interrupt` が消える（記録済みの画面の `workingDraft`・`streamingDraft`）ため、スピナーの行で判定する。
  スピナーの行は書きかけがあっても残る。
- スピナーは入力欄の上に描かれ、その間には空行と字下げのある行（TodoWrite の一覧 `  ⎿  ☐ Step 1`・tip `  ⎿  Tip: …` など）だけが入る。会話の履歴にも同じ記号で始まる行（`/compact` の後の `✻ Conversation compacted · ctrl+o for history` など）や、本文中の `esc to interrupt` が残りうるため、入力欄のある画面では上の位置だけを見る（ローカルレビュー第 6 周の指摘で変更。それまでは画面全体を見ていた）。入力欄の無い画面（描き直しの途中など）は画面全体を見る。
- 第 6 周の変更では「上の罫線の直上の空でない最初の行」だけを見ていたため、スピナーの下に todo の一覧・tip が出ていて、入力欄に書きかけがある（`esc to interrupt` が消える）作業中の画面を `idle` と判定していた。ローカルレビュー第 7 周の指摘で、1 桁目が空白の行を飛ばした最初の行を見るように変更した。
- 圧縮の行は入力欄の直上（字下げの行を飛ばした最初の行。`  ⎿  Read …` が続く場合も）に来ることもあるため、要約の行と同じく、スピナーの文字 + 空白 + `Conversation compacted` で始まる行はスピナーの行とみなさない（同じ周の追加の修正）。
- スピナーの文字は 1 桁目だけを見る（`fullscreen` の画面の箇条書き `  · …` は字下げがあるので当たらない）。
- claude は作業を終えた後に `✻ Worked for 1m 3s`・`✻ Cooked for 12s` のような要約の行を 1 桁目から出すため、スピナーの文字 + 空白 + 1 語 + ` for ` + 経過時間（`12s`・`1m 3s`・`1h 2m 3s`）で終わる行はスピナーの行とみなさない（`…` を必須にはしない。記録済みの再試行の行 `✻ Connection refused — … · Retrying in 1s …` が作業中の根拠のため）。
- 表示の文言: `working` → `作業中`、`idle` → `入力待ち`、`permission` → `許可待ち`、`confirm` → `確認待ち`、`unknown` → `実行中`（従来の文言）。
- `starting` → `起動中`、`none` → `未起動`、`exited` → `終了`（帯は従来どおり `終了しました（終了コード N）`）は変えない。

### 判定に読む範囲

既存の `readViewportLines` は表示中の範囲（`viewportY`。利用者がスクロールで戻していれば、その位置）を読む。活動の判定は利用者のスクロールに
左右されないよう、**画面の末尾**（`baseY` から `rows` 行。`claude` が描いている現在の画面）を読む関数を足す。裏のタブ（取り外した xterm）も
バッファは更新され続けるので、同じく読める。

## 再判定のきっかけ

- controller に「出力を書き終えた」ことを購読する口（`onOutputWritten(listener)`。xterm の `onRender`〈画面の再描画〉と紛れないよう別の名前にする）を足す。`terminal.write(data, callback)` のコールバック
  （xterm が出力をバッファに反映し終えた時点）で呼ぶ。保留していた出力をセッションが決まって書き出したときも同じ。
- 活動の hook（下記）は、タブごとに最後の通知から **150ms**（`AGENT_ACTIVITY_SETTLE_MS`）出力が途絶えたら画面を読んで判定する（デバウンス。`setTimeout` を使う。
  ウィンドウが背面でも止まらないよう `requestAnimationFrame` は使わない）。
- 出力が途絶えなくても、最初の未判定の通知から **500ms**（`AGENT_ACTIVITY_MAX_WAIT_MS`。lodash の debounce の `maxWait` に当たる）が経てば判定する。
  claude は作業中にスピナー・経過時間・トークン数を描き続け、通知が 150ms より短い間隔で続くことがあるため（上限が無いと、入力待ち・許可待ちから作業に入ったとき、
  前の活動が作業の間ずっと残る）。判定したら上限の起点を消し、次の上限は判定の後の最初の通知から数える。
- 上限の判定は出力が続いている最中に画面を読むため、claude の描き直しの途中（入力欄・スピナーを消した後、描き直す前）を読みうる（pty の出力は塊ごとに届き、
  xterm の `write` も非同期に解析するため）。そこで上限の判定の結果が `unknown` なら採らず、前の活動を保つ。このとき上限の起点だけを消し、待ちのタイマーは残して、
  出力が途絶えた後の待ちの判定に任せる（待ちの判定なら `unknown` も採る）。
- セッションが変わったとき（起動・終了）は、そのタブの活動を `unknown` に戻し、待っている判定（待ちと上限の両方）を取り消す。
- タブが running に入ったとき（hook が初めて見たタブが running のときを含む）は、通知を待たずに 150ms 後の判定を予約する。起動の直後に保留していた出力を書き出した通知は running になる前に届いて捨てられ、その後 claude が何も描かずに入力欄で待つことがあるため。
- 判定の結果が前と同じなら state を更新しない（描画を増やさない）。

## 構成

### 判定（新規 `src/renderer/src/lib/agentActivity.ts`）

- `type AgentActivity = 'working' | 'idle' | 'permission' | 'confirm' | 'unknown'`
- `classifyAgentScreen(lines: readonly ViewportLine[]): AgentActivity` — 上の表の規則の純粋な関数。`locateInputBox`（入力欄と上下の罫線の行番号を返す。`agentInputBox.ts` に追加し、既存の `findInputBox` はこれを使う形にした）を使う。
  版に依存する規則（スピナーの記号・要約の行・中断の案内・許可の問い・確認の案内）はこのファイルの定数に閉じる。
- `describeAgentActivity(activity)` — 文言（`agentSessionMessages.ts` に置く）。`describeAgentTabStatus(status, activity)` は活動を必須の引数にし
  （渡し忘れると running のタブが常に `実行中` になるため）、`running` のときだけ活動の文言を使う。

### 画面の末尾の読み取り（`agentViewport.ts`）

- `readScreenLines(buffer, rows)` — `baseY` から `rows` 行を読む（`ViewportBufferLike` に `baseY` を足す）。

### controller（`agentTerminalController.ts`）

- `onOutputWritten(listener): () => void` — 出力を xterm がバッファに反映し終えたら呼ぶ。`dispose` の後は呼ばない。
- `readScreen(): ViewportLine[]` — `readScreenLines` を使う。
- 判定・デバウンス・活動の解釈は持たない（購読側の hook が持つ）。
- `TerminalLike.write` にコールバックの引数を足す（xterm の `write(data, callback)`）。

### 活動の hook（新規 `src/renderer/src/hooks/useAgentActivity.ts`）

- 入力: タブの一覧（`slotId`・`controller`・`status`。`useAgentSessions` の `tabs` をそのまま渡す）、判定の関数 `classify`（既定は `classifyAgentScreen`。テストで差し替える）。
- タブごとに controller の `onOutputWritten` を購読し、デバウンス（上限の待ち付き）して `classify(controller.readScreen())` を判定する。
  `status` が `running` でないタブは判定せず `unknown` とする。セッションの区切りは `status` の変化（running へ入る・出る）で見る。
  タブごとの控え（購読・判定のタイマー〈待ちと上限〉・前回 running だったか）は 1 つの記録にまとめ、`acquireWatch`（初めて見たとき・controller が変わったときだけ購読を張る）と
  `releaseWatch`（購読の解除とタイマーの取り消し）で出し入れする。タブが消えたとき・アンマウントのとき（StrictMode の取り付け直しを含む）にまとめて手放す。
- 出力: `ReadonlyMap<slotId, AgentActivity>`。
- `useAgentSessions` とは分ける（セッションの起動・停止の手順と、画面の解釈は変更の理由が違う）。`useAgentWorkspace` で組み合わせ、
  結果の Map をタブの表示用のデータ（`AgentSessionTabView`）とは別に、`AgentTerminalPanelState.activities`（パネル）と
  ステータスバーの hook（下記）へ渡す。

### ステータスバーのまとめ（新規 `src/renderer/src/lib/agentActivitySummary.ts`）

- 純粋な関数だけを置く。`summarizeAgentActivities(tabs, activities)`（running のタブの活動を数え、並び `SUMMARY_ORDER` の順に 0 件を除いて並べる）、
  `pickWaitingTab(tabs, activities, selectedSlotId)`（押したときに選ぶタブ。利用者を待っている活動〈許可待ち・確認待ち・入力待ち〉を `SUMMARY_ORDER` の順に見て、
  同じ活動なら選択中のタブ、選択中のタブが当たらなければ並びの先頭）、
  `needsAgentAttention(items)`（強調の判定）、`formatAgentActivitySummary(items)`（表示の文言）、`describeAgentActivitySummary(items)`（`aria-label`）。
- 並び順の知識は `SUMMARY_ORDER` の 1 か所に置く（まとめで先に出る活動と、押したときに選ばれるタブを食い違わせないため）。
  `SUMMARY_ORDER` は活動ごとの順位 `SUMMARY_RANK`（`Record<AgentActivity, number>`）から組み立て、活動の種類を増やしたときに順位の足し忘れ（そのタブがまとめから黙って抜ける）を型エラーにする。

### ステータスバーの hook（新規 `src/renderer/src/hooks/useAgentStatusBar.ts`）

- 入力: 方式（`enabled`）・タブの一覧・選択中のタブ（`slotId` と `controller` の `focus`）・`selectTab`・活動の Map・`openPanel`。
- 出力: `AgentStatusBarState | null`（`items`・`needsAttention`・`onActivate`。エージェント CLI 方式でなければ `null`）。型は lib の型を含むため、
  共通の型（`types.ts`）ではなくこの hook に置く。`useAgentWorkspace` が `statusBarAgent` として返し、`useAppState` → `App` → `StatusBar` へ渡す。
- 押したときは、パネルを開き、`pickWaitingTab` のタブを選び、描画の後（そのタブの xterm が取り付けられてから）にフォーカスを移す。
  数え方・選ぶタブ・文言は `agentActivitySummary` に任せ、hook は副作用の順序だけを持つ。

### 表示

- **タブ**: 印の色・形を活動で分ける（`working` は緑の中抜きの輪で点滅する〈`prefers-reduced-motion` では点滅しないが、輪の形は変わらない〉、
  `idle` は緑の塗りの丸、`permission`・`confirm` は橙の角の丸い四角〈`border-radius: 2px`。大きさは丸と同じ〉、`unknown`〈`実行中`〉は色は従来どおりの青緑のまま、形を中心に点のある輪にする〈class `agent-session-tabs__dot--unknown`〉、
  `running` でないタブは従来どおり）。`working` と `idle` は同じ緑なので、点滅が無くても形で見分けられるようにする。`unknown` と `idle` も色相の差（青緑と緑）
  だけでは色覚の多様性で見分けにくく、判定が外れた（`claude` の版の違いなど）タブを入力待ちと誤認させないよう形を変える（ローカルレビュー第 3 周で変更）。
  `permission`・`confirm`（利用者の操作が要る）と `idle`（次の指示を待つだけ）も、橙と緑の色相の差だけでは第 1・第 2 色覚で見分けにくいため、橙を角の丸い四角にして形で分ける（第 9 周で変更）。読み上げの名前は `claude 2（許可待ち）` のように活動の文言にする。
- **帯**: 選択中のタブの状態の文言を活動の文言にする（`running` のとき）。
- **ステータスバー**（`StatusBar.tsx`。この機能の前は固定の飾りだった。props `agent` は必須で、`null` なら出さない）:
  - エージェント CLI 方式で、`running` のタブが 1 つ以上あるときだけ（閉じる途中〈`isClosing`〉のタブは `running` のままでも数えず、押したときの選択の候補にもしない。
    間もなく消えるタブへフォーカスを移さないため。`running` のタブがすべて閉じる途中ならまとめは出ない。ローカルレビュー第 4 周で変更）、左側に「エージェント: 許可待ち 1 · 作業中 2」のようなまとめを出す。
    並びは 許可待ち → 確認待ち → 作業中 → 入力待ち → 実行中（不明）、0 件の活動は出さない。
  - 操作が必要な活動（許可待ち・確認待ち）が 1 つでもあれば強調する（ボタンの背景をタブの印と同じ橙 `#e08a3c`、文字を濃い色 `#1e1e1e` にする）。
  - ボタンにする（`aria-label` は見える文字そのままに `（押すとターミナルを開きます）` を足したもの。例: `エージェント: 許可待ち 1 · 作業中 2（押すとターミナルを開きます）`。見える文字を名前に含めるのは、音声操作が見える文字で当たるようにするため〈ローカルレビュー第 4 周で変更〉）。押すと、パネルを開き（最大化は
    変えない）、許可待ち → 確認待ち → 入力待ち の順で最初に当たるタブを選択し、そのタブのターミナルへフォーカスを移す。同じ活動のタブが
    複数あれば選択中のタブを選び（同時に起きやすい入力待ちなどで、押すたびに見ていたタブから外れないため。ローカルレビュー第 3 周で変更）、
    選択中のタブがその活動でなければ並びの先頭を選ぶ。当たるタブが無ければパネルを開くだけ。
  - タッチで押せる大きさ（32px 以上の高さ）にする。

## エラーと境界の扱い

- 判定は例外を投げない。読めない行（バッファに無い行）は、画面の読み取り（`agentViewport` の `readLines`）が空の行にして判定へ渡すので、判定は読めない行を扱わない。`unknown` は従来どおり `実行中` と表示するので、誤判定より不明に倒す。
- 起動の直後（描画の途中）は `unknown` になりうる。描画が落ち着けば判定し直される。
- 利用者がターミナルをスクロールで戻していても、画面の末尾を読むので判定は変わらない。
- 閉じたタブの controller からの通知は、活動の hook がタブの消えたときに自分の購読を外し、controller も `dispose` で購読を空にするので届かない。

## 既知の制約（ROADMAP・実機テスト仕様書に反映する）

- 画面の見た目から判定するため、`claude` の版で画面が変わると判定が外れうる（記録済みの画面は `claude` 2.1.288）。外れたときは `実行中` と表示する。
  版を上げたら、記録済みの画面を記録し直し、判定のテストを流す。
- 入力欄が画面の高さを超えて上の罫線が見えない画面（書きかけが長い）は、スピナーの行が画面の外にあり、書きかけがあると `esc to interrupt` も消えるため、作業中か入力待ちかを判定できないので `実行中` と表示する（出力が続いている間は前の活動を保つ）。
- 入力欄の上が画面の上端まで字下げの行（todo の一覧など）で続き、スピナーの行が画面の外に押し出された画面も、書きかけがあると `esc to interrupt` が消えて根拠が無いので同じく `実行中` と表示する（ローカルレビュー第 18 周）。根拠なしとするのは、上の罫線の上（空行を除いて最も近い）の字下げの行から上へ折り返しの継続行（字下げが todo の項目の記号の桁〈5 桁〉以上で、todo の項目の行でない行。`       configuration format`・`     CLAUDE.md files` など）を飛ばした最初の行（項目の先頭の行）が todo の項目の行（`/^\s*(?:⎿\s+)?[☐☒◻◼]\s/`。`⎿` の有無を問わないので、1 行目が画面の外に出て 2 行目以降だけが見える場合も含む）か tip の行（`/^\s*⎿\s+Tip:/`）のときだけで（todo の一覧・tip は入力欄の直上に描かれる）、そうでなければ画面より長い応答の継続行・箇条書き・ツールの結果・`!` のシェルのモードやスラッシュコマンドの出力とみなして `入力待ち` とする（ローカルレビュー第 19・20 周）。第 19 周までは `⎿` で始まる行すべてを根拠なしの根拠にしており、`! git log` や `/context` の出力が上端まで続く入力待ちの画面を `実行中` と表示していた（第 20 周で修正）。第 20 周までは飛ばした字下げの行のどれか 1 行が todo の項目の行・tip の行なら根拠なしとし、todo の記号に `✔` を含めていたため、`! node --test`・`! npx mocha` の出力（合格したテストの行の先頭の `✔`）が上端まで続く入力待ちの画面を `実行中` と表示していた（第 21 周で、見る行を上の罫線の上の字下げの行だけにし、`✔` を記号から外して修正）。第 21 周の版は最も近い字下げの行だけを見たため、最後の todo の項目・tip が画面の幅で折り返されると継続行を見て、作業中の画面（書きかけあり）を `入力待ち` と表示していた（第 22 周で、継続行を飛ばして項目の先頭の行で判定するよう修正）。todo の項目の記号（`☐☒◻◼`）は `claude` 2.1.288 で記録した画面が無い手書きの推測で、`claude` の版で外れうる（外れると、todo の一覧がスピナーを押し出した作業中の画面〈書きかけあり〉を `入力待ち` と表示する）。todo の一覧が出る作業中の画面を `agentScreens.json` に記録できたら記号を確かめる。
- 判定は出力が 150ms 途絶えた後（出力が続いていても最初の未判定の通知から 500ms 以内）なので、作業の始まり・終わり・許可の確認の出現の表示は少し遅れる。
- 作業中に何も描画しない時間が長い場合（スピナーが止まる・ネットワークの待ちなど）でも、最後に描いた画面で判定するため、そのまま作業中と表示する。
