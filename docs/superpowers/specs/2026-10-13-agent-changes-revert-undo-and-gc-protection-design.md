# エージェントの変更の戻した操作の取り消しと記録の gc からの保護 設計書

- 日付: 2026-10-13
- ROADMAP の項目: 「エージェント実行の支援（MVP の次）」→「エージェントの変更の確認の拡張」の残りのうち、(1) 戻した操作の取り消し、(2) 記録の blob を gc から守る
- 前提の設計書: `2026-10-06-agent-changes-review-design.md`（記録のインデックス・戻す操作・確認の結果 12・21・22〈gc の後は戻せない〉・「undo の可否」）、`2026-10-12-agent-changes-runs-and-auto-refresh-design.md`（累積の始点と実行の区切り・`tree`・所有者の列・静かな取り直し）、`2026-10-04-agent-terminal-mvp-design.md`（IPC の安全策）

## 目的

エージェントの変更のセクション（ソース管理パネル）の「戻す」操作（行の `↶`・diff タブのハンクの `このハンクを実行前に戻す`・`すべて戻す`）は、確認のダイアログで「この操作は元に戻せません」と出し、押し間違えると戻した内容（エージェントの変更）を取り返せない（ゴミ箱へ移した追加のファイルだけは OS のゴミ箱から戻せる）。また、記録（累積の始点と実行の区切り）の blob と tree はどの ref からもたどれず、記録中に利用者が `git gc --prune=now`（または `gc.pruneExpire=now` の設定での gc）を実行すると消え、戻す操作は拒否され、一覧と途中の実行の表示も失敗する（2026-10-06 の確認の結果 12・22）。

この機能では、(1) 直前の 1 回の戻す操作を、セクションの帯のボタンで取り消せるようにし、(2) 記録中だけ、記録の tree を利用者のブランチと別の専用の ref からたどれるようにして、gc で消えないようにする。

## 決めたこと（利用者の確認済み）

| 項目           | 決定                                                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 範囲           | 戻した操作の取り消しと、記録の blob を gc から守ることの 2 つ                                                                                                      |
| 取り消しの回数 | 直前の 1 回だけ（取り消しの取り消し〈やり直し〉は無い）                                                                                                            |
| 入口           | セクションの帯のボタン（戻した直後にセクションに「戻した操作を取り消す」を出す。次の戻す操作・確認を終える・フォルダの切り替えなどまで）。ショートカットは付けない |
| gc の守り      | 記録中だけ、専用の ref（`refs/prompt-ide/...`）から記録の tree をたどれるようにする。確認を終える・フォルダの切り替え・アプリの終了などで消す                      |

## 決めたこと（推奨案で決めた事項）

| 項目                                  | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | 理由                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 取り消しのために保存するもの          | 戻す操作が書き換える各パスについて、戻す**直前**の作業ツリーの状態（無い・ファイルの中身のバイト列と権限・シンボリックリンクの指す先）と、戻した**直後**の状態の指紋（無い・ファイルの大きさと中身の SHA-256 と権限・リンクの指す先）を控える。直前のファイルの中身は、記録と同じアプリの一時ディレクトリ（`fs.mkdtemp`・0700。接頭辞 `prompt-ide-agent-undo-`）にファイルとして写す                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | 取り消しは「戻す前のバイト列」へ正確に戻す必要がある。object の DB（`git hash-object`）に書いて `git restore` で戻すと、clean・smudge のフィルタと改行コードの変換（`text=auto`・`core.autocrlf`）がかかり、戻した後の内容がバイト単位で違いうる（2026-10-06 の既知の制約と同じ）。一時ディレクトリなら gc に関係せず、専用の ref の寿命とも絡まず、`git push --mirror` で戻す前の内容が送られることも無い                                                                                                                                                         |
| 保存する場所と寿命                    | 取り消しの控えは、main の registry の記録（`AgentChangesRecord`）に `undo`（0 か 1 つ）として持つ。控えの一時ディレクトリは、取り消しを実行した・次の戻す操作で置き換えた・記録を捨てた（確認を終える・所有者の文脈の終わり）・アプリの終了で消す                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | 取り消しの控えは記録（戻す先の始点）と同じ寿命の範囲でしか意味を持たない。記録に持たせれば、記録を捨てる既存の契機（`clear`・`close`）でまとめて消せる（`agentChangesRecordTempDirs` に足す）                                                                                                                                                                                                                                                                                                                                                                      |
| 控えの上限                            | 控えるファイルの中身の合計が 100MB（`AGENT_CHANGES_UNDO_MAX_BYTES`。記録の未追跡のファイルの合計の上限と同じ値）を超える、または対象に追加されたフォルダ（`isDirectory`。ゴミ箱へ移す）を含む戻す操作は、控えを取らずに戻す（取り消せない）。対象の今の種類がファイルとリンク以外（FIFO など）のときも同じ。戻した後の状態の控え（`after`。SHA-256 はストリームで計算する。作り直したファイル〈before が無い〉は上限の対象外で大きくなりうるため、全体をメモリに読まない）が取れなかったとき（`lstat`・読み込みの失敗、適用の後にディレクトリ・ファイルとリンク以外が現れた、`before`・`after` がどちらも無い）は、戻す操作を成功のまま、控えを null にする。理由は `AgentRevertUndoOutcome` の `unavailable` の `reason`（`directory`・`too-large`・`unsupported-type`・`capture-failed`）で返し、戻した結果の読み上げで伝える                                                                                                                                                                                                        | 追加されたフォルダ（`node_modules/` など）は中身が大きく、写すと戻す操作が重くなる（OS のゴミ箱から戻せる）。上限を超えたときに戻す操作そのものを拒むと、今まで戻せたものが戻せなくなる。`after` は作業ツリーを変えた後にしか取れないため、取れなかったことで戻す操作を失敗にすると、変わった作業ツリーを失敗として伝えてしまう（L-001）                                                                                                                                                                                                                           |
| 控えを取る順序                        | 戻す操作は、既存の検査（一覧に含まれるか・分類・重なり・blob の存在・`filter=`）の後、作業ツリーを変える**前**に控えを取る。控えの書き込み・読み込みが上限以外の理由（権限・ディスクの空き）で失敗したら、何も変えずに戻す操作を中止する（`取り消しの準備に失敗したため、戻すのを中止しました: <path>`）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | 確認のダイアログで「直後なら取り消せる」と見せてから戻すため、控えが取れないまま取り消せない書き換えをしない（L-003）                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| 直前の控えを置き換える条件            | 新しい戻す操作が作業ツリーを 1 件以上変えたときだけ、前の控えを捨てて新しい控え（取れなかったときは「無し」）にする。新しい戻す操作が何も変えずに失敗した（一覧と合わない・拒否・例外）ときは、前の控えを残す。置き換えは registry の公開のメソッド `commitRevertUndo(ownerId, record, result)` が行い、registry が `closed`・記録が今の記録でない（戻す操作の途中で捨てられた）ときは新しい控えを付けずに消し、結果の `undo` を `discarded` にする                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | 「直前に戻した操作」は、作業ツリーを実際に変えた最後の戻す操作を指す。何も変えなかった依頼で前の取り消しの機会を消さない。前の控えを捨てるのは新しい結果が決まった後にする（L-003）。新しい操作が取り消せない（上限）なら、古い操作を「直前」として出し続けない                                                                                                                                                                                                                                                                                                    |
| 取り消してよいかの照合                | 取り消しの実行時に、控えたすべてのパスの今の状態が「戻した直後の指紋」と一致することを、書き換えの前に全件確かめる（大きさ・SHA-256・権限・種類・リンクの指す先。直後に無かったパスは今も無いこと）。あわせて、各パスの親のフォルダが、許可のフォルダの下の本物のディレクトリ（シンボリックリンクでない）であることを確かめる。全件を照合してから判定し、不一致が 1 件でもあれば（読み込みの失敗が混ざっていても）何も書き換えずに拒否して控えを捨てる（`戻した後に変わったファイルがあるため、取り消せません（<最大 5 件>）`）。不一致が無く読み込みの失敗（`ENOENT` 以外）があるときは、何も書き換えずに拒否し、控えを残す                                                                                                                                                                                                                                                                                                                                                                                                           | 戻した後に利用者・エージェントがそのファイルをさらに変えていたら、取り消しはその変更を黙って上書きする。既存の `すべて戻す` の expected の照合と同じく、状態の組（パスと中身）で完全に照合する（L-036）。件数や更新時刻ではなく中身で比べる（L-422 と同じく、時刻は同じ秒の書き換えで当てにならない）。照合に失敗した控えは以後も必ず失敗するため、ボタンを出し続けない                                                                                                                                                                                            |
| ファイルの種類ごとの取り消しの動作    | 戻す前と戻した後の組で、動作を肯定の根拠で決める。「書き戻す」: 前がファイル・リンクで後もファイル・リンク（変更 `M`・種類の変更 `T`・ハンク）。「作り直す」: 前がファイル・リンクで後が無い（追加 `A` のファイルをゴミ箱へ移した）。「ゴミ箱へ移す」: 前が無く後がファイル・リンク（削除 `D` を記録の時点の内容で作り直した）。前も後も無い・ディレクトリ・それ以外の種類（FIFO など）は控えの時点で「取り消せない」にする                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | 「一覧に無いから追加」のような否定の分類をしない（L-006）。作り直したファイルを消すときも、既存の戻す操作と同じくゴミ箱を経由する（完全な削除をしない）                                                                                                                                                                                                                                                                                                                                                                                                            |
| 書き戻しの方法                        | 「書き戻す」は、同じフォルダに元の名前によらない短い一時の名前（`.prompt-ide-undo-<乱数 16 桁の 16 進>`）へ控えを `copyFile(…, COPYFILE_EXCL)` で写してから権限を控えの値にし、`rename` で置き換える。「作り直す」は、一時の名前へ控えを写して権限を控えの値（`before.mode`）にしてから `link` で目的の名前を作り（既にあれば `EEXIST` で止まる）、一時の名前を消す。`link` が `EPERM`・`ENOTSUP`・`EXDEV` で失敗した（ハードリンクを作れないファイルシステム）ときは、一時の名前を消してから `copyFile(控え, パス, COPYFILE_EXCL)` で目的の名前に直接写し、権限を `before.mode` にする（既にあれば `EEXIST` で止まる。権限を変えられなければ、自分が写せたそのファイルを消す）。どの写しも中身を main のメモリに読まない。リンクは `symlink`（既にあれば `EEXIST`）。書く直前に、そのパスの照合をもう一度行う。git は使わない                                                                                                                                                                                                         | 途中で失敗しても元のファイルが半端な内容にならない（L-014）。照合の後に同じ名前のものが現れても上書きしない（L-011）。一時の名前を元の名前から作ると、長い名前で `ENAMETOOLONG` になる。exFAT・FAT・一部のネットワークのフォルダはハードリンクを作れないため、`link` だけに頼ると作り直しが必ず失敗する（直接書く方式は途中の失敗で半端なファイルが一瞬見えうるが、自分が作ったものとして消す）。git の `restore` を使わないので、フィルタ・改行コードの変換がかからず、控えたバイト列のまま戻る                                                                   |
| 取り消しの途中の失敗                  | 照合をすべて通った後の書き換え（`rename`・`link`・直接の書き込み・ゴミ箱）で失敗したら、そこで止め、1 件以上済んでいれば `partial`（`取り消しが途中で失敗しました（k / n 件を取り消し済み）: <path>: <理由>`）、0 件なら例外 `取り消しに失敗しました: <path>: <理由>` にする。書く直前の照合で合わなかったときも同じくそこで止め、理由は `<path> が戻した後に変わりました`（0 件なら例外 `戻した後に変わったファイルがあるため、取り消せません（<path>）`）、書く直前の照合で読み込めなかったときは理由を `<path> を読み込めませんでした: <理由>`（0 件なら例外 `取り消しに失敗しました: <path> を読み込めませんでした: <理由>`）にする。書き換えを始めた後は、成功・失敗に関わらず控えを捨てる。書き換えの前の全件の照合で、不一致が無く読み込みの失敗（権限など）だけがあったときは控えを残す                                                                                                                                                                                                                                        | 既存の `すべて戻す` の `partial` と同じ扱い（パターン 52・L-038）。書き換えの途中で止まった後は、控えの「戻した直後」の前提が崩れているため、同じ控えで続けさせない                                                                                                                                                                                                                                                                                                                                                                                                |
| 取り消しの ID                         | 控えに `undoId`（所有者ごとに単調に増える正の整数。記録を捨てても戻さない）を振る。renderer は帯に出した控えの `undoId` を取り消しの依頼に渡し、main は記録の今の控えの `undoId` と一致するときだけ取り消す（違えば `取り消せる操作が変わりました。一覧を更新してください`）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | 「直前の操作」という位置で指すと、帯を見てから押すまでの間に別の戻す操作（別の経路・古い写し）で控えが入れ替わったとき、見ていない操作を取り消す（L-035・L-037）                                                                                                                                                                                                                                                                                                                                                                                                   |
| 取り消しと範囲（累積・実行 N）        | 取り消しは、セクションで選んでいる範囲に関わらず使える（実行の範囲でもボタンを押せる）。IPC に範囲の引数を持たせない                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | 戻す操作を累積の範囲に限ったのは、実行の範囲の diff から作ったパッチを逆適用すると戻す先が変わるため。取り消しは一覧・diff の内容を使わず、main の控えだけで決まる                                                                                                                                                                                                                                                                                                                                                                                                 |
| 取り消しの対象が無くなる契機          | (a) 次の戻す操作が作業ツリーを変えた（新しい控えに置き換わる）、(b) 取り消しを実行した（成功・`partial`・照合の不一致）、(c) 確認を終える、(d) フォルダの切り替え・リロード・ウィンドウの破棄・renderer の終了（所有者の文脈の終わり）、(e) アプリの終了。プロンプトの送信（実行の区切り）・一覧の取り直し・範囲の切り替え・Git の操作・アプリでの保存では消さない                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | 利用者の決めた「次の戻す操作・確認を終える・フォルダの切り替えなどまで」に合わせる。送信や保存の後も、取り消しの実行時の照合が「戻した後に変わったファイル」を拒むため、続けて送っただけで取り消しの機会を消す必要が無い                                                                                                                                                                                                                                                                                                                                           |
| 取り消しの状態の持ち主                | 控えの有無・`undoId`・対象のパスと動作の真実の源は main。`getState`・`begin`・`list` の結果（`recording`・`scope-unavailable`）に `undo`（要約。無ければ null）を入れ、renderer は写しから帯を出す                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | 記録の状態と同じく、renderer が独自の状態を持つと main とずれる。一覧の取り直しのたびに main の値へ戻る。静かな取り直しの写しの比較（`isSameAgentChangesView`）は中身の比較なので、`undo` が変わったときだけ写しが置き換わる（L-423）                                                                                                                                                                                                                                                                                                                              |
| 帯の配置と文言                        | セクションの本文の先頭（範囲の選択の直後、エラーと一覧の上）に帯を置く。文言は `直前に戻した操作: <対象>`（対象は戻した操作の種類〈`operation`〉で決める。`file` なら `a.txt`、`hunk` なら `a.txt のハンク`、`all` なら件数に関わらず `3 件（すべて戻す）`〈1 件でも `1 件（すべて戻す）`〉）と、ボタン `戻した操作を取り消す`（`aria-label="戻した操作を取り消す（直前: <対象>）"`）。押せない理由は帯の中に見える文字で出し、ボタンの `aria-describedby` で結ぶ                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | 一覧が空になった後（`すべて戻す` の後）も見える位置にする。既存の理由の領域（一覧の上の 1 か所）は「すべて戻す」の理由を優先して出す作りで、取り消しの押せない理由（実行中・他の Git 操作）と食い違うため、帯に自分の理由を持たせる（L-057）                                                                                                                                                                                                                                                                                                                       |

## 範囲

含めるもの:

- 戻す操作（ファイル・ハンク・すべて）の前後の控えと、直前の 1 回の取り消し（main の控え・照合・書き戻し、IPC、セクションの帯、確認の文言、画面の更新）
- 戻す操作の確認の文言・結果の読み上げの変更（取り消せるか）
- 記録中の専用の ref による記録の tree の保護（作成・更新・削除・終了時の削除・異常終了で残った ref の掃除）
- 既知の制約・前の設計書・ROADMAP の該当の記述の更新

含めないもの（頼まれていない。ROADMAP の「エージェントの変更の確認の拡張」に残す）:

- 2 回以上前の戻す操作の取り消し、取り消しの取り消し（やり直し）
- 取り消しのショートカット・diff タブやターミナルの帯からの取り消し
- 追加されたフォルダをゴミ箱へ移した操作の取り消し（OS のゴミ箱から戻す）
- 既存のソース管理の取り消し（「変更」の `↶`・ハンク・`すべて取り消す`）の取り消し
- `claude` の hooks で利用者の編集と区別すること、Git 管理外のフォルダでの記録
- 保護の ref の状態の画面への表示

## 確認の結果（設計時に実測。2026-10-13）

macOS 26.6（arm64）・git 2.50.1（Apple Git-155）で、scratchpad の一時ディレクトリに作ったリポジトリで確かめた（このリポジトリの作業ツリー・`.git` は変えていない）。git は `GIT_CONFIG_GLOBAL=/dev/null`・`GIT_CONFIG_NOSYSTEM=1`・`LC_ALL=C` で利用者の設定から切り離した。

1. **ref は tree を直接指せる**: `git update-ref refs/prompt-ide/agent-changes/x/1/baseline <tree>` は終了コード 0 で、`git for-each-ref` に `tree` として出た。`git mktree` に `040000 tree <sha>\tbaseline` の行を渡すと、記録の tree を子に持つ tree ができ、その ref から子の tree の blob までたどれた
2. **tree を指す ref は、履歴の表示に出ない**: その ref がある状態で、`git log --all --oneline`・`git log --all --graph`・`git rev-list --all` はコミットだけを出し、エラーにならなかった。`git branch -a`・`git describe --all` にも出なかった。`git show-ref`・`git for-each-ref` には出た。`git fsck` は何も出さなかった
3. **ref からたどれる blob は `git gc --prune=now` で消えない**: 作業ツリーのファイルを消してから `git gc --prune=now` を実行しても、ref の tree の（入れ子の tree の下の）blob は `git cat-file -t` で `blob` のままだった。ref を消してから同じ gc を実行すると、`could not get object info` で消えていた
4. **compare-and-swap**: `git update-ref -z --stdin` の `create <ref> <値>` は、ref が既にあると `fatal: cannot lock ref '…': reference already exists`（終了コード 128）で失敗した。`delete <ref> <値>` は値が違うと `is at <今の値> but expected <値>` で失敗した。どちらも stderr に出力があり、何も変えなかった。`git pack-refs --all` で packed-refs に入った ref も、正しい値の `delete` で消えた
5. **`update-ref` は `reference-transaction` の hook を動かす**: `.git/hooks/reference-transaction` を置くと、`update-ref` で `prepared`・`committed` の 2 回動いた。`-c core.hooksPath=<存在しないディレクトリ>` を付けると動かなかった
6. **`git mktree` は gitlink の commit の存在を確かめない**: `160000 commit <存在しない sha>\tsub` を含む行でも tree を作れた（記録の tree の入れ子のリポジトリ〈gitlink〉を子に持っても作れる）。blob・tree の項目は存在を確かめる（`--missing` を付けないとき）
7. **`git push --mirror` は ref を送る・既定の clone と fetch は受け取らない**: bare のリポジトリへ `push --mirror` すると、送り先に `refs/prompt-ide/...` の tree の ref ができた。そこから既定の `git clone`・`git fetch` をしたリポジトリには、その ref は来なかった
8. **SHA-256 のリポジトリ・linked worktree**: `--object-format=sha256` のリポジトリでも `create` で作れた（64 桁の tree の ID）。`git worktree add` で作った worktree で作った ref は、元のリポジトリの `for-each-ref` にも出た（`refs/prompt-ide/` は worktree の間で共有される）
9. **速さ**: `git mktree`・`git update-ref -z --stdin` は、どちらも約 0.01 秒だった

## 戻した操作の取り消し（main）

### 控えの中身（新しいファイル `agentChangesUndoModel.ts`）

控えの型（`AgentChangesUndo` など）は `agentChangesUndoModel.ts` に置き、控えを取る・照合する・書き戻すファイルの読み書きは `agentChangesUndo.ts` が持つ（SRP リファクタリングの第 3 周で分けた）。

記録（`AgentChangesRecord`）に `undo: AgentChangesUndo | null` を足す。

| 項目        | 内容                                                                                                                                                                                                   |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `undoId`    | 所有者ごとに単調に増える正の整数（registry が記録とは別の `Map<ownerId, number>` で振る。`clear` でも戻さない。`runId` と同じ作り）                                                                    |
| `operation` | `'file'`・`'hunk'`・`'all'`（帯の文言に使う）                                                                                                                                                          |
| `dir`       | 控えの一時ディレクトリ（`prompt-ide-agent-undo-`。記録の一時ディレクトリとは別）                                                                                                                       |
| `items`     | パスの昇順。各要素は `path`（リポジトリ相対。末尾の `/` なし）・`before`・`after`                                                                                                                      |
| `before`    | `{ kind: 'absent' }`・`{ kind: 'file'; savedName; mode }`（`savedName` は控えの一時ディレクトリの中の連番のファイル名。パスを名前に使わない。`mode` は `mode & 0o777`）・`{ kind: 'symlink'; target }` |
| `after`     | `{ kind: 'absent' }`・`{ kind: 'file'; size; sha256; mode }`・`{ kind: 'symlink'; target }`                                                                                                            |

取り消しの動作は `before`・`after` の組から決める（「決めたこと」の種類ごとの動作）。

| 戻した操作                                    | `before`                                    | `after`          | 取り消しの動作 |
| --------------------------------------------- | ------------------------------------------- | ---------------- | -------------- |
| 変更（`M`）・ハンク                           | ファイル・リンク                            | ファイル・リンク | 書き戻す       |
| 種類の変更（`T`）                             | ファイル・リンク                            | ファイル・リンク | 書き戻す       |
| 追加（`A`）のファイルをゴミ箱へ               | ファイル・リンク                            | 無い             | 作り直す       |
| 削除（`D`）を記録の時点の内容で作り直した     | 無い                                        | ファイル・リンク | ゴミ箱へ移す   |
| 追加されたフォルダをゴミ箱へ（`isDirectory`） | 控えを取らない（取り消せない。`directory`） | —                | —              |

`before` を取るときに、パスがディレクトリ・FIFO などファイルとリンク以外だった項目があれば、その戻す操作の控えは取らない（`unsupported-type`。追加されたフォルダの行は `directory`）。`after` を取るときに、`lstat`・読み込みが失敗した、ファイルとリンク以外が現れた、`before`・`after` がどちらも `absent` になった項目があれば、戻す操作は成功のまま控えを捨てる（`capture-failed`。下の「戻す操作の流れの変更」）。

### 戻す操作の流れの変更（`agentChangesRevert.ts`）

戻す 3 つの関数（`revertAgentChange`・`revertAgentChangeHunk`・`revertAllAgentChanges`）の今の手順（いまの一覧との照合 → 全件の検査 → 適用）の、検査と適用の間に控えを挟む。関数は文脈で控えの設定（`undoCapture`: 控えの一時ディレクトリを作る場所 `tempRoot` と上限 `maxBytes`）を受け取り、`withUndoRecorder` で控えの部品（`startAgentChangesUndoRecorder` が返す recorder。`recordAfter`・`finish`・`discard`）を始めてから適用する。

1. 既存の検査（一覧に含まれるか・照合・分類・重なり・blob の存在・`filter=`・コンフリクト）。ハンクはパッチの検査（`verifyHunkPatch`）までをここに含める。ここで拒否したら何も変えない（今と同じ）
2. 控えの準備（`startAgentChangesUndoRecorder(folderPath, targets, undoCapture)`。ハンクでは `verifyHunkPatch` の後）: 対象に追加されたフォルダがあれば `directory`。各パスを `lstat` し、ファイルとリンク以外があれば `unsupported-type`。ファイルは大きさを足し合わせ、合計が上限を超えたら `too-large`（読み込まない）。どれでもなければ、控えの一時ディレクトリを作り（`mkdtemp`）、ファイルは控えのディレクトリへ `copyFile(元, 控え, COPYFILE_EXCL)` で写して権限を 0600 にし（中身を main のメモリに読まない。PR #55 のレビューの指摘で `readFile` から変えた）、リンクは `readlink` の結果を持つ。`ENOENT` は `absent`。それ以外の失敗は控えの一時ディレクトリを消して例外（戻す操作の中止。作業ツリーは変えていない）
3. 適用（今と同じ `applyDiscard`・`discardHunkPatch`・`applyInOrder`）。1 件を適用するたびに、控えを取っていればそのパスの `after`（`lstat`・ファイルは中身の SHA-256。`createReadStream` で読みながら `createHash('sha256')` に流して計算し、ファイル全体をメモリに読まない）を控える。`after` の控えが失敗した（`lstat`・読み込みの失敗、ディレクトリ・ファイルとリンク以外が現れた、`before`・`after` がどちらも `absent`）ときは、例外にせず適用を続け、控えを `capture-failed` にする（控えの一時ディレクトリはその時点で消す）。戻す操作の成否は今どおり適用の結果だけで決める（L-001）
4. 結果: 適用した件数と、控え（取れたなら `AgentChangesUndo` の材料、取れなかったなら理由）を返す。`partial` では適用した項目だけを控えに入れる（途中で失敗した項目と、適用しなかった項目は入れない）
5. 後始末: 戻す関数は、2 で作った控えの一時ディレクトリを `try`/`finally` で持ち、関数が例外で終わる（適用が 0 件の失敗）・控えを `capture-failed` にしたときは、自分で消してから返す。控えの一時ディレクトリの持ち主は、結果を返すまでは戻す関数、返した後は `commitRevertUndo`（記録へ移すか消す）

handler は記録の列の中（`withRecord` のタスクの中）で、戻す関数の結果を registry の公開のメソッド `commitRevertUndo(ownerId, record, result)` に渡す（handler の `deps.registry` の `Pick` に `commitRevertUndo` と `undoLastRevert`〈下〉を足す）。`undoId` の採番はこのメソッドの中で registry の `Map` から行う。メソッドは最初に「registry が `closed` でない」かつ「`records.get(ownerId) === record`」を確かめ、満たさなければ（戻す操作の途中で `close` された・`begin` が前の記録を列を通さずに置き換えた）、新しい控えを記録に付けずに控えの一時ディレクトリを消し（`closed` なら `removeDirSync`、そうでなければ `removeDir`）、`{ undo: { kind: 'discarded' }, undoSummary: null }` を返す（控えが取れていても、付けなかった控えを「取り消せます」と伝えない）。メソッドは renderer に返す控えの成否 `undo` と要約 `undoSummary` の組（`AgentRevertResult`）を返し、handler はそれをそのまま結果にする（ローカルレビューの指摘で、handler が控えの成否を無条件に作っていたのを直した）。満たせば、次の規則で記録の控えを置き換える。

- 適用が 0 件（例外で中止・`partial` でない失敗）: 前の控えを残す（新しく作った控えの一時ディレクトリは、戻す関数が例外で終わる前に消してある）
- 適用が 0 件で成功した（確認の一覧も今の一覧も空の `すべて戻す`）: 前の控えを残す。registry の `commitRevertUndo` が適用の件数（`applied`）を見て前の控えを残し、今の記録の控えの要約を返す（SRP リファクタリングの第 2 周で handler から移した）（何も変えなかった依頼で前の取り消しの機会を消さない）
- 適用が 1 件以上で控えが取れた: `undoId` を振って新しい控えにし、その後に前の控えの一時ディレクトリを消す
- 適用が 1 件以上で控えが取れなかった（`directory`・`unsupported-type`・`too-large`・`capture-failed`）: 控えを null にし、前の控えの一時ディレクトリを消す

結果の型は、ファイル・ハンクが `AgentRevertResult = { undo: AgentRevertUndoOutcome; undoSummary: AgentChangesUndoSummary | null }`、すべてが `AgentRevertAllResult = DiscardAllResult & { undo: AgentRevertUndoOutcome; undoSummary: AgentChangesUndoSummary | null }`（`AgentRevertUndoOutcome = { kind: 'saved' } | { kind: 'unavailable'; reason: 'directory' | 'unsupported-type' | 'too-large' | 'capture-failed' } | { kind: 'discarded' }`。`discarded` は registry が控えを記録に付けずに消したとき。`undoSummary` は `commitRevertUndo` の後の記録の控えの要約）。renderer は `undo` を読み上げに使い、`undoSummary` で写しの `undo` をその場で置き換える（「帯の写しの即時の反映」）。

### 取り消しの流れ（`executeAgentChangesUndo`）

1. 入力の検証（送信元のメインフレーム → `undoId` → フォルダ）。handler は registry の `undoLastRevert(ownerId, folderPath, undoId)` を呼び、registry が記録の列に並べる（`withRecord`）
2. 記録の控えが無い・`undoId` が違う → 例外 `取り消せる操作が変わりました。一覧を更新してください`（作業ツリーは変えない）
3. 照合（全件。何も書かない）: 各項目について、
   - 親のフォルダの各段（許可のフォルダの直下から親まで）が `lstat` でディレクトリ（シンボリックリンクでない）であること。親が無いのも不一致
   - 今の状態（`lstat`。ファイルは中身の SHA-256〈ストリームで計算〉と大きさ〈先に比べ、違えば読まない〉と権限、リンクは指す先、無いなら `ENOENT`）が `after` と完全に一致すること。`after` が `absent` なら、そのパスに何も無いこと（ディレクトリが現れていても不一致）
   - 項目ごとの結果を「一致」「不一致」「読み込みの失敗（`ENOENT` 以外）」に分け、途中で止めずに全件を調べてから判定する
   - 不一致が 1 件でもあれば（読み込みの失敗が混ざっていても）、控えを捨てて例外 `戻した後に変わったファイルがあるため、取り消せません（<不一致のパスを最大 5 件>）`
   - 控えのファイルの中身を使う項目（`before` が `file`）について、控えの一時ディレクトリの `savedName` を `lstat` し、ファイルであることを確かめる。不一致が無く、無い・ファイルでない控えが 1 件でもあれば（長いセッションで OS の一時ディレクトリの掃除に消されたなど）、何も書かずに控えを捨てて例外 `取り消しの控えが見つからないため、取り消せません（<パスを最大 5 件>）`（もう一度押しても戻らない。書き換えの途中で読めずに `partial` で止まるのを防ぐ）
   - 不一致も控えの欠けも無く、読み込みの失敗があれば、控えを残して例外 `取り消しの対象を読み込めませんでした（<パス>）: <理由>`（権限の一時的な問題などで、もう一度押せる）
4. 書き換え（パスの昇順）。各項目の直前にそのパスの照合をもう一度行い、合わない・読み込めないとき、または書き換えが失敗したときはそこで止める。文言と控えの扱いは次の表（控えの扱いは 5）

   | 止まった理由                 | 済んだ件数が 1 件以上（`partial`。控えを捨てる）                                                | 0 件（例外）                                                     | 0 件のときの控え |
   | ---------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | ---------------- |
   | 書く直前の照合が合わない     | `取り消しが途中で失敗しました（k / n 件を取り消し済み）: <path> が戻した後に変わりました`       | `戻した後に変わったファイルがあるため、取り消せません（<path>）` | 捨てる           |
   | 書く直前の照合で読み込めない | `取り消しが途中で失敗しました（k / n 件を取り消し済み）: <path> を読み込めませんでした: <理由>` | `取り消しに失敗しました: <path> を読み込めませんでした: <理由>`  | 残す             |
   | 書き換えの失敗               | `取り消しが途中で失敗しました（k / n 件を取り消し済み）: <path>: <理由>`                        | `取り消しに失敗しました: <path>: <理由>`                         | 残す             |

   0 件で止まったときは作業ツリーが変わっていない。書く直前の照合が合わない（戻した後に変わった）なら、もう一度押しても戻らないため控えを捨てる。書く直前に読み込めない・書き換えの失敗（ゴミ箱への移動の失敗・`EACCES` など）は一時的な失敗でありうるため控えを残し、直してからもう一度取り消せる（3 の全件の照合の「読み込みの失敗だけなら控えを残す」と揃える。PR #55 のレビューの指摘で、0 件の失敗でも控えを捨てていたのを直した）。結果の `failed` は `keepUndo` を持ち、止まった理由（`AgentChangesUndoStop`）から `undoStopExecution` が決める
   - 書き戻す: 同じフォルダの一時の名前（`.prompt-ide-undo-<乱数 16 桁の 16 進>`）へ控えを `copyFile(控え, 一時の名前, COPYFILE_EXCL)` で写す（リンクは `symlink`）→ 権限を `before.mode` に（`chmod`）→ `rename` で置き換え。失敗したら一時の名前を（自分が作れていたときだけ）消す
   - 作り直す: 一時の名前へ控えを `copyFile(控え, 一時の名前, COPYFILE_EXCL)` で写す → 権限を `before.mode` に（`chmod`）→ `link(一時の名前, パス)`（既にあれば `EEXIST` で止まる）→ 一時の名前を消す。`link` が `EPERM`・`ENOTSUP`・`EXDEV` で失敗したら、一時の名前を消し、`copyFile(控え, パス, COPYFILE_EXCL)` で目的の名前に直接写して権限を `before.mode` にする（既にあれば `EEXIST` で止まる。権限を変えられなければ、自分が写せたそのファイルを消す）。失敗したら一時の名前を（自分が作れていたときだけ）消す。リンクは `symlink(before.target, パス)`
   - ゴミ箱へ移す: `ipcHandlers.ts` が `executeAgentChangesUndo` に `moveToTrash` を渡し、registry の依存 `AgentBaselineRegistryDeps.executeUndo` として配線する（registry はファイルの読み書きを持たず、`undoLastRevert` が `executeUndo` を呼んで結果で控えを残すか捨てるかを決める。SRP リファクタリングの第 2 周で `trash` の依存から変えた）

5. 書き換えを始めた後は、4 の表で控えを残す 0 件の失敗を除き、成功・失敗に関わらず控えを捨てる（一時ディレクトリを消す）。結果は `AgentChangesUndoResult`: `{ status: 'done'; restoredPaths; trashedPaths }`・`{ status: 'partial'; message; restoredPaths; trashedPaths }`（済んだものだけ）。0 件で失敗したら例外。どの結果にも、操作の後の記録の控えの要約 `undoSummary`（書き換えを始めた後は常に null）を入れる

照合に使う指紋と、書き換えに使う控えは、どちらも main が戻す操作のときに自分で取ったもので、renderer の値は `undoId` だけ（L-019）。照合と書き換えは同じリポジトリ相対のパスから同じ規則（`join(record.baseline.folderPath, path)`）で求めた絶対パスに対して行う（L-018）。

### 所有者の列との関係

- 戻す操作の控えの準備・適用・控えの置き換えは、1 つの `withRecord` のタスクの中で行う（今の戻す操作と同じ列）
- 取り消しも `withRecord` のタスク。区切りの取得・一覧・diff・保護の同期と直列になる
- `clear` は記録をすぐに外し、列の後ろで記録の一時ディレクトリ（累積の始点・区切り・控え）を消す（`agentChangesRecordTempDirs` が控えの `dir` も返す）。実行中の取り消しは最後まで行う（今の戻す操作と同じ）
- `close` は控えの一時ディレクトリも同期で消す
- `close`・`begin` の前の記録の置き換えは列を通らないため、戻す操作の途中で記録が捨てられることがある。戻す操作の最後の `commitRevertUndo(ownerId, record, result)` が `closed` と `records.get(ownerId) === record` を確かめ、満たさなければ新しい控えを付けずに控えの一時ディレクトリを消し（`closed` なら同期で）、結果の `undo` を `discarded` にする

## 記録の blob を gc から守る（main）

### ref の名前と指す先（新しいファイル `agentChangesProtectionRules.ts`・`agentChangesProtectionRef.ts`）

ref の名前の組み立て（`protectionRefName`）と `instanceId` の形（`createProtectionInstanceId`）は純粋な関数として `agentChangesProtectionRules.ts` に置き、指す先の tree を作る git の実行（`makeProtectionTree`）は `agentChangesProtectionRef.ts` が持つ（SRP リファクタリングの第 3 周で分けた）。

- 名前: `refs/prompt-ide/agent-changes/<instanceId>/<recordSerial>`。`instanceId` は main の組み立て（`ipcHandlers.ts`）で 1 回だけ作り（`createProtectionInstanceId(process.pid, randomBytes(4).toString('hex'))`。`<pid>-<16 進 8 桁>`）、registry に渡す。`recordSerial` は registry が累積の始点を取るたびに振る（インスタンスの中で 1 から増える）
- 指す先: `git mktree` の入力（NUL 区切り。`-z`）に `040000 tree <baseline.tree>\tbaseline` と、`start.kind === 'snapshot'` の実行ごとの `040000 tree <snapshot.tree>\trun-<runId>` を渡して作った tree。`baseline` の実行（開始が累積の始点）・`failed` の実行は項目を作らない
- 記録に保護の状態 `protection: { refName; value: string | null; swept: boolean }` を持たせる（`value` は最後に書けた ref の値。`swept` は掃除を済ませた印）。保護をやめたか（`abandoned`）は記録の側に持たず、registry の `abandonedSerials` に記録の番号があるかで決める（記録を捨てた後も掃除で残すため番号で持ち、同じ印を 2 か所に持たない。SRP リファクタリングの第 9 周で記録の側の印を外した）

### 同期（`syncProtection(ownerId, record)`。所有者の列の中で行う）

同期は、先に同じ所有者の**捨てた記録の削除の試し直し**をしてから、`record` について下の 1〜7 を行う。捨てた記録とは、`protectedRecords` にあり、その所有者の今の記録でも、これから同期する `record` でもない記録（所有者は記録を作ったときに `recordOwners: WeakMap<AgentChangesRecord, number>` に控える）。`clear`・`begin` の置き換えで並べた削除が一時的に失敗し（`packed-refs.lock` の競合など。読み直しが前に書いた値のまま）、まだ `protectedRecords` に残っているものがこれに当たる。各記録について 1〜7 を行い（あるべき値は null なので、前に書いた値との compare-and-swap の `delete`。失敗の後の読み直しの分類も同じ）、失敗は握って `record` の同期へ進む。一覧は試し直しを始める時点で作り、1 回の同期で試すのは捨てた記録の数だけ（消せなかったものは、その所有者の次の同期〈次の記録の最初の同期・実行の追加・`clear`〉でまた試す）。ほかの所有者の捨てた記録は試さない（その記録の書き込みはその所有者の列の中だけで行い、列の外から書き換えない）。所有者がそれきり同期しなければ、今までどおり `close` で消す

1. アプリの終了中、または `abandoned`（記録の番号が `abandonedSerials` にある）なら何もしない
2. あるべき値を求める: 記録が今の記録（`records.get(ownerId) === record`）なら、項目（`baseline` と `run-<runId>`）の tree の ID を `git cat-file --batch-check` の標準入力に 1 行ずつ渡し（出力が `<ID> missing` の項目は object が無い）、ある項目だけで作った `mktree` の tree。ある項目が 1 つも無ければ、この同期では何もしない（`value`・`protectedRecords` を変えない）。記録が今の記録でなければ（捨てた記録）null
3. あるべき値が `value` と同じなら何もしない
4. `value` が null であるべき値がある（作る）: `swept` でなければ、先に掃除（下の「残った ref の掃除」）をして `swept` にする。`create <refName> <あるべき値>`
5. `value` があり、あるべき値がある（更新する）: `update <refName> <あるべき値> <value>`
6. `value` があり、あるべき値が null（消す）: `delete <refName> <value>`
7. 成功したら `value` をあるべき値にする。失敗したら ref の今の値を `git for-each-ref --format=%(objectname) <refName>` で読み直し（終了コードが 0 で出力が空のときだけ「無い」。それ以外の失敗は読み直しの失敗）、あるべき値と同じなら成功として扱い、`value` と同じ（作るときは「無い」）なら次の同期で試し直す。どちらでもなければ記録の番号を `abandonedSerials` に入れて `abandoned` にする。読み直し自体が失敗した（終了コードが 0 でない・打ち切り・起動の失敗。出力が空を「無い」と読まない）ときは、`value`・`protectedRecords` を変えずに次の同期で試し直す。`cat-file --batch-check`・`mktree` が失敗したときは、何も変えずに次の同期で試し直す（`abandoned` にしない）

同期を並べる契機:

| 契機                                                 | 並べ方                                                                                       |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 累積の始点を取って記録にした（`begin` の始点の取得） | 記録を `records` に入れた後に `queue.enqueue(ownerId, …)`。`begin` はその完了を待たない      |
| 前の記録を新しい記録で置き換えた（`begin` の中）     | 前の記録の同期（削除）を、新しい記録の同期の前に並べる                                       |
| 実行を足した・10 件を超えて外した（`addRun`）        | 列のタスクの中で、結果を返す前に同期を列の後ろに並べる（待たない。送信の前の待ちに含めない） |
| `clear`（確認を終える・所有者の文脈の終わり）        | 記録を外した後に、捨てた記録の同期（削除）を一時ディレクトリの削除の前に並べる               |
| `close`（アプリの終了）                              | 列を使わない。下の「アプリの終了」                                                           |

- registry は ref を作れた記録の集合 `protectedRecords: Set<AgentChangesRecord>` を持つ。入れるのは `create` が成功して `value` が null から非 null になった時点（同期の 7 の中、同じタスクの中で同期的に）、外すのは次の時点だけ: 同期の `delete` が成功した（読み直しで ref が無く、あるべき値も null のため成功として扱ったときを含む。捨てた記録の削除の試し直しで成功したときも同じ）、`create`・`update` の成功の後に `closed` を見て行った同期の削除（`deleteProtectionRefSync`）が成功した、`close` の同期の削除が成功した、`abandoned` にした（利用者が ref を消した・書き換えた）。object が無いことでは外さない。今の記録も、捨てて削除を待っている記録も、ref があればこの集合に入っている。`close` と掃除はこの集合だけを見る
- `clear` の時点で `create` の git が走っていた記録は、`create` の成功で `protectedRecords` に入り、`clear` が後ろに並べた同期（削除）がその後に消す（同じ所有者の列で直列）。`create`・`update` が成功した時点で `closed` なら、そのタスクの中ですぐに新しい値での同期の削除（`deleteProtectionRefSync`）を行い、`protectedRecords` から外す（`close` が見た後に作られた・書き換えられた ref を残さない）
- git は記録の git と同じ環境（`buildBaselineGitEnv`。`GIT_DIR` などを除く）で、作業ツリーは記録のフォルダ（`record.baseline.folderPath`）。`mktree`・`update-ref --stdin`・`cat-file --batch-check`・`for-each-ref`（読み直し・掃除の一覧）・`ls-tree`（掃除の形の確認）は、すべて `runBaselineGitWithInput`（標準入力を渡せる。終了コードが 0 でなければ reject する。標準入力の要らないものは空の入力を渡す）で実行する。simple-git（`createBaselineGit`）は stderr が空で終了コードが 0 でないときに reject しない（2026-10-06 の確認の結果 21）ため、空の出力を「無い」と読まないよう使わない。「無い」と読むのは終了コード 0 で出力が空のときだけで、それ以外は失敗として扱う。設定に `core.hooksPath=<userData>/agent-changes-no-hooks`（決めたこと「保護の ref の書き込み」）と `core.logAllRefUpdates=false` を足す。打ち切りは記録の git と同じ 10 秒

### 残った ref の掃除（`sweepStaleProtectionRefs`）

記録の ref を作る前に 1 回だけ行う。

1. `git for-each-ref --format=%(refname)%00%(objectname)%00%(objecttype) refs/prompt-ide/agent-changes/` で一覧する（`for-each-ref` には `-z` が無い〈git 2.50.1 で unknown switch〉。1 行が 1 つの ref で、行の中の名前と値と種類を `%00`〈NUL〉で分ける。ref の名前は改行を含めない）
2. 名前を `refs/prompt-ide/agent-changes/<pid>-<16 進 8 桁>/<整数>` として解釈する。形が違うものは何もしない
3. 消す対象: 自分の `instanceId` で、`recordSerial` が残す番号の集合に無いもの。残す番号の集合は、1 の一覧の結果を受け取った**後**に、`await` を挟まずに同期で作る（一覧の取得中に別の所有者の `create` が成功して `protectedRecords` に入った記録の番号も含める）。中身は、registry の**すべての所有者**の今の記録（`records` の全要素。同じインスタンスの別のウィンドウの記録を含む）の `recordSerial`・`protectedRecords` の記録の `recordSerial`・保護をやめた番号 `abandonedSerials`（利用者が書き換えた ref を消さない）の和。別の `instanceId` で、`process.kill(pid, 0)` が `ESRCH` で失敗するもの（例外が無い・`EPERM` は生きているとみなして残す）
4. 3 の対象のうち、値が自分の書く形のもの、つまり次のすべてを満たすものだけを: (i) 一覧の `%(objecttype)` が `tree`（先に確かめ、commit・tag・blob は `ls-tree` に渡さない）、(ii) `git ls-tree -z <値>` が終了コード 0 で終わる、(iii) 子が 1 つ以上で、すべて tree、名前が `baseline` の子は 0 か 1 つ、それ以外の子の名前はすべて `run-<整数>`（空の tree は (iii) を満たさない。`baseline` が 0 の形は、gc で累積の始点の tree が消えた後に、同期が `run-<runId>` だけで作る値で、自分が書きうる値に含める）。1 つずつ `delete <ref> <一覧で読んだ値>` で消す。形を確かめられない（`ls-tree` の失敗）・形が違う値は消さない（利用者が書き換えた値。インスタンスが終わった後も、別のインスタンスの掃除で消さない）。失敗は握って次へ進む（同期そのものは続ける）

pid の判定は、`isProcessAlive` を registry の依存として注入する（テストで差し替える）。

### アプリの終了（`close`）

順序は、`protectedRecords` の ref の削除 → 記録の一時ディレクトリ（累積の始点・区切り・控え）の削除（hook の無いディレクトリは消さない）。`protectedRecords` の各記録（`value` は非 null で `abandoned` でない。集合の定義による）の ref を、`spawnSync('git', [-c …, 'update-ref', '-z', '--stdin'], { input: 'delete <ref>\0<value>\0', cwd, env, timeout: 2000 })` で消す（`deleteProtectionRefSync`）。1 つが失敗・打ち切りでも残りを試す。終了中に列で待っていた非同期の同期は `closed` を見て何もしない。走り始めていた `create`・`update` は、成功した時点で `closed` を見て、新しい値で自分で同期の削除を行う（上の `protectedRecords` の規則。`close` の削除が古い値で compare-and-swap に失敗しても、ここで消える）。それでも消せなかった ref は、次にそのリポジトリで記録を取るときの掃除で消える。

### 利用者の git 操作への影響

| 操作                                                   | 影響                                                                                                                                                                   |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `git gc`・`git gc --prune=now`・`git maintenance`      | 記録中は記録の object を消さない。確認を終えた後は到達できない object に戻る（既定の gc で 2 週間の後に消える）                                                        |
| `git log --all`・`git rev-list --all`・`git branch -a` | 出ない（確認の結果 2）                                                                                                                                                 |
| `git for-each-ref`・`git show-ref`                     | 記録中は `refs/prompt-ide/agent-changes/…` の tree の ref が 1 つ（ウィンドウごと）出る                                                                                |
| `git push --mirror`・`refs/*` を送る設定の push        | ref と、記録の tree（記録の時点の作業ツリーの、ignore されていない未追跡のファイルを含む）が送り先へ送られる（確認の結果 7）。既定の push・clone・fetch には影響しない |
| アプリのブランチ・タグ・履歴の表示                     | 影響しない（`refs/heads`・`refs/tags`・`refs/remotes` だけを見る。履歴の `--all` は tree の ref を無視する）                                                           |
| linked worktree                                        | ref は worktree の間で共有され、別の worktree の `for-each-ref` にも出る（確認の結果 8）。名前がインスタンスと記録ごとなので重ならない                                 |
| 利用者が ref を消した・書き換えた                      | その記録の保護をやめる（作り直さない・消さない）。書き換えた値が自分の書く形でなければ、アプリの終了の後も掃除で消さない。以後の gc では、今と同じく戻す前に拒否する   |

### 共有の型（`src/shared/types/agentChanges.ts`）

- `AgentChangesUndoAction = 'rewrite' | 'recreate' | 'trash'`
- `AgentChangesUndoSummary = { undoId: number; operation: 'file' | 'hunk' | 'all'; entries: { path: string; action: AgentChangesUndoAction }[] }`（パスの昇順。戻す操作の上限〈500 件〉を超えない）
- `AgentRevertUndoOutcome`・`AgentRevertResult`・`AgentRevertAllResult`・`AgentChangesUndoResult`（上の「戻す操作の流れの変更」「取り消しの流れ」）

### 入力の検証（`agentChangesPayloadParser.ts`）

- `parseAgentChangesUndoId(value)`: `Number.isSafeInteger` でない・1 未満（`undefined`・文字列・`NaN`・小数を含む）は例外
- 検証の順序: 送信元のメインフレームの確認 → `undoId` → フォルダ（無ければ `AGENT_CHANGES_NO_RECORD_MESSAGE`）→ 記録の列。検証の失敗は列に入る前に拒否する
- renderer から受け取るのは `undoId` だけ。取り消すパス・控え・ref の名前は main が決め、renderer に控えの一時ディレクトリ・ref の名前を返さない（パターン 144・L-019）

## renderer

### 記録の写し（`useAgentChanges`・`agentChangesView.ts`）

- `AgentChangesView` の `recording` に `undo: AgentChangesUndoSummary | null` を足し、state・`begin`・`list` の結果から写す（`scope-unavailable` の結果でも写す）
- `applyUndoSummary(summary: AgentChangesUndoSummary | null, startedAt: number)` を足す。`startedAt` は、戻す・取り消しの依頼を出した時点の写しの `startedAt`（記録の開始の時刻。呼び出し側が依頼の前に控える）。今の写しが記録中で、その `startedAt` が渡された値と同じときだけ、写しの `undo` を置き換える。記録中でない・`startedAt` が違う（結果の到着の前に確認を終えた・フォルダを切り替えた・新しい記録になった）ときは捨てる（前の記録の帯を新しい記録に出さない）。戻す・取り消しの IPC の結果の `undoSummary` を、結果を受け取った時点（実行中の印を下ろす前）に渡す。IPC が例外で終わったときは、実行中の印を下ろす前に `applyUndoSummary(null, startedAt)` を呼ぶ（帯を隠し、その後の一覧の取り直しで main の値に戻る）
- 静かな取り直しの比較（`isSameAgentChangesView`）は中身の比較のため、`undo` を足すだけで「変わったときだけ置き換える」になる（テストで固定する）

### 実行の共有（`useAgentChangesRevert` の切り出し）

- 今の `useAgentChangesRevert` の実行の部分（`run`・`revertingRef`・実行中の印・失敗の表示〈`error`・`errorPath`・発生源〉・記録の世代での古い失敗の破棄）を、新しい hook `useAgentChangesWriteRunner` に切り出し、戻す操作と取り消しで共有する。`run` の形は `run<T>(source: 'file' | 'hunk' | 'all' | 'undo', path: string | null, execute: () => Promise<T>, hooks: { onResult: (result: T) => void; onError: (error: unknown) => void; onFailure?: (message: string) => void }): Promise<{ ok: true; result: T } | { ok: false }>`。
  - 第 1 引数は今の `run` の失敗の発生源 `source` に `'undo'` を足したもの。実行中の印 `runningOperation` は `source === 'undo'` なら `'undo'`、それ以外は `'revert'` にする。失敗の表示は今どおり `{ message, path, source }` を持ち、`isErrorAnnouncedInDiff` は `source === 'hunk'`（今と同じ）
  - `onResult` は `execute` が解決した直後、`onError` は reject した直後に、どちらも実行中の印を下ろす `finally` より**前**に、記録の世代に関わらず呼ぶ（`applyUndoSummary` が `startedAt` で古い結果を捨てる）
  - `onFailure` は今の `onFailure` と同じく、reject したときに記録の世代が依頼の時点と同じ場合だけ、失敗の表示（`setError`）の後に呼ぶ（ハンクの失敗の `announceHunk` に使う。古い記録の失敗を読み上げない）
  - runner は記録の世代を扱う公開の値も返す: `captureGeneration(): number`（依頼の前に呼んで控える）・`isCurrentGeneration(generation): boolean`（ハンクの成功の読み上げの判定など。今の `generation === recordGenerationRef.current`）・`showWarning(message, source, generation)`（世代が同じときだけ `setError({ message, path: null, source })` で警告を出す。`すべて戻す`・取り消しの `partial` の警告を、タブの読み直しの後に出すのに使う。今の `revertAll` の `setError` の置き換え）
  - 戻す操作の hook は依頼の前に写しの `startedAt` を控え、`onResult` で `changes.applyUndoSummary(result.undoSummary, startedAt)`、`onError` で `changes.applyUndoSummary(null, startedAt)` を呼ぶ。取り消しの hook も同じ
  - 切り出しの最初のタスク（タスク 6）では `onResult`・`onError` を空の関数にし、`source`・`onFailure`・`captureGeneration`・`isCurrentGeneration`・`showWarning` で今の `revertFile`・`revertHunk`・`revertAll` を書き直して挙動を変えない（今の `revertHunk` の `announceHunk` の `onFailure`・成功の読み上げの世代の判定・`revertAll` の `partial` の警告の `setError` がそれぞれ移る先）
    最初のタスクで挙動を変えずに切り出し、既存のテストが通ることを確かめてから取り消しを足す
- 実行中の印は `runningOperation: 'revert' | 'undo' | null` にする。`AgentRevertAvailability` の `isReverting` を `runningOperation` に置き換え、押せない理由は `revert` なら今の `AGENT_CHANGES_BUSY_REVERTING`（`戻す操作の実行中です`）、`undo` なら新しい `AGENT_CHANGES_BUSY_UNDOING`（`取り消しの実行中です`）
- 失敗の発生源に `'undo'` を足す。取り消しの失敗はセクションに `role="alert"` で出す（帯はセクションにあるため、押したときにセクションが見えている）

### 取り消しの hook（新しい `useAgentChangesUndo`）

- 入力: `folderPath`・`changes`（`view`・`announce`・`applyUndoSummary` の `Pick`）・実行の共有（`useAgentChangesWriteRunner` の戻り値）・`fileLock`・`agentRunning`・`hasDirtyTabAtOrInside`・`reloadOpenFile`・`closeTabsAtOrInside`・`refreshAfterWrite`（書き換えの後の取り直し。`useAgentChangesWiring` が `refreshAfterAgentChangesWrite` でツリー → git status → 一覧 → diff の順に取り直す関数を 1 つ作り、戻す操作の hook と同じものを渡す）・`onConfirm = confirm`

## 新しい状態と既存の入口（L-061）

新しい状態「取り消しの控えがある」に対し、作業ツリー・記録を変える入口を列挙して扱いを決める（`agentChangesHandlers.ts` の `ipcMain.handle`・preload の API・renderer の呼び出し元から拾った）。

| 入口                                                                                                   | 控えへの影響                                                                                       |
| ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 行の `↶`・diff タブのハンク・`すべて戻す`                                                              | 1 件以上変えたら新しい控えに置き換え（取れなければ null）。何も変えずに失敗したら残す              |
| 取り消し                                                                                               | 書き換えを始めたら捨てる。照合の不一致でも捨てる。照合で不一致が無く読み込みの失敗だけのときは残す |
| `確認を終える`（`clearAgentChanges`）                                                                  | 記録ごと捨てる                                                                                     |
| フォルダの切り替え・リロード・ウィンドウの破棄・renderer の終了                                        | 記録ごと捨てる（`setupAgentBaselineLifecycle` の `clear`）                                         |
| アプリの終了                                                                                           | 記録ごと捨てる（`close`）                                                                          |
| `実行`（送信の前の `begin`）・`いまから記録する`                                                       | 影響しない（区切りを足すだけ）                                                                     |
| `更新`・`変更を確認`・自動の取り直し・範囲の切り替え                                                   | 影響しない                                                                                         |
| 既存の Git の操作（ソース管理の取り消し・pull・checkout など）・アプリでの保存・エージェントの書き込み | 控えは残る。取り消しの実行時の照合が、戻した後に変わったファイルを拒む                             |

## テスト方針

### 結合（実 git。既存の流儀〈`isolatedGitEnv`〉）

- 取り消しの往復: 変更・削除・追加・種類の変更・ハンク・すべてを戻してから取り消すと、作業ツリーのバイト列と権限（実行権）が戻す前と一致する。`core.autocrlf=true` と `text=auto` の CRLF のファイルでも、取り消しの後のバイト列が戻す前と一致する（戻す操作は改行が変わりうるが、取り消しは控えたバイト列に戻す）
- 戻した後にファイルを変えると拒否され、作業ツリーが変わらない（変異: 照合を外すとテストが落ちる。パターン 130）
- 取り消しの前後で、利用者の `.git/index` の更新時刻（ナノ秒）と内容・stash・HEAD・`refs/heads`・`refs/tags` が変わらない
- 保護: 記録を取ると `refs/prompt-ide/agent-changes/<instanceId>/<n>` が tree として 1 つでき、`baseline`・`run-<runId>` の子を持つ。`git gc --prune=now` の後も、累積の一覧・途中の実行の一覧・diff・戻す操作が成功する（2026-10-06 の確認の結果 12・22 の回帰の逆）。`clear` で ref が消え、その後の `gc --prune=now` で記録だけの blob が消える。`git log --all` の出力と `refs/heads`・`refs/tags`・HEAD・stash・`.git/index` が記録の前後で変わらない。`reference-transaction` の hook を置いても動かない。利用者が ref を消してから実行を足しても、ref を作り直さない。SHA-256 のリポジトリで作れる。変異: 同期を外すと gc の後の戻す操作のテストが落ちる
- 掃除: 存在しない pid の名前の ref を置いてから記録を取ると、その ref が消え、形の違う名前の ref と、値が commit・空の tree の ref は残る
- object が無い項目: 区切りの tree を `git gc --prune=now` で消した後（ref を作る前の状態を作る）に同期すると、`cat-file --batch-check` がその項目を `missing` と答え、残りの項目だけの tree で ref が更新される（git 2.50.1 の `mktree` の失敗の文言に依らない）。`clear` で ref が消える
- hook の無いディレクトリ: `core.hooksPath` が `userData` の下の空のディレクトリを指し、記録の一時ディレクトリを消した後の同期でも `reference-transaction` の hook が動かない
- 既存の「記録・一覧・戻す操作の前後で ref の一覧が変わらない」のテスト（`agentBaselineGit.test.ts` ほか、関数を直接呼ぶもの）は、保護を registry に置くため変えない

- 記録がある状態で、端末で `git for-each-ref --format='delete %(refname)' refs/prompt-ide/ | git update-ref --stdin` を実行してから `実行` を 1 回送る → ref は作り直されない（`git for-each-ref refs/prompt-ide/` が何も出さない）
- 記録がある状態で、端末で `R=$(git for-each-ref --format='%(refname)' refs/prompt-ide/) && git update-ref "$R" HEAD` を実行してから `実行` を 1 回送り、`確認を終える` を押す。アプリを終了して起動し直し、同じリポジトリで `いまから記録する` を押す → `$R` はどの時点でも消えず、HEAD のコミットを指したまま残る（利用者が書き換えた ref は消さない）。確かめたら端末で `git update-ref -d "$R"` を実行する

## 既知の制約（ROADMAP・実機テスト仕様書に反映する）

- 取り消せるのは直前の 1 回の戻す操作だけで、取り消しの取り消し（やり直し）は無い。取り消しの後にもう一度戻すことはできる（記録は残る）
- 追加されたフォルダをゴミ箱へ移した操作と、控えるファイルの中身の合計が 100MB を超える戻す操作は取り消せない（OS のゴミ箱から戻す）
- 取り消しは、戻した後に利用者・エージェントがそのファイルを変えていると拒否する（同じ中身・権限に戻してあれば取り消せる）。照合から書き換えまでの短い間にエージェントが書いた変更は上書きされうる。また、戻す操作で控えを取ってから適用するまでの短い間にエージェントが書いた変更は、戻す操作で上書きされ、取り消しでも戻らない（取り消しは控えの時点の内容に戻す）
- 取り消しで作り直した追加のファイルは、OS のゴミ箱にも残る（ゴミ箱を空にしない）。削除を作り直したファイルの取り消しはゴミ箱へ移し、戻すときに作られた空のフォルダは残る
- 取り消しの書き換えは、同じフォルダの一時の名前（`.prompt-ide-undo-<乱数 16 桁の 16 進>`）を経由する。書き換えの途中でアプリが異常終了すると、その一時ファイルが残ることがある
- ハードリンクを作れないファイルシステム（exFAT・FAT・一部のネットワークのフォルダ）では、作り直しは目的の名前に直接書く。書き込みの途中でアプリが異常終了すると、中身が途中までのファイルが残ることがある
- 取り消しの控え（戻す前のファイルの中身）は、記録と同じアプリの一時ディレクトリ（0700）に置く。異常終了で残った控えは OS の一時ディレクトリの掃除に任せる
- Windows では、読み取り専用（0o444）のファイルへの `rename` による書き戻しが `EPERM` で失敗することがある（取り消しは `failed`・`partial` で止まり、ファイルは壊れない）。実際の Windows では確かめていない
- 戻す操作の途中で記録が捨てられた・置き換わった（確認を終えた・フォルダを切り替えた）、またはアプリが終了中のときは、控えを付けずに消すため、その戻す操作は取り消せない。結果の読み上げは戻した旨だけを伝え、取り消せるかには触れない
- 取り消しの帯はセクションにだけ出る（diff タブ・ターミナルの帯・ショートカットからは取り消せない）
- 記録中は、ウィンドウごとに `refs/prompt-ide/agent-changes/…` の tree の ref が 1 つ、利用者のリポジトリにできる（`git for-each-ref`・`git show-ref` に出る。`git log --all`・ブランチ・タグには出ない）。`git push --mirror` など `refs/*` を送る操作では、ref と記録の tree（記録の時点の、ignore されていない未追跡のファイルを含む）が送り先へ送られる
- 記録中は `git gc --prune=now` でも記録の object は消えない。ただし、記録を取ってから ref を作るまでの短い間の gc・利用者が ref を消した後の gc・ref の作成に失敗したときは、今までどおり gc の後は戻せない（戻す前に拒否する）。確認を終えた後は到達できない object に戻り、既定の gc で 2 週間の後に消える
- 異常終了などで残った ref は、次にアプリがそのリポジトリで記録を取るときに消す（その pid のプロセスがこのマシンに無く、値が自分の書く形〈子が 1 つ以上ですべて tree、`baseline` は 0 か 1 つ、ほかはすべて `run-<整数>` の tree〉のとき）。保護をやめるのは利用者が ref を消した・書き換えたときだけで、消した場合は消すものが無い。書き換えた ref は、そのインスタンスが動いている間はアプリが消さない（`abandonedSerials`）。インスタンスが終わった後は、別のインスタンスの掃除が、値が自分の書く形のときだけ消す（書き換えた値が自分の書く形でなければ、アプリが消すことは無く、手で消す）。そのリポジトリを開かなければ残る（`git for-each-ref --format='delete %(refname)' refs/prompt-ide/ | git update-ref --stdin` で消せる）。ネットワーク上のフォルダなどを別のマシンのアプリと同時に使うと、別のマシンの記録の ref を消すことがある（そのときは gc の後に戻せないだけで、ファイルは消えない）。異常終了したインスタンスの pid が別のプロセスに使い回されていると、その pid が空くまで残った ref は消えない（安全側。手で消せる）
- 保護の ref の作成・更新は `reference-transaction` の hook を動かさない（`core.hooksPath` を、`userData` の下の hook の無い空のディレクトリ〈0700。消さない〉にして実行する）

## 反映した知見（dev-flow-kit の review-lessons.md）

- L-001: 戻す操作は控えの成否（`saved`・`unavailable`）を、取り消しは書き換えたパス・ゴミ箱へ移したパスを結果で返し、renderer は結果を見て読み上げ・タブの同期を決める。保護の同期は成功したときだけ `value` を進める（「戻す操作の流れの変更」「取り消しの流れ」「同期」）
- L-002: 控えの準備の失敗・照合の読み込みの失敗を「無い」「一致」として扱わず例外にする。ref の書き込みの失敗を読み直しで分類し、読み直し自体の失敗を「ref が無い」と読まず、`mktree` の失敗で空の tree を作らず、一時的な失敗で保護をやめない（「控えを取る順序」「保護の失敗」「同期」）
- L-003: 控えは作業ツリーを変える前に取り、取れなければ戻さない。前の控えを捨てるのは新しい戻す操作が作業ツリーを変えた後（「控えを取る順序」「直前の控えを置き換える条件」）
- L-004: ref の更新・削除は自分が書いた値との compare-and-swap に限り、掃除は自分の形の名前と値（子の名前が `baseline`・`run-<整数>` の tree）だけを対象にし、保護をやめた番号を残す（利用者が書き換えた ref を消さない）。戻す操作の途中に記録が捨てられたら、`commitRevertUndo` が控えの一時ディレクトリを自分で消す。書き戻しの一時ファイルは乱数入りの名前を `wx` で作り、自分が作れたものだけを消す（「保護の ref の書き込み」「残った ref の掃除」「書き戻しの方法」）
- L-005: 取り消しが書き換えうるもの（対象のパス・親の各段・作り直す位置の既存のエントリ）を列挙して照合で確かめる（「取り消しの流れ」3）
- L-006: 取り消しの動作を `before`・`after` の肯定の根拠で決め、どれにも当てはまらない種類は控えない（「ファイルの種類ごとの取り消しの動作」）
- L-008: 取り消しの後に、書き戻したパスのタブを読み直し、ゴミ箱へ移したパスのタブを閉じる（「取り消しの後の画面の更新」）
- L-010: `close` は ref と一時ディレクトリの削除を、1 つが失敗しても残りを試す。取り消しの途中の失敗は `partial` で済んだ範囲を伝える（「アプリの終了」「取り消しの途中の失敗」）
- L-011: 照合は「戻した直後に無かったパスに何かが現れた」「ディレクトリに置き換わった」「親がリンクになった」を不一致にし、作り直しは `link`・`symlink` の `EEXIST` で既存のものを上書きしない（「取り消してよいかの照合」「書き戻しの方法」）
- L-012: 確認の後の編集を再確認する仕組みは足さない。既存の戻す操作と同じ作りで、確認はモーダル（`window.confirm`）で、承諾の直後に同期で実行を始めるため、確認と実行の間に編集を挟む画面の経路が無い。実行中（IPC の待ち）に入ったタブの編集の扱いは既存の `reloadOpenFile` のまま（取り消しのために変えない）（「取り消しの確認」）
- L-014: 書き戻しは同じフォルダの一時ファイルに書いてから `rename`・`link` で置き換える（「書き戻しの方法」）
- L-018: 照合と書き換えは、main が控えた同じリポジトリ相対のパスから同じ規則で求めた絶対パスに対して行い、親の各段が本物のディレクトリであることを確かめる（「取り消しの流れ」）
