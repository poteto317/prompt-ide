# 実機テスト仕様書の HTML をデータ駆動にする 設計書

日付: 2026-11-11 / 対象: `scripts/build-manual-test-spec.mjs`・`scripts/__tests__/build-manual-test-spec.test.mjs`・`docs/developer-guide.md`

## 背景と目的

`node scripts/build-manual-test-spec.mjs` は、`docs/manual-test-spec.md` を、項目ごとに HTML を並べた 1 枚のページ（`.superpowers/manual-test-spec.html`）に変換し、Artifact として公開している。項目が 1565 件になり、HTML は 1,569,876 バイト（約 16,000 行）になった。

困りごとは再公開である。Artifact は、このセッションで公開していないページを上書きするとき、公開中の版を最後の行まで読むことを求める。約 1.5MB を読むと、文脈を大きく使い、公開までに何十回もの読み込みが要る（2026-11-11 の再公開で実際にそうなった）。

項目の HTML は 1 件ごとに同じ 10 行ほどの枠（`li`・`label`・`input`・`span` の入れ子）を繰り返しており、本文（手順と期待結果）より枠のほうが大きい。**項目をデータ（JSON）で持ち、ブラウザ上の JavaScript で描く**ことで、ファイルを小さくする。

## 決めたこと

1. **データの置き場**: `<script type="application/json" id="spec-data">` に仕様全体を JSON で埋め込む。ページを開くと、描画用のスクリプトがそれを読んで DOM を作る。外部ファイルは使わない（Artifact は 1 ファイルで公開できるため）。`#spec-data` のタグは、描画用の `<script>`（`type` なし）より**前**に置く（描画スクリプトは、実行時にデータの要素が DOM にあることを前提にする）。
2. **データの形（1 行 1 件の行の列）**: JSON は、行の配列を 1 行ずつ並べた形にする。1 行は次のどれか。領域・機能・前提・項目のすべてが 1 行 1 件で、2 行以上に分かれることも、2 件が 1 行に入ることもない。
   - `["a","領域名"]` 領域の始まり
   - `["f","機能名"]` 機能の始まり（`parseSpec` の `features` を順にたどり、機能ごとに `f`（名前が空でも出す。領域の直下の前提や、機能の見出しが無い領域の項目は、名前が空文字の機能に入る）→ その機能の `n` を全件 → `i` を全件の順に出す）
   - `["n","前提の本文"]` 機能（または領域の直下の名前の無い機能）の前提 1 件
   - `["i","EXP-001","手順","期待結果"]` 項目 1 件

   JSON 全体は `{"total":N,"rows":[` の次の行から 1 行ずつ行を並べ、最後に `]}` で閉じる。1 行が極端に長いファイルは、Artifact の「全行を読む」手順で読めないため、行を分ける。行の配列にしてキー名を繰り返さないことで、サイズも抑える。

3. **本文の表現は変えない**: 領域名・機能名・前提・手順・期待結果は、md の文字列をそのまま（バッククォートのコードを含めて）データに入れる。バッククォートの区切りを `<code>` にする処理は、現行の `inline` と同じ正規表現 ``/`([^`]+)`/g`` で、描画側（ブラウザ）で、**領域名・機能名・前提・手順・期待結果のすべて**に対して行う（現行の `inline` と同じ）。`textContent` と `createElement` で組み立て、`innerHTML` は使わない。
4. **JSON の埋め込みの安全**: JSON を `<script>` の中に置くため、`JSON.stringify` の結果のうち、`<` の文字をバックスラッシュ・`u003c` の 6 文字（ASCII）に、U+2028 と U+2029 を同じ形のバックスラッシュ・`u2028`・`u2029` に置き換える。`</script>` や `<!--` が本文にあっても、ページが壊れず、スクリプトも実行されない。`JSON.parse` で元の文字に戻る。**実装とテストでは、U+2028・U+2029 の文字そのものをソースに書かない**。書き方は `String.fromCharCode(0x2028)`・`String.fromCharCode(0x2029)` に限る（エスケープ表記をシェルのヒアドキュメント経由で書くと、この環境では不可視文字そのものに変わり、構文エラーになる）。
5. **見た目・DOM の構造・操作は変えない**: CSS（ライト／ダーク）、進捗バー、未確認のみ表示、すべて未確認に戻す（確認つき）、領域ごとの `n / m`、項目・機能・領域の DOM は、現行の `renderItem`・`renderFeature`・`renderArea` と同じ要素・クラス・属性（`section.feature`・名前があるときだけ `h3.feature__title`・`p.note`・`ul.items`・`li.item[data-id]`・`label.item__label`・`input#chk-<ID>.item__check[data-id]`・`.item__body`・`.item__id`・`.item__step`・`.item__expect` の中の `.item__arrow[aria-hidden]` と `.visually-hidden`（「期待結果: 」）、`details.area[data-area][open]`・`summary.area__summary`・`.area__name`・`.area__count[data-area-count]`）で、今のまま。外から見える違いを作らない。
6. **チェック状態の保存は変えない**: localStorage のキー `manual-test-spec:v1`、値は `{ "<ID>": true }`。ID が同じなら、ビルドし直してもチェックが残る。公開済みの Artifact に保存されているチェックが、新しいページでもそのまま復元される。保存データがオブジェクト以外（`null`・文字列・配列）のときは空として扱い、描画は失敗させない。localStorage が使えない環境（取得や読み書きが例外を投げる）では、メモリ上でチェックでき、「保存できません」の警告を出す（レビューで確かめて足した。テストで固定している）。
7. **静的に出す部分**: `<title>`・`<h1>`・導入の段落・進捗バーの枠・ボタンは今までどおり HTML に書く（JS が動かなくても見出しと説明が読める）。導入の段落には、ビルド側の `inline`（バッククォート → `<code>`）を残して適用する（実物の導入にもコードがあるため）。領域の描画（`details.area`）だけを JS が行う。件数の総数はビルド時に数えて HTML の `#total` と進捗バーの `aria-valuemax` に書き、描画後は、DOM のチェックボックスの数を基準に `done` と `percent` を数える（現行の `refresh` と同じ。`total` の表示は上書きしない。データの `total` と DOM の数が違えば描画の失敗とみなす — 決めたこと 9）。
8. **ビルド関数の形**: `parseSpec`（md → 構造）と `findArrow` は変えない。`renderHtml(spec)` が、データ JSON と、描画＋操作のスクリプトを含む HTML を返す。描画のスクリプトは、テストでそのまま実行できるよう、`<script>`（`type` なし）に 1 つにまとめる。
9. **描画の失敗**: データが壊れている、データの `total` と描画した項目の数が違う、スクリプトが途中（描画とチェックの初期化まで。チェックを押した後のイベントハンドラーは含まない）で投げる、のいずれのときも、`#root` の**中身を、失敗を知らせる 1 文（`ページを表示できませんでした。仕様書を作り直してください`）に置き換える**（空白のまま黙らない。原因の詳細は出さない）。
10. **サイズの検査（枠の大きさ）**: 目安は「HTML のサイズが現行の半分以下（1,569,876 → 約 0.75MB 以下。MB は 10^6 バイト）」。実物で試算すると、データ JSON は約 652KB、CSS と JS が約 15KB で、約 0.67MB になる。md は増え続けるため、**テストでは絶対値で縛らず、枠の大きさを縛る**: 「HTML のバイト数 − データ JSON のバイト数 ≤ 40,000」と「HTML のバイト数 ≤ md のバイト数 × 1.1」。あわせて、最長の行が 4,000 バイト以下であることを固定する（実物の最長は項目の約 2,056 バイト〈AGT-224〉。前提 1 件も 1 行に分かれるため、最長の行は「最長の項目か前提 1 件」で決まる）。

## 範囲外

- md の書式・ID の扱い・`parseSpec` の検査の変更。
- 本文の圧縮（gzip や base64 の埋め込み）。人が読めない版になり、レビューと差分の確認ができなくなるため行わない。
- 領域ごとの遅延描画や、検索の機能の追加。
- Artifact の公開方法の変更（公開は今までどおり Artifact ツールで、同じ URL に上書きする）。
- `CLAUDE.md` と `docs/developer-guide.md` の手順の変更（再公開の手順は変わらない）。`docs/developer-guide.md` には、仕様書の HTML の構造の説明が無いため、1 文だけ（「項目を JSON で持ち、ブラウザで描く」）を、221〜222 行目あたりの「再生成して `npx vitest run scripts` を通す」段落の後に書き足す。
- `docs/manual-test-spec.md` への項目の追加（アプリの挙動は変わらない）。最終タスクで HTML を再生成し、Artifact を同じパスで再公開する。新しい形式で最初に再公開するときは、公開中の旧版（約 1.5MB）を読む必要が 1 回だけ残る。

## 変更するファイル

- `scripts/build-manual-test-spec.mjs`: `renderHtml` を、データ JSON＋描画スクリプトの出力に変える。`renderItem`・`renderFeature`・`renderArea` の HTML 文字列組み立てを、描画スクリプトの側へ移す。ビルド側には `escapeHtml` と `inline` を、`<title>`・`<h1>`・導入の段落のために残す。データの組み立て（行の列）と、埋め込みのエスケープを、ビルド側の関数に分ける。
- `scripts/__tests__/build-manual-test-spec.test.mjs`: 出力の形（JSON の埋め込み・エスケープ・行の形・1 行の長さ・サイズ）と、描画後の動作（既存のチェック動作のテスト）を更新する。
- `docs/developer-guide.md`: 上記の 1 文。

## テストの方針

既存のテストは、ビルドした HTML を jsdom に流し込み、スクリプトを実行して DOM を確かめている。この形を保つ。`mount` は、`<script>`（属性なし）だけに一致する非貪欲な正規表現で描画スクリプトを取り出して取り除き、`#spec-data` の `<script type="application/json">` は `innerHTML` に残す（jsdom は `innerHTML` で入れたスクリプトを実行しない。`textContent` で読める）。

1. 描画後の DOM が、今までと同じ（項目のチェックボックスの数・`id`・`data-id`・領域ごとの `data-area-count`・件数。`h3.feature__title` は名前のある機能にだけあること、`p.note` の数と文言、`.visually-hidden` の「期待結果: 」、`.item__arrow` の `aria-hidden`）。
2. 手順・期待結果・領域名・機能名・前提の表示: バッククォートのコードが `<code>` になり、それ以外の文字（`<`・`&`・`"`）はテキストとして出る。`<b>` などのタグは要素にならない。バッククォートが奇数個の本文と、2 つ続くバッククォートを含む本文（実物にもある）で、`<code>` の数とテキストが現行の `inline`（ビルド側の同名の関数）の出力と同じになることを固定する。
3. JSON の埋め込み: 本文に `</script>`・`<!--`・U+2028 があっても、jsdom の HTML パーサーでページが壊れず、データとして読み出せる（エスケープしないと壊れることも、テストで確かめる）。
4. データの往復: ページの JSON を読み出して、`parseSpec` の結果と一致する（領域・機能・前提・項目の順序と内容、機能の見出しが無い領域）。
5. 行の形: データの行がすべて 1 行 1 件で、`a`・`f`・`n`・`i` のいずれかである。
6. 実物の md から作った HTML で、最長の行が 4,000 バイト以下、「HTML − データ JSON」が 40,000 バイト以下、HTML が md の 1.1 倍以下。
7. 既存の動作（チェック・復元・リセットの確認・未確認のみ表示・all-done）は、そのまま通る。
8. 描画の失敗（データが壊れている・`total` と項目の数が違う）のとき、`#root` の中身が失敗の 1 文に置き換わる。
9. `build-manual-test-spec.mjs` とテストファイルのソースのバイトに、U+2028・U+2029 の文字が含まれない。

## 気をつける知見

- L-455: 保存データのキーである ID を変えない（キー `manual-test-spec:v1` と ID の書式は不変）。
- L-618: テストの後始末で、再帰削除をしない（このテストは `document.body.innerHTML` を空にするだけで、ファイルを消さない）。
- 出力に使う文字列は、HTML 文字列に連結せず、DOM の API（`textContent`）で入れる。

## 決めたこと（推奨案の採用）

- データの形は「行の配列を 1 行ずつ」（キー名の繰り返しを避け、可読性は 1 行 1 件で確保する）。
- 外部 JSON ファイルへの分離は採用しない（Artifact を 1 ファイルで公開するため）。
- 描画失敗時の表示は、最小限の文言とする（原因の詳細は出さない）。
- サイズは絶対値でなく「枠の大きさ」と「md に対する比」で検査する（md が増えても、無関係な機能の追加でテストが落ちないように）。
