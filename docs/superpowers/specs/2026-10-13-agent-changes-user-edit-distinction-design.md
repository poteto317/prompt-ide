## 目的

エージェントの変更のセクション（ソース管理パネル）は、記録を始めた後（累積の始点の後）に作業ツリーで変わったファイルを、すべて「エージェントの変更」として出す。利用者がエディタ（アプリの外を含む）や端末で編集したファイルも同じ一覧に混ざり、`すべて戻す` で利用者の編集まで実行前の状態に戻ってしまう（2026-10-06 の確認の結果 4。今はアプリで保存したパスにだけ `あなたの保存を含む` の印を付け、確認の文言で `記録を始めた後にあなたが編集した内容も戻ります` と断っている）。

この機能では、アプリが起動する `claude` に hooks を渡し、エージェントがファイルを書くツール（`Write`・`Edit` など）とシェル（`Bash`）を実行している区間を main が知る。エージェントのツールが動いていない間に変わったファイルを「利用者の変更」として一覧の行に印を付け、`すべて戻す` の対象から外す。

| hooks が届かなくなったことの検知（2026-10-14） | `confirmed` のセッションで、renderer の画面の活動が `working` から `working` 以外（`idle`。下の「hooks が届かなくなったことの検知（段階 B）」）に変わったのに、30 秒（`AGENT_HOOKS_TURN_END_WAIT_MS`）たっても `Stop`・`StopFailure` が届かなければ、そのセッションを「次の知らせまで保留」にする（下の行。当初は `unconfirmed` にして区別をやめる形だったが、同じ日の決定で保留に変えた）。renderer から `working` の終わりを送る IPC を足す |
| 中断の後などの「次の知らせまで保留」（2026-10-14） | 上の検知で `Stop` が届かないとき（中断〈Esc〉の後・hooks が本当に届かなくなったとき）は、区別をやめない（`lost` にしない）。保留の間に変わったファイルはエージェントの変更として扱い（割り当てない。利用者の変更にしない）、そのセッションに次の hooks の知らせ（`UserPromptSubmit`・`PreToolUse` など、照合の通ったどの知らせでも）が届けば保留を解いて区別を続ける。hooks が本当に届かなくなった場合も保留のまま（エージェントの変更として扱う）になり、安全側。追跡の合図 `unassignable` の仕組みで表す（新しい状態・理由を足さない） |
| 段階 B を 2 つの PR に分ける（2026-10-14） | B-1（受け取りの変更・検知と起動の守り・区別のモデル・registry の同期とつなぎ込み。区別を内部で持つだけで画面は変わらない）を 2026-10-14 のサイクルで作り、B-2（`author` と `すべて戻す`・IPC の型・renderer・ROADMAP の完了）は次のサイクルで作る（「実装の分割」） |

2. **設定の形** (B): `hooks` → イベント名 → matcher の組の配列 → `hooks` の配列（`type`・`command` か `url`・`timeout` など）。hooks は設定の元をまたいで足し合わされ（merge）、置き換えない。`disableAllHooks: true` で無効にでき、管理者の設定の `allowManagedHooksOnly` は利用者・プロジェクト・ローカルの hooks を止め、`allowedHttpHookUrls` は `http` の hook の URL の許可リスト
3. **イベントと終了の意味** (B): `SessionStart`・`UserPromptSubmit`・`Stop`・`StopFailure`・`PreToolUse`・`PermissionRequest`・`PostToolUse`・`PostToolUseFailure`・`SubagentStart`・`SubagentStop`・`SessionEnd` など。**`SessionStart` は `Only type: "command" and type: "mcp_tool" hooks are supported.`（`Setup` も同じ）で、`http` の hook は使えない**（利用者が確かめた）。`PreToolUse` は終了コード 2 でツールを止められる（hook が終わるまでツールを動かさない）。`PostToolUse`・`PostToolUseFailure`・`SessionEnd` の終了コード 2 は無視される。それ以外の 0 でない終了・失敗は止めない（non-blocking error）。`SessionEnd` は matcher に終了の理由（`clear`・`resume`・`logout`・`prompt_input_exit` など）を持ち、`/clear`・`/resume` でも届く
4. **matcher** (B): `"*"`・`""`・省略はすべてに一致。英字・数字・`_`・`-`・空白・`,`・`|` だけなら完全一致の名前（`|` 区切りの並び）。それ以外の文字を含むと JavaScript の正規表現（前後を固定しない）。ツールのイベントはツールの名前、`SubagentStop` はエージェントの種類と照合する
5. **入力の JSON** (B): すべてのイベントに `session_id`・`transcript_path`・`cwd`・`hook_event_name`・`permission_mode` など。サブエージェントのときは `agent_id`・`agent_type`。ツールのイベントは `tool_name`・`tool_input`・`tool_use_id`（`PostToolUse` は `tool_response` も）。ファイルのツールの `tool_input` は `file_path` か `notebook_path` を持ち、**絶対パス**。サブエージェントのツールでもツールのイベントが動く
6. **`http` の hook** (B): 必須は `type`・`url`。`headers`（値の中の `$VAR` は `allowedEnvVars` に挙げた環境変数だけを展開）・`onFailure`。応答の 2xx で本文が空 → 成功・出力なし、2xx で JSON → コマンドの hook の標準出力と同じ解釈、2xx でそれ以外の本文・2xx 以外・接続の失敗 → 止めない失敗、打ち切り → hook を取り消して判断なし。`onFailure: "block"`（失敗でツールを止める）は 2.1.295 以降。`SessionStart`・`Setup` 以外（今回使う `UserPromptSubmit`・ツールのイベント・`SubagentStop`・`Stop`・`StopFailure`・`SessionEnd`）は `http` を使える
7. **実行のされ方** (B): 一致した hooks は並行に動く。`command` の hook は `args` を省くとシェルで動く（macOS・Linux は `sh -c`、Windows は PowerShell か Git Bash）。hook は `claude` の環境を受け継ぐ
8. **打ち切り** (B): `timeout` は秒。既定は `command`・`http` が 600 秒（`UserPromptSubmit` などは 30 秒）。`SessionEnd` の hooks は合わせて 1.5 秒の持ち時間
9. **設定の読み込み** (B): hooks は起動時と、ファイルの監視が変更を見つけたときに読み直す
10. **`http` の hook が入った版** (https://code.claude.com/docs/en/changelog.md を 2026-10-13 に取得して確かめた): `<Update label="2.1.63" description="February 28, 2026">` に `Added HTTP hooks, which can POST JSON to a URL and receive JSON instead of running a shell command`。それより前の版に `--settings` で `http` の hook を渡したときの動きは書かれていない。渡す hooks に関わる変更: `<Update label="2.1.69" description="March 5, 2026">` に `Added agent_id (for subagents) and agent_type (for subagents and --agent) to hook events`、`<Update label="2.1.78" description="March 17, 2026">` に `Added StopFailure hook event that fires when the turn ends due to an API error`、`<Update label="2.1.101" description="April 10, 2026">` に `Improved settings resilience: an unrecognized hook event name in settings.json no longer causes the entire file to be ignored`（2.1.101 より前は、知らないイベント名〈`StopFailure` など〉を含む設定のファイルが全体で無視されうる）。このため下限は 2.1.101 にする。コードを grep した範囲（`src/main`）に、`claude` の版を確かめる既存の仕組み（`--version` の実行など）は無い

13. **中断・失敗・バッチ・要求の形** (B。https://code.claude.com/docs/en/hooks.md を 2026-10-13 に取得して確かめた): `Stop` は `Does not run if the stoppage occurred due to a user interrupt.`（API のエラーは `StopFailure`）。`PostToolUseFailure` の `is_interrupt` の説明に `Cancelling a running tool does not fire this hook; the tool result carries the interruption message instead`。`PermissionDenied` は `When auto mode denies a tool call`（auto mode の拒否だけで、許可の確認で利用者が拒否したときに届く知らせは書かれていない）。`http` の hook は `Content-Type: application/json` で本文を POST する。`PostToolBatch` は `Runs once after every tool call in a batch has resolved, before Claude Code sends the next request to the model`（matcher なし）

## hooks の受け取り（main。段階 A）

### 受け口（新しいファイル `agentHookReceiver.ts`）

- Node の `http.createServer`。最初のエージェントのセッションを起動するときに `listen({ host: '127.0.0.1', port: 0 })` で始め（Promise を持ち回し、2 つ目の起動は同じ Promise を待つ）、失敗したらその起動は hooks なし（`hookSettingsPath: null`）で行い、次の起動で始め直す。`headersTimeout` 5 秒・`requestTimeout` 15 秒。アプリの終了（`will-quit`）で `close` と `closeAllConnections`
- 受け付ける要求（どれかが外れたら状態を変えずに答える。外れた理由ごとに件数を数え、最初の 1 件と 100 件ごとに `[agent-hooks] 拒んだ要求: <理由> <件数> 件` をログに出す）

  | 検査                                                                                                  | 外れたとき（理由）      |
  | ----------------------------------------------------------------------------------------------------- | ----------------------- |
  | メソッドが `POST`                                                                                     | 405（`method`）         |
  | パスが `/prompt-ide/agent-hooks/v1/<イベント>`（`<イベント>` は下の表の 8 つのどれか。完全一致）      | 404（`path`）           |
  | `Host` が `127.0.0.1:<ポート>`、`Origin` が無い                                                       | 403（`host`・`origin`） |
  | `Authorization` が `Bearer <64 桁の 16 進>` で、その SHA-256 を鍵にした表に生きているセッションがある | 401（`token`）          |
  | `Content-Type` が `application/json` で始まる                                                         | 415（`content-type`）   |

- `Host`・`Content-Type` の検査は、未確認事項 1 の実測の値に合わせる（実測で違えば、段階 A のタスク 1 で検査とテストを直す）
- 本文の大きさ: 上の表の検査（メソッド・パス・`Host`・`Origin`・トークン・`Content-Type`）がすべて通った要求だけ本文を読み、16 MiB までを持つ。16 MiB を超えたら、それ以上は持たずに残りの本文を最後まで読み捨て（`requestTimeout` の 15 秒が上限）、照合が通っているので ID なしの知らせとして `deliver` し、通常どおり 200 を返す（`PreToolUse` は `onToolStart` を待ってから）。`too-large` は拒んだ要求ではないが、同じ件数のログに数える
- 本文が 16 MiB を超えた・JSON として読めない・`hook_event_name` がパスのイベントと違う（L-023）ときは、パスのイベントだけを使う（ツールのイベントは `tool_use_id` が無いものとして扱う。下の「区間の追跡」）。`Write` の `tool_input` はファイルの中身をすべて含むため、大きなファイルを書くと本文が大きくなる
- 照合の通った知らせ 1 件につき、追跡の `deliver(ownerId, sessionId, event)` を 1 回だけ呼ぶ。追跡はその中で確かめた状態（`pending` なら `confirmed`）と区間を更新し、あるべき段階を 1 回だけ求め、変わっていれば `onPhaseChange` を呼び終えてから戻る
- `PreToolUse` の順序: (1) `deliver`（`tool-start`）を呼び終える（その中で `onPhaseChange` まで同期的に済む）、(2) その後で `onToolStart(ownerId, signal)` を呼び、5 秒（`AGENT_PRE_TOOL_USE_WAIT_MS`）を上限に待つ、(3) 打ち切ったら `signal` を中止して `onToolStartTimedOut(ownerId)` を呼ぶ、(4) 応答する。`onToolStart`・`onToolStartTimedOut` は必須の依存で、段階 A ではすぐ解決する Promise を返す・何もしない（段階 B で registry の `waitForAgentPhase`・`markToolStartTimedOut` につなぐ）
- 応答は本文の無い 200（`Content-Length: 0`）。`PreToolUse` 以外は追跡を更新した直後に返す。失敗の応答も本文は空にし、理由を返さない
- トークンの表は `sha256(token) → { ownerId, sessionId }`。セッションの `activate` で足し、`release` で外す（文字列の比較の時間で推測させない）。ログにはトークン・本文を出さない（L-017）

| ----------------------- | -------------------- |
| `user-prompt-submit`    | `UserPromptSubmit`   |
| `pre-tool-use`          | `PreToolUse`         |
| `post-tool-use`         | `PostToolUse`        |

### 入力の解釈（新しいファイル `agentHookEvents.ts`。純粋な関数）

- 使う欄は `hook_event_name`（文字列）・`tool_name`（ツールのイベントだけ。matcher の 6 つのどれか。違えば、`PreToolUse` は区間を開いてログに残し〈知らない名前で捨てると、そのツールの書き込みが利用者の変更に入る。L-002〉、`PostToolUse`・`PostToolUseFailure` は知らせを捨ててログに残す〈知らない名前を区間を閉じる根拠にしない。L-044〉。どちらも、照合が通っていれば確かめた知らせには数える）・`tool_use_id`（1〜256 文字の文字列。無い・形が違えば「ID なし」）・`agent_id`（1〜256 文字の文字列。無ければ null。形が違えば、`PreToolUse` は `tool_use_id` が読めても ID なしの区間として開いてログに残し〈捨てると、そのツールの書き込みが利用者の変更に入る。L-002〉、`PostToolUse`・`PostToolUseFailure`・`SubagentStop` は知らせを捨ててログに残す〈形の違う値を区間を閉じる根拠にしない。L-044〉。どちらも、照合が通っていれば確かめた知らせには数える）だけ。ほかの欄は読まない
- 結果は判別共用体 `AgentHookEvent`。どの要素も照合の通った知らせで、追跡は受け取ったら必ず確かめた状態を更新する。すべての要素に `hookEventName: AgentHookEventName`（パスから決めたイベント名。渡す 8 つのイベントの列挙型 `'UserPromptSubmit' | 'PreToolUse' | 'PostToolUse' | 'PostToolUseFailure' | 'SubagentStop' | 'Stop' | 'StopFailure' | 'SessionEnd'`）を持ち、ツールのイベント（`PreToolUse`・`PostToolUse`・`PostToolUseFailure` から作った要素。`confirm-only` を含む）には `toolName: string | null` も持つ（検証済みの値: 1〜64 文字の英数字・`_`・`-` だけの文字列。matcher の 6 つ以外でも形が合えば入れる。読めない・形が違えば null。開発版のログにだけ使い、区間の判定には使わない）
  - `{ kind: 'confirm-only'; reason }`: 区間を変えずに確かめるだけ。`reason` は `prompt-submit`（`UserPromptSubmit`）・`unknown-tool-end`（知らない `tool_name` の `PostToolUse`・`PostToolUseFailure`）・`bad-agent-id`（形の違う `agent_id` の `PostToolUse`・`PostToolUseFailure`・`SubagentStop`）・`subagent-stop-without-agent`（`agent_id` が無い・本文を読めない `SubagentStop`）
  - `{ kind: 'tool-start'; toolId: ToolIdRead; agentId: string | null }`・`{ kind: 'tool-end'; toolId: ToolIdRead; agentId: string | null }`: `ToolIdRead` は `{ kind: 'read'; id: string } | { kind: 'unreadable' }`（読めた ID と読めない〈本文が大きすぎる・読めない・形が違う〉を型で区別する）。`tool-start` は、形の違う `agent_id` でも `toolId: { kind: 'unreadable' }`・`agentId: null` にして開く
  - `{ kind: 'subagent-stop'; agentId: string }`（`agentId` は必須。無い・読めないときは `confirm-only`）
  - `{ kind: 'turn-end' }`（`Stop`・`StopFailure`。どちらかは `hookEventName` で見分ける）・`{ kind: 'session-end' }`
  - 例: 知らない `tool_name` の `PostToolUseFailure` は `{ kind: 'confirm-only'; reason: 'unknown-tool-end'; hookEventName: 'PostToolUseFailure'; toolName: 'Foo' }`

- 一時ディレクトリ: `createAgentHookSettingsDir()` が返すオブジェクト `AgentHookSettingsDir`（`ensure(): Promise<string>`・`removeSync(): void`）を `settingsDir` として受け口の `listen` と同じ形で扱う。`ensure` は最初の呼び出しで `mkdtemp`（0700）し、その Promise を共有する。失敗したら Promise を捨て（次の `ensure` で作り直す）、その起動は `receiver-unavailable` にする。共有の Promise が解決した後も、`ensure` のたびにそのパスを `lstat` で確かめ（依存の `isPrivateDir`。判定は純粋な関数 `isOwnPrivateDirStat`）、シンボリックリンクでないディレクトリで、Windows 以外では自分の持ち物（`uid === process.getuid()`）かつ `mode & 0o077` が 0 のときだけ使う。無い（OS の一時ディレクトリの掃除などで外から消された）・条件を満たさないときは、そのパスを使わずに作り直して新しいパスを返す（共有の `/tmp` で、消えた後に別の利用者が同じ名前のディレクトリを作ると、設定のファイルを差し替えて `command` の hook を利用者の権限で動かせるため）。同時の呼び出しでも作り直しは 1 回。`removeSync` は先頭で閉じた印を立て（以後の `ensure` は reject し、作らない。`will-quit` の後に作り直したディレクトリが残らない）、作れていればディレクトリごと同期で消し（失敗は握ってパスだけをログ）、作れていなければ何も消さない。`mkdtemp` の最中に `removeSync` が来たときは、できた時点でそのディレクトリを `rmSync` で消してから `ensure` を reject する（作り直しの待ちの後も閉じていれば reject）
- 書き込み: `settingsDir.ensure()` のディレクトリに `<乱数 32 桁の 16 進>.json` を `wx`・0600 で書く。書けなかったら、その起動は hooks なしにする（`receiver-unavailable`）
- 削除: `release` で消す（失敗は握ってパスだけをログ）。アプリの終了（`will-quit`）で `settingsDir.removeSync()` がディレクトリごと同期で消す（1 つの失敗で止めない。L-010）

- `session-end`: そのセッションのすべての区間（期限切れ・`anonymousOpen` を含む）を外し、外した ID を `droppedToolIds` に控える（セッションは外さない。`/clear`・`/resume` でも届くため）

- ツールの終わりの猶予: 所有者のすべての区間が閉じた時点（どの閉じ方でも）から 2 秒のタイマー（`unref`）。その間に `tool-start` が来たら取り消す
- タイマーはすべて `unref` にし、`will-quit` の後始末（`close`）で外す

### ウィンドウのあるべき段階

`desiredPhase(ownerId)` を次の順で決める:

1. 生きているセッションのどれかが `unconfirmed` → 区別をやめる合図（理由 `hooks-not-confirmed`・`receiver-unavailable`・`claude-version-unsupported`）。段階は `agent` とする
2. `pending` のセッションがある → `agent`
3. `confirmed` のセッションが 1 つも無い → `paused`（ツールの終わりの猶予は効かない）
4. `confirmed` のセッションのどれかに開いた区間（`openTools` か `anonymousOpen`。期限切れの区間を含む）がある、またはツールの終わりの猶予の間 → `agent`
5. それ以外 → `idle`

- `unassignable` は段階の分岐と別に、生きているセッションのどれかに期限切れの区間が残っているかで常に求める（段階が `paused` でも立ちうる）

- 状態が変わるたびに（知らせ・作業中の知らせ・起動・終了・タイマー）、ウィンドウの合図（`activityOf(ownerId)` が返す `{ phase, lost: 理由 | null, unassignable: boolean }`）が変わったら、依存の `onPhaseChange(ownerId)` を同期的に呼ぶ（段階 A では開発版のログだけ。段階 B で registry の `syncAttribution` につなぐ）
- 所有者ごとのツールの開始の通し番号を `toolStartSeqOf(ownerId)` で返す（段階 B の始点の判定に使う）
- 開発版のログ: `[agent-hooks] owner=<id> session=<sessionId の先頭 8 桁> event=<イベント名か 起動・終了・作業中・確認の待ちの終わり> tool=<ツールの名前> id=<あり/なし> agent=<あり/なし> hooks=<確かめた状態> phase=<前>→<後>`

### hooks が届かなくなったことの検知（段階 B）

- renderer: `useAgentHooksWorkingReport` を、作業の始まりと終わりの両方を送る形にする。タブごとに前回の活動と「`working` を見てから `idle` をまだ見ていない」印を ref に控え、(a) 今どおり `working` 以外から `working` に変わったときに `reportAgentSessionWorking(sessionId)`、(b) 印があって活動が `idle` になったときに `reportAgentSessionWorkingEnded(sessionId)` を送って印を下ろす。`permission`・`confirm`（利用者の操作を待つ間で、ターンは終わっておらず `Stop` は来ない）・`unknown`（画面の判定の途中）では送らない。`controller.getSessionId()` が null なら送らない。消えたタブの控えは捨てる（今どおり）

- 理由・文言・型は足さない（`lost` にしないため、`AgentChangesAttributionLostReason` も変えない）

### 段階 A の最終レビューで残した頑健性の 5 項目（段階 B）

  - それ以外 → `tracking`・`phase` は取り終えた時点のあるべき段階 d1・`checkpoint` は始点（`sharedWithBaseline: true`）。通し番号が s0 から変わった、または d0・d1 のどちらかが `agent` なら `periodUnassignable: true` にし、同期を 1 回並べる。始点を取り始めた時点か記録を作る時点のどちらかで合図の `unassignable` が立っている（保留・期限切れ・あふれの最中。取っている間に保留が解けた往復も拾う。L-103）なら `periodUnassignable: true` にする（`syncNow` は偽。合図が下りたときの同期に任せる。取っている間に下りた場合は、その `onPhaseChange` の時点では記録がまだ無いため、`syncNow` を真にする）。両方（通し番号・段階の条件と合図の条件）が成り立つときは印を立てて `syncNow` を真にする（その同期の手順 9 は合図だけを理由に並べ直さないため、回り続けない）。どちらでもなく d1 が `paused` でなければ `trackingSince` を始点の時刻にする（印を立てたときは null のまま、手順 9 で割り当てる区間が始まった時刻にする）。始点を取っている間の区間（始点から最初の同期まで）は割り当てない。`pending` の間はあるべき段階が `agent` なので、最初の同期の後はエージェントの区間として数える（最初のプロンプトの前に記録を始めて利用者が編集しても、利用者の変更にならない）

### 同期（registry の `syncAttribution(ownerId)`。所有者の列の中で行う）

1. 記録が無い・`lost`・registry が `close` 済み → 何もしない（段階は `deps.attributionSource.activityOf(ownerId)` で、この時点に読む）
2. 区別をやめる合図（`lost`）があれば `lost` にして終わる（下の「やめる」）。無ければ、合図の `unassignable` が立っているときに `periodUnassignable = true` にして手順 3 へ進む（`onPhaseChange` の時点でも列の外で同期的に立てる。合図が下りたときの同期は、手順 3 で印を見て区切りを取り、期限切れの区間を閉じる）
3. あるべき段階が今の `phase` と同じで、`periodUnassignable` も無い → 何もしない
4. `unassignableBefore = periodUnassignable`・`timeoutBefore = timedOutPending` を控え、`periodUnassignable = false`・`timedOutPending = false` にする（この後に `PreToolUse` の待ちの打ち切りが起きると、受け口の `onToolStartTimedOut`〈`markToolStartTimedOut`〉がまた両方を `true` にする）。`timeoutBefore` は、同期を始める前に打ち切られたツールが、同期の開始の時点でまだ動いていることがあるために控える（打ち切りは列が埋まっているときに起きる）
5. `this.deps.takeSnapshot(folderPath, { isCanceled, now: this.deps.now, baseIndexPath: checkpoint.snapshot.indexPath })` で区切り S を取る（`isCanceled` は registry の `close` と世代の変化を見る。ただし `addRun` と違い、比べる世代と記録は依頼を並べた時点ではなく、タスクが走り始めた時点〈手順 1〉で読む。並べた時点で控えると、古い記録のときに並んだ同期が新しい記録の同期として合流され、世代の違いで `canceled`〈`skipped`〉になって `waitForAgentPhase` が解決し、段階が `idle` のままツールが始まる。L-040・L-103）。`canceled`（記録を捨てた・世代が変わった・`close` した）→ 取れたものを消して終わる（`close` の後は `discardSnapshot` が同期で消す。L-435）。`unavailable` → `lost`（`checkpoint-failed`）
6. `markedDuringSnapshot = periodUnassignable`（手順 4 の後、区切りを取り終えるまでに列の外で印が立ったか。打ち切りの `markToolStartTimedOut`・合図の unassignable の `notifyAttributionSignal` のどちらも）を控える
7. `collectAgentChangeEntriesBetween(checkpoint.snapshot, S)` のパスを、`unassignableBefore` か `markedDuringSnapshot` なら割り当てず（閉じた区間〈前の区切りから S まで〉を印のために割り当てなかったときは、`trackingSince` があれば `hadUnassignedSince = true` にする。区間の途中で列の外から立った印〈打ち切りの `markToolStartTimedOut`・合図が立ってから同期が走るまでに下りた `notifyAttributionSignal` の印〉も拾う。拾わないと、その区間の利用者の編集が `すべて戻す` で戻るのに確認で伝わらない。L-152）、そうでなければ `phase` が `idle` なら `userPaths`、`agent` なら `agentPaths` へ足す（`paused` はどちらにも足さない）。失敗したら S を消して `lost`（`checkpoint-failed`）
8. この時点のあるべき段階 d を求める（区切りを取っている間に始まった・終わったツールを反映する）
9. `timedOut = timeoutBefore || （手順 8 の時点の timedOutPending）`（同期を始める前の打ち切りと、手順 4 の後に立った打ち切り〈手順 6 の `markedDuringSnapshot` の元と、手順 7 の await の間の印を含む〉）とし、`timedOutPending = false` にする（この同期で片付けた。手順 9 より後の打ち切りは次の同期が片付ける）。`checkpoint = { snapshot: S, sharedWithBaseline: false }` にし、`phase = d` にする。`periodUnassignable = (timedOut && d !== 'agent') || 合図の unassignable || 手順 2 で読んだ合図の unassignable`（打ち切られたツールが S の後も書いた可能性がある・期限切れ・あふれ・保留のセッションがある。手順 2 の時点で立っていた保留・期限切れが手順 7 の await の窓の中で下りると、今の合図だけでは S から下りるまでの変更が段階 d に割り当たり、利用者の変更と誤る側に倒れるため、手順 2 の値も足す。下りたときの `notifyAttributionSignal` が同期を 1 つ並べているので、その同期が印のある区間として片付け、並べ直しは増えず回り続けない。`timedOut` が同期の開始の前と手順 8 までの印を含むため、同期を始める前に打ち切られて動き続けたツールの書き込みも、手順 7 の間に立った印も、次の区間に残る。L-103・L-434）。同期をもう 1 回並べるのは `timedOut && d !== 'agent'` のときだけ（「覆われなかったツールの開始」と同じ条件。`timedOutPending` を手順 9 で下ろし、引き継いだ印では立てないため、次の同期の `timedOut` は新しい打ち切りが無ければ偽になり、並べ直しは打ち切り 1 回につき高々 1 回）。合図の `unassignable` が理由の印は残すだけで並べ直さず、合図が下りたときの `notifyAttributionSignal` が並べる同期に任せる（合図が立ち続ける間に同期が自分を並べ直し続けると、約 0.3 秒ごとに区切りを取り続け、`waitForAgentPhase` の「並んでいる・走っている同期が無い」を満たさず、`PreToolUse` が毎回 5 秒で打ち切られる）。新しい区間が割り当てる区間（`periodUnassignable` が無く `d` が `paused` でない）で `trackingSince` が null なら今の時刻にする。`trackingSince` があり、新しい区間が `paused` か割り当てられない区間なら `hadUnassignedSince = true`
10. 前の区切りが始点と共有でなければ一時ディレクトリを消す（L-003・L-004）。消せなければ `staleCheckpointDirs` に入れる（L-428）
11. `await` のたびに `isCanceled()`（registry の `close`・世代の変化。手順 5 と同じ）と、記録が `records` の今の記録か（`this.records.get(ownerId) === record`）を確かめる。違えば S を `discardSnapshot` で消し（`close` の後は同期で消す。L-435）、記録を変えずに終わる（`AgentBaselineRegistry.close()` は世代を進めないため、世代だけでは手順 7 の最中の `close` を見落とす）

同期は registry の所有者の列（`this.queue`。`KeyedSerialQueue`。戻す操作・一覧と同じ列）に並べる。同期の依頼は、同じ所有者の列で待っている（まだ走り始めていない）同期の依頼があり、それを並べた時点の記録が今の記録と同じ（`this.records.get(ownerId)` が同じもの）ときだけ、その Promise を返す（記録が作り直されていれば新しく並べる。所有者ごとの「待っている同期」の `Map<number, Promise<SyncResult>>` に控え、タスクが走り始めた時点で外す。L-101・L-434）。走り始めた同期は所有者ごとの「走っている同期」の `Map<number, Promise<SyncResult>>` に移し、終わったら外す（待っている同期の Map だけでは走っている同期が分からないため。`waitForAgentPhase` の「並んでいる・走っている同期が無い」と「走っている同期より後に並んだもの」はこの 2 つの Map で判定する）。`syncAttribution` は失敗を `lost` にして解決し、reject しない。解決する値は内部の結果 `'synced'`（区切りを取った）か `'skipped'`（手順 1〜3 で終わった。区切りの途中の取り消し・失敗も含む）で、`waitForAgentPhase` の繰り返しの終わり方に使う（呼び出し元の `notifyAttributionSignal`・`waitForAgentPhase` が結果を見ずに済む）。`clear`・`close` で列の後ろの同期は記録が無いため何もしない。

### `PreToolUse` の待ち（registry の `waitForAgentPhase(ownerId, signal)`。受け口の `onToolStart` につなぐ）

- 次を `signal` が中止されるまで繰り返す
  1. 記録が無い・`lost`・registry が `close` 済み → 解決
  2. あるべき段階（`deps.attributionSource.activityOf(ownerId).phase`）が `agent` でない → 解決（待ちの最中にタブを閉じた〈`removeSession`〉などで、覆うべきツールが無くなった）
  3. 記録の `phase` が `agent` で、並んでいる・走っている同期が無い → 解決
  4. それ以外 → そのとき並んでいる最新の同期（走っている同期より後に並んだものがあればそれ、無ければ新しく並べる）の Promise と `signal` の中止の早い方を待つ。待った同期が区切りを取らずに終わった（同期の手順 1〜3 で終わった。`syncAttribution` は内部の結果 `'synced' | 'skipped'` を返す）のに 1〜3 のどれも満たさないときは、それ以上待たずに解決する。それ以外は 1 に戻る
- 繰り返しが 1 に戻るのは、待った同期が区切りを取った（`takeSnapshot` の I/O を待った）ときだけなので、同じ状態のまま 2 回回らない。区切りを取らない同期はすぐ解決し、`KeyedSerialQueue` は `previous.then(task)` で繋ぐため、何もしない同期を並べ直し続けると microtask の中で回り続け、5 秒の `setTimeout` も `close` の中止も実行されずに main のイベントループが止まる（L-052 の上限が効かない）。上の 2 と 4 の終わり方でこれを防ぐ。打ち切りの印のやり取りでも回り続けない: 同期を並べ直すのは手順 9 の `timedOut && d !== 'agent'`（打ち切り 1 回につき高々 1 回）だけで、並べ直した同期は印があるため手順 3 で終わらず区切りを取る（I/O を待つ）
- 受け口は、追跡の更新と `onPhaseChange` を終えてから呼ぶ（上の「受け口」）ため、手順 3 で並べる同期は、そのツールの開始を反映したあるべき段階（`agent`）で走る
- 同期の手順 8 の後（手順 9・10 の await の間）に届いた `PreToolUse` は、手順 8 の時点の段階が `idle` なら、走っている同期が解決しても記録の `phase` は `agent` にならず（繰り返しの手順 3 を満たさない）、その `PreToolUse` の `onPhaseChange` で走っている同期の後ろに並んだ同期を待つ（繰り返しの手順 4 の「走っている同期より後に並んだもの」）
- 5 秒の上限は受け口が通して数え、打ち切った・待ちが失敗したら `signal` を中止して `markToolStartTimedOut(ownerId)`（今の記録の `periodUnassignable = true`・`timedOutPending = true`。列の外で同期的に立てる。記録が無い・`lost`・`close` 済みなら何もしない）を呼ぶ
- `waitForAgentPhase` は `async` 関数にし、同期で投げない（受け口も `Promise.resolve().then` で包む。頑健性の 2）。`signal` の中止で繰り返しをやめて解決する（reject しない）

### やめる（`lost`）

- `kind` を `lost` にし、`reason`・`lostAt` を入れ、`userPaths`・`agentPaths` は残す。`checkpoint` の一時ディレクトリは始点と共有でなければ消す（消せなければ削除待ち）
- 関数: `agentChangesAttributionSync.ts` の `markAttributionLost(record, reason: AgentChangesAttributionLostReason, deps: { now; removeDir }): Promise<void>`（記録を書き換える。所有者の列の中でだけ呼ぶ。列の外から呼ばない）。呼び出し元は同期の手順 2・5・7（B-1）、吸収の (1)・(3) の失敗（B-1）、一覧の今の区間の比較の失敗（`agentChangesScopedQuery`。B-2）。registry には公開のメソッドとして置かない。B-1 のタスク 4 で作る
- 理由: `hooks-not-confirmed`（作業中なのに知らせが届かないセッション）・`receiver-unavailable`（受け口を用意できずに hooks なしで起動したセッション）・`claude-version-unsupported`（版が分からない・古いために hooks なしで起動したセッション）・`checkpoint-failed`（区切り・差分・今の区間の比較の失敗）

### 行の `author`（累積の一覧。`agentChangesScopedQuery.ts` の `cumulative` の解決のときだけ）

1. `tracking` で `periodUnassignable` が無いとき、今の区間を求める: `checkpoint` が始点と共有ならその一覧のパス、そうでなければ `collectAgentChangeEntries(checkpoint.snapshot)` のパス。`phase` が `idle` なら利用者、`agent` ならエージェント、`paused` ならどちらでもない。比較が失敗したら記録を `lost`（`checkpoint-failed`）にし、今の区間は割り当てない（一覧は失敗にしない）
2. U = `userPaths` ∪ 今の区間（利用者）、A = `agentPaths` ∪ 今の区間（エージェント）
3. 行ごとに `matches(entryPath, p)`: 完全一致、または片方が `/` で終わるフォルダの表記でもう片方がその下（前方一致は `/` の境目でだけ。L-007）
4. `notRecorded` の行 → `null`。U に一致があり A に無い → `user`、両方にある → `mixed`、それ以外 → `agent`
5. 区別していない記録（`tracking` で `trackingSince` が null、`lost` で集合が空）→ すべて `null`。`lost` で集合があれば、手順 1 の今の区間を除いて 2〜4 を行う
6. 実行の範囲（`toWorktree`・`between`）→ すべて `null`

- パスの照合は、git の出力のパス（同じ記録のインデックスの系統）どうしだけで行い、hook のパスや OS のパスと比べない（L-009・L-018）

### アプリの戻す操作・取り消しの吸収（registry の `withAttributionAbsorbed(ownerId, record, task, changed)`）

- 戻す 3 つの IPC（`agentChangesHandlers.ts` の行の `↶`・ハンク・`すべて戻す`。`withRecordOrThrow`・`withRecordAtPath` のタスクの中）と取り消し（`AgentBaselineRegistry.undoLastRevert` の `withRecord` のタスクの中。取り消しは registry の中にあるため、registry の中で包む）の処理を包む。`withAttributionAbsorbed` は列の中で呼ぶ（自分では列に並ばない。同期と同じ列の中で直列になる）。`tracking` のとき、(1) 同期の手順 5〜7 と同じく区切り S1 を取り（手順 4 の印を下ろすことはしない。`unassignableBefore` は控える）、前の区切りからの差分を今の `phase` に割り当て（印があれば割り当てない）、`checkpoint = { snapshot: S1, sharedWithBaseline: false }`・`periodUnassignable = unassignableBefore || （S1 を取り始めた後に立った印） || 合図の unassignable`（実際には下ろさずに `||=` で合図を足すだけ。段階を変えないので、吸収の前に立った打ち切りの印も、差分を求めている最中の印もすべて残す）にし、`timedOutPending` も下ろさない（打ち切られたツールが動き続けている場合を、続く同期が手順 4・9 で片付ける）。`phase` は変えない。S1 の `await` のたびに同期の手順 11 と同じく確かめる、同期の手順 7・9 と同じく `hadUnassignedSince` を更新し（S1 までの差分を印のために割り当てなかったときは、`trackingSince` があれば立てる。(3) で捨てる S1 から S2 の差分はアプリの操作なので対象外）、手順 10 で前の区切りを消す、(2) `task` を行う、(3) 作業ツリーを 1 件以上変えたら（引数 `changed: (result) => boolean` で `task` の結果から決める。包む `task` は戻す関数の呼び出し〈`agentChangesHandlers.ts` の `revertAgentChange`・`revertAgentChangeHunk`・`revertAllAgentChanges`。結果の `applied` を持つ〉と、registry の取り消しの実行〈`this.deps.executeUndo` から結果を作るまで〉だけで、控えを記録へ移す `commitRevert`〈`registry.commitRevertUndo`〉は吸収の外〈吸収の後、同じ `withRecord` のタスクの中〉で呼ぶ。戻す操作は `applied > 0`、取り消しは結果（`AgentChangesUndoResult`）の `restoredPaths`・`trashedPaths` のどちらかが空でない。`task` が投げたときは変えたかが分からない〈`undoLastRevert` は 1 件以上書き換えた後の失敗で投げ、戻す操作も途中まで適用して投げうる〉ため、必ず S2 を取ってから同じ例外を投げ直す）、区切り S2 を取り直して `checkpoint = { snapshot: S2, sharedWithBaseline: false }` に置き換え（S1 を消す）、その差分はどちらの集合にも入れず、`periodUnassignable ||= 合図の unassignable` とする（上書きしない。(1) の後に立った印〈列の外の打ち切り〉は残る。吸収の後に印が消えない）。S2 を取る最中の `canceled`・`close`・世代の変化は、同期の手順 5・11 と同じく取れたものを消して記録を変えない（L-435）

- 戻した行のパスを集合から外すことはしない（取り消しで戻ってくる内容の帰属を控えに持たずに済ませる。古い印が残ることは既知の制約）

| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 区別していない（`attribution` が区別していない形） | 今のまま `記録を始めた後にあなたが編集した内容も戻ります。`                                                                 |
| 区別している                                       | `エージェントのツールが動いている間（終わってから 2 秒を含む）にあなたが編集した内容は、エージェントの変更として戻ります。` |
| 区別を始めたのが記録の開始より後                   | 上に `HH:MM より前のあなたの編集も戻ります。` を足す                                                                        |
| `hadUnassignedSince`                               | 上に `アプリの中で claude が動いていなかった間などのあなたの編集も戻ります。` を足す                                        |
| `lost` で印がある                                  | 上に `区別をやめた後（HH:MM から）のあなたの編集も戻ります。` を足す                                                        |
| 除く行がある                                       | 最後に `利用者の変更 M 件（印の付いた行）は戻しません。行の ↶ で個別に戻せます。` を足す                                    |

行の `↶` の確認は、今の文言の後に、`user` なら `このファイルは、エージェントのツールが動いていない間に変更されました（利用者の変更）。`、`mixed` なら `このファイルには、エージェントのツールが動いていない間の変更（利用者の変更）が含まれます。` を足す。

## 記録・実行ごとの記録・取り消し・自動の取り直しとの関係（段階 B）

| 既存の仕組み                       | 関係                                                                                                                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 累積の始点・`確認を終える`         | 区別は記録ごと。`確認を終える`・フォルダの切り替え・リロードで記録とともに捨て、判定の区切りと削除待ちの一時ディレクトリも消す。次の記録で改めて判定する    |
| 実行の区切り（送信の前の `begin`） | 変えない。実行の区切りと判定の区切りは別に持つ（送信を遅らせない）                                                                                          |
| 実行の範囲の一覧・diff             | `author` は `null`。印・`すべて戻す` の表示は出さない（戻す操作は今どおり累積でだけ）                                                                       |
| 取り消しの控え・保護の ref         | 控えの照合・書き戻しは変えない。取り消しは上の吸収で包む。保護の ref に判定の区切りは足さない                                                               |
| 自動の取り直し・静かな取り直し     | 変えない。印・区別の状態は一覧の結果に含まれ、静かな取り直しは中身が変わったときだけ写しを置き換える                                                        |
| `あなたの保存を含む`               | 今のまま（renderer の保存の記録）。`利用者の変更` の印と独立に出す。`すべて戻す` の対象は `author` だけで決める（アプリで保存したパスを除く規則は足さない） |

## IPC と型

段階 A: 新しい IPC は `agentTerminal:reportWorking`（renderer → main の send。引数は pty の sessionId だけ）。hooks の知らせは IPC ではなく HTTP の受け口に届く。

段階 B: 新しい IPC は `agentTerminal:reportWorkingEnded`（renderer → main の send。引数は pty の sessionId だけ。作業中の知らせと同じ検査。「hooks が届かなくなったことの検知（段階 B）」）だけ。記録・一覧の IPC は引数を変えず、結果の型だけを変える。型の置き場所は `src/shared/types/agentChanges.ts`。B-1 では下の 3 つの型（`AgentChangeAuthor`・`AgentChangesAttributionLostReason`・`AgentChangesAttributionSummary`）を定義するだけで（main の `agentChangesAttribution.ts` が使う）、`AgentChangeEntry.author` と `AgentChangesState`・`AgentChangesListResult` への `attribution` の追加は B-2 で行う（B-1 では IPC の結果は変わらない）:

- `AgentChangeAuthor = 'agent' | 'user' | 'mixed'`、`AgentChangeEntry.author: AgentChangeAuthor | null`
- `AgentChangesAttributionLostReason = 'hooks-not-confirmed' | 'receiver-unavailable' | 'claude-version-unsupported' | 'checkpoint-failed'`
- `AgentChangesAttributionSummary = { kind: 'tracking'; since: number | null; hadUnassignedSince: boolean } | { kind: 'lost'; reason: AgentChangesAttributionLostReason; lostAt: number; hadMarks: boolean; since: number | null; hadUnassignedSince: boolean }`（`since` は `trackingSince`。`hadMarks` は集合が空でないか）
- `AgentChangesState` の `recording`（registry の `recordingState` が作る。`begin`・`getState`・戻す操作の後の状態）と `AgentChangesListResult` の `recording`・`scope-unavailable`（`listAgentChangesInScope` の `common`）に `attribution: AgentChangesAttributionSummary`（必須）
- main の追跡の理由の型 `AgentHooksLostReason`（`agentToolActivity.ts`）と記録の理由 `AgentChangesAttributionLostReason` は別の型にし、記録の側は追跡の理由に `checkpoint-failed` を足した union にする（用途ごとに型を分け、`string` で受けない。L-439）
- preload・`index.d.ts`・`agentChangesApi.ts` は型の変更だけ（`reportAgentSessionWorkingEnded` は `agentTerminalApi.ts`）

## renderer（段階 B）

- `hooks/useAgentHooksWorkingReport.ts`: 作業の終わり（`working` を見た後の `idle`）も `reportAgentSessionWorkingEnded` で送る（「hooks が届かなくなったことの検知（段階 B）」）。送るかの規則（タブごとの控えと今の活動 → 送る知らせと次の控え）は純粋な関数 `lib/agentHooksWorkingReport.ts` の `nextWorkingReport` に置き、hook は控えを持って送るだけ。`lib/agentTerminalApi.ts` に `reportAgentSessionWorkingEnded`
- `AgentChangesFileItem.tsx`: 必須の props `author`（`AgentChangeAuthor | null`）を足し、`user` → `利用者の変更`、`mixed` → `利用者の変更を含む` の印（`agent-changes__mark`）を出す
- `agentChangesMessages.ts`: 印の文言・`すべて戻す` の除く旨の 1 行・理由・上の「確認の文言」・区別の状態の 1 行と理由の文言（`hooks-not-confirmed` → `claude の hooks から知らせが届きません`、`receiver-unavailable` → `hooks の知らせの受け口を用意できませんでした`、`claude-version-unsupported` → `claude の版が古いか、版を確かめられませんでした`、`checkpoint-failed` → `作業ツリーの記録に失敗しました`）
- `agentChangesAvailability.ts`: `agentRevertAllDisabledReason` に `revertAllTargetCount`（必須）を足し、今の理由の後に、行があって対象が 0 件なら `利用者の変更だけのため…` を返す
- `useAgentChangesRevert.ts`: `revertAll` の `expected`・確認の件数・ゴミ箱へ移す件数・フォルダの有無・`savedInApp` を、`user`・`mixed` を除いた行で求める。除く件数と `attribution` を確認の文言に渡す。行の `↶` の確認に `author` を渡す
- `agentChangesView.ts`: 写しの `attribution`、`isSameAgentChangesView` に `author`・`attribution` を含める
- `AgentChangesSection.tsx`: 行に `author` を渡す（実行の範囲では null のまま）。累積の範囲で区別の状態の 1 行と、`すべて戻す` の除く旨の 1 行（id を振って `aria-describedby`）を出す
- 新しいボタン・フォーカスの移動は無い（L-408 の対象の操作を足さない）

## セキュリティ

| 脅威                                                 | 対策                                                                                                                                                                                                                 |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 別のマシンからの要求                                 | `127.0.0.1` だけで待ち受ける（`0.0.0.0`・`::` にしない）                                                                                                                                                             |
| 同じマシンの別のアプリ・別の利用者の偽の知らせ       | セッションごとの 256 ビットのトークン。トークンは 0700 のディレクトリの 0600 のファイルと main のメモリにだけ置き、起動の引数・環境変数・renderer・ログに出さない                                                    |
| ブラウザのページからの要求（CSRF・DNS rebinding）    | `Origin` のある要求と、`Host` が `127.0.0.1:<ポート>` でない要求を拒む。CORS に答えない                                                                                                                              |
| プロキシへのトークンの流出                           | `claude` の環境の `NO_PROXY`・`no_proxy` に `127.0.0.1`・`localhost` を足す                                                                                                                                          |
| renderer の乗っ取り                                  | 起動の引数・設定のファイルのパスと中身・URL・トークンは main が決め、renderer から受け取らない（L-019）。作業中の知らせ・作業の終わりの知らせ（B）は sessionId だけで、送信元のウィンドウのセッションだけを指せる。効果は、`pending` のセッションを `unconfirmed` にする・`confirmed` のセッションを保留にする（どちらも印を増やさない側）と、作業中の知らせでターンの終わりの待ち（まだ発火していない 30 秒のタイマー）を取り消すことだけ。取り消しても保留を立てないだけで、区間・確かめた状態・記録は変えない（乗っ取られた renderer は hooks が止まったことの検知を遅らせられるが、区間を閉じたり印を増やしたりはできない） |
| 引数インジェクション                                 | `--settings` の値は main が作った絶対パスだけ（L-034）。hook の入力の値は git の引数にもファイルのパスにも使わない                                                                                                   |
| 大きな本文・多数の要求でのメモリの消費               | 本文は 16 MiB より先を持たずに読み捨てる（`requestTimeout` の 15 秒が上限）。セッションごとの開いた区間は 256 件まで。要求の打ち切り（ヘッダー 5 秒・全体 15 秒）                                                    |
| 設定のファイルを差し替えられて別の hook を動かされる | `mkdtemp` のディレクトリ（0700）に `wx` で作る（共有の一時ディレクトリで先に同じ名前を置かれても上書きしない）                                                                                                       |
| エージェント自身による偽の知らせ                     | 防がない。エージェントは利用者と同じ権限で動き、`ps` から設定のファイルのパスを知って読める。偽の知らせで変わるのは印だけで、作業ツリー・記録は変わらない（既知の制約）                                              |
| git の環境の漏れ                                     | 判定の区切りは既存の `takeBaselineSnapshot`・`collectAgentChangeEntries*` だけを使い、記録の git の環境（`buildBaselineGitEnv`。L-075）をそのまま使う                                                                |

## 新しい状態と既存の入口（L-061）

新しい状態「ウィンドウの段階」（段階 A）と「記録の区別の段階・集合」（段階 B）に対し、作業ツリー・記録を変える入口（`agentChangesHandlers.ts` の `ipcMain.handle`・registry の公開のメソッド・`agentTerminalHandlers.ts`・hooks の受け口から拾った）の扱いを決める。

| 入口                                                                      | 影響                                                                                                              |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| エージェントのセッションの起動・終了・停止（タブの開閉）                  | 追跡にセッションを足す（`pending`）・外す。あるべき段階が変われば通知（A）・同期（B）                             |
| hooks の知らせ                                                            | 確かめた状態・区間を変える。あるべき段階が変われば通知（A）・同期（B）。`PreToolUse` は通知の後に待つ（B で効く） |
| 作業中の知らせ（`agentTerminal:reportWorking`）                           | `pending` のセッションの 15 秒のタイマーを張る（A）。`confirmed` のセッションのターンの終わりの待ちを取り消す（B）。`unconfirmed` になれば区別をやめる（B） |
| 作業の終わりの知らせ（`agentTerminal:reportWorkingEnded`。B）             | `confirmed` のセッションで、`Stop`・`StopFailure` を受けていなければ 30 秒のタイマーを張る。発火で保留になり（合図 `unassignable`）、次の知らせまで割り当てない |
| アプリの終了（`before-quit` の停止の待ち → `will-quit`）                  | 停止の待ちの間も知らせを受け付ける。`will-quit` で受け口・設定のファイル・タイマーを片付ける（A）                 |
| `begin`（`send`・`manual`）で記録を作る                                   | 区別を始める（B）                                                                                                 |
| `begin`（`send`）で実行の区切りを足す                                     | 影響しない                                                                                                        |
| `list`・`getDiff`（累積）                                                 | 今の区間を求めて `author` を付ける（比較の失敗で `lost`。B）                                                      |
| `list`・`getDiff`（実行）                                                 | 影響しない（`author` は null）                                                                                    |
| 行の `↶`・ハンク・`すべて戻す`・取り消し                                  | 吸収で包む。`すべて戻す` は `user`・`mixed` を除く（B）                                                           |
| `clear`・所有者の文脈の終わり・`close`                                    | 記録とともに捨てる。判定の区切りと削除待ちの一時ディレクトリを消す（B）                                           |
| 既存の Git の操作（ソース管理の取り消し・pull・checkout）・アプリでの保存 | 区別しない（そのときの段階で、次の区切りで割り当てる。既知の制約）                                                |

## 既知の制約（ROADMAP・実機テスト仕様書に反映する）

- 区別するのは、アプリの中のタブで起動した `claude` のツールの区間だけ。アプリの外で起動した `claude`、エージェントが起動した別の `claude`、ほかのエージェント CLI の変更は区別しない（アプリの中で `claude` が動いていない間は印を付けない。動いている間に外で書かれた変更は `利用者の変更` になる）
- 利用者の変更とするのは、エージェントのツール（`Write`・`Edit`・`MultiEdit`・`NotebookEdit`・`Bash`・`PowerShell`）が動いていない間に変わったファイルだけ。ツールの実行中・許可の確認を待つ間・ツールの終わりから 2 秒の間（利用者の `PostToolUse` の hook の自動整形をエージェントに数えるための猶予）・`claude` の起動から最初のプロンプトの知らせが届くまで（`pending`）・中断（Esc）の後に次のターンの `Stop` が届くまで（届かなければ最大 15 分）に利用者が書いた変更は、エージェントの変更になり `すべて戻す` で戻る（確認の文言で伝える）
- エージェントのツールの開始の待ちが 5 秒で打ち切られた区間（区切りに時間がかかった・ほかの操作が先に並んでいた）、15 分を超えて開いた区間が、その区間の本来の閉じ方（`Stop`・`SubagentStop`・`SessionEnd` など）で閉じるまでの区間（16 MiB を超える知らせ〈大きなファイルを書いた `Write` など〉で ID を読めずに開き、終わりの `PostToolUse` も 16 MiB を超えて ID を読めず `tool-end` の規則 (3) でも閉じられない区間は、`SessionEnd`・終了まで閉じないため、15 分の後はそのセッションの終わりまで）、累積の始点を取っている間の区間（その間にツールが動いた・`pending` のセッションがあったとき）の変更は、どちらとも決めず、印を付けない（`すべて戻す` で戻る）。`pending` の間（最初の知らせが届くまで）の変更はエージェントの変更として数える
- 上のツール以外（MCP のツール・プラグインのツールなど）がファイルを書いた・`Bash` で背景に起動したプロセス（開発サーバー・監視のビルドなど）がツールの終わりから 2 秒の後に書いた・エディタの自動整形など別のプロセスが書いた・利用者の `PostToolUse` の hook がツールの終わりから 2 秒を超えて書いた・`claude` の `/rewind`（ツールを使わずにファイルを戻す）で戻った変更は、`利用者の変更` になる（`すべて戻す` から外れるだけで、行の `↶` で戻せる）
- エージェントがツールを呼ぶたびに（動いていない状態からのとき）、作業ツリーの区切りを取り終えるまでツールの開始が待たされる（上限 5 秒）。区切りは未追跡のファイルが多いリポジトリほど遅い
- hooks が効いているかは、最初の知らせ（ふつうはプロンプトを送ったときの `UserPromptSubmit`）で確かめる。知らせが届かないことは、画面の活動の判定が作業中を検知してから 15 秒後に分かる。画面の判定が、プロンプトを送る前に作業中と誤って判定すると（`claude` の起動時の表示など）、hooks が効いていても区別をやめることがある
- 判定の区切り・差分の比較に失敗した（未追跡のファイルが多すぎる・時間切れ・`git gc --prune=now` で区切りが消えた）・作業中なのに知らせの届かないセッションがあった記録は、それ以降の変更に印を付けない（それまでの印は残る）。次の記録（`確認を終える` の後）で改めて区別する
- 区別が始まった後（`confirmed` の後）に hooks が無効にされた場合（設定の読み直しで `disableAllHooks` が効いたなど）は、画面の活動が作業の終わり（`working` の後の `idle`）になってから 30 秒後に割り当てを保留し、その pty の終了まで（知らせが届かないため）以後の変更に印を付けない（段階 B）。保留が立つ前の区間（hooks が届かなくなってから保留までの間）も、保留が立った時点の同期で割り当てない。ただし、その間に別の契機（ほかのタブの段階の変化・戻す操作の吸収）で同期が走った分は、`PreToolUse` が届かないため `利用者の変更` に入りうる
- 中断（Esc）では `Stop` が届かないため、中断の後 30 秒以内に次の指示を送らないと（起動の直後の最初のターンを含む）、次の指示（`UserPromptSubmit`）が届くまで割り当てを保留する（その間の利用者の編集は印が付かず、`すべて戻す` で戻る。区別そのものは次の指示で続く）。許可の確認で拒否した後に `Stop` が届かない場合も同じ（未確認事項 3）。メインの `Stop` の後に背景のサブエージェントの作業で画面が作業中に戻り、その終わりに `Stop` が届かない場合も同じになりうる。`/compact` など、モデルのターンでない作業中の表示の後も Stop が届かなければ同じく保留になりうる（AGC-111 で確かめる）
- ツールの終わりの猶予は、メインのエージェントのツール（ID があって `agent_id` の無い区間）では `PostToolBatch` から 2 秒で、利用者の `PostToolUse` の hook が長くかかっても覆う。サブエージェントのツール（`agent_id` のある区間）と ID を読めなかった区間は `PostToolUse`・`PostToolUseFailure` から 2 秒のまま（2 秒を超える hook の書き込みは `利用者の変更` になる）。`PostToolBatch` を知らない版の `claude` では、メインのエージェントのツールの区間はそのターンの `Stop` まで開いたまま（ツールの後の利用者の編集はエージェントの変更になる）
- 保留は追跡の `signalOf` を通してウィンドウ全体の合図 `unassignable` になるため、保留したタブの pty が終わる（または次の知らせが届く）まで、同じウィンドウのほかのタブのエージェント・利用者の変更も割り当てない（同じウィンドウの記録は 1 つで、区別が実質止まる）
- `Stop` が届いた後に画面の判定が一時的に `working` へ揺れて `idle` に戻ると、その後の `Stop` は来ないため、30 秒後に誤って保留が立ちうる（安全側。次の知らせで解ける）
- 同期の手順 5〜7 の間（約 0.3 秒）に、手順 2 の時点では下りていた合図の `unassignable` が立ってすぐ下りると、手順 9 の印は手順 2 と今の合図のどちらにも当たらず、その短い窓の変更が手順 8 の段階 d に割り当たりうる（手順 2 の時点で立っていた合図が窓の中で下りる場合は、手順 2 の値で印を残す）
- 1 つのセッションで同時に開いた区間が 256 件を超えると、そのセッションの `SessionEnd`（`/clear` を含む）・終了まで、その間の変更を割り当てない（印を付けない）。`PostToolBatch` を知らない版の `claude` では、`ended` の区間が `Stop` まで残って 256 件の上限に数えられるため、1 つのターンでツールを 256 回より多く呼ぶとあふれ、`Stop` では下りないため、そのセッションの終わりまで割り当てない（安全側）
- アプリの戻す操作・取り消しの最中（吸収の区切りを 2 回取る間。`すべて戻す` で件数が多く、ゴミ箱への移動を伴うと長くなる）に外で書かれた変更は、アプリの操作の差分（S1 から S2）と一緒にどちらとも決めず、`すべて戻す` で戻り、確認の文言では伝えない（`hadUnassignedSince` も立てない）。窓は利用者自身がアプリで戻す操作をしている間に限られるため、その間の外での編集はまれとして受け入れる
- hooks が使えない `claude`（利用者・管理者の設定の `disableAllHooks`・`allowManagedHooksOnly`・`allowedHttpHookUrls`、`--bare`・`--safe-mode` 相当の起動）では区別しない。`claude` の版が 2.1.101 より古い・版を確かめられない（`claude --version` が 5 秒で終わらない・出力の形が違う）ときは hooks を渡さず、区別しない（起動は今までどおり）
- 起動のたびに（同じ `claude` では main の起動の間に 1 回だけ）`claude --version` を実行するため、最初の起動が少し遅くなる。版の確認が打ち切られた（5 秒）・起動に失敗した・0 でない終了だったときは結果を控えないため、`claude --version` が毎回 5 秒を超える環境では、起動のたびに最大で約 6 秒（打ち切りの 5 秒と SIGKILL までの 1 秒）遅くなり、hooks も渡らない
- 同じフォルダを 2 つのウィンドウで開くと、別のウィンドウのエージェントの変更は `利用者の変更` になる
- 一度 `利用者の変更` に入ったパスは、行の `↶` で戻した後もその記録の間は覚えたままで、エージェントが同じファイルを書き直すと `利用者の変更を含む` になる
- 既存の Git の操作（ソース管理の取り消し・pull・checkout など）とアプリでの保存は、そのときの段階で利用者かエージェントの変更に数える
- 記録していないファイル（大きすぎる・ignore 済み）の行は区別しない（印なし。今どおり `すべて戻す` は使えない）
- 起動の引数に `--settings <一時ディレクトリのファイル>` が付く（`ps` で見える。トークンはファイルの中で、持ち主だけが読める）。`claude` の `/hooks` にアプリの hooks（段階 A は 8 つ、段階 B から `PostToolBatch` を加えて 9 つ）が出る。`claude` の環境の `NO_PROXY`・`no_proxy` に `127.0.0.1`・`localhost` が足される
- エージェント自身は、設定のファイルを読んで偽の知らせを送れる（印が変わるだけで、作業ツリー・記録は変わらない）
- アプリが異常終了すると、設定のファイルの一時ディレクトリ（トークン入り。トークンはアプリの終了で無効）が残る。OS の一時ディレクトリの掃除に任せる
- Windows・Linux では確かめていない（ループバックの待ち受けでファイアウォールの確認が出るか、パスに空白を含む `--settings` の引数の渡り方、`PowerShell` のツールの名前）
