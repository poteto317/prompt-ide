## 目的

エージェントの変更のセクション（ソース管理パネル）は、記録を始めた後（累積の始点の後）に作業ツリーで変わったファイルを、すべて「エージェントの変更」として出す。利用者がエディタ（アプリの外を含む）や端末で編集したファイルも同じ一覧に混ざり、`すべて戻す` で利用者の編集まで実行前の状態に戻ってしまう（2026-10-06 の確認の結果 4。今はアプリで保存したパスにだけ `あなたの保存を含む` の印を付け、確認の文言で `記録を始めた後にあなたが編集した内容も戻ります` と断っている）。

この機能では、アプリが起動する `claude` に hooks を渡し、エージェントがファイルを書くツール（`Write`・`Edit` など）とシェル（`Bash`）を実行している区間を main が知る。エージェントのツールが動いていない間に変わったファイルを「利用者の変更」として一覧の行に印を付け、`すべて戻す` の対象から外す。

| ツールの終わりの猶予                 | ツールの終わり（`PostToolUse`・`PostToolUseFailure`）から 2 秒（`AGENT_TOOL_END_GRACE_MS`）は、まだエージェントが動いているとみなす。利用者の `PostToolUse` の hook による自動整形などをエージェントの変更に数えるため（誤って利用者の変更になる方向より安全）。覆えるのは 2 秒以内に終わる整形に限る（一致した hooks は並行に動き〈確認の結果 7〉、アプリの `http` の hook は利用者の hook の終わりを待たずに届いてすぐ返るため、2 秒を超えて書いた変更は利用者の変更になる）。その間の利用者の編集はエージェントの変更に数えられる（既知の制約）。`PostToolBatch` で覆う案は段階 B の設計で決める（下の「`PostToolBatch`（A では使わない）」） |
| 実装の分け方                         | 2 つの PR（実装プラン）に分ける。段階 A（hooks の受け取りと区間の追跡。画面はほぼ変わらない）だけで完結してテストでき、段階 A の終わりの状態で main に入れてよい形にする。段階 A ではウィンドウの段階を追跡して内部で持つだけで、一覧には影響しない。段階 B で写しによる判定・印・`すべて戻す` を入れる                                                                                                                                                                                                                                                                                                                                          |
| hooks が効いているかの確かめ方       | `SessionStart` は `command`・`mcp_tool` の hook だけを受け付け、`http` の hook は使えない（確認の結果 3）。そこで、どのイベントでも照合が通った最初の知らせが届いたら、そのセッションを `confirmed` にする。確かめるためだけに `UserPromptSubmit` も渡す（区間には使わない。`UserPromptSubmit` では区間を閉じない）。起動から最初の知らせまでは `pending` で、あるべき段階は `agent`（安全な方向）。`unconfirmed` にするのは、既存の画面の活動の判定で「作業中」を検知したのに、一定時間（`AGENT_HOOKS_UNCONFIRMED_AFTER_WORKING_MS`）知らせが 1 つも届かないとき                                                                                |

## 確認の結果（設計時に確かめた事実。2026-10-13）

手元の `claude` は `2.1.291 (Claude Code)`。実物の `claude` を起動して API を呼ぶ実験はしていない。出典は (A) `claude --help`（2.1.291）、(B) Claude Code の hooks のドキュメント（https://code.claude.com/docs/en/hooks 。https://docs.claude.com/en/docs/claude-code/hooks から 301 で移動。2026-10-13 に取得）。

1. **`--settings` と hooks の無効化** (A): `--settings <file-or-json>  Path to a settings JSON file or a JSON string to load additional settings from`。`--bare` は `skip hooks (those defined in settings and by installed plugins…)`。`--safe-mode` は hooks を含むカスタマイズを無効にする。`--setting-sources <sources>` で読み込む設定の元（user・project・local）を選べる
2. **設定の形** (B): `hooks` → イベント名 → matcher の組の配列 → `hooks` の配列（`type`・`command` か `url`・`timeout` など）。hooks は設定の元をまたいで足し合わされ（merge）、置き換えない。`disableAllHooks: true` で無効にでき、管理者の設定の `allowManagedHooksOnly` は利用者・プロジェクト・ローカルの hooks を止め、`allowedHttpHookUrls` は `http` の hook の URL の許可リスト
3. **イベントと終了の意味** (B): `SessionStart`・`UserPromptSubmit`・`Stop`・`StopFailure`・`PreToolUse`・`PermissionRequest`・`PostToolUse`・`PostToolUseFailure`・`SubagentStart`・`SubagentStop`・`SessionEnd` など。**`SessionStart` は `Only type: "command" and type: "mcp_tool" hooks are supported.`（`Setup` も同じ）で、`http` の hook は使えない**（利用者が確かめた）。`PreToolUse` は終了コード 2 でツールを止められる（hook が終わるまでツールを動かさない）。`PostToolUse`・`PostToolUseFailure`・`SessionEnd` の終了コード 2 は無視される。それ以外の 0 でない終了・失敗は止めない（non-blocking error）。`SessionEnd` は matcher に終了の理由（`clear`・`resume`・`logout`・`prompt_input_exit` など）を持ち、`/clear`・`/resume` でも届く
4. **matcher** (B): `"*"`・`""`・省略はすべてに一致。英字・数字・`_`・`-`・空白・`,`・`|` だけなら完全一致の名前（`|` 区切りの並び）。それ以外の文字を含むと JavaScript の正規表現（前後を固定しない）。ツールのイベントはツールの名前、`SubagentStop` はエージェントの種類と照合する
5. **入力の JSON** (B): すべてのイベントに `session_id`・`transcript_path`・`cwd`・`hook_event_name`・`permission_mode` など。サブエージェントのときは `agent_id`・`agent_type`。ツールのイベントは `tool_name`・`tool_input`・`tool_use_id`（`PostToolUse` は `tool_response` も）。ファイルのツールの `tool_input` は `file_path` か `notebook_path` を持ち、**絶対パス**。サブエージェントのツールでもツールのイベントが動く
6. **`http` の hook** (B): 必須は `type`・`url`。`headers`（値の中の `$VAR` は `allowedEnvVars` に挙げた環境変数だけを展開）・`onFailure`。応答の 2xx で本文が空 → 成功・出力なし、2xx で JSON → コマンドの hook の標準出力と同じ解釈、2xx でそれ以外の本文・2xx 以外・接続の失敗 → 止めない失敗、打ち切り → hook を取り消して判断なし。`onFailure: "block"`（失敗でツールを止める）は 2.1.295 以降。`SessionStart`・`Setup` 以外（今回使う `UserPromptSubmit`・ツールのイベント・`SubagentStop`・`Stop`・`StopFailure`・`SessionEnd`）は `http` を使える
7. **実行のされ方** (B): 一致した hooks は並行に動く。`command` の hook は `args` を省くとシェルで動く（macOS・Linux は `sh -c`、Windows は PowerShell か Git Bash）。hook は `claude` の環境を受け継ぐ
8. **打ち切り** (B): `timeout` は秒。既定は `command`・`http` が 600 秒（`UserPromptSubmit` などは 30 秒）。`SessionEnd` の hooks は合わせて 1.5 秒の持ち時間
9. **設定の読み込み** (B): hooks は起動時と、ファイルの監視が変更を見つけたときに読み直す
10. **`http` の hook が入った版** (https://code.claude.com/docs/en/changelog.md を 2026-10-13 に取得して確かめた): `<Update label="2.1.63" description="February 28, 2026">` に `Added HTTP hooks, which can POST JSON to a URL and receive JSON instead of running a shell command`。それより前の版に `--settings` で `http` の hook を渡したときの動きは書かれていない。渡す hooks に関わる変更: `<Update label="2.1.69" description="March 5, 2026">` に `Added agent_id (for subagents) and agent_type (for subagents and --agent) to hook events`、`<Update label="2.1.78" description="March 17, 2026">` に `Added StopFailure hook event that fires when the turn ends due to an API error`、`<Update label="2.1.101" description="April 10, 2026">` に `Improved settings resilience: an unrecognized hook event name in settings.json no longer causes the entire file to be ignored`（2.1.101 より前は、知らないイベント名〈`StopFailure` など〉を含む設定のファイルが全体で無視されうる）。このため下限は 2.1.101 にする。コードを grep した範囲（`src/main`）に、`claude` の版を確かめる既存の仕組み（`--version` の実行など）は無い
11. **既存の起動** (コード): `buildAgentLaunchArgs` は `--session-id <UUID>`（新規）か `--resume <UUID>`（再開）だけを返し、`agentSessionStarter` が `launch.plan.args`（空）の後ろに足す。pty の sessionId（`createSessionId()`）は、`records.whenLoaded()` の後の await を挟まない区間（ID の選択と予約の間）で振る。ROADMAP の実装済みの機能に「`claude` の起動の引数はセッションの指定だけ…hooks は使わない」とある
12. **既存の記録** (コード): 1 つのウィンドウ（`event.sender.id`）に記録が 1 つ。同じウィンドウの複数のエージェントのタブは同じ記録を共有する。区切りは `takeBaselineSnapshot(folderPath, { baseIndexPath, isCanceled })` で取る。tree どうしの差分は `agentChangesQuery.ts` の `collectAgentChangeEntriesBetween(start, end)`（除外・入れ子のリポジトリの扱いを含む。今は export していない）

### 受け口（新しいファイル `agentHookReceiver.ts`）

- Node の `http.createServer`。最初のエージェントのセッションを起動するときに `listen({ host: '127.0.0.1', port: 0 })` で始め（Promise を持ち回し、2 つ目の起動は同じ Promise を待つ）、失敗したらその起動は hooks なし（`hookSettingsPath: null`）で行い、次の起動で始め直す。`headersTimeout` 5 秒・`requestTimeout` 15 秒。アプリの終了（`will-quit`）で `close` と `closeAllConnections`

  | 検査                                                                                                  | 外れたとき（理由）      |
  | ----------------------------------------------------------------------------------------------------- | ----------------------- |
  | メソッドが `POST`                                                                                     | 405（`method`）         |
  | パスが `/prompt-ide/agent-hooks/v1/<イベント>`（`<イベント>` は下の表の 8 つのどれか。完全一致）      | 404（`path`）           |
  | `Host` が `127.0.0.1:<ポート>`、`Origin` が無い                                                       | 403（`host`・`origin`） |
  | `Authorization` が `Bearer <64 桁の 16 進>` で、その SHA-256 を鍵にした表に生きているセッションがある | 401（`token`）          |
  | `Content-Type` が `application/json` で始まる                                                         | 415（`content-type`）   |

- `Host`・`Content-Type` の検査は、未確認事項 1 の実測の値に合わせる（実測で違えば、段階 A のタスク 1 で検査とテストを直す）
- 本文の大きさ: 上の表の検査（メソッド・パス・`Host`・`Origin`・トークン・`Content-Type`）がすべて通った要求だけ本文を読み、16 MiB までを持つ。16 MiB を超えたら、それ以上は持たずに残りの本文を最後まで読み捨て（`requestTimeout` の 15 秒が上限）、照合が通っているので ID なしの知らせとして `deliver` し、通常どおり 200 を返す（`PreToolUse` は `onToolStart` を待ってから）。`too-large` は拒んだ要求ではないが、同じ件数のログに数える
- 本文が 16 MiB を超えた・JSON として読めない・`hook_event_name` がパスのイベントと違う（L-023）ときは、パスのイベントだけを使う（ツールのイベントは `tool_use_id` が無いものとして扱う。下の「区間の追跡」）。`Write` の `tool_input` はファイルの中身をすべて含むため、大きなファイルを書くと本文が大きくなる
- 照合の通った知らせ 1 件につき、追跡の `deliver(ownerId, sessionId, event)` を 1 回だけ呼ぶ。追跡はその中で確かめた状態（`pending` なら `confirmed`）と区間を更新し、あるべき段階を 1 回だけ求め、変わっていれば `onPhaseChange` を呼び終えてから戻る

### 入力の解釈（新しいファイル `agentHookEvents.ts`。純粋な関数）

- 使う欄は `hook_event_name`（文字列）・`tool_name`（ツールのイベントだけ。matcher の 6 つのどれか。違えば、`PreToolUse` は区間を開いてログに残し〈知らない名前で捨てると、そのツールの書き込みが利用者の変更に入る。L-002〉、`PostToolUse`・`PostToolUseFailure` は知らせを捨ててログに残す〈知らない名前を区間を閉じる根拠にしない。L-044〉。どちらも、照合が通っていれば確かめた知らせには数える）・`tool_use_id`（1〜256 文字の文字列。無い・形が違えば「ID なし」）・`agent_id`（1〜256 文字の文字列。無ければ null。形が違えば、`PreToolUse` は `tool_use_id` が読めても ID なしの区間として開いてログに残し〈捨てると、そのツールの書き込みが利用者の変更に入る。L-002〉、`PostToolUse`・`PostToolUseFailure`・`SubagentStop` は知らせを捨ててログに残す〈形の違う値を区間を閉じる根拠にしない。L-044〉。どちらも、照合が通っていれば確かめた知らせには数える）だけ。ほかの欄は読まない
- 結果は判別共用体 `AgentHookEvent`。どの要素も照合の通った知らせで、追跡は受け取ったら必ず確かめた状態を更新する。すべての要素に `hookEventName: AgentHookEventName`（パスから決めたイベント名。渡す 8 つのイベントの列挙型 `'UserPromptSubmit' | 'PreToolUse' | 'PostToolUse' | 'PostToolUseFailure' | 'SubagentStop' | 'Stop' | 'StopFailure' | 'SessionEnd'`）を持ち、ツールのイベント（`PreToolUse`・`PostToolUse`・`PostToolUseFailure` から作った要素。`confirm-only` を含む）には `toolName: string | null` も持つ（検証済みの値: 1〜64 文字の英数字・`_`・`-` だけの文字列。matcher の 6 つ以外でも形が合えば入れる。読めない・形が違えば null。開発版のログにだけ使い、区間の判定には使わない）
  - `{ kind: 'confirm-only'; reason }`: 区間を変えずに確かめるだけ。`reason` は `prompt-submit`（`UserPromptSubmit`）・`unknown-tool-end`（知らない `tool_name` の `PostToolUse`・`PostToolUseFailure`）・`bad-agent-id`（形の違う `agent_id` の `PostToolUse`・`PostToolUseFailure`・`SubagentStop`）・`subagent-stop-without-agent`（`agent_id` が無い・本文を読めない `SubagentStop`）
  - `{ kind: 'tool-start'; toolId: ToolIdRead; agentId: string | null }`・`{ kind: 'tool-end'; toolId: ToolIdRead; agentId: string | null }`: `ToolIdRead` は `{ kind: 'read'; id: string } | { kind: 'unreadable' }`（読めた ID と読めない〈本文が大きすぎる・読めない・形が違う〉を型で区別する）。`tool-start` は、形の違う `agent_id` でも `toolId: { kind: 'unreadable' }`・`agentId: null` にして開く
  - `{ kind: 'subagent-stop'; agentId: string }`（`agentId` は必須。無い・読めないときは `confirm-only`）
  - `{ kind: 'turn-end' }`（`Stop`・`StopFailure`。どちらかは `hookEventName` で見分ける）・`{ kind: 'session-end' }`
  - 例: 知らない `tool_name` の `PostToolUseFailure` は `{ kind: 'confirm-only'; reason: 'unknown-tool-end'; hookEventName: 'PostToolUseFailure'; toolName: 'Foo' }`

- `tool-end`: (1) 読めた ID が `openTools` にあれば外す（期限切れでも同じ）。(2) 読めた ID が `droppedToolIds` にあれば、控えから消すだけで何も閉じない（外した区間の遅れた知らせで、別の区間を閉じない）。(3) 読めた ID がどちらにも無ければ、`PreToolUse` を読めなかった区間の終わりとみなし、`anonymousOpen` の一番古い要素を 1 つ外す（無ければ何もしない）。(4) ID を読めない（本文が大きすぎる・読めない）`tool-end` は何も閉じない（ID ありで開いた区間の終わりかもしれず、ID なしの別の区間を閉じうるため。閉じ損ねは期限切れと `SessionEnd` に任せる）
- `subagent-stop`: その `agent_id` の区間を外す（期限切れでも同じ。外した ID は控えない〈その区間の遅れた `PostToolUse` は (3) で ID なしの区間を閉じうるが、`agent_id` が同じ `PostToolUse` は `SubagentStop` の後には届かない前提とする〉）
- `turn-end`: ID があって `agentId` が null の区間を外し（期限切れでも同じ）、外した ID を `droppedToolIds` に控える。`anonymousOpen` と `agent_id` のある区間は変えない（ID なしで開いた区間は、背景のサブエージェントのものかもしれない）
- `session-end`: そのセッションのすべての区間（期限切れ・`anonymousOpen` を含む）を外し、外した ID を `droppedToolIds` に控える（セッションは外さない。`/clear`・`/resume` でも届くため）
- pty の終了（`release`）: セッションごと外す（タイマーも外す）
- `reportWorking`: `pending` で `workingTimer` が無ければ 15 秒のタイマーを張る。発火したときにまだ `pending` なら `unconfirmed`（`hooks-not-confirmed`）にする
- 期限切れ: 開いて 15 分を超えた区間（`openTools`・`anonymousOpen` の各要素）を外さずに `expired` にする。期限切れの区間は、上の各知らせで区間の種類ごとの本来の閉じ方で閉じる（ID があって `agent_id` の無い区間は自分の `tool-end` か `turn-end`、`agent_id` のある区間は自分の `tool-end` か同じ `agent_id` の `subagent-stop`、ID なしの区間は (3) の `tool-end` か `session-end`・pty の終了）。期限切れの区間が 1 つでも残る間、ウィンドウの合図 `unassignable` を立てる（所有者ごとに 1 つのタイマー。一番早い期限に張り直す。`unref`）。開発版のログに `event=interval-expired` を出す
- ツールの終わりの猶予: 所有者のすべての区間が閉じた時点（どの閉じ方でも）から 2 秒のタイマー（`unref`）。その間に `tool-start` が来たら取り消す
- タイマーはすべて `unref` にし、`will-quit` の後始末（`close`）で外す

### ウィンドウのあるべき段階

`desiredPhase(ownerId)` を次の順で決める:

1. 生きているセッションのどれかが `unconfirmed` → 区別をやめる合図（理由 `hooks-not-confirmed`・`receiver-unavailable`・`claude-version-unsupported`）。段階は `agent` とする
2. `pending` のセッションがある → `agent`
3. `confirmed` のセッションが 1 つも無い → `paused`（ツールの終わりの猶予は効かない）
4. `confirmed` のセッションのどれかに開いた区間（`openTools` か `anonymousOpen`。期限切れの区間を含む）がある、またはツールの終わりの猶予の間 → `agent`
5. それ以外 → `idle`

- `unassignable` は段階の分岐と別に、生きているセッションのどれかに期限切れの区間が残っているかで常に求める（段階が `paused` でも立ちうる）

- 状態が変わるたびに（知らせ・作業中の知らせ・起動・終了・タイマー）、ウィンドウの合図（`activityOf(ownerId)` が返す `{ phase, lost: 理由 | null, unassignable: boolean }`）が変わったら、依存の `onPhaseChange(ownerId)` を同期的に呼ぶ（段階 A では開発版のログだけ。段階 B で registry の `syncAttribution` につなぐ）
- 所有者ごとのツールの開始の通し番号を `toolStartSeqOf(ownerId)` で返す（段階 B の始点の判定に使う）
- 開発版のログ: `[agent-hooks] owner=<id> session=<sessionId の先頭 8 桁> event=<イベント名か 起動・終了・作業中・確認の待ちの終わり> tool=<ツールの名前> id=<あり/なし> agent=<あり/なし> hooks=<確かめた状態> phase=<前>→<後>`

## 利用者の変更の判定（main。段階 B）

### 記録に持つもの（`agentChangesRecord.ts` に `attribution` を足す。型と純粋な関数は新しいファイル `agentChangesAttribution.ts`）

| 項目                  | 内容                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------------- |
| `kind`                | `tracking`（区別している）・`lost`（区別をやめた。`reason`・`lostAt`）                            |
| `phase`               | `idle`・`agent`・`paused`（`tracking` のときだけ）                                                |
| `periodUnassignable`  | 今の区間（最後の判定の区切りから今まで）を割り当てられない印（`tracking` のときだけ）             |
| `checkpoint`          | 最後の判定の区切り（`BaselineSnapshot`）と `sharedWithBaseline: boolean`（`tracking` のときだけ） |
| `staleCheckpointDirs` | 消せなかった前の判定の区切りの一時ディレクトリ（削除待ち）                                        |
| `userPaths`           | 利用者が変えたパスの集合（リポジトリ相対。git の表記）                                            |
| `agentPaths`          | エージェントが変えたパスの集合                                                                    |
| `trackingSince`       | 最初に割り当てる区間（`idle`・`agent` で印の無い区間）が始まった時刻（まだなら null）             |
| `hadUnassignedSince`  | `trackingSince` の後に、`paused` の区間か割り当てられない区間があったか                           |

- 記録（累積の始点）を作るとき（`begin` が始点を取り始める時点で、所有者のツールの開始の通し番号 s0 とあるべき段階 d0 を控える）:
  - 区別をやめる合図がある → `lost`（理由。`lostAt` は記録の開始の時刻）
  - それ以外 → `tracking`・`phase` は取り終えた時点のあるべき段階 d1・`checkpoint` は始点（`sharedWithBaseline: true`）。通し番号が s0 から変わった、または d0・d1 のどちらかが `agent` なら `periodUnassignable: true` にし、同期を 1 回並べる。そうでなく d1 が `paused` でなければ `trackingSince` を始点の時刻にする（`pending` のセッションがあると d が `agent` になるため、最初のプロンプトの前に記録を始めたときは最初の区間を割り当てない）

### 同期（registry の `syncAttribution(ownerId)`。所有者の列の中で行う）

1. 記録が無い・`lost` → 何もしない
2. 区別をやめる合図がある → `lost` にする（下の「やめる」）。合図の `unassignable` が立っていれば `periodUnassignable = true` にする（`onPhaseChange` の時点でも列の外で同期的に立てる。合図が下りたときの同期は、手順 3 で印を見て区切りを取り、期限切れの区間を閉じる）
3. あるべき段階が今の `phase` と同じで、`periodUnassignable` も無い → 何もしない
4. `unassignableBefore = periodUnassignable` を控え、`periodUnassignable = false` にする（この後に `PreToolUse` の待ちの打ち切りが起きると、受け口の `onToolStartTimedOut` がまた `true` にする）
5. `takeBaselineSnapshot(folderPath, { baseIndexPath: checkpoint.indexPath, isCanceled })` で区切り S を取る。`canceled`（記録を捨てた・世代が変わった）→ 取れたものを消して終わる。`unavailable` → `lost`（`checkpoint-failed`）
6. `timedOutDuring = periodUnassignable`（手順 4 の後に打ち切りがあったか）を控える
7. `collectAgentChangeEntriesBetween(checkpoint, S)` のパスを、`unassignableBefore` か `timedOutDuring` なら割り当てず、そうでなければ `phase` が `idle` なら `userPaths`、`agent` なら `agentPaths` へ足す（`paused` はどちらにも足さない）。失敗したら S を消して `lost`（`checkpoint-failed`）
8. この時点のあるべき段階 d を求める（区切りを取っている間に始まった・終わったツールを反映する）
9. `checkpoint = S`（`sharedWithBaseline: false`）にし、`phase = d` にする。`periodUnassignable = (timedOutDuring && d !== 'agent') || 合図の unassignable`（打ち切られたツールの書き込みが S の後に続いた可能性がある・期限切れのセッションがある）。`true` なら同期をもう 1 回並べる。新しい区間が割り当てる区間（`periodUnassignable` が無く `d` が `paused` でない）で `trackingSince` が null なら今の時刻にする。`trackingSince` があり、新しい区間が `paused` か割り当てられない区間なら `hadUnassignedSince = true`
10. 前の区切りが始点と共有でなければ一時ディレクトリを消す（L-003・L-004）。消せなければ `staleCheckpointDirs` に入れる（L-428）
11. `await` のたびに記録が今の記録か（世代）を確かめ、違えば S を消して終わる（2026-10-12 の区切りと同じ）

同期の依頼は、同じ所有者の列で待っている同期の依頼があればその Promise を返す（L-101）。`clear`・`close` で列の後ろの同期は記録が無いため何もしない。

### `PreToolUse` の待ち（registry の `waitForAgentPhase(ownerId, signal)`。受け口の `onToolStart` につなぐ）

- 次を `signal` が中止されるまで繰り返す
  1. 記録が無い・`lost` → 解決
  2. 記録の `phase` が `agent` で、並んでいる・走っている同期が無い → 解決
  3. それ以外 → そのとき並んでいる最新の同期（走っている同期より後に並んだものがあればそれ、無ければ新しく並べる）の Promise と `signal` の中止の早い方を待ち、1 に戻る
- 受け口は、追跡の更新と `onPhaseChange` を終えてから呼ぶ（上の「受け口」）ため、手順 3 で並べる同期は、そのツールの開始を反映したあるべき段階（`agent`）で走る
- 同期の手順 8 の後（手順 9・10 の await の間）に届いた `PreToolUse` は、手順 8 の時点の段階が `idle` なら、走っている同期が解決しても手順 2 を満たさないため、後ろの同期（`onPhaseChange` で並んだもの）を待つ
- 5 秒の上限は受け口が通して数え、打ち切ったら `signal` を中止して `markPeriodUnassignable(ownerId)`（今の記録の `periodUnassignable = true`。列の外で同期的に立てる）を呼ぶ

### やめる（`lost`）

- `kind` を `lost` にし、`reason`・`lostAt` を入れ、`userPaths`・`agentPaths` は残す。`checkpoint` の一時ディレクトリは始点と共有でなければ消す（消せなければ削除待ち）
- 理由: `hooks-not-confirmed`（作業中なのに知らせが届かないセッション）・`receiver-unavailable`（受け口を用意できずに hooks なしで起動したセッション）・`claude-version-unsupported`（版が分からない・古いために hooks なしで起動したセッション）・`checkpoint-failed`（区切り・差分・今の区間の比較の失敗）

### 行の `author`（累積の一覧。`agentChangesScopedQuery.ts` の `cumulative` の解決のときだけ）

1. `tracking` で `periodUnassignable` が無いとき、今の区間を求める: `checkpoint` が始点と共有ならその一覧のパス、そうでなければ `collectAgentChangeEntries(checkpoint)` のパス。`phase` が `idle` なら利用者、`agent` ならエージェント、`paused` ならどちらでもない。比較が失敗したら記録を `lost`（`checkpoint-failed`）にし、今の区間は割り当てない（一覧は失敗にしない）
2. U = `userPaths` ∪ 今の区間（利用者）、A = `agentPaths` ∪ 今の区間（エージェント）
3. 行ごとに `matches(entryPath, p)`: 完全一致、または片方が `/` で終わるフォルダの表記でもう片方がその下（前方一致は `/` の境目でだけ。L-007）
4. `notRecorded` の行 → `null`。U に一致があり A に無い → `user`、両方にある → `mixed`、それ以外 → `agent`
5. 区別していない記録（`tracking` で `trackingSince` が null、`lost` で集合が空）→ すべて `null`。`lost` で集合があれば、手順 1 の今の区間を除いて 2〜4 を行う
6. 実行の範囲（`toWorktree`・`between`）→ すべて `null`

- パスの照合は、git の出力のパス（同じ記録のインデックスの系統）どうしだけで行い、hook のパスや OS のパスと比べない（L-009・L-018）

### `すべて戻す`（`agentChangesRevert.ts` の `revertAllAgentChanges`）

- 文脈に `authorOf: (entries: AgentChangeEntry[]) => Promise<AgentChangeEntry[]>`（上の手順で `author` を付けた一覧を返す。handler が記録から作る）を足す（必須）
- 実行時の一覧に `author` を付け、`user`・`mixed` を除いた一覧を対象として、今の件数の上限の検査（除く前の件数で行う。打ち切った一覧では使えない今の規則のまま）・`expected` との完全一致の照合・検査・適用を行う

### アプリの戻す操作・取り消しの吸収（registry の `withAttributionAbsorbed(ownerId, record, task)`）

- 戻す 3 つの IPC と取り消しの IPC の処理（`withRecord` の中）を包む。`tracking` のとき、(1) 同期の手順 4〜7・10 と同じく区切りを取り、前の区切りからの差分を今の `phase` に割り当てる（印があれば割り当てない。段階は変えない）、(2) `task` を行う、(3) 作業ツリーを 1 件以上変えたら、区切りを取り直して `checkpoint` を置き換え、その差分はどちらの集合にも入れない
- (1)・(3) の失敗は `lost`（`checkpoint-failed`）にし、`task` は止めない（区別はおまけ）。(1) の失敗のときも `task` を行う
- 戻した行のパスを集合から外すことはしない（取り消しで戻ってくる内容の帰属を控えに持たずに済ませる。古い印が残ることは既知の制約）

### 確認の文言（renderer の `agentChangesMessages.ts`）

`すべて戻す` の確認は、件数を対象（`user`・`mixed` を除いた行）の件数にし、`記録を始めた後にあなたが編集した内容も戻ります。` の部分を次で組み立てる。

| 記録の区別の状態                                   | 文言                                                                                                                        |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 区別していない（`attribution` が区別していない形） | 今のまま `記録を始めた後にあなたが編集した内容も戻ります。`                                                                 |
| 区別している                                       | `エージェントのツールが動いている間（終わってから 2 秒を含む）にあなたが編集した内容は、エージェントの変更として戻ります。` |
| 区別を始めたのが記録の開始より後                   | 上に `HH:MM より前のあなたの編集も戻ります。` を足す                                                                        |
| `hadUnassignedSince`                               | 上に `アプリの中で claude が動いていなかった間などのあなたの編集も戻ります。` を足す                                        |
| `lost` で印がある                                  | 上に `区別をやめた後（HH:MM から）のあなたの編集も戻ります。` を足す                                                        |
| 除く行がある                                       | 最後に `利用者の変更 M 件（印の付いた行）は戻しません。行の ↶ で個別に戻せます。` を足す                                    |

行の `↶` の確認は、今の文言の後に、`user` なら `このファイルは、エージェントのツールが動いていない間に変更されました（利用者の変更）。`、`mixed` なら `このファイルには、エージェントのツールが動いていない間の変更（利用者の変更）が含まれます。` を足す。

## renderer（段階 B）

| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |

## テスト方針

### 段階 A（vitest。偽のタイマー・一時ディレクトリの実ファイル・実際の listen）

- `agentHookEvents`: 8 つのイベントの解釈（`UserPromptSubmit` は `prompt-submit`）、すべての要素の `hookEventName` がパスのイベント名になる（`Stop`・`StopFailure` の `turn-end`、`PostToolUse`・`PostToolUseFailure` の `confirm-only` を見分けられる）、ツールのイベントの `toolName`（matcher の名前・matcher に無い形の合う名前はそのまま、65 文字・記号を含む・数値・無いときは null）、`tool_name` が 6 つ以外のとき `PreToolUse` は `tool-start`（区間を開く）・`PostToolUse` は捨てる、`tool_use_id` の形（空・257 文字・数値で ID なし）、`agent_id` の形が違うとき `PreToolUse` は ID なしの `tool-start`・`PostToolUse`・`PostToolUseFailure`・`SubagentStop` は捨てる、`hook_event_name` とパスの不一致で ID なし、余分な欄を読まない
- `agentHookProtocol`: 8 つのイベントの列挙の順・イベントとパスの相互の引き当て・完全一致でないパスは null・matcher の文字列・`PreToolUse` の hook の `timeout` が受け口の待ちの上限より長い

- エージェントに `sleep 20 を実行して` を送り、実行中に端末で `echo during >> b.txt` を実行し、終わった後に `更新` → `M b.txt` は印なし（ツールの実行中の利用者の編集はエージェントに数える）
- 許可を求めるツール（`rm` など）の確認が出ている間に、端末で `echo wait >> b.txt` を実行してから許可し、終わった後に `更新` → `M b.txt` は印なし（許可を待つ間はツールの区間に含まれる）
- エージェントに `sleep 20 を実行して` を送り、実行中に Esc で中断し、すぐ端末で `echo after >> b.txt` を実行して `更新` → `M b.txt` は印なし（中断では `Stop` が届かず、次のターンの `Stop` まで区間が開いたまま）。次の指示を送って作業が終わった後に端末で `echo after2 >> c.txt` を実行して `更新` → `M c.txt` に `利用者の変更` が出る
- 端末で `echo x >> b.txt` を実行した直後（1 秒以内）にエージェントの `Edit` が終わるよう、作業中に操作する → ツールの終わりから 2 秒の間の編集は印なし（猶予）
- `claude` を起動した後、何も送らずに `いまから記録する` を押し、端末で `echo pre >> b.txt` を実行してから `こんにちは` を送って `更新` → `M b.txt` は印なし（最初の知らせの前の `pending` の区間は割り当てない）。区別の状態の 1 行に `利用者の変更の区別は HH:MM からです…` が出る
- `a.txt` の `↶` で戻した後、エージェントに同じ変更をやり直させる → `M a.txt` は印なし（戻す操作は利用者の変更に数えない）
- エージェントにファイルを変えさせた後、`claude` の `/rewind` でその変更を戻してから `更新` → 戻ったファイルの行が残っていれば `利用者の変更` の印が付く（`/rewind` はツールを使わないため。既知の制約）。出方を記録する
- 2 つ目のタブで `claude` を起動し（`こんにちは` を送って確かめた状態にする）、1 つ目のタブのエージェントの作業中に、2 つ目のタブは止めたまま端末で `echo x >> b.txt` を実行 → `M b.txt` は印なし（どれかのタブが動いていればエージェントの区間）
- すべてのエージェントのタブを閉じてから端末で `echo closed >> b.txt` を実行して `更新` → `M b.txt` に印が付かず、区別の状態の 1 行 `アプリの中で claude が動いていなかった間などの変更には、印を付けていません` が出る。`すべて戻す` の確認に `アプリの中で claude が動いていなかった間などのあなたの編集も戻ります。` が出る
- 利用者の設定に `"disableAllHooks": true` を書いてから `claude` を起動し、`いまから記録する` を押してから `a.txt を読んで要約して` を送り、作業中になってから 15 秒以上待って `更新` → セクションに `HH:MM から利用者の変更を区別できなくなりました（claude の hooks から知らせが届きません）…` か `利用者の変更を区別できません（claude の hooks から知らせが届きません）…` が出て、印は付かない。確かめたら設定を戻す
- `表示` で `実行 1` を選ぶ → 印・区別の状態の 1 行・除く旨の 1 行が出ない

既存の項目の変更（段階 B。ID は変えない）: 直すのは `すべて戻す` の確認の文言（`記録を始めた後にあなたが編集した内容も戻ります。`）を期待結果に書いた項目だけで、区別しているときの文言に直す。対象は、`grep -n 'あなたが編集した内容も戻ります' docs/manual-test-spec.md` で拾った行のうち `すべて戻す` の確認の項目に限る（行の `↶` の確認〈AGC-012 など〉は `記録を始めた後にあなたが編集した内容も戻ります。` のまま変えない）。行の `↶` の確認の項目は、`author` に応じて足す文（`このファイルは、エージェントのツールが動いていない間に…`）が出る条件を期待結果に加えるだけにする。端末で利用者の編集を作ってから `すべて戻す` で戻ることを期待している項目（AGC-001 の `echo user >> a.txt` は記録の前の編集なので対象外。記録の後の編集の項目）は、エージェントが止まっている間の編集が `利用者の変更` になり `すべて戻す` から外れることに合わせて直す。

## 既知の制約（ROADMAP・実機テスト仕様書に反映する）

- 区別するのは、アプリの中のタブで起動した `claude` のツールの区間だけ。アプリの外で起動した `claude`、エージェントが起動した別の `claude`、ほかのエージェント CLI の変更は区別しない（アプリの中で `claude` が動いていない間は印を付けない。動いている間に外で書かれた変更は `利用者の変更` になる）
- 利用者の変更とするのは、エージェントのツール（`Write`・`Edit`・`MultiEdit`・`NotebookEdit`・`Bash`・`PowerShell`）が動いていない間に変わったファイルだけ。ツールの実行中・許可の確認を待つ間・ツールの終わりから 2 秒の間（利用者の `PostToolUse` の hook の自動整形をエージェントに数えるための猶予）・`claude` の起動から最初のプロンプトの知らせが届くまで（`pending`）・中断（Esc）の後に次のターンの `Stop` が届くまで（届かなければ最大 15 分）に利用者が書いた変更は、エージェントの変更になり `すべて戻す` で戻る（確認の文言で伝える）
- エージェントのツールの開始の待ちが 5 秒で打ち切られた区間（区切りに時間がかかった・ほかの操作が先に並んでいた）、15 分を超えて開いた区間が、その区間の本来の閉じ方（`Stop`・`SubagentStop`・`SessionEnd` など）で閉じるまでの区間（16 MiB を超える知らせ〈大きなファイルを書いた `Write` など〉で ID を読めずに開き、終わりの `PostToolUse` も 16 MiB を超えて ID を読めず `tool-end` の規則 (3) でも閉じられない区間は、`SessionEnd`・終了まで閉じないため、15 分の後はそのセッションの終わりまで）、累積の始点を取っている間にツールが動いた・`pending` のセッションがあった最初の区間の変更は、どちらとも決めず、印を付けない（`すべて戻す` で戻る）
- 上のツール以外（MCP のツール・プラグインのツールなど）がファイルを書いた・`Bash` で背景に起動したプロセス（開発サーバー・監視のビルドなど）がツールの終わりから 2 秒の後に書いた・エディタの自動整形など別のプロセスが書いた・利用者の `PostToolUse` の hook がツールの終わりから 2 秒を超えて書いた・`claude` の `/rewind`（ツールを使わずにファイルを戻す）で戻った変更は、`利用者の変更` になる（`すべて戻す` から外れるだけで、行の `↶` で戻せる）
- エージェントがツールを呼ぶたびに（動いていない状態からのとき）、作業ツリーの区切りを取り終えるまでツールの開始が待たされる（上限 5 秒）。区切りは未追跡のファイルが多いリポジトリほど遅い
- hooks が効いているかは、最初の知らせ（ふつうはプロンプトを送ったときの `UserPromptSubmit`）で確かめる。知らせが届かないことは、画面の活動の判定が作業中を検知してから 15 秒後に分かる。画面の判定が、プロンプトを送る前に作業中と誤って判定すると（`claude` の起動時の表示など）、hooks が効いていても区別をやめることがある
- 判定の区切り・差分の比較に失敗した（未追跡のファイルが多すぎる・時間切れ・`git gc --prune=now` で区切りが消えた）・作業中なのに知らせの届かないセッションがあった記録は、それ以降の変更に印を付けない（それまでの印は残る）。次の記録（`確認を終える` の後）で改めて区別する
- 区別が始まった後（`confirmed` の後）に hooks が無効にされた場合（設定の読み直しで `disableAllHooks` が効いたなど）は、以後の `PreToolUse` が届かず、エージェントの書き込みが `利用者の変更` になる（段階 A・この設計書の段階 B の形では検知しない。下の「段階 B の設計で決めること」）
- hooks が使えない `claude`（利用者・管理者の設定の `disableAllHooks`・`allowManagedHooksOnly`・`allowedHttpHookUrls`、`--bare`・`--safe-mode` 相当の起動）では区別しない。`claude` の版が 2.1.101 より古い・版を確かめられない（`claude --version` が 5 秒で終わらない・出力の形が違う）ときは hooks を渡さず、区別しない（起動は今までどおり）
- 起動のたびに（同じ `claude` では main の起動の間に 1 回だけ）`claude --version` を実行するため、最初の起動が少し遅くなる。版の確認が打ち切られた（5 秒）・起動に失敗した・0 でない終了だったときは結果を控えないため、`claude --version` が毎回 5 秒を超える環境では、起動のたびに最大で約 6 秒（打ち切りの 5 秒と SIGKILL までの 1 秒）遅くなり、hooks も渡らない
- 同じフォルダを 2 つのウィンドウで開くと、別のウィンドウのエージェントの変更は `利用者の変更` になる
- 一度 `利用者の変更` に入ったパスは、行の `↶` で戻した後もその記録の間は覚えたままで、エージェントが同じファイルを書き直すと `利用者の変更を含む` になる
- 既存の Git の操作（ソース管理の取り消し・pull・checkout など）とアプリでの保存は、そのときの段階で利用者かエージェントの変更に数える
- 記録していないファイル（大きすぎる・ignore 済み）の行は区別しない（印なし。今どおり `すべて戻す` は使えない）
- 起動の引数に `--settings <一時ディレクトリのファイル>` が付く（`ps` で見える。トークンはファイルの中で、持ち主だけが読める）。`claude` の `/hooks` にアプリの hooks（8 つ）が出る。`claude` の環境の `NO_PROXY`・`no_proxy` に `127.0.0.1`・`localhost` が足される
- エージェント自身は、設定のファイルを読んで偽の知らせを送れる（印が変わるだけで、作業ツリー・記録は変わらない）
- アプリが異常終了すると、設定のファイルの一時ディレクトリ（トークン入り。トークンはアプリの終了で無効）が残る。OS の一時ディレクトリの掃除に任せる
- Windows・Linux では確かめていない（ループバックの待ち受けでファイアウォールの確認が出るか、パスに空白を含む `--settings` の引数の渡り方、`PowerShell` のツールの名前）

## 段階 B の設計で決めること

段階 B の実装プランの前に、段階 A の実機テストの結果（未確認事項 3・5・6）を見て、次を決める（決めたらこの設計書に追記する）。

- 区別が始まった後に hooks が無効にされたことの検知（例: `confirmed` のセッションで、画面の活動が `working` から `working` 以外に変わったのに `Stop`・`StopFailure` が一定時間届かなければ `unconfirmed` にする）
- 中断・許可の拒否の後に区間が閉じない時間の長さ（未確認事項 3 の結果）

段階 A の最終レビューで見つかった、段階を帰属につなぐ前に段階 B で直すこと（忘れないよう残す）。

- 受け口: `listen` の後も `once('error')` が残り、待ち受けの後の server の `error`（`EMFILE` など）で、死んだ `baseUrl` を返し続ける → 常駐の `error` ハンドラで `listening`・`server` を `null` に戻す
- 受け口: `onToolStart` が同期で投げるとタイマーが残り、500 を返す → `waitForAgentPhase` につなぐ前に `Promise.resolve().then(() => onToolStart(...))` で包む
- 受け口: `close` の後も待っている `PreToolUse` の上限のタイマーが `onToolStartTimedOut` を呼ぶ → `closed` を見て止める（`markPeriodUnassignable` につなぐため）
- 追跡: 区間の上限 256 であふれた区間を外すと「自分の契機より早く閉じない」に反する → あふれたら外さずに `unassignable` を立てる（または `session-end` まで保つ）。`subagent-stop` で外した ID も `droppedToolIds` に控える
- starter: `hooks.activate` と `exited` の中の `hooks.release` を守るものが無い（`onPhaseChange` をつなぐと投げうる）→ `exited` の購読を `activate` より前に置くか、`activate` を `try`/`catch` で包む
